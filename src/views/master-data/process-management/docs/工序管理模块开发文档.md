### **1. 功能开发清单 (What to Develop)**

#### **A. 基础工序定义 (Operation Management)**

1.  **工序主数据列表 (Operation List)**
    *   **功能**:
        *   以表格形式清晰展示所有工序。
        *   **客户端搜索**: 提供按`工序代码`或`工序名称`进行实时文本搜索。
        *   **客户端筛选**: 提供按`工序类型`和`状态`进行多选或单选筛选。
        *   **分页**: 支持前端分页，提高大数据量下的渲染性能。
        *   **列排序**: 支持点击表头对`工序代码`、`工序名称`等列进行升/降序排序。

2.  **工序创建/编辑 (Operation Create/Edit)**
    *   **功能**:
        *   以模态框（Modal/Dialog）形式提供表单，用于新建或编辑工序。
        *   **表单校验**:
            *   `工序代码`: 必填，全局唯一（在mock数据中检查重复），建议限制为大写字母、数字和下划线。
            *   `工序名称`: 必填，不允许为空。
            *   `工序类型`: 必填。
        *   **新建模式**: 表单为空，`工序代码`可编辑。
        *   **编辑模式**: 表单回填所选工序的数据，`工序代码`应设为只读，防止主键被修改。

3.  **工序状态变更 (Operation Status Change)**
    *   **功能**:
        *   在列表的每一行提供“禁用”或“启用”按钮，根据当前状态动态显示。
        *   点击按钮后，应有二次确认提示框（例如 "您确定要禁用'退火'工序吗？"）。

#### **B. 工艺路线编排 (Routing Management)**

1.  **工艺路线列表 (Routing List)**
    *   **功能**:
        *   以表格形式展示所有工艺路线的主信息。
        *   支持按`路线代码`、`路线名称`、`适用产品`进行搜索。
        *   支持按`状态`（草稿、待审批、生效、历史/归档）进行筛选。
        *   支持分页和列排序。
        *   **删除与批量删除 (Deletion & Batch Deletion)**
            *   **功能入口**: 在列表工具栏提供“批量删除”按钮，在每行操作列提供“删除”按钮。
            *   **可见性与业务规则**:
                - **删除按钮 (行内)**: 仅当工艺路线的所有版本都处于“草稿”或“已归档”状态时才可见并启用。如果存在任何“生效”或“待审批”的版本，则禁用此按钮，并提供Tooltip提示：“无法删除，该路线下存在正在生效或审批中的版本”。
                - **批量删除按钮 (工具栏)**: 当用户勾选列表项后启用。
            *   **核心处理流程**:
                - **单个删除**:
                    1.  点击行内“删除”按钮，弹出确认对话框：“您确定要永久删除工艺路线 ‘[路线代码] - [路线名称]’ 及其所有版本吗？此操作不可恢复。”
                    2.  确认后，从Mock数据源中移除该路线代码对应的所有版本记录。
                - **批量删除**:
                    1.  勾选多个工艺路线后，点击“批量删除”按钮。
                    2.  **智能预检**: 后端(Mock)逻辑会检查所有选中的路线。
                    3.  **分类确认对话框**:
                        - 如果所有选中路线均可删除，显示：“您确定要永久删除选中的 [N] 条工艺路线吗？”
                        - 如果部分路线不可删除，显示一个分类列表：“以下 [X] 条路线无法删除，因为它们包含生效或待审批的版本：[路线列表]。是否继续删除剩余的 [Y] 条可删除路线？”
                    4.  确认后，仅删除符合条件的路线。
            *   **用户反馈**:
                - 删除成功后，显示全局成功消息：“[N] 条工艺路线已成功删除。”
                - 如果操作被阻止，则通过对话框或Tooltip清晰地告知用户原因。

        *   **批量归档 (Batch Archiving)**
            *   **功能入口**: 在列表工具栏提供“批量归档”按钮。
            *   **可见性与业务规则**:
                - 仅当用户勾选了状态为“生效”的工艺路线时，该按钮才启用。
                - 如果勾选的路线中包含非“生效”状态的，按钮禁用或在点击后提示错误。
            *   **核心处理流程**:
                1.  勾选一个或多个“生效”状态的工艺路线。
                2.  点击“批量归档”按钮，弹出确认对话框：“您确定要归档选中的 [N] 条生效中的工艺路线吗？归档后，它们将不再可被直接使用。”
                3.  确认后，将所有选中路线的当前“生效”版本的`status`更新为`'Archived'`。
            *   **用户反馈**:
                - 操作成功后，显示全局成功消息：“[N] 条工艺路线已成功归档。”
                - 列表数据刷新，显示更新后的状态。

2.  **工艺路线创建/编辑 (Routing Editor)**
    *   **功能**:
        *   这是一个独立的页面，用于对单个工艺路线进行完整操作。
        *   **主信息区**:
            *   表单校验：`路线代码`（唯一性、必填）、`路线名称`（必填）。
            *   `适用产品`：提供一个用户友好的多选组件（如标签输入、带搜索的下拉多选），方便用户添加或删除产品。
        *   **工序步骤区**:
            *   **添加工序**: 点击按钮弹出一个“工序选择器”模态框。该模态框应展示所有“启用”状态的基础工序列表，并支持搜索和多选。
                *   **重复工序检查**: 系统会自动检查所选工序是否已存在于当前工艺路线中。如果已存在，将阻止重复添加并给出统一的警告提示，避免消息重叠。
                *   **唯一步骤ID (`stepId`) 生成**: 无论是否为重复的基础工序（业务上不允许），每个添加到工艺路线的步骤都会被分配一个全新的、唯一的 `stepId` (使用 UUID)，确保数据和渲染的唯一性。
                *   **智能消息提示**: 优化了添加工序后的消息提示逻辑，确保成功、警告或信息提示以单一、清晰的方式展示，避免多条提示同时弹出造成的遮挡问题。
            *   **步骤排序**: 每行提供“上移”和“下移”按钮，点击后直接修改`steps`数组的顺序并重新渲染。当步骤在最顶或最底时，相应按钮应禁用。
                *   **智能步骤号管理**：每当步骤被添加、移动或删除时，系统会自动重新计算并分配步骤号（例如，按 `10, 20, 30...` 的规则递增），确保流程顺序的清晰性和连续性。
                *   **流程逻辑自动重置**：为了避免因步骤顺序变化导致的流程逻辑链断裂问题（如 `nextStep` 指向无效步骤），在进行步骤移动或删除操作后，系统会自动清空所有步骤的流程逻辑配置（包括“下一步骤”、“成功后跳转”和“失败后跳转”）。同时，会弹出明确的提示框，强制用户重新审视并配置受影响的流程，确保工艺路线的有效性和健壮性。
            *   **步骤详情配置**:
                *   当用户在主编辑区点击一个步骤时，右侧的属性面板将动态渲染。其核心逻辑是**根据所选步骤的 `operation.type` 和 `timeStandards` 中各个 `type` 字段的值来动态展示和切换UI控件**。
                *   **面板结构 (以选中 `步骤20 - 退火后检验` 为例)**:
                    ```
                    +----------------------------------------------------------------------+
                    | [ 步骤属性配置 ]                                                     |
                    |   --- 步骤 20: 退火后检验 (检验类型) ---                             |
                    |----------------------------------------------------------------------|
                    | [▼] 流程逻辑 (Flow Logic)                                            |
                    |                                                                      |
                    |     * 成功下一步: [ 30 - 分切 ▼ ]                                    |
                    |     * 失败下一步: [ 50 - 表面处理返工 ▼ ]                            |
                    |                                                                      |
                    |----------------------------------------------------------------------|
                    | [▼] 时间标准 (Time Standards)                                        |
                    |                                                                      |
                    |   [ 准备时间 ]                                                       |
                    |     计算规则: [ 使用固定时间 ▼ ]  (选项: 使用固定时间, 使用切换矩阵) |
                    |     * 时间 (分钟) (i): [ 10         ]                                 |
                    |                                                                      |
                    |   [ 加工时间 ]                                                       |
                    |     计算规则: [ 使用固定时间 ▼ ]  (选项: 使用固定时间, 使用公式计算) |
                    |     * 时间:      [ 15         ] [ 分钟/卷 ▼ ] (i)                      |
                    |                                                                      |
                    +----------------------------------------------------------------------+
                    ```
                *   **动态交互逻辑详解**:
                    1.  **面板标题**: `--- 步骤 20: 退火后检验 (检验类型) ---`
                        *   动态显示**步骤号**、**工序名称**和**工序类型**，让用户时刻明确配置对象。
                    2.  **流程逻辑 (Flow Logic) 分组**:
                        *   **判断依据**: `operation.type`
                        *   **如果 `type` 是 "Inspection"**:
                            *   显示“成功下一步”和“失败下一步”两个下拉框。
                            *   下拉框选项为除自身外的所有步骤。
                            *   选择后，更新数据模型中的 `step.flowLogic.onSuccessStep` 和 `step.flowLogic.onFailureStep`。
                        *   **如果 `type` 是 "Production" 或其他**:
                            *   只显示一个“下一步”下拉框。
                            *   选择后，同时更新 `step.flowLogic.nextStep` 和 `step.flowLogic.onSuccessStep`，并将 `onFailureStep` 设为 `null`。
                    3.  **时间标准 (Time Standards) 分组**:
                        *   **[准备时间] 子分组**:
                            *   **`计算规则` 下拉框**:
                                *   **UI**: 绑定到数据模型的 `step.timeStandards.setup.type` 字段。
                                *   **选项**: "使用固定时间" (对应值 `Fixed`), "使用切换矩阵" (对应值 `Matrix`)。
                                *   **交互**: 当用户切换此选项时，下方的输入控件会动态变化。
                                    *   **选择 "使用固定时间"**: 显示一个标签为 `* 时间 (分钟) (i)` 的数字输入框，该输入框绑定到 `step.timeStandards.setup.value`。
                                    *   **选择 "使用切换矩阵"**: `* 时间 (分钟)` 输入框变为 `后备时间 (分钟)`（非必填），下方新增一个标签为 `* 关联矩阵` 的下拉框，绑定到 `step.timeStandards.setup.matrixId`。
                        *   **[加工时间] 子分组**:
                            *   **`计算规则` 下拉框**:
                                *   **UI**: 绑定到数据模型的 `step.timeStandards.processing.type` 字段。
                                *   **选项**: "使用固定时间" (`Fixed`), "使用公式计算" (`Formula`)。
                                *   **交互**:
                                    *   **选择 "使用固定时间"**: 显示复合输入控件 `[ * 时间 ] [ * 单位 ▼ ] (i)`，分别绑定到 `step.timeStandards.processing.value` 和 `unit`。
                                    *   **选择 "使用公式计算"**: 复合输入控件被一个标签为 `* 计算公式 (i)` 的多行文本输入框取代，该文本框绑定到 `step.timeStandards.processing.formula`。旁边可以提供一个“变量助手”按钮。
            *   **步骤删除**: 每行提供删除按钮，并有二次确认。
        *   **版本与状态控制**:
            *   页面底部或顶部的操作按钮（保存、提交审批等）根据当前路线的`status`和`version`动态显示/禁用。
            *   **创建新版本**: 
                
                **1. 功能入口与可见性 (Entry Point & Visibility)**
                - **功能入口设计**: 在工艺路线详情查看或编辑页面添加"创建新版本"按钮
                - **可见性控制**: 仅当工艺路线状态为"生效 (Enabled)"时显示该按钮
                - **状态限制**: 对于"草稿 (Draft)"、"待审批 (InApproval)"、"历史/归档 (Archived)"状态必须隐藏或禁用按钮
                - **权限验证**: 确保只有具备相应权限的用户才能看到此功能入口
                
                **2. 用户交互与意图确认 (User Interaction & Intent Confirmation)**
                - **确认对话框**: 点击按钮后弹出非侵入式确认对话框，防止误操作
                - **对话框标题**: 明确显示"确认创建新版本"
                - **动态内容**: 显示"您确定要基于当前**[路线名称] v[当前版本号]**创建一个新的可编辑草稿版本吗？"
                - **操作选项**: 提供"确定"和"取消"两个明确选项
                - **页面遮罩**: 等待用户响应期间对页面背景进行遮罩处理
                - **防重复操作**: 操作期间将按钮设为加载中或禁用状态，防止重复请求
                
                **3. 核心处理流程 (Core Processing Flow)**
                
                *3.1 前置条件校验 (Pre-condition Validation)*
                - **存在性校验**: 确认"生效"版本在数据源中依然存在
                - **状态一致性校验**: 再次确认版本状态仍为"生效"，处理并发场景
                - **草稿唯一性校验**: 检查是否已存在相同路线代码的草稿版本
                - **失败处理**: 校验失败时显示具体错误提示，不进行页面跳转
                
                *3.2 数据克隆 (Data Cloning)*
                - **深度克隆**: 递归复制源版本对象的所有层级，包括嵌套对象与数组
                - **完整性验证**: 确保steps数组及其内部flowLogic、timeStandards对象完全复制
                - **内存独立**: 生成与源对象无任何内存引用的全新实例
                
                *3.3 新版本属性赋值 (New Version Attribute Assignment)*
                - **唯一标识符**: 为新版本生成全新的全局唯一ID
                - **版本号递增**: 实现确定性版本号递增逻辑（如v1.0→v1.1，v1.9→v1.10）
                - **状态设置**: 将新版本状态硬编码设为"草稿 (Draft)"
                - **审计字段更新**: 更新createdBy、createdAt为当前操作人和时间
                - **历史记录处理**: 清空approvalHistory，重置changelog并添加创建记录
                - **步骤ID重新生成**: 为新版本中所有步骤重新生成stepId确保唯一性
                
                *3.4 数据持久化 (Data Persistence)*
                - **新记录添加**: 将新版本作为全新记录添加，不覆盖现有记录
                - **原子性操作**: 确保数据持久化操作的原子性，在单个事务中完成
                - **数据完整性**: 验证保存后的数据完整性和一致性
                
                **4. 后续流程与用户反馈 (Post-processing & User Feedback)**
                - **成功反馈**: 显示"新版本 v[新版本号] 已创建成功！"的成功提示
                - **自动导航**: 成功后自动跳转到新创建草稿版本的编辑页面
                - **数据上下文切换**: 确保编辑页面加载新版本数据，用户可立即开始编辑
                - **URL一致性**: 更新浏览器地址栏URL反映新版本ID或版本号
                - **错误处理**: 操作失败时提供详细错误信息和恢复建议
            
            *   **提交审批/批准/驳回**:
                **1. 功能入口与上下文感知 (Context-aware Entry Point)**
                - **动态按钮**: 在工艺路线编辑页面，操作按钮（如“提交审批”、“批准”、“驳回”）的可见性与可用性，需严格根据当前路线的`status`进行动态控制。
                - **状态驱动逻辑**:
                  - `status: 'Draft'` -> 显示“提交审批”按钮。
                  - `status: 'InApproval'` -> 显示“批准”和“驳回”按钮（需权限验证）。
                  - `status: 'Enabled'` 或 `'Archived'` -> 隐藏所有审批操作按钮。
                

                **2. 用户交互与确认 (User Interaction & Confirmation)**
                - **标准化确认**: 所有状态变更操作前，必须弹出确认对话框，明确告知用户操作的后果。
                - **动态提示信息**: 对话框内容应动态生成，例如：
                  - 提交审批: "您确定要将工艺路线 '[路线名称] v[版本号]' 提交审批吗？"
                  - 批准: "您确定要批准此版本的工艺路线吗？批准后将覆盖当前生效版本（如有）。"
                  - 驳回: "您确定要驳回此版本的工艺路线吗？请在下方填写驳回原因。" (可带输入框)
                - **加载状态**: 操作期间，按钮应显示加载指示，防止重复提交。

                **3. 核心处理流程 (Core Processing Flow)**
                - **状态变更**: 根据操作类型，在Mock数据中精确修改`status`字段。
                  - `提交审批` -> `status`变为 `'InApproval'`。
                  - `批准` -> `status`变为 `'Enabled'`。
                  - `驳回` -> `status`变回 `'Draft'`。
                - **版本管理 (批准时)**: 当一个版本被`批准 (Enabled)`时，系统需自动处理同路线代码下的其他版本：
                  - **旧版本归档**: 查找该路线代码之前状态为`'Enabled'`的旧版本，并将其`status`更新为`'Archived'`。
                  - **唯一生效性**: 确保任何时候，一个工艺路线代码只有一个版本是`'Enabled'`状态。
                - **审批历史记录 (`approvalHistory`)**: 
                  - **记录生成**: 每次执行审批操作（提交、批准、驳回）后，都在`approvalHistory`数组的**头部**（`unshift`）添加一条新的记录对象。
                  - **记录结构**: `{ action: 'Submit', actor: 'user_name', timestamp: 'YYYY-MM-DD HH:mm:ss', notes: '提交以待审核' }` 或 `{ action: 'Reject', actor: 'approver_name', timestamp: '...', notes: '原因...' }`。

                **4. 后续流程与反馈 (Post-processing & Feedback)**
                - **成功提示**: 操作成功后，显示清晰的全局消息（如 “已成功提交审批”）。
                - **UI刷新**: 视图应自动刷新，以反映最新的状态和数据。例如，按钮状态更新，列表中的状态标签变化。
                - **导航 (可选)**: 批准或驳回后，可考虑将用户导航回工艺路线列表页面，以便他们查看全局状态。

        *   **历史记录查看**:

            **1. 功能设计与UI布局 (Feature Design & UI Layout)**
            - **集成视图**: 在工艺路线编辑页面的一个显著位置（如右侧面板、底部Tab页或可展开区域），提供“历史记录”查看功能。
            - **双重信息展示**: 该区域应包含两个子部分，清晰地展示：
              - **版本变更日志 (`changelog`)**: 记录了从创建到每次版本迭代的关键信息。
              - **审批历史 (`approvalHistory`)**: 详细追踪了每次状态流转的审批过程。

            **2. 版本变更日志 (`changelog`) 的呈现**
            - **数据源**: 直接绑定到工艺路线对象的 `changelog` 数组。
            - **显示格式**: 以时间线（Timeline）或简洁列表的形式展示。
            - **条目内容**: 每个条目应至少包含：
              - **时间戳 (`timestamp`)**: 变更发生的具体时间。
              - **操作 (`action`)**: 如 `Create` (创建), `NewVersion` (创建新版)。
              - **描述 (`details`)**: 对操作的详细说明，例如 "基于 v1.0 创建了新的草稿版本 v1.1"。
              - **操作人 (`actor`)**: 执行该操作的用户。

            **3. 审批历史 (`approvalHistory`) 的呈现**
            - **数据源**: 绑定到 `approvalHistory` 数组。
            - **显示格式**: 同样建议使用时间线或表格，按时间倒序排列（最新记录在最前）。
            - **条目内容**: 每个审批记录应突出显示：
              - **时间戳 (`timestamp`)**: 审批操作的时间。
              - **审批动作 (`action`)**: `Submit`, `Approve`, `Reject`，并可用不同颜色或图标区分。
              - **审批人 (`actor`)**: 执行审批的用户。
              - **审批意见 (`notes`)**: 特别是驳回时，必须清晰展示驳回原因。

            **4. 交互与体验 (Interaction & UX)**
            - **只读性**: 历史记录区域为纯信息展示，所有内容均为只读。
            - **可访问性**: 用户应能在任何时候方便地展开或切换到此视图，以了解路线的完整生命周期。
            - **数据为空提示**: 如果 `changelog` 或 `approvalHistory` 为空，应显示友好的提示信息，如“暂无版本记录”或“暂无审批历史”。

### **2. 注意点 (Key Considerations)**

1.  **分层设计，逐步实施**: 先完成“基础工序定义”，再做“工艺路线编排”。
2.  **版本控制是生命线**: 任何对“生效”路线的修改都必须通过创建新版本进行。
3.  **与产品主数据的关系**: 工艺路线必须能明确关联到一个或多个产品。
4.  **抽象与具体的分离**: “工序”是可复用的基础定义，“步骤”是工序在具体路线中的一次应用。
5.  **为未来扩展做准备**: 数据结构中预留了`reportingPoint`, `associatedResourceType`, `standardSetupTime`等字段，即使初期UI不完全实现，模型也已具备扩展性。
6.  **用户体验**: 即使没有拖拽，通过“上移/下移”和清晰的属性面板也能提供良好的编辑体验。

### **附录：动态时间预留扩展设计说明**

#### **附录A：标准准备时间 (`standardSetupTime`) 的动态化扩展**

*   **设计思想**: 采用“**默认值 + 扩展**”模式。系统承认“准备时间”可能依赖于上一个任务的属性（例如，从生产A产品切换到B产品）。
*   **数据模型预留**:
    *   **保留字段**: `standard_setup_time` (DECIMAL)。在当前版本中，此字段用于存储一个**固定的、默认的**准备时间。
    *   **预留字段**: `setup_matrix_id` (VARCHAR/INT, 可为`NULL`)。
        *   **作用**: 这是一个外键，指向一个未来可能创建的`setup_matrices`（准备时间切换矩阵）表。
        *   **当前状态**: 在当前版本中，该字段值**始终为`NULL`**。系统逻辑不依赖此字段。
*   **未来升级路径**:
    1.  **新建模块**: 创建“准备时间切换矩阵”主数据管理模块，允许用户定义不同产品属性之间切换所需的准备时间（例如，颜色、规格）。
    2.  **修改UI**: 在“工艺路线编辑器”中，允许用户为步骤的准备时间关联一个已定义的切换矩阵。选择后，`setup_matrix_id`字段将被赋值。
    3.  **修改核心逻辑**: 升级**排程引擎**。在计算任务间准备时间时：
        *   **优先检查** `setup_matrix_id` 字段。
        *   如果该字段有值，则根据前后任务的属性，在对应的切换矩阵中查找准确的准备时间。
        *   如果该字段为`NULL`，或在矩阵中找不到匹配规则，则**回退**使用`standard_setup_time`字段中的固定值。

#### **附录B：标准加工时间 (`standardProcessingTime`) 的动态化扩展**

*   **设计思想**: 采用“**默认值 + 扩展**”模式。系统承认“加工时间”可能依赖于当前任务所加工物料的自身属性（例如，厚度、宽度）。
*   **数据模型预留**:
    *   **保留字段**: `standard_processing_time` (DECIMAL) 和 `processing_time_unit` (VARCHAR)。在当前版本中，用于存储一个**固定的、默认的**加工时间及其单位。
    *   **预留字段**: `processing_time_formula` (VARCHAR/TEXT, 可为`NULL`)。
        *   **作用**: 用于存储一个可被解析的文本**计算公式**。
        *   **当前状态**: 在当前版本中，该字段值**始终为`NULL`**。
*   **未来升级路径**:
    1.  **修改UI**: 在“工艺路线编辑器”的步骤详情中，提供一个“高级”或“公式”模式，允许高级用户输入加工时间计算公式（例如：`"10 * [thickness] + 20"`，其中 `[thickness]` 是一个变量）。
    2.  **引入公式引擎**: 在后端引入一个简单的公式解析与计算引擎。
    3.  **修改核心逻辑**: 升级**计划与排程模块**。在计算任务的加工时间时：
        *   **优先检查** `processing_time_formula` 字段。
        *   如果该字段有值，则：
            *   从产品主数据中获取公式所需的变量值（如`thickness`）。
            *   使用公式引擎计算出动态的加工时间。
        *   如果该字段为`NULL`，则**回退**使用`standard_processing_time`字段中的固定值。
