
# Moses API 用户注册管理模块接口文档

## 概述

本文档详细说明了 Moses API 用户注册管理模块的所有接口，包括请求方法、路径、参数、请求和响应数据结构、功能描述、错误码和返回示例。**本文档严格基于实际代码实现编写**，确保前端开发人员能够准确对接。

- **字符编码**: UTF-8

## 统一响应格式

### 成功响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
    // 具体的业务数据，根据接口而不同
  },
  "message": "操作成功的描述信息",
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

## 用户注册管理接口详细说明

### 1. 提交注册申请

**接口路径**: `POST /v1/auth/register-application`

**功能描述**: 用户提交注册申请，提供基本信息和部门岗位信息，系统创建申请记录并等待管理员审批。根据需求文档3.6.2用户注册管理功能实现。

**认证要求**: 无

**请求头**:

```
Content-Type: application/json
```

**请求参数**:

| 参数名            | 类型   | 必填 | 限制                                             | 描述                 | 示例                   |
| ----------------- | ------ | ---- | ------------------------------------------------ | -------------------- | ---------------------- |
| applicantName     | string | 是   | 1-255字符                                        | 申请人姓名           | "张三"                 |
| applicantEmail    | string | 是   | 有效邮箱格式                                     | 申请人邮箱，必须唯一 | "zhangsan@example.com" |
| username          | string | 是   | 3-50字符，支持字母、数字、下划线，不能以数字开头 | 用户名               | "zhangsan"             |
| password          | string | 是   | 至少8位，必须包含字母和数字                      | 密码                 | "password123"          |
| departmentId      | string | 否   | 有效的部门ID格式                                 | 部门ID               | "dept-001"             |
| jobTitle          | string | 否   | 最多100字符                                      | 职位名称             | "软件工程师"           |
| phone             | string | 否   | 有效的手机号码格式                               | 手机号码             | "13800138000"          |
| employeeId        | string | 否   | 最多50字符                                       | 员工ID               | "EMP001"               |
| applicationReason | string | 否   | -                                                | 申请原因             | "新员工入职"           |

**请求示例**:

```
curl -X POST http://localhost:3000/v1/auth/register-application \
  -H "Content-Type: application/json" \
  -d '{
    "applicantName": "张三",
    "applicantEmail": "zhangsan@example.com",
    "username": "zhangsan",
    "password": "password123",
    "departmentId": "dept-001",
    "jobTitle": "软件工程师",
    "phone": "13800138000",
    "employeeId": "EMP001",
    "applicationReason": "新员工入职"
  }'
```

## 错误码说明

系统使用统一的错误码体系，便于客户端处理和日志追踪。错误码格式：模块前缀\_数字编号。

### 注册管理相关错误码 (BIZ_xxx)

| 错误码  | HTTP 状态码 | 错误消息                         | 说明                                 | 处理建议               |
| ------- | ----------- | -------------------------------- | ------------------------------------ | ---------------------- |
| BIZ_011 | 409         | 邮箱已被使用                     | 用户提交的邮箱已被其他用户注册       | 提示用户更换邮箱       |
| BIZ_012 | 409         | 用户名已被使用                   | 用户提交的用户名已被其他用户使用     | 提示用户更换用户名     |
| BIZ_018 | 404         | 申请记录不存在                   | 查询的申请记录不存在                 | 检查申请ID是否正确     |
| BIZ_020 | 409         | 该邮箱已有申请记录，请勿重复申请 | 用户提交的邮箱已有未处理的申请记录   | 提示用户勿重复申请     |
| BIZ_021 | 409         | 该用户名已被申请，请更换用户名   | 用户提交的用户名已有未处理的申请记录 | 提示用户更换用户名     |
| BIZ_022 | 422         | 所选部门不存在                   | 用户选择的部门ID在系统中不存在       | 提示用户选择正确的部门 |

### 通用错误码

**参考认证模块文档中的通用错误码部分，包括：**
- 认证相关错误码 (AUTH_xxx)
- 验证相关错误码 (VAL_xxx)
- 业务逻辑错误码 (BIZ_xxx)
- 系统错误码 (SYS_xxx)

### 错误处理最佳实践

1. **统一错误处理**: 前端应根据错误码进行统一处理，而不是依赖 HTTP 状态码

2. **错误码模式识别**: 建议根据错误码前缀进行模式识别处理
   - `AUTH_`: 认证相关错误，可能需要重新登录或刷新令牌
   - `VAL_`: 验证相关错误，需要检查输入参数
   - `BIZ_`: 业务逻辑错误，需要根据业务规则处理
   - `SYS_`: 系统错误，通常需要重试或联系支持

3. **错误消息展示**: 直接使用 `error.message` 字段的内容，无需前端硬编码错误消息

4. **重试机制**: 对于包含 `retryAfter` 字段的错误，应按照指定时间后重试

5. **日志记录**: 使用 `traceId` 进行错误追踪和问题排查

## 数据模型

### 注册申请模型

注册申请数据结构定义：

```json
{
  "id": "string",              // 申请ID (UUID)
  "applicantName": "string",   // 申请人姓名
  "applicantEmail": "string",  // 申请人邮箱
  "username": "string",        // 用户名
  "departmentId": "string",    // 部门ID (可选)
  "jobTitle": "string",        // 职位名称 (可选)
  "phone": "string",           // 手机号码 (可选)
  "employeeId": "string",      // 员工ID (可选)
  "applicationReason": "string", // 申请原因 (可选)
  "status": "string",          // 申请状态 (pending/approved/rejected/cancelled)
  "notes": "string",           // 备注信息
  "createdAt": "2024-01-20T10:30:00.000Z",  // 创建时间
  "updatedAt": "2024-01-20T10:30:00.000Z"   // 更新时间
}
```

### 字段说明

**日期时间格式**:
- 所有日期时间字段均使用 ISO 8601 格式：`YYYY-MM-DDTHH:mm:ss.sssZ`
- 示例：`"2024-01-20T10:30:00.000Z"`

**状态字段说明**:
- `pending`: 待审批状态
- `approved`: 已批准状态
- `rejected`: 已拒绝状态
- `cancelled`: 已取消状态

## 安全说明

### 认证机制

注册申请相关接口无需认证，任何人都可以提交注册申请。

### 安全特性

1. **数据验证**: 所有输入数据都经过严格验证，防止恶意数据注入
2. **重复检查**: 系统会检查邮箱和用户名的唯一性，防止重复申请
3. **密码安全**: 密码在存储前会进行哈希处理，确保安全性
4. **部门验证**: 如果指定了部门，系统会验证部门ID的有效性

### 使用建议

1. **前端验证**: 建议在前端进行基础验证后再提交到后端
2. **错误处理**: 妥善处理各种错误情况，提供友好的用户提示
3. **申请跟踪**: 建议引导用户保存申请ID，以便后续查询申请状态
