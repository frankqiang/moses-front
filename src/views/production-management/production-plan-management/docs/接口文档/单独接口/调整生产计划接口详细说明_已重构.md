## 功能概述

### 所有功能

调整生产计划（Adjust Production Plan）是生产计划管理模块中的核心操作之一，用于根据实际生产情况或客户需求变化调整计划的需求数量、交期、优先级等关键信息，以支持灵活的生产调度和订单管理的业务场景。该接口支持同时调整主计划和子批次，并自动记录完整的变更审计日志。

### 关键特性

- ✅ **灵活调整**：支持调整需求数量、计划交期、优先级、备注等多个字段
- ✅ **子计划同步**：支持同时调整主计划和关联的子批次（重量、数量、炉窗时间等）
- ✅ **数据一致性校验**：自动验证子计划总重量与主计划需求数量的一致性
- ✅ **状态控制**：仅允许特定状态下的计划进行调整，保证业务流程合规性
- ✅ **事务保证**：使用数据库事务确保调整操作的原子性，失败自动回滚
- ✅ **审计追踪**：自动记录变更历史日志，包含操作者、变更字段、原值/新值等完整信息

---

### 使用前提

- ✅ **权限要求**：用户必须具有 `prod.production-plan.adjust` 权限
- ✅ **认证要求**：需要提供有效的 JWT Token 进行身份认证
- ✅ **计划存在性**：请求的计划ID必须存在于系统中且未被删除
- ✅ **状态限制**：计划状态必须为 `RECEIVED`（已接收）或 `CONFIRMED`（已确认）
- ✅ **未冻结状态**：计划的 `isFrozen` 字段必须为 `false`（未冻结）

### 不适用场景

- ❌ **已发布计划**：状态为 `RELEASED`（已发布）或 `IN_PROGRESS`（执行中）的计划不允许调整
- ❌ **已完成计划**：状态为 `COMPLETED`（已完成）的计划不允许调整
- ❌ **已取消计划**：状态为 `CANCELLED`（已取消）的计划不允许调整
- ❌ **冻结计划**：已被冻结的计划（`isFrozen: true`）禁止任何调整操作
- ❌ **状态变更**：如需变更计划状态，应使用 `PATCH /v1/prod/plans/:planId/status` 接口
- ❌ **拆分合并**：如需拆分或合并计划，应使用对应的专用接口

### 详细步骤说明

#### 步骤1: 权限验证
- 验证用户JWT Token的有效性
- 检查用户是否具有 `prod.production-plan.adjust` 权限
- 权限不足返回 403 Forbidden

#### 步骤2: 参数验证
- 验证路径参数 `planId` 格式（必须是UUID v4）
- 验证请求体参数：
  - `demandQuantity`: 正数，最多3位小数
  - `plannedDeliveryDate`: ISO 8601日期格式
  - `planPriority`: 枚举值（LOW, NORMAL, HIGH, URGENT）
  - `items`: 子计划调整数组（如提供）
- 至少需要提供一个可更新的字段

#### 步骤3: 计划查询与锁定
- 使用 `FOR UPDATE` 行级锁查询计划，防止并发修改
- 检查计划是否存在，不存在返回 404
- 加载关联的子计划列表

#### 步骤4: 状态校验
- 检查计划状态是否允许调整（`RECEIVED` 或 `CONFIRMED`）
- 检查计划是否被冻结（`isFrozen` 字段）
- 不符合条件返回 400 错误

#### 步骤5: 主计划更新
- 记录调整前的原始数据快照
- 构建更新数据对象：
  - `demandQuantity`: 需求数量
  - `plannedDeliveryDate`: 计划交期
  - `planPriority`: 计划优先级
  - `remarks`: 备注说明
- 执行主计划表更新操作

#### 步骤6: 子计划调整
如果请求中包含 `items` 数组：
- 遍历每个子计划调整项
- 验证子计划ID是否存在
- 验证子计划状态是否合法
- 更新子计划字段：
  - `plannedWeight`: 计划重量
  - `plannedQuantity`: 计划数量
  - `status`: 子计划状态
  - `expectedFurnaceWindowStart/End`: 炉窗时间

#### 步骤7: 一致性校验
- 如果调整了主计划需求数量或子计划重量
- 计算所有子计划总重量
- 验证总重量是否与主计划需求数量一致
- 不一致返回 400 错误

#### 步骤8: 审计日志记录
- 创建变更日志记录：
  - `changeType`: "ADJUST"（调整）
  - `originalValue`: 调整前快照
  - `newValue`: 调整后快照
  - `changeDescription`: 变更描述
  - `changeContext`: 包含调整字段、操作者信息等
  - `operationSource`: "MANUAL"（手动操作）
  - `operatorId/operatorName/operatorIp`: 操作者信息

#### 步骤9: 事务提交与响应
- 提交数据库事务
- 记录操作日志
- 返回调整后的完整计划信息（包含子计划列表）

## 接口文档

### 基本信息

**接口路径**: `PATCH /v1/prod/plans/:planId`

**功能描述**: 调整生产计划的需求数量、交期、优先级等信息，支持同时调整主计划和子批次

**认证要求**: Bearer Token 认证，需要 `prod.production-plan.adjust` 权限

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 路径参数

| 参数名 | 类型   | 必填 | 限制         | 描述             | 示例                                   |
| ------ | ------ | ---- | ------------ | ---------------- | -------------------------------------- |
| planId | string | 是   | UUID v4 格式 | 生产计划唯一标识 | "7f3c6d8e-9a2b-4f1c-8e5d-6a9b0c1d2e3f" |

### 请求参数

| 参数名              | 类型   | 必填 | 限制                                 | 描述                     | 示例                       |
| ------------------- | ------ | ---- | ------------------------------------ | ------------------------ | -------------------------- |
| demandQuantity      | number | 否   | 正数，最多3位小数                    | 调整后的需求数量         | 1200.5                     |
| plannedDeliveryDate | string | 否   | ISO 8601日期格式                     | 调整后的计划交期         | "2024-11-30T23:59:59.000Z" |
| planPriority        | string | 否   | 枚举: LOW, NORMAL, HIGH, URGENT      | 调整后的计划优先级       | "HIGH"                     |
| remarks             | string | 否   | 最大500字符                          | 备注说明                 | "客户要求提前交货"         |
| changeDescription   | string | 否   | 最大500字符                          | 变更描述（用于审计日志） | "调整交期和优先级"         |
| items               | array  | 否   | 子计划调整列表，见下方子计划调整结构 | 子批次调整信息           | 见下方结构说明             |

⚠️ **重要提示**:
- 至少需要提供一个可更新的字段（`demandQuantity`、`plannedDeliveryDate`、`planPriority`、`remarks` 或 `items`）
- 如果调整了 `demandQuantity` 或子计划的 `plannedWeight`，必须确保所有子计划总重量与主计划需求数量一致

### 子计划调整（items）结构

| 参数名                     | 类型   | 必填 | 限制                                                 | 描述                 | 示例                                   |
| -------------------------- | ------ | ---- | ---------------------------------------------------- | -------------------- | -------------------------------------- |
| id                         | string | 是   | UUID v4格式，必须是该计划下存在的子计划ID            | 子计划唯一标识       | "8e4d7f9c-0b3a-5g2d-9f6e-7b0c2e3d4f5a" |
| plannedWeight              | number | 否   | 正数，最多3位小数                                    | 调整后的计划重量     | 400.5                                  |
| plannedQuantity            | number | 否   | 正整数                                               | 调整后的计划数量     | 12                                     |
| status                     | string | 否   | 见附录：子计划状态枚举                               | 调整后的子计划状态   | "READY_FOR_SCHEDULING"                 |
| expectedFurnaceWindowStart | string | 否   | ISO 8601日期格式                                     | 调整后的装炉时段开始 | "2024-02-01T08:00:00.000Z"             |
| expectedFurnaceWindowEnd   | string | 否   | ISO 8601日期格式，必须晚于expectedFurnaceWindowStart | 调整后的装炉时段结束 | "2024-02-01T16:00:00.000Z"             |

⚠️ **注意**: 每个子计划调整项至少需要提供一个可更新的字段

## 常见问题

### Q1: 为什么调整失败提示"计划已冻结"？

**A**: 当计划的 `isFrozen` 字段为 `true` 时，系统会拒绝所有调整操作。这是为了防止在关键时期（如审批中、执行中）对计划进行意外修改。

**解决方案**:
1. 检查计划详情，确认 `isFrozen` 字段
2. 联系有权限的管理员解冻计划
3. 解冻后重新执行调整操作

### Q2: 调整子计划重量时为什么提示"总重量不一致"？

**A**: 系统要求所有子计划的 `plannedWeight` 总和必须等于主计划的 `demandQuantity`，这是为了保证数据一致性。

**解决方案**:
1. 计算所有子计划的总重量
2. 确保总重量等于主计划的需求数量
3. 如果主计划数量也需要调整，在同一请求中同时更新

**示例**:
```json
{
  "demandQuantity": 1200.0,  // 主计划需求
  "items": [
    { "id": "item-1", "plannedWeight": 600.0 },
    { "id": "item-2", "plannedWeight": 600.0 }
  ]
  // 总重量 600 + 600 = 1200，与主计划一致 ✓
}
```

### Q3: 哪些状态的计划可以调整？

**A**: 只有以下状态的计划允许调整：
- `RECEIVED` (已接收)
- `CONFIRMED` (已确认)

**不允许调整的状态**:
- `RELEASED` (已发布) - 已下达生产，不可修改
- `IN_PROGRESS` (执行中) - 正在生产，不可修改
- `COMPLETED` (已完成) - 已完成，不可修改
- `CANCELLED` (已取消) - 已取消，不可修改
- `PENDING_APPROVAL` (待审批) - 审批中，不可修改

### Q4: 调整操作会触发审批流程吗？

**A**: 不会。调整操作（`PATCH /v1/prod/plans/:planId`）直接生效，不需要审批。

**需要审批的操作**:
- 下达计划（状态变更为 `RELEASED`）
- 取消计划（状态变更为 `CANCELLED`）

这些操作需要使用状态更新接口 `PATCH /v1/prod/plans/:planId/status`。

### Q5: 如何查看调整历史记录？

**A**: 调整操作会自动记录到变更审计日志中，可以通过以下方式查看：

1. **获取计划详情**：`GET /v1/prod/plans/:planId`，响应中包含 `changeLogs` 数组
2. **获取审计日志**：`GET /v1/prod/plans/:planId/audit-logs`，专门的审计日志接口

**审计日志包含**:
- 变更类型：`ADJUST`
- 变更描述：用户提供的 `changeDescription`
- 变更上下文：调整的字段、子计划ID等
- 操作者信息：ID、姓名、IP地址等
- 时间戳：操作时间

### Q6: 可以只调整部分子计划吗？

**A**: 可以。`items` 数组中只需包含需要调整的子计划，未包含的子计划保持不变。

**示例**:
```json
{
  "changeDescription": "仅调整第一个子计划",
  "items": [
    {
      "id": "item-1-uuid",
      "plannedWeight": 700.0
    }
    // item-2 不包含在请求中，保持不变
  ]
}
```

⚠️ **注意**: 如果调整后导致总重量与主计划不一致，需要同时更新 `demandQuantity`。

### Q7: 调整后数据会立即生效吗？

**A**: 是的，调整操作使用数据库事务，一旦提交成功，数据立即生效。

**事务保证**:
- 所有更新操作在同一事务中完成
- 任何步骤失败都会自动回滚
- 保证数据的原子性和一致性

### Q8: 如何处理并发调整冲突？

**A**: 系统使用行级锁（`FOR UPDATE`）防止并发修改冲突。

**并发处理机制**:
1. 调整操作开始时对计划记录加锁
2. 其他并发请求会等待锁释放
3. 先到先得，后续请求基于最新数据操作
4. 事务提交后释放锁

**建议**:
- 前端显示"正在保存"状态，防止重复提交
- 失败后提示用户刷新数据重试
- 使用乐观锁（版本号）进一步优化

### 状态转换规则

#### 计划状态转换图

```
RECEIVED (已接收)
  ↓
  ├─→ CONFIRMED (已确认) ← 允许调整
  │     ↓
  │     ├─→ PARTIALLY_RELEASED (部分发布)
  │     │     ↓
  │     │     └─→ RELEASED (已发布)
  │     │           ↓
  │     │           └─→ IN_PROGRESS (执行中)
  │     │                 ↓
  │     │                 └─→ COMPLETED (已完成)
  │     │
  │     └─→ PENDING_APPROVAL (待审批)
  │           ↓
  │           ├─→ RELEASED (已发布)
  │           └─→ CANCELLED (已取消)
  │
  └─→ PENDING_APPROVAL (待审批)
        ↓
        └─→ CANCELLED (已取消)
```

**调整操作限制**:
- ✅ `RECEIVED` 和 `CONFIRMED` 状态可以调整
- ❌ 其他所有状态禁止调整
