## 功能概述

### 所有功能

获取退火任务详情（Get Annealing Task Detail）是退火任务管理模块中的核心查询接口之一，用于获取指定退火任务的完整详细信息，以支持任务查看、状态追踪、物料管理、排程监控等业务场景。

本接口通过任务ID获取任务的所有相关信息，包括：
- 任务基本信息（编号、名称、状态、优先级等）
- 关联的生产计划信息
- 关联的工艺模板信息
- 产品信息（产品编码、名称、合金牌号等）
- 排程信息（炉号、计划装炉/出炉时间等）
- 执行信息（实际装炉/执行/出炉时间等）
- 物料明细列表（可选）
- 操作日志记录（可选）

### 关键特性

- ✅ **完整数据聚合**：一次请求获取任务的所有关联信息，包括生产计划、工艺模板、产品信息等
- ✅ **灵活数据控制**：通过查询参数控制是否加载物料明细和操作日志，优化查询性能
- ✅ **多维度关联**：支持查看任务与生产计划、计划批次、工艺模板、产品的关联关系
- ✅ **排程信息展示**：提供完整的排程结果，包括炉号、计划时间、预计能耗等
- ✅ **执行进度追踪**：展示任务各阶段的实际执行时间（装炉、执行、出炉）
- ✅ **物料清单管理**：可选择性加载绑定的物料明细，包括料框/料垛信息
- ✅ **操作日志审计**：可选择性查看任务的历史操作记录，支持审计和问题追溯

---

### 使用前提

- ✅ **权限要求**：用户必须具有 `prod.annealing-task.view` 权限
- ✅ **任务存在**：指定的任务ID必须对应有效的退火任务记录
- ✅ **认证要求**：请求必须携带有效的JWT访问令牌

### 不适用场景

- ❌ **批量查询**：本接口仅支持单个任务查询，批量查询请使用列表接口
- ❌ **统计分析**：不适合用于数据统计和分析，建议使用专门的统计接口
- ❌ **实时监控**：如需实时追踪任务执行进度，应使用进度查询接口 `/tasks/:taskId/progress`

### 详细步骤说明

#### 步骤1: 权限验证
系统验证当前用户是否具有 `prod.annealing-task.view` 权限。如果权限验证失败，返回 403 Forbidden 错误。

#### 步骤2: 参数验证
验证请求参数的合法性：
- **taskId**: 必须为有效的UUID v4格式
- **includeMaterials**: 可选，字符串 'true' 或 'false'，默认为 'true'
- **includeLogs**: 可选，字符串 'true' 或 'false'，默认为 'false'

#### 步骤3: 查询任务基本信息
根据任务ID查询退火任务的主表记录，包括：
- 任务编号、名称、状态、优先级
- 计划重量、实际重量、物料数量
- 产品编码、合金牌号
- 创建时间、更新时间等

如果任务不存在，返回 404 Not Found 错误。

#### 步骤4: 加载关联数据
通过 Sequelize 的 `include` 机制，一次性加载所有关联的数据模型：
- **生产计划** (ProductionPlan): 关联的计划编号、优先级、交期等
- **计划批次** (ProductionPlanItem): 关联的批次编号、计划重量/数量等
- **工艺模板** (ProcessTemplate): 工艺模板编码和名称
- **工艺模板版本** (ProcessTemplateVersion): 当前使用的工艺版本
- **产品信息** (AluminumFoilProduct): 产品主数据的详细规格

#### 步骤5: 条件加载物料明细
如果 `includeMaterials` 参数不为 'false'（默认为 true），则加载任务关联的物料明细列表：
- 查询 AnnealingTaskMaterial 表
- 按 loadSequence（装炉顺序）升序排列
- 包含物料ID、编码、类型、重量、位置等信息

物料明细用于展示任务绑定的料框或料垛清单。

#### 步骤6: 条件加载操作日志
如果 `includeLogs` 参数为 'true'（默认为 false），则加载任务的操作日志：
- 查询 AnnealingTaskLog 表
- 按创建时间降序排列（最新的在前）
- 限制返回最近100条记录
- 包含操作类型、描述、操作人、操作时间等信息

日志用于审计追溯和问题分析。

#### 步骤7: 数据转换和格式化
将查询结果转换为统一的响应格式：
- **task**: 任务基本信息对象
- **planInfo**: 关联的生产计划信息（如果存在）
- **planItemInfo**: 关联的计划批次信息（如果存在）
- **scheduleInfo**: 排程相关信息（炉号、计划时间等）
- **executionInfo**: 执行相关信息（实际时间等）
- **processInfo**: 工艺模板信息（如果存在）
- **productInfo**: 产品详细信息（如果存在）
- **materials**: 物料明细列表（如果请求加载）
- **logs**: 操作日志列表（如果请求加载）

#### 步骤8: 返回响应
返回包含完整任务详情的成功响应，HTTP状态码为 200 OK。

## 接口文档

### 基本信息

**接口路径**: `GET /v1/prod/annealing-tasks/:taskId`

**功能描述**: 根据任务ID获取退火任务的详细信息，支持选择性加载物料明细和操作日志。

**认证要求**: Bearer Token认证，需要 `prod.annealing-task.view` 权限

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 统一响应格式

#### 成功响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
    // 具体的业务数据，根据接口而不同
  },
  "message": "操作成功的描述信息",
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

#### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

### 路径参数

| 参数名 | 类型   | 必填 | 限制         | 描述       | 示例                                   |
| ------ | ------ | ---- | ------------ | ---------- | -------------------------------------- |
| taskId | string | 是   | UUID v4 格式 | 退火任务ID | "a1b2c3d4-e5f6-7890-abcd-ef1234567890" |

### 查询参数

| 参数名           | 类型   | 必填 | 限制              | 描述                          | 默认值  | 示例    |
| ---------------- | ------ | ---- | ----------------- | ----------------------------- | ------- | ------- |
| includeMaterials | string | 否   | 'true' 或 'false' | 是否包含物料明细列表          | 'true'  | "false" |
| includeLogs      | string | 否   | 'true' 或 'false' | 是否包含操作日志（最近100条） | 'false' | "true"  |

**注意**：
- `includeMaterials` 控制是否加载任务绑定的料框/料垛明细，默认加载以提供完整信息
- `includeLogs` 控制是否加载操作日志，默认不加载以优化查询性能，仅在需要审计追溯时传入 'true'

#### cURL 命令

```bash
# 获取任务详情（包含物料明细，不含日志 - 默认行为）

  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."

  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."

# 获取任务详情（含物料明细和操作日志）
curl -X GET "http://localhost:3000/v1/prod/annealing-tasks/a1b2c3d4-e5f6-7890-abcd-ef1234567890?includeMaterials=true&includeLogs=true" \
```

## 使用示例

### 场景1: 查看任务基本信息和关联数据

**业务需求**: 在任务列表页点击某个任务，查看其基本信息、关联的生产计划、排程信息等，但不需要物料明细和操作日志，以加快加载速度。

**业务需求**: 在生产监控大屏上展示任务的当前执行状态和各阶段的完成时间。

**业务需求**: 车间人员需要根据任务查看产品的详细规格（厚度、宽度、态别等），以便准备生产。

## 常见问题

### Q1: 为什么有些关联信息字段是 null？

**A**: 这取决于任务的来源和当前状态：
- **planInfo 和 planItemInfo**: 只有从生产计划生成的任务才有这些信息，手工创建的任务这些字段为 null
- **scheduleInfo 的部分字段**: 未排程的任务（status 为 draft 或 pending-schedule），排程相关字段为 null
- **executionInfo 的字段**: 未执行到对应阶段的任务，相应字段为 null
- **processInfo**: 如果任务创建时未关联工艺模板，该字段为 null
- **productInfo**: 如果任务的 productCode 未在产品主数据中匹配到记录，该字段为 null

### Q2: materials 字段什么时候会返回？

**A**: 默认情况下会返回物料明细列表。只有当请求参数明确传入 `includeMaterials=false` 时，响应中才不会包含 materials 字段。这样设计是因为物料明细通常是任务详情的重要组成部分。

### Q3: 如何控制是否加载操作日志？

**A**: 操作日志默认不加载，以优化查询性能。只有当请求参数明确传入 `includeLogs=true` 时，响应中才会包含 logs 字段。日志最多返回最近100条记录，按时间倒序排列。

### Q4: 如何理解 actualWeight 和 plannedWeight 的区别？

**A**:
- **plannedWeight**: 任务创建时设定的计划重量，来自生产计划或手工输入，不会自动变化
- **actualWeight**: 绑定物料后，根据实际绑定的所有物料的重量之和自动计算得出。未绑定物料时，actualWeight 为 null 或 0

### Q5: scheduleLockedUntil 字段的作用是什么？

**A**: 该字段表示任务被排程系统锁定的截止时间。在锁定期内，排程算法会跳过该任务，避免重复排程。锁定时间到期后，任务会自动释放，可再次参与排程。这个机制用于支持分布式排程场景。

### Q6: 为什么有时 productInfo 为 null，但 task.productCode 有值？

**A**: task 对象中的 productCode、productName、alloyGrade 是冗余字段，在任务创建时从产品主数据复制过来的快照。如果后续产品主数据被删除或修改，task 中的这些字段仍保留历史值，但 productInfo（关联查询产品主数据）会返回 null 或最新的产品信息。

### Q7: 如何区分任务是从计划生成还是手工创建？

**A**: 通过 `task.source` 字段判断：
- `plan-split`: 从生产计划批次拆分生成
- `manual`: 手工创建

### Q8: 物料明细中的 isPrimary 字段有什么用？

**A**: isPrimary 标识是否为主料框，主料框通常是第一个加入的料框，用于确定某些工艺参数（如炉温曲线）。一个任务通常只有一个主料框。

### Q9: 操作日志中的 originalValue 和 newValue 字段是什么格式？

**A**: 这两个字段是 JSON 对象，记录操作前后的数据变化。不同的操作类型（action）会有不同的数据结构。例如：
- **status-changed**: 记录状态变更前后的值
- **material-bound**: 记录绑定的物料数量和总重量
- **schedule-applied**: 记录排程结果（炉号、时间等）

### Q10: 为什么查询速度有时较慢？

**A**: 查询速度取决于加载的关联数据量：
- 仅加载基本信息（includeMaterials=false, includeLogs=false）速度最快
- 加载物料明细会增加查询时间，物料数量越多耗时越长
- 加载操作日志（最多100条）会进一步增加查询时间

建议根据实际需求选择性加载数据，在列表场景使用最小加载，在详情页按需加载完整信息。
