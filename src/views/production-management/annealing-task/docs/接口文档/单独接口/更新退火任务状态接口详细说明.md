## 📝 版本更新记录

### v1.2 (2025-11-01) - 禁止直接回退和取消限制

**重要变更**：
- ❌ **禁止排程回退** - 不再允许从 `scheduled` 状态直接回退到 `pending-schedule`，必须通过取消排程方案实现
- ❌ **取消任务限制** - 已关联排程方案的任务不允许直接取消，必须先取消排程方案

**变更原因**：
- 确保排程方案与任务状态的数据一致性
- 强制用户遵循正确的业务流程
- 防止出现任务状态显示"待排程"但仍关联排程方案的数据不一致情况

**影响分析**：
- ⚠️ **破坏性变更**：之前可以直接回退的操作现在会被拒绝
- ✅ **正确流程**：需要重新排程时，先到排程模块取消排程方案，任务会自动回到待排程状态
- ✅ **错误提示**：提供清晰的错误信息和正确操作指引

**升级建议**：
- 前端需要移除"重新排程"按钮，或改为跳转到排程管理模块
- 取消任务前先检查是否关联排程方案，如有则提示用户先取消排程方案

### v1.1 (2025-10-31) - 增加物料绑定前置校验

**新增功能**：
- ✅ **提交排程前置校验** - 在状态从 `draft` 转换到 `pending-schedule` 时，增加物料绑定校验
- ✅ **明确错误提示** - 未绑定物料时会返回清晰的错误信息：`"任务未绑定物料，无法提交排程。请先绑定待退火的料框或料垛"`

**变更原因**：
- 确保提交排程的任务已经准备好物料，避免空任务进入排程队列
- 提高数据质量，减少无效排程请求

**设计说明**：
- 本接口只校验是否已绑定物料（`materialCount > 0`），不校验重量范围
- 重量匹配由排程系统根据分配的炉子容量进行精确校验
- 这种设计提供了更大的灵活性，支持不同容量的设备

**升级影响**：
- ⚠️ **行为变化**：之前未绑定物料也能提交排程，现在会被拒绝
- ✅ **向后兼容**：对已绑定物料的任务无影响
- ✅ **用户体验**：提供清晰的错误提示，指导用户先绑定物料

## 功能概述

### 所有功能

更新退火任务状态（Update Annealing Task Status）是退火任务管理模块中的核心操作之一，用于驱动退火任务在整个生命周期中的状态流转，以支持从计划排程、装炉准备、执行监控到完成出炉的完整业务场景。

系统会自动根据状态流转规则校验状态变更是否合法，并根据新状态自动更新相应的时间字段（如装炉开始时间、执行开始时间等）。所有状态变更操作都会记录详细的操作日志，包含操作人、操作时间、变更原因等信息，同时会与生产计划状态保持联动同步。

### 关键特性

- ✅ **严格的状态流转校验**：基于预定义的状态转换规则，确保只允许合法的状态变更，防止业务流程错乱
- ✅ **智能时间字段更新**：根据目标状态自动更新装炉开始/完成时间、执行开始/完成时间、出炉时间等关键时间节点
- ✅ **完整的操作日志记录**：详细记录状态变更的原始值、新值、操作人、操作原因等信息，支持审计追溯
- ✅ **生产计划状态联动**：自动同步更新关联的生产计划批次状态，保持任务执行与计划管理的数据一致性
- ✅ **强制原因说明机制**：对于暂停、取消、异常终止等敏感操作，必须提供原因说明，确保业务可追溯
- ✅ **事务处理保障**：所有状态更新操作在数据库事务中执行，确保数据一致性和原子性

---

### 使用前提

- ✅ **任务必须存在**：目标退火任务必须已创建且未被删除
- ✅ **权限要求**：操作用户必须具有 `prod.annealing-task.manage` 权限
- ✅ **状态流转合法**：目标状态必须是当前状态允许转换的下一状态之一
- ✅ **原因说明要求**：执行暂停、取消、异常终止操作时必须提供 `reason` 参数

### 不适用场景

- ❌ **终态任务无法变更**：已完成（completed）、已取消（cancelled）、已终止（terminated）的任务不允许再次变更状态
- ❌ **跨越式状态跳转**：不允许跳过中间状态直接变更（如从 draft 直接跳到 in-progress），必须按照业务流程逐步流转
- ❌ **并发状态冲突**：多个操作同时尝试修改同一任务状态时，只有一个会成功，其他会因为数据版本冲突而失败

### 详细步骤说明

#### 步骤1: 接收状态更新请求

从 HTTP 请求中提取路径参数 `taskId` 和请求体参数：
- `status`: 目标状态（必填）
- `remarks`: 备注说明（可选）
- `reason`: 变更原因（暂停/取消/终止时必填）
- `additionalData`: 附加数据（可选）

同时从认证上下文中提取操作人信息（`operatorId`、`operatorName`）和客户端 IP 地址。

#### 步骤2: 参数校验

在进入业务逻辑前，先进行基础参数校验：
- **taskId 校验**：不能为空，必须是有效的 UUID 格式
- **status 校验**：不能为空，必须是系统定义的合法状态值之一
- **operatorId 校验**：必须存在，确保操作可追溯
- **reason 校验**：当目标状态为 `paused`、`cancelled`、`terminated` 时，必须提供 `reason` 说明

#### 步骤3: 开启数据库事务

使用 Sequelize 事务机制开启数据库事务，确保后续所有数据库操作的原子性。如果任何步骤失败，会自动回滚所有已执行的操作，保证数据一致性。

#### 步骤4: 锁定任务记录

使用 `SELECT ... FOR UPDATE` 语句锁定目标任务记录，防止并发操作导致的数据冲突。在事务提交前，其他事务无法修改该记录。

#### 步骤5: 任务存在性校验

检查任务是否存在：
- 如果任务不存在，抛出 `404 RESOURCE_NOT_FOUND` 错误
- 如果任务存在，继续后续流程

#### 步骤6: 查询关联的计划批次

如果任务包含 `planItemId`（从生产计划拆分而来），则查询关联的生产计划批次记录，用于后续的状态联动同步。

#### 步骤7: 状态流转合法性校验

根据预定义的状态转换规则（STATE_TRANSITIONS）校验状态流转是否合法：

1. **相同状态校验**：检查目标状态是否与当前状态相同，如果相同则抛出错误
2. **允许的状态流转校验**：检查从当前状态到目标状态的转换是否在允许列表中
3. **终态校验**：如果当前状态是终态（completed、cancelled、terminated），不允许任何状态变更

如果校验不通过，抛出 `400 INVALID_STATUS` 错误，并返回允许的下一状态列表供前端参考。

#### 步骤8: 业务前置条件校验

对于特定的状态转换，执行业务规则校验：

**提交排程校验（draft → pending-schedule）**：
- 检查任务是否已绑定物料（`materialCount > 0`）
- 如果未绑定物料，抛出 `400 PARAM_ERROR` 错误
- 错误信息：`"任务未绑定物料，无法提交排程。请先绑定待退火的料框或料垛"`
- 校验通过后记录信息日志（物料数量、总重量）

**设计说明**：
- 本接口不校验重量范围，由排程系统根据分配的炉子容量进行精确匹配
- 只确保任务已准备好物料，具体重量是否合适由排程分配时判断

#### 步骤9: 计算时间字段更新

根据目标状态，自动计算需要更新的时间字段：

| 目标状态        | 自动更新的时间字段         | 说明             |
| --------------- | -------------------------- | ---------------- |
| scheduled       | schedulePublishedAt        | 排程发布时间     |
| loading         | actualLoadingStartedAt     | 实际装炉开始时间 |
| waiting-execute | actualLoadingCompletedAt   | 实际装炉完成时间 |
| in-progress     | executionStartedAt         | 退火执行开始时间 |
| waiting-unload  | executionCompletedAt       | 退火执行完成时间 |
| completed       | actualUnloadingCompletedAt | 实际出炉完成时间 |

所有时间字段都使用当前服务器时间（UTC），且只在字段为空时才更新（避免覆盖已有的时间记录）。

#### 步骤10: 更新任务状态和时间字段

执行数据库 UPDATE 操作，更新任务表（annealing_tasks）的以下字段：
- `status`: 新状态
- 自动计算的时间字段（如有）
- `updatedBy`: 操作人 ID
- `updatedAt`: 更新时间（Sequelize 自动维护）

#### 步骤11: 记录操作日志

在任务日志表（annealing_task_logs）中插入一条状态变更日志，包含：
- `taskId`: 任务 ID
- `action`: 操作类型（"status-changed"）
- `description`: 操作描述（用户提供的 reason 或自动生成的描述）
- `originalValue`: 原始值（包含旧状态）
- `newValue`: 新值（包含新状态和更新的时间字段）
- `operatorId`: 操作人 ID
- `operatorName`: 操作人姓名
- `operatorIp`: 操作人 IP 地址
- `operationContext`: 操作上下文（包含 remarks、reason、additionalData）

#### 步骤12: 同步生产计划批次状态

如果任务关联了生产计划批次（planItemId 不为空），根据任务新状态自动同步更新计划批次状态：

| 任务状态             | 计划批次状态变更逻辑                               |
| -------------------- | -------------------------------------------------- |
| pending-schedule     | draft → ready-for-scheduling                       |
| scheduled            | ready-for-scheduling/draft → scheduled             |
| in-progress          | scheduled/ready-for-scheduling → in-progress       |
| completed            | 检查该批次下所有任务，如全部完成则标记为 completed |
| cancelled/terminated | 检查该批次下所有任务，如全部结束则标记为 cancelled |

同步逻辑确保生产计划的执行进度能准确反映退火任务的实际状态。

#### 步骤13: 提交事务

所有操作成功完成后，提交数据库事务。如果任何步骤发生异常，自动回滚事务，确保数据一致性。

#### 步骤14: 重新加载任务数据

从数据库重新加载任务完整数据，包括关联的计划批次信息，确保返回给前端的数据是最新的。

#### 步骤15: 返回更新后的任务对象

将更新后的任务对象封装到统一响应格式中返回，HTTP 状态码 200，包含 success、data、message、meta 等字段。

## 接口文档

### 基本信息

**接口路径**: `PATCH /v1/prod/annealing-tasks/:taskId/status`

**功能描述**: 更新退火任务的状态，系统会自动校验状态流转合法性、更新关联的时间字段、记录操作日志，并与生产计划状态保持联动同步。

**认证要求**: Bearer Token 认证，需要 `prod.annealing-task.manage` 权限

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
    // 具体的业务数据，根据接口而不同
  },
  "message": "操作成功的描述信息",
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }

```

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "allowedNextStatuses": ["status1", "status2"],
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息（如允许的下一状态列表）
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

### 路径参数

| 参数名 | 类型   | 必填 | 限制     | 描述                                 | 示例                                   |
| ------ | ------ | ---- | -------- | ------------------------------------ | -------------------------------------- |
| taskId | string | 是   | UUID格式 | 退火任务ID，必须是系统中已存在的任务 | "554e4422-beac-48bd-a22b-43b38a3c212b" |

### 请求参数

| 参数名         | 类型   | 必填     | 限制             | 描述                                                      | 示例                                   |
| -------------- | ------ | -------- | ---------------- | --------------------------------------------------------- | -------------------------------------- |
| status         | string | 是       | 有效的任务状态值 | 目标状态，必须是系统定义的合法状态之一                    | "in-progress"                          |
| remarks        | string | 否       | 最大1000字符     | 备注说明，用于记录额外的操作信息                          | "开始执行退火工艺"                     |
| reason         | string | 条件必填 | 最大500字符      | 状态变更原因，当状态为 paused/cancelled/terminated 时必填 | "设备故障需要暂停"                     |
| additionalData | object | 否       | JSON对象         | 附加数据，用于存储业务相关的扩展信息                      | {"operator": "张三", "comment": "..."} |

**字段详细说明**:

1. **status**: 目标状态，所有可用状态值请参见附录中的"退火任务状态枚举"。状态流转必须符合预定义的转换规则，不允许跨越式跳转。

2. **remarks**: 可选的备注信息，用于记录操作说明、注意事项等，会保存在操作日志的 `operationContext.remarks` 中。

3. **reason**: 对于敏感操作（暂停、取消、终止）必须提供的原因说明，确保业务可追溯。如果在执行这些操作时未提供 reason，请求将被拒绝并返回 400 错误。

4. **additionalData**: 灵活的扩展字段，可以存储业务相关的任意 JSON 数据，如操作关联的设备信息、异常代码等。

## 使用示例

### 场景1: 任务从"待排程"变更为"已排程"

**业务需求**: 排程系统完成任务排程后，需要将任务状态从 `pending-schedule` 更新为 `scheduled`，系统会自动记录排程发布时间。

**关键点**:
- 系统自动填充 `schedulePublishedAt` 字段
- 如果任务关联了生产计划批次，批次状态会同步更新为 `scheduled`

---

### 场景2: 开始装炉操作

**业务需求**: 操作工确认开始装炉，将任务状态从 `waiting-loading` 更新为 `loading`，系统会自动记录装炉开始时间。

**关键点**:
- 系统自动填充 `actualLoadingStartedAt` 字段
- 可用于后续计算装炉耗时

---

### 场景3: 设备故障暂停任务

**业务需求**: 退火炉出现故障，需要暂停正在执行的任务，必须提供暂停原因和故障信息。
### 场景4: 任务异常终止

**业务需求**: 退火过程中发现物料质量问题，需要终止任务，避免继续生产不合格产品。
### 场景5: 恢复暂停的任务

**关键点**:
- 从 `paused` 状态可以恢复到暂停前的状态
- 恢复操作不强制要求 `reason` 字段，但建议提供 `remarks` 说明恢复原因

### 状态流转规则表

| 当前状态         | 允许的下一状态                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------- |
| draft            | pending-schedule, cancelled                                                                              |
| pending-schedule | scheduled, draft, cancelled                                                                              |
| scheduled        | waiting-loading, ~~pending-schedule~~, paused, cancelled                                                 |
| waiting-loading  | loading, paused, cancelled                                                                               |
| loading          | waiting-execute, waiting-loading, paused, terminated                                                     |
| waiting-execute  | in-progress, paused, terminated                                                                          |
| in-progress      | waiting-unload, paused, terminated                                                                       |
| waiting-unload   | completed, paused, terminated                                                                            |
| paused           | scheduled, waiting-loading, loading, waiting-execute, in-progress, waiting-unload, cancelled, terminated |
| completed        | 无（终态）                                                                                               |
| cancelled        | 无（终态）                                                                                               |
| terminated       | 无（终态）                                                                                               |

**说明**:
- 终态（completed、cancelled、terminated）不允许任何状态变更
- paused 状态可以恢复到暂停前的状态，具体取决于业务需求
- 不在允许列表中的状态流转会被系统拒绝，并返回 400 错误
- ❌ **v1.2 变更**：不再允许从 `scheduled` 直接回退到 `pending-schedule`，必须通过取消排程方案实现
- ❌ **v1.2 变更**：取消任务（变更到 `cancelled`）时，如果任务已关联排程方案（有 `schedulePlanId`），会被拒绝
