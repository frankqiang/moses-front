## 功能概述

### 所有功能

应用排程结果（Apply Schedule Result）是退火任务管理中的核心排程集成操作，用于接收排程模块计算后回传的炉号分配、计划装炉/出炉时间等排程结果，并将这些数据落库到退火任务记录中，同时自动更新任务状态为"已排程"，记录操作日志，联动生产计划批次状态，以支持排程系统与执行系统的无缝集成和数据一致性维护的业务场景。

### 关键特性

- ✅ **排程结果落库**：接收并存储排程方案ID、炉号、计划装炉/出炉时间、预计时长、预计能耗等排程结果数据
- ✅ **自动状态更新**：支持根据配置自动将任务状态从"待排程/草稿"更新为"已排程"，触发后续业务流程
- ✅ **状态校验保护**：仅允许处于"待排程"或"草稿"状态的任务应用排程结果，防止重复排程或状态混乱
- ✅ **时间合法性校验**：自动校验计划装炉时间必须早于计划出炉时间，确保排程数据的逻辑正确性
- ✅ **事务保证**：使用数据库事务确保排程数据更新、任务状态变更、日志记录、计划状态联动的原子性操作
- ✅ **排程日志追踪**：详细记录排程应用操作，包含操作人、排程方案ID、炉号、时间等关键信息，便于追溯和审计
- ✅ **上下文信息保存**：支持保存排程算法的上下文信息（JSON格式），用于后续排程复盘和优化分析

---

### 使用前提

- ✅ 退火任务必须已创建且处于"待排程"（pending-schedule）或"草稿"（draft）状态
- ✅ 调用方必须拥有 `prod.annealing-task.schedule` 权限，通常为排程系统或具有排程管理权限的操作员
- ✅ 排程结果数据必须完整：包含排程方案ID、炉号编码、计划装炉时间、计划出炉时间
- ✅ 计划装炉时间必须早于计划出炉时间，符合生产工艺逻辑

### 不适用场景

- ❌ 不适用于已处于"装炉中"、"执行中"、"已完成"等后续状态的任务，这些任务已经不能再应用排程结果
- ❌ 不适用于"已取消"、"异常终止"状态的任务，因为这些任务已终止业务流程
- ❌ 不适用于手工修改排程信息的场景，手工修改应通过任务编辑接口完成

### 详细步骤说明

#### 步骤1: 接收排程结果数据
排程模块完成排程计算后，将排程结果通过HTTP POST请求发送到本接口，包含以下核心数据：
- `schedulePlanId`: 排程方案的唯一标识ID
- `plannedFurnaceCode`: 分配的退火炉编号（如 AF-01、AF-02）
- `plannedLoadingAt`: 计划装炉时间（ISO 8601格式）
- `plannedUnloadingAt`: 计划出炉时间（ISO 8601格式）
- 可选数据：炉ID、预计时长、预计能耗、排程上下文信息

#### 步骤2: 基础参数校验
使用Joi验证器对请求参数进行严格校验：
- **taskId**: 路径参数，必须是有效的UUID v4格式
- **schedulePlanId**: 必填，UUID v4格式，关联到排程方案
- **plannedFurnaceCode**: 必填，炉号编码，自动转大写
- **plannedLoadingAt**: 必填，ISO 8601日期时间格式
- **plannedUnloadingAt**: 必填，必须晚于plannedLoadingAt
- **expectedDurationMinutes**: 可选，整数，范围1-10080分钟（7天）
- **estimatedEnergyConsumption**: 可选，正数，精度6位小数
- **scheduleContext**: 可选，JSON对象
- **autoUpdateStatus**: 可选，布尔值，默认true
- **operatorId**: 从认证上下文获取，必须存在

校验失败时返回400错误，包含详细的错误字段和原因。

#### 步骤3: 时间合法性校验
在服务层进一步校验排程时间的业务逻辑合法性：
- 将 `plannedLoadingAt` 和 `plannedUnloadingAt` 转换为Date对象
- 检查 `plannedLoadingAt < plannedUnloadingAt`
- 如果校验失败，抛出400错误：`计划装炉时间必须早于计划出炉时间`
- 错误详情中包含两个时间值，便于排程系统调试

#### 步骤4: 开启数据库事务
使用Sequelize事务确保数据一致性：
```javascript
const transaction = await sequelize.transaction();
```
后续所有数据库操作都在此事务内执行，任何环节失败都会触发回滚。

#### 步骤5: 锁定任务记录
使用 `FOR UPDATE` 行锁防止并发冲突：
```javascript
const task = await AnnealingTask.findOne({
  where: { id: taskId },
  transaction,
  lock: transaction.LOCK.UPDATE,
});
```
这确保同一时间只有一个请求能够更新该任务的排程信息。

#### 步骤6: 任务存在性校验
检查查询结果：
- 如果 `task === null`，抛出404错误：`退火任务不存在`
- 错误详情包含 `taskId`，便于定位问题

#### 步骤7: 查询关联的计划批次
如果任务是由生产计划批次生成的（`task.planItemId` 存在），则查询关联的 `ProductionPlanItem`：
```javascript
if (task.planItemId) {
  task.planItem = await ProductionPlanItem.findOne({
    where: { id: task.planItemId },
    transaction,
  });
}
```
这是为后续的计划状态联动做准备。

#### 步骤8: 任务状态合法性校验
只有特定状态的任务允许应用排程结果：
- **允许状态**: `pending-schedule`（待排程）、`draft`（草稿）
- 如果任务状态不在允许范围内，抛出400错误
- 错误消息：`任务状态为 {currentStatus}，不允许应用排程结果`
- 错误详情包含当前状态和允许的状态列表

这样做的目的：
- 防止对已装炉、执行中、已完成的任务重复排程
- 防止对已取消、异常终止的任务进行排程
- 确保排程操作只在合适的业务阶段执行

#### 步骤9: 保存原排程数据
在更新前，先保存任务的原排程数据，用于操作日志的新旧值对比：
```javascript
const oldScheduleData = {
  schedulePlanId: task.schedulePlanId,
  plannedFurnaceId: task.plannedFurnaceId,
  plannedFurnaceCode: task.plannedFurnaceCode,
  plannedLoadingAt: task.plannedLoadingAt,
  plannedUnloadingAt: task.plannedUnloadingAt,
  expectedDurationMinutes: task.expectedDurationMinutes,
};
```

#### 步骤10: 更新任务排程信息
构建更新数据并执行更新：
```javascript
const updateData = {
  schedulePlanId,                                // 排程方案ID
  plannedFurnaceId: plannedFurnaceId || null,   // 炉ID（可选）
  plannedFurnaceCode: plannedFurnaceCode.trim().toUpperCase(), // 炉号（大写）
  plannedLoadingAt: new Date(plannedLoadingAt),  // 计划装炉时间
  plannedUnloadingAt: new Date(plannedUnloadingAt), // 计划出炉时间
  schedulePublishedAt: new Date(),               // 排程发布时间
  scheduleContext: scheduleContext || null,      // 排程上下文（JSON）
  updatedBy: operatorId,                         // 更新人
};

// 可选字段
if (expectedDurationMinutes) {
  updateData.expectedDurationMinutes = expectedDurationMinutes;
}
if (estimatedEnergyConsumption) {
  updateData.estimatedEnergyConsumption = estimatedEnergyConsumption;
}

await task.update(updateData, { transaction });
```

#### 步骤11: 自动更新任务状态
如果 `autoUpdateStatus === true`（默认）且任务当前状态不是"已排程"，则自动更新状态：
```javascript
if (autoUpdateStatus && task.status !== ANNEALING_TASK_STATUSES.SCHEDULED) {
  updateData.status = ANNEALING_TASK_STATUSES.SCHEDULED;
  updateData.schedulePublishedAt = new Date();
}
```

**状态转换逻辑**：
- `draft` → `scheduled`（草稿 → 已排程）
- `pending-schedule` → `scheduled`（待排程 → 已排程）

**autoUpdateStatus参数说明**：
- `true`（默认）: 自动更新状态，适用于正式排程发布场景
- `false`: 仅更新排程数据，不改变任务状态，适用于排程预演或测试场景

#### 步骤12: 记录排程应用日志
调用日志服务记录本次排程应用操作：
```javascript
await recordTaskLog({
  taskId,
  action: ANNEALING_TASK_LOG_ACTIONS.SCHEDULE_APPLIED, // 'schedule-applied'
  description: `应用排程方案 ${schedulePlanId}，分配炉号 ${plannedFurnaceCode}`,
  originalValue: oldScheduleData,  // 原排程数据
  newValue: {                      // 新排程数据
    schedulePlanId,
    plannedFurnaceCode,
    plannedLoadingAt: updateData.plannedLoadingAt,
    plannedUnloadingAt: updateData.plannedUnloadingAt,
    expectedDurationMinutes: updateData.expectedDurationMinutes,
    status: updateData.status,
  },
  referenceId: schedulePlanId,     // 关联的排程方案ID
  referenceCode: schedulePlanId,
  operatorId,
  operatorName,
  operatorIp,
  operationContext: {
    schedulePlanId,
    furnaceCode: plannedFurnaceCode,
    autoUpdateStatus,
  },
}, transaction);
```

日志记录包含：
- 操作动作类型（schedule-applied）
- 操作描述（排程方案ID、炉号）
- 新旧值对比（便于审计和回溯）
- 操作人信息（ID、姓名、IP地址）
- 操作上下文（排程方案ID、炉号、是否自动更新状态）

#### 步骤13: 联动更新计划批次状态
如果任务是从生产计划批次生成的，且 `autoUpdateStatus === true`，则同步更新计划批次的状态：
```javascript
if (autoUpdateStatus && task.planItemId && task.planItem) {
  await syncPlanItemStatus(
    task.planItem,
    ANNEALING_TASK_STATUSES.SCHEDULED,
    {
      transaction,
      operatorId,
    }
  );
}
```

**状态联动逻辑**：
- 当退火任务状态变为"已排程"时，关联的生产计划批次状态也应同步更新
- `syncPlanItemStatus` 会根据该批次下所有任务的状态，智能判断计划批次应该处于什么状态
- 例如：如果所有任务都已排程，则计划批次状态变为"已排程"

#### 步骤14: 提交事务
所有数据库操作成功完成后，提交事务：
```javascript
await transaction.commit();
```
此时数据正式落库，排程结果生效。

#### 步骤15: 记录成功日志
使用logger记录操作成功的信息日志：
```javascript
logger.info(
  `应用排程结果成功: 任务编号=${task.taskCode}, 排程方案ID=${schedulePlanId}, 炉号=${plannedFurnaceCode}, 操作人ID=${operatorId}`
);
```
这些日志用于：
- 运维监控和问题排查
- 业务数据分析和统计
- 审计和合规要求

#### 步骤16: 重新加载任务数据
为了确保返回的数据包含最新的关联信息，重新从数据库加载任务：
```javascript
await task.reload({
  include: [
    {
      model: ProductionPlanItem,
      as: 'planItem',
    },
  ],
});
```
这样返回的任务对象包含了最新的排程信息和关联的计划批次信息。

#### 步骤17: 返回更新后的任务对象
将任务对象转换为JSON并返回：
```javascript
return task.toJSON();
```
返回数据包含：
- 任务的所有基本信息
- 更新后的排程信息（炉号、计划时间等）
- 最新的任务状态
- 关联的计划批次信息（如有）

## 接口文档

### 基本信息

**接口路径**: `POST /v1/prod/annealing-tasks/:taskId/schedule`

**功能描述**: 接收排程模块回传的炉号、计划装炉/出炉时间等排程结果，并落库、更新任务状态、记录日志、联动计划状态

**认证要求**: JWT Bearer Token认证，需要 `prod.annealing-task.schedule` 权限

## 统一响应格式

### 成功响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
    // 具体的业务数据，根据接口而不同
  },
  "message": "操作成功的描述信息",
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### scheduleContext 对象结构（可选）

`scheduleContext` 字段用于保存排程算法的上下文信息，具体结构由排程系统定义，以下是常见的字段示例：

| 参数名              | 类型   | 必填 | 描述                         | 示例                     |
| ------------------- | ------ | ---- | ---------------------------- | ------------------------ |
| algorithm           | string | 否   | 使用的排程算法名称           | "genetic-algorithm-v2.0" |

### 场景3: 批量任务排程回写（循环调用）

**业务需求**: 排程系统完成一次排程计算后，需要将结果应用到多个任务

**Node.js 代码示例**:

```javascript
const axios = require('axios');

const scheduleResults = [
  {
    taskId: '123e4567-e89b-12d3-a456-426614174000',
    furnaceCode: 'AF-01',
    loadingAt: '2024-01-25T08:00:00.000Z',
    unloadingAt: '2024-01-26T10:00:00.000Z',
  },
  {
    taskId: '223e4567-e89b-12d3-a456-426614174001',
    furnaceCode: 'AF-02',
    loadingAt: '2024-01-25T08:00:00.000Z',
    unloadingAt: '2024-01-26T08:00:00.000Z',
  },
  {
    taskId: '323e4567-e89b-12d3-a456-426614174002',
    furnaceCode: 'AF-01',
    loadingAt: '2024-01-26T11:00:00.000Z',
    unloadingAt: '2024-01-27T13:00:00.000Z',
  },
];

const schedulePlanId = 'schedule-plan-batch-001';
const apiBaseUrl = 'http://localhost:3000/v1/prod/annealing-tasks';
const authToken = '<SCHEDULE_SYSTEM_TOKEN>';

async function applyScheduleResults() {
  const results = await Promise.all(
    scheduleResults.map(async (result) => {
      try {
        const response = await axios.post(
          `${apiBaseUrl}/${result.taskId}/schedule`,
          {
            schedulePlanId,
            plannedFurnaceCode: result.furnaceCode,
            plannedLoadingAt: result.loadingAt,
            plannedUnloadingAt: result.unloadingAt,
            expectedDurationMinutes: 1560,
            autoUpdateStatus: true,
          },
          {
            headers: {
              'Content-Type': 'application/json',
              'Authorization': `Bearer ${authToken}`,
            },
          }
        );
        return {
          taskId: result.taskId,
          success: true,
          data: response.data,
        };
      } catch (error) {
        return {
          taskId: result.taskId,
          success: false,
          error: error.response?.data || error.message,
        };
      }
    })
  );

  console.log('批量应用排程结果完成：');
  console.log(`- 成功: ${results.filter(r => r.success).length} 个任务`);
  console.log(`- 失败: ${results.filter(r => !r.success).length} 个任务`);

  // 输出失败的任务详情
  const failedTasks = results.filter(r => !r.success);
  if (failedTasks.length > 0) {
    console.log('失败任务详情：');
    failedTasks.forEach(task => {
      console.log(`- 任务ID: ${task.taskId}`);
      console.log(`  错误: ${task.error.error?.message || task.error}`);
    });
  }
}

applyScheduleResults();
```

**业务说明**:
- 使用 `Promise.all` 并行调用接口，提高批量处理效率
- 每个任务独立处理，单个任务失败不影响其他任务
- 记录成功和失败的任务数量，便于排程系统监控
- 对失败的任务记录详细错误信息，便于问题排查和重试

### 场景5: 错误处理和重试机制

**业务需求**: 排程系统在应用排程结果时遇到错误，需要根据错误类型进行重试或告警

**Node.js 代码示例**:

```javascript
const axios = require('axios');

async function applyScheduleWithRetry(taskId, scheduleData, maxRetries = 3) {
  const apiUrl = `http://localhost:3000/v1/prod/annealing-tasks/${taskId}/schedule`;
  const authToken = '<SCHEDULE_SYSTEM_TOKEN>';

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      const response = await axios.post(apiUrl, scheduleData, {
        headers: {
          'Content-Type': 'application/json',
          'Authorization': `Bearer ${authToken}`,
        },
      });

      console.log(`任务 ${taskId} 排程应用成功`);
      return { success: true, data: response.data };
    } catch (error) {
      const errorCode = error.response?.data?.error?.code;
      const errorMessage = error.response?.data?.error?.message;
      const httpStatus = error.response?.status;

      console.log(`任务 ${taskId} 排程应用失败（第${attempt}次尝试）: ${errorMessage}`);

      // 根据错误类型决定是否重试
      if (httpStatus === 404) {
        // 任务不存在，不重试
        console.error(`任务 ${taskId} 不存在，停止重试`);
        return { success: false, error: '任务不存在' };
      } else if (httpStatus === 400 && errorCode === 'INVALID_STATUS') {
        // 任务状态不允许，不重试
        console.error(`任务 ${taskId} 状态不允许应用排程结果，停止重试`);
        return { success: false, error: '任务状态不允许' };
      } else if (httpStatus === 401 || httpStatus === 403) {
        // 认证或权限问题，不重试
        console.error(`认证或权限问题，停止重试`);
        return { success: false, error: '认证或权限问题' };
      } else if (httpStatus === 500) {
        // 服务器错误，可以重试
        if (attempt < maxRetries) {
          const waitTime = attempt * 1000; // 递增等待时间
          console.log(`服务器错误，等待 ${waitTime}ms 后重试...`);
          await new Promise(resolve => setTimeout(resolve, waitTime));
          continue;
        } else {
          console.error(`任务 ${taskId} 重试${maxRetries}次后仍失败`);
          return { success: false, error: '服务器错误，重试失败' };
        }
      } else {
        // 其他错误，不重试
        console.error(`未知错误: ${errorMessage}`);
        return { success: false, error: errorMessage };
      }
    }
  }
}

// 使用示例
const taskId = '123e4567-e89b-12d3-a456-426614174000';
const scheduleData = {
  schedulePlanId: 'schedule-plan-001',
  plannedFurnaceCode: 'AF-01',
  plannedLoadingAt: '2024-01-25T08:00:00.000Z',
  plannedUnloadingAt: '2024-01-26T10:00:00.000Z',
  autoUpdateStatus: true,
};

applyScheduleWithRetry(taskId, scheduleData)
  .then(result => {
    if (result.success) {
      console.log('排程应用成功');
    } else {
      console.error('排程应用失败:', result.error);
      // 发送告警通知
    }
  });
```

**业务说明**:
- 对 500 服务器错误进行重试，最多重试3次
- 对 404、400（状态不允许）、401、403 等错误不重试，因为重试无意义
- 使用递增等待时间（1秒、2秒、3秒）避免频繁重试加重服务器负担
- 记录详细的错误日志，便于问题排查
- 重试失败后可触发告警通知，人工介入处理

### 相关接口

- **获取待排程任务列表**: `GET /v1/prod/annealing-tasks/scheduling/pending`
  - 排程系统在计算排程方案前，调用此接口获取需要排程的任务列表

- **锁定任务用于排程**: `POST /v1/prod/annealing-tasks/scheduling/lock`
  - 排程系统在开始计算前，锁定任务避免重复排程

- **释放任务排程锁定**: `POST /v1/prod/annealing-tasks/scheduling/unlock`
  - 排程系统在计算失败或取消时，释放任务锁定

- **获取退火任务详情**: `GET /v1/prod/annealing-tasks/:taskId`
  - 查看任务的完整信息，包含排程数据

- **更新退火任务状态**: `PATCH /v1/prod/annealing-tasks/:taskId/status`
  - 手工更新任务状态（如需要手动修改排程状态）

### 数据库事务说明

本接口使用数据库事务确保以下操作的原子性：

1. 任务记录更新（排程信息、状态）
2. 操作日志记录
3. 计划批次状态联动（如适用）

如果任何一个操作失败，整个事务回滚，数据库保持一致性。

### 性能优化建议

1. **批量处理**：排程系统应批量调用本接口，使用并发控制（如 Promise.all）提高处理效率
2. **错误重试**：对 500 错误进行有限次数的重试，避免临时性故障导致排程失败
3. **异步回写**：排程系统可将排程结果先保存到本地缓存，再异步批量回写
4. **监控告警**：对回写失败率、响应时间等指标进行监控，及时发现问题

### 安全性说明

1. **权限控制**：只有具有 `prod.annealing-task.schedule` 权限的用户或系统账号才能调用本接口
2. **状态校验**：严格校验任务状态，防止误操作覆盖已执行的排程结果
3. **数据完整性**：使用行锁防止并发冲突，使用事务确保数据一致性
4. **操作追溯**：记录详细的操作日志，包含操作人、IP、时间等信息，满足审计要求
