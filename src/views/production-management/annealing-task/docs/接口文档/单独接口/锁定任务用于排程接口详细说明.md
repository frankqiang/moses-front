## 功能概述

### 所有功能

锁定任务用于排程（Lock Tasks for Scheduling）是退火任务管理模块中的排程管理核心操作之一，用于为排程算法提供任务锁定机制。在生成排程方案时，通过锁定任务可以避免同一批任务被多个排程方案重复选取，确保排程算法在执行期间任务状态的稳定性。该接口支持批量锁定（最多100个任务），并可自定义锁定时长（默认30分钟），锁定失败的任务会在响应中单独列出并说明失败原因。

### 关键特性

- ✅ **批量锁定**：支持一次性锁定多个任务，最多支持100个任务同时锁定，满足大批量排程需求
- ✅ **灵活时长**：支持自定义锁定时长（1-1440分钟），默认30分钟，适应不同排程算法的执行时间
- ✅ **状态校验**：自动检查任务状态，只有"草稿"或"待排程"状态的任务才能被锁定
- ✅ **重复锁定保护**：自动检测已锁定的任务，避免重复锁定导致的冲突，并在响应中明确说明
- ✅ **部分成功处理**：锁定失败的任务会单独列出（包含失败原因、任务编号、当前锁定状态等），不影响其他任务的锁定
- ✅ **事务保证**：使用数据库事务确保批量操作的原子性，防止数据不一致
- ✅ **操作审计**：完整记录锁定操作的日志，包括锁定时长、排程方案ID、操作人等信息
- ✅ **并发安全**：使用行级锁（UPDATE LOCK）确保高并发场景下的数据一致性
- ✅ **方案关联**：支持关联排程方案ID，便于追溯任务被哪个排程方案锁定

---

### 使用前提

- ✅ 用户必须具有 `prod.annealing-task.schedule` 权限（排程管理权限）
- ✅ 提供的任务ID必须为有效的UUID v4格式
- ✅ 任务ID列表不能为空，至少包含1个任务ID
- ✅ 任务ID列表不能超过100个，避免单次操作过多影响性能
- ✅ 任务必须处于"草稿"或"待排程"状态才能被锁定
- ✅ 任务不能已经被其他排程锁定（除非锁定已过期）

### 不适用场景

- ❌ 不适用于已处于"已排程"、"执行中"、"已完成"等状态的任务（这些任务无需再次排程）
- ❌ 不适用于已被其他排程方案锁定且锁定时间未过期的任务（会返回锁定失败）
- ❌ 不适用于已取消或已终止的任务（终态任务不能参与排程）
- ❌ 不适用于需要长时间锁定（超过24小时）的场景（最大锁定时长限制为1440分钟）

### 详细步骤说明

#### 步骤1: 接收锁定请求

接收前端提交的锁定请求参数：

**输入参数**：
- `taskIds`: 需要锁定的任务ID数组
- `lockDurationMinutes`: 锁定时长（分钟），可选，默认30分钟
- `schedulePlanId`: 排程方案ID，可选，用于关联排程方案

**请求来源**：
- 排程算法开始执行前
- 排程方案生成过程中
- 手动触发排程时

#### 步骤2: 参数校验

在 Validation 层使用 Joi 验证器进行参数格式校验：

**taskIds 校验规则**：
- 必须为数组类型
- 数组至少包含1个元素
- 数组最多包含100个元素
- 数组元素必须唯一（不能重复）
- 每个元素必须为有效的UUID v4格式

**lockDurationMinutes 校验规则**：
- 必须为整数类型
- 最小值：1分钟
- 最大值：1440分钟（24小时）
- 可选参数，不提供时使用默认值30分钟

**schedulePlanId 校验规则**：
- 必须为有效的UUID v4格式
- 可选参数

**校验失败响应**：
- HTTP 400 Bad Request
- 错误码：`PARAM_ERROR`
- 错误信息：具体的验证失败原因（如"任务ID列表至少包含一条记录"）

#### 步骤3: 业务参数校验

在 Service 层进行业务逻辑相关的参数校验：

**operatorId 校验**：
- 操作人ID不能为空
- 如果为空，抛出 HTTP 400 错误："操作人ID不能为空"

**校验失败处理**：
- 抛出 `ApiError.badRequest` 异常
- 错误码：`PARAM_ERROR`
- 事务不会开启，直接返回错误

#### 步骤4: 权限校验

通过认证中间件校验用户是否具有排程管理权限：

**权限要求**：
- 权限代码：`prod.annealing-task.schedule`
- 权限名称：退火任务排程权限
- 权限说明：允许锁定/释放任务、应用排程结果

**校验失败响应**：
- HTTP 403 Forbidden
- 错误码：`FORBIDDEN`
- 错误信息：无权限执行此操作

**校验实现**：
- 在路由层通过 `auth('prod.annealing-task.schedule')` 中间件校验
- 中间件会自动检查当前用户的权限列表
- 如果权限不足，请求不会到达 Controller 层

#### 步骤5: 开启数据库事务

使用 Sequelize 的事务机制确保批量操作的原子性：

```javascript
const transaction = await sequelize.transaction();
```

**事务隔离级别**：默认（READ COMMITTED）

**作用**：
- 确保所有任务的锁定操作要么全部成功，要么全部回滚
- 防止部分任务锁定成功、部分失败导致的数据不一致
- 提供并发控制，防止多个排程同时锁定同一任务

**错误处理**：
- 如果任何步骤发生错误，事务会自动回滚
- 回滚后所有数据库修改都会被撤销

#### 步骤6: 计算锁定截止时间

根据指定的锁定时长计算锁定截止时间：

```javascript
const lockUntilTime = new Date(Date.now() + lockDurationMinutes * 60 * 1000);
```

**计算逻辑**：
- 当前时间 + 锁定时长（分钟）
- 结果为 ISO 8601 格式的时间戳

**示例**：
- 当前时间：2024-01-20T10:00:00.000Z
- 锁定时长：30分钟
- 锁定截止时间：2024-01-20T10:30:00.000Z

**用途**：
- 设置任务的 `scheduleLockedUntil` 字段
- 在响应中返回给前端
- 用于后续的锁定状态检查

#### 步骤7: 逐个处理任务

使用 `reduce` 方法顺序处理每个任务ID，确保操作的顺序性：

```javascript
const result = await taskIds.reduce(async (previousPromise, taskId) => {
  const acc = await previousPromise;
  // 处理单个任务...
  return acc;
}, Promise.resolve({ lockedTaskIds: [], failedTasks: [] }));
```

**为什么使用 reduce**：
- 确保任务按顺序逐个处理，避免并发竞争
- 符合 ESLint 规范（no-await-in-loop）
- 便于错误处理和结果收集

**累加器结构**：
- `lockedTaskIds`: 成功锁定的任务ID数组
- `failedTasks`: 锁定失败的任务信息数组

#### 步骤8: 查询任务并加行级锁

使用行级锁查询任务，确保并发安全：

```javascript
const task = await AnnealingTask.findOne({
  where: { id: taskId },
  transaction,
  lock: transaction.LOCK.UPDATE,
});
```

**锁定类型**：
- `transaction.LOCK.UPDATE`: 排他锁（X锁）
- 等价于 SQL 的 `SELECT ... FOR UPDATE`

**作用**：
- 阻止其他事务同时修改该任务
- 确保任务状态在事务期间保持一致
- 防止多个排程同时锁定同一任务

**查询失败处理**：
- 如果任务不存在（`task === null`）
- 添加到失败列表：`{ taskId, taskCode: null, reason: '任务不存在' }`
- 继续处理下一个任务（不中断整个流程）

#### 步骤9: 检查任务是否已被锁定

检查任务的 `scheduleLockedUntil` 字段：

```javascript
if (task.scheduleLockedUntil && task.scheduleLockedUntil > new Date()) {
  // 任务已被锁定且锁定未过期
}
```

**检查逻辑**：
- `scheduleLockedUntil` 不为空
- 且锁定截止时间大于当前时间

**检查失败处理**：
- 添加到失败列表：
  ```javascript
  {
    taskId,
    taskCode: task.taskCode,
    reason: '任务已被锁定',
    lockedUntil: task.scheduleLockedUntil
  }
  ```
- 继续处理下一个任务

**业务意义**：
- 防止同一任务被多个排程方案重复锁定
- 保护正在进行的排程操作不被打断
- 前端可根据 `lockedUntil` 时间判断何时可以重试

#### 步骤10: 检查任务状态

检查任务是否处于允许锁定的状态：

```javascript
const allowedStatuses = [
  ANNEALING_TASK_STATUSES.PENDING_SCHEDULE,  // 'pending-schedule'
  ANNEALING_TASK_STATUSES.DRAFT              // 'draft'
];
if (!allowedStatuses.includes(task.status)) {
  // 状态不允许锁定
}
```

**允许锁定的状态**：
- `draft`（草稿）：新创建的任务，尚未提交排程
- `pending-schedule`（待排程）：已提交但尚未排程的任务

**不允许锁定的状态**：
- `scheduled`（已排程）：已经完成排程的任务
- `in-progress`（执行中）：正在执行的任务
- `completed`（已完成）：已完成的任务
- `cancelled`（已取消）：已取消的任务
- 其他所有状态

**检查失败处理**：
- 添加到失败列表：
  ```javascript
  {
    taskId,
    taskCode: task.taskCode,
    reason: `任务状态为 ${task.status}，不允许锁定`,
    currentStatus: task.status
  }
  ```
- 继续处理下一个任务

#### 步骤11: 更新任务锁定状态

通过所有检查后，更新任务的锁定信息：

```javascript
await task.update(
  {
    scheduleLockedUntil: lockUntilTime,
    updatedBy: operatorId,
  },
  { transaction }
);
```

**更新字段**：
- `scheduleLockedUntil`: 设置为计算好的锁定截止时间
- `updatedBy`: 记录操作人ID

**事务控制**：
- 更新操作在事务中执行
- 如果后续步骤失败，更新会被回滚

**数据库约束**：
- `scheduleLockedUntil` 字段类型：TIMESTAMP
- 允许为 NULL（未锁定状态）

#### 步骤12: 记录操作日志

记录任务锁定的详细日志：

```javascript
await recordTaskLog(
  {
    taskId,
    action: ANNEALING_TASK_LOG_ACTIONS.SYNCED,
    description: `任务已锁定用于排程，锁定至 ${lockUntilTime.toISOString()}`,
    newValue: {
      scheduleLockedUntil: lockUntilTime,
      schedulePlanId: schedulePlanId || null,
    },
    operatorId,
    operatorName,
    operatorIp,
    operationContext: {
      action: 'lock',
      lockDurationMinutes,
      schedulePlanId: schedulePlanId || null,
    },
  },
  transaction
);
```

**日志字段说明**：
- `action`: 操作类型（SYNCED - 同步操作）
- `description`: 操作描述，包含锁定截止时间
- `newValue`: 新值（锁定截止时间、排程方案ID）
- `operationContext`: 操作上下文（锁定时长、排程方案ID等）

**日志用途**：
- 审计追踪：记录谁在什么时间锁定了任务
- 问题排查：锁定冲突时可查看日志定位原因
- 数据恢复：必要时可根据日志恢复数据

#### 步骤13: 添加到成功列表

将成功锁定的任务ID添加到结果列表：

```javascript
acc.lockedTaskIds.push(taskId);
return acc;
```

**累加器更新**：
- `lockedTaskIds` 数组增加一个元素
- 继续处理下一个任务

#### 步骤14: 提交事务

所有任务处理完成后，提交事务：

```javascript
await transaction.commit();
```

**提交时机**：
- 所有任务都处理完成（无论成功还是失败）
- 没有发生系统异常

**提交效果**：
- 所有成功锁定的任务的数据库更改生效
- 所有操作日志记录生效
- 事务释放，其他事务可以访问这些任务

**异常处理**：
- 如果在处理过程中发生异常（非业务逻辑失败）
- 事务会在 catch 块中回滚
- 所有数据库修改都会被撤销

#### 步骤15: 记录操作日志（应用层）

记录整体操作的日志信息：

```javascript
logger.info(`锁定任务用于排程: 成功=${lockedTaskIds.length}, 失败=${failedTasks.length}, 操作人ID=${operatorId}`);
```

**日志内容**：
- 成功锁定的任务数量
- 失败的任务数量
- 操作人ID

**日志级别**：INFO

**日志用途**：
- 监控锁定操作的成功率
- 追踪系统使用情况
- 性能分析和优化

#### 步骤16: 返回成功结果

组装响应数据并返回：

```javascript
return {
  lockedCount: lockedTaskIds.length,
  lockedTaskIds,
  failedTasks,
  lockUntilTime,
};
```

**响应字段**：
- `lockedCount`: 成功锁定的任务数量
- `lockedTaskIds`: 成功锁定的任务ID数组
- `failedTasks`: 失败任务的详细信息数组
- `lockUntilTime`: 锁定截止时间（所有成功锁定的任务使用相同的截止时间）

**Controller 层封装**：
- Service 返回数据后，Controller 使用 `sendSuccess` 包装
- 添加统一的响应格式（success、data、message、meta）

## 接口文档

### 基本信息

**接口路径**: `POST /v1/prod/annealing-tasks/scheduling/lock`

**功能描述**: 为排程算法提供任务锁定机制，避免重复排程。锁定后的任务在锁定时间内不会被其他排程方案重复选取，支持批量锁定（最多100个任务），锁定时长默认30分钟。锁定失败的任务会在响应中单独列出，包含失败原因。

**认证要求**: JWT Bearer Token 认证，需要 `prod.annealing-task.schedule` 权限

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 请求参数

| 参数名              | 类型   | 必填 | 限制                                | 描述                                     | 示例                                     |
| ------------------- | ------ | ---- | ----------------------------------- | ---------------------------------------- | ---------------------------------------- |
| taskIds             | array  | 是   | UUID数组，1-100项，唯一，每项为UUID | 需要锁定的任务ID列表                     | ["554e4422-beac-48bd-a22b-43b38a3c212b"] |
| lockDurationMinutes | number | 否   | 整数，1-1440                        | 锁定时长（分钟），默认30分钟，最长24小时 | 30                                       |
| schedulePlanId      | string | 否   | UUID格式                            | 排程方案ID，用于关联锁定任务的排程方案   | "664e4422-beac-48bd-a22b-43b38a3c212b"   |

**参数详细说明**：

- **taskIds**：
  - 必须为有效的UUID v4格式数组
  - 数组不能为空，至少包含1个任务ID
  - 数组最多包含100个任务ID（限制批量操作规模）
  - 数组中的UUID必须唯一，不能重复
  - 示例：`["554e4422-beac-48bd-a22b-43b38a3c212b", "664e4422-beac-48bd-a22b-43b38a3c212b"]`

- **lockDurationMinutes**：
  - 可选参数，不提供时使用默认值30分钟
  - 必须为正整数
  - 最小值：1分钟
  - 最大值：1440分钟（24小时）
  - 建议根据排程算法的预计执行时间设置合理的锁定时长
  - 过短可能导致排程未完成任务就被释放，过长可能影响其他排程

- **schedulePlanId**：
  - 可选参数，用于追踪任务被哪个排程方案锁定
  - 必须为有效的UUID v4格式
  - 记录在操作日志中，便于问题排查
  - 释放锁定时无需提供此参数

## 使用示例

### 场景1: 排程算法开始前锁定任务

**业务需求**: 排程算法在开始计算前，需要锁定一批待排程的任务，避免其他排程同时处理这些任务。
**业务处理**：
1. 前端从待排程任务列表中选择需要排程的任务
2. 调用锁定接口，锁定时长设置为预计排程算法执行时间的1.5-2倍
3. 提供排程方案ID，便于追踪和问题排查
4. 检查响应，确认所有任务都成功锁定（`failedTasks` 为空）
5. 开始执行排程算法
6. 排程完成后应用排程结果或释放锁定

### 场景2: 处理部分锁定失败的情况

**业务需求**: 锁定一批任务，但其中部分任务已被其他排程锁定或状态不符合要求。
**业务处理**：
1. 检查响应中的 `lockedCount` 和 `failedTasks`
2. 如果有失败任务，根据 `reason` 字段判断失败原因：
   - **"任务已被锁定"**：
     - 查看 `lockedUntil` 时间，判断何时可以重试
     - 或者从排程列表中排除这些任务
   - **"任务状态为 XX，不允许锁定"**：
     - 查看 `currentStatus` 字段
     - 从排程列表中移除这些任务（已排程或已完成的任务不需要再次排程）
   - **"任务不存在"**：
     - 任务可能已被删除
     - 从排程列表中移除这些任务
3. 决定是否继续排程：
   - 如果成功锁定的任务足够，继续执行排程
   - 如果失败任务过多，可能需要取消排程或重新选择任务
4. 对于成功锁定的任务（`lockedTaskIds`），执行排程算法

### 场景3: 快速排程使用较短锁定时长

**业务需求**: 对于简单的排程场景，预计排程算法在10分钟内完成，使用较短的锁定时长。

**业务处理**：
1. 对于预计执行时间较短的排程，使用较短的锁定时长（如15分钟）
2. 锁定成功后立即开始排程算法
3. 确保在锁定时间内完成排程并应用结果
4. 如果排程超时，任务锁定会自动过期，其他排程可以重新锁定这些任务

**优势**：
- 减少任务被锁定的时间，提高系统的排程效率
- 降低因排程异常中断导致任务长时间锁定的风险

### 场景4: 处理权限不足错误

**业务需求**: 用户尝试锁定任务，但没有排程管理权限。

**前端处理建议**：
1. 检查 `error.code === 'FORBIDDEN'`
2. 显示友好的错误提示："您没有排程管理权限，请联系管理员"
3. 引导用户：
   - 联系系统管理员分配 `prod.annealing-task.schedule` 权限
   - 或者使用其他有权限的账号进行排程操作
4. 在界面上隐藏或禁用排程相关的操作按钮，避免重复触发错误

## 常见问题

### Q1: 锁定任务后，锁定会在什么情况下自动解除？

**A1**: 锁定会在以下情况下自动解除：

1. **锁定时间到期**：
   - 任务的 `scheduleLockedUntil` 字段记录了锁定截止时间
   - 当当前时间超过锁定截止时间后，任务锁定自动失效
   - 系统在检查任务时会自动判断锁定是否过期

2. **手动释放锁定**：
   - 调用释放锁定接口 `POST /v1/prod/annealing-tasks/scheduling/unlock`
   - 明确将任务的 `scheduleLockedUntil` 设置为 NULL

3. **应用排程结果**：
   - 调用应用排程结果接口
   - 任务状态变更为"已排程"或其他状态后，锁定自动清除

**注意**：锁定不会因为系统重启或服务中断而被清除，锁定信息持久化在数据库中。

### Q2: 如果锁定时间不够用，排程还没完成怎么办?

**A2**: 处理方案：

1. **预防措施**：
   - 根据排程算法的预计执行时间，设置合理的锁定时长
   - 建议设置为预计时间的1.5-2倍，留有充足余量
   - 如果排程复杂度高、任务数量多，可以设置更长的锁定时长（最长1440分钟）

2. **锁定过期后的处理**：
   - 如果锁定时间到期，任务可以被其他排程重新锁定
   - 原排程继续执行时，应用排程结果可能会失败（因为任务可能已被其他排程锁定）
   - 系统会返回明确的错误信息，提示任务状态已变更

3. **延长锁定时间**：
   - 目前接口不支持延长已锁定任务的锁定时间
   - 如果需要此功能，可以联系技术团队评估实现

4. **最佳实践**：
   - 监控排程算法的实际执行时间
   - 根据历史数据调整锁定时长
   - 对于长时间运行的排程，考虑分批处理任务

### Q3: 如果锁定了部分任务后，排程算法失败了，需要手动释放锁定吗？

**A3**: 处理建议：

1. **自动过期机制**：
   - 如果不手动释放，锁定会在锁定时间到期后自动失效
   - 默认30分钟后任务可以被重新锁定

2. **建议手动释放**：
   - **推荐做法**：排程失败后立即调用释放锁定接口
   - 这样可以让任务立即可用于其他排程，不需要等待锁定过期
   - 提高系统的排程效率和响应速度

3. **实现方式**：
   ```javascript
   try {
     // 1. 锁定任务
     const lockResult = await lockTasks(taskIds);

     // 2. 执行排程算法
     const scheduleResult = await executeScheduling(lockResult.lockedTaskIds);

     // 3. 应用排程结果
     await applyScheduleResult(scheduleResult);
   } catch (error) {
     // 4. 排程失败，释放锁定
     await unlockTasks(taskIds);
     throw error;
   }
   ```

4. **幂等性保证**：
   - 释放锁定接口是幂等的
   - 重复调用不会产生副作用
   - 即使任务锁定已过期，调用释放接口也不会报错

### Q4: 可以锁定已经被其他排程锁定的任务吗？

**A4**: 不可以，具体说明：

1. **锁定冲突检查**：
   - 接口会检查任务的 `scheduleLockedUntil` 字段
   - 如果锁定时间大于当前时间，说明任务已被锁定
   - 此时会锁定失败，并在响应的 `failedTasks` 中说明

2. **失败响应示例**：
   ```json
   {
     "failedTasks": [
       {
         "taskId": "664e4422-beac-48bd-a22b-43b38a3c212b",
         "taskCode": "AT-20240120-102030456-789",
         "reason": "任务已被锁定",
         "lockedUntil": "2024-01-20T11:00:00.000Z"
       }
     ]
   }
   ```

3. **处理建议**：
   - 检查 `lockedUntil` 时间，判断锁定何时过期
   - 可以选择：
     - 等待锁定过期后重试
     - 从排程列表中排除这些任务
     - 选择其他未锁定的任务进行排程

4. **锁定过期后**：
   - 锁定时间到期后，任务可以被重新锁定
   - 不需要先调用释放接口，可以直接锁定

### Q5: 为什么有些任务锁定失败，原因是"任务状态不允许锁定"？

**A5**: 状态限制说明：

1. **允许锁定的状态**：
   - `draft`（草稿）：新创建的任务
   - `pending-schedule`（待排程）：已提交但尚未排程的任务

2. **不允许锁定的状态及原因**：
   - `scheduled`（已排程）：任务已经完成排程，无需再次排程
   - `in-progress`（执行中）：任务正在生产执行，不能修改排程
   - `completed`（已完成）：任务已完成，不能再排程
   - `cancelled`（已取消）：任务已取消，不应再参与排程
   - `terminated`（已终止）：任务已终止，不能再使用
   - 其他所有非草稿/待排程状态

3. **业务逻辑**：
   - 只有尚未排程的任务才需要锁定
   - 已经进入执行流程的任务，不应该再被排程算法处理

4. **前端处理建议**：
   - 从待排程列表中排除状态不符的任务
   - 刷新任务列表，获取最新的任务状态
   - 只选择"草稿"或"待排程"状态的任务进行排程

### Q6: 一次最多可以锁定多少个任务？

**A6**: 限制说明：

1. **数量限制**：
   - 单次请求最多锁定 **100个任务**
   - 最少锁定 **1个任务**

2. **限制原因**：
   - 防止单次操作时间过长，影响系统性能
   - 避免长时间占用数据库事务
   - 保证接口响应速度

3. **超过限制的处理**：
   - 如果 `taskIds` 数组包含超过100个元素
   - 接口会返回 HTTP 400 错误
   - 错误消息："单次锁定任务数量不能超过100条"

4. **批量处理建议**：
   - 如果需要锁定超过100个任务，分批调用接口
   - 示例：
     ```javascript
     const allTaskIds = [...]; // 150个任务ID
     const batchSize = 100;

     for (let i = 0; i < allTaskIds.length; i += batchSize) {
       const batch = allTaskIds.slice(i, i + batchSize);
       await lockTasks(batch);
     }
     ```

### Q7: 锁定时长最长可以设置多久？

**A7**: 时长限制：

1. **最小值**：1分钟
2. **最大值**：1440分钟（24小时）
3. **默认值**：30分钟（不提供 `lockDurationMinutes` 参数时）

4. **限制原因**：
   - 防止任务被长时间锁定，影响其他排程
   - 保证系统的排程效率
   - 避免因排程异常导致任务长期无法使用

5. **超过限制的处理**：
   - 如果 `lockDurationMinutes > 1440`，返回 HTTP 400 错误
   - 错误消息："锁定时长不能超过1天（1440分钟）"

6. **时长选择建议**：
   - **快速排程**（10分钟内）：设置15-20分钟
   - **常规排程**（30分钟内）：设置30-60分钟
   - **复杂排程**（1小时以上）：设置120-240分钟
   - **极复杂排程**：最多设置1440分钟，但建议优化算法或分批处理

### Q8: 锁定操作是否支持回滚？如果部分任务锁定失败会怎样？

**A8**: 事务处理说明：

1. **事务机制**：
   - 接口使用数据库事务确保操作的原子性
   - 所有任务的锁定操作在同一个事务中执行

2. **部分失败处理**：
   - **业务逻辑失败**（如任务不存在、已锁定、状态不符）：
     - 这些失败不会导致事务回滚
     - 成功锁定的任务会被提交
     - 失败的任务会在响应中的 `failedTasks` 数组中列出
   - **系统异常**（如数据库连接失败、程序错误）：
     - 整个事务会回滚
     - 所有任务都不会被锁定（包括之前成功的）
     - 返回 HTTP 500 错误

3. **部分成功响应**：
   ```json
   {
     "success": true,
     "data": {
       "lockedCount": 2,
       "lockedTaskIds": ["task1", "task2"],
       "failedTasks": [
         { "taskId": "task3", "reason": "任务已被锁定" }
       ]
     }
   }
   ```
   - 注意：即使有失败任务，`success` 仍为 `true`
   - 需要检查 `failedTasks` 数组判断是否有失败

4. **业务处理建议**：
   - 总是检查响应中的 `lockedCount` 和 `failedTasks`
   - 根据成功锁定的任务数量决定是否继续排程
   - 对失败的任务进行相应的处理（如重试、排除等）

### Q9: 如何追踪任务被哪个排程方案锁定？

**A9**: 追踪机制：

1. **schedulePlanId 参数**：
   - 锁定任务时可以提供 `schedulePlanId` 参数
   - 这个ID会记录在操作日志中

2. **日志记录**：
   - 每次锁定操作都会记录详细日志
   - 日志包含：
     - 锁定时间
     - 锁定截止时间
     - 排程方案ID（如果提供）
     - 操作人信息

3. **查询日志**：
   ```javascript
   // 示例：查询任务的锁定日志
   SELECT * FROM annealing_task_logs
   WHERE task_id = '任务ID'
     AND action = 'synced'
     AND operation_context->>'action' = 'lock'
   ORDER BY created_at DESC;
   ```

4. **使用建议**：
   - 始终在锁定时提供 `schedulePlanId`
   - 便于追踪和问题排查
   - 有助于分析排程方案的执行情况
