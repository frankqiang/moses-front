## 功能概述

### 所有功能

释放任务排程锁定（Unlock Tasks for Scheduling）是退火任务管理模块中的排程管理操作之一，用于释放已被锁定的待排程任务，使其可以再次参与排程。该接口主要应用于排程取消、排程失败或排程异常中断等场景，确保任务不会因锁定而无法重新排程。

### 关键特性

- ✅ **批量释放**：支持一次性释放多个任务的锁定状态，最多支持100个任务同时释放
- ✅ **容错处理**：不存在的任务ID会被自动忽略，不影响其他有效任务的释放操作
- ✅ **事务保证**：使用数据库事务确保批量操作的原子性，要么全部成功，要么全部回滚
- ✅ **操作审计**：完整记录释放操作的日志，包括操作人、操作时间、原值和新值
- ✅ **并发安全**：使用行级锁（UPDATE LOCK）确保并发场景下的数据一致性
- ✅ **幂等性**：重复释放同一任务不会产生副作用，可安全重试

---

### 使用前提

- ✅ 用户必须具有 `prod.annealing-task.schedule` 权限
- ✅ 提供的任务ID必须为有效的UUID v4格式
- ✅ 任务ID列表不能为空，至少包含1个任务ID
- ✅ 任务ID列表不能超过100个，避免单次操作过多

### 不适用场景

- ❌ 不适用于释放未锁定的任务（已经是释放状态的任务会被忽略，但不会报错）
- ❌ 不适用于正在执行中的任务（执行中的任务不应该被释放排程锁定）
- ❌ 不适用于已完成或已取消的任务（终态任务不需要释放锁定）

### 详细步骤说明

#### 步骤1: 接收请求参数

接收前端提交的任务ID列表（taskIds），该列表包含需要释放锁定的所有任务的UUID。

**输入**：
- `taskIds`: 任务ID数组

#### 步骤2: 参数校验

在 Validation 层使用 Joi 验证器进行参数格式校验：

**校验规则**：
- `taskIds` 必须为数组类型
- 数组至少包含1个元素
- 数组最多包含100个元素
- 数组元素必须唯一（不能重复）
- 每个元素必须为有效的UUID v4格式

**校验失败响应**：
- HTTP 400 Bad Request
- 错误码：`PARAM_ERROR`
- 错误信息：具体的验证失败原因

#### 步骤3: 权限校验

通过认证中间件校验用户是否具有排程管理权限：

**权限要求**：
- 权限代码：`prod.annealing-task.schedule`
- 权限名称：排程管理权限

**校验失败响应**：
- HTTP 403 Forbidden
- 错误码：`FORBIDDEN`
- 错误信息：无权限执行此操作

#### 步骤4: 开启数据库事务

使用 Sequelize 的事务机制确保批量操作的原子性：

```javascript
const transaction = await sequelize.transaction();
```

**事务隔离级别**：默认（READ COMMITTED）

**作用**：
- 确保所有任务的释放操作要么全部成功，要么全部回滚
- 防止部分任务释放成功、部分失败导致的数据不一致

#### 步骤5: 逐个处理任务

使用 `reduce` 方法按顺序处理每个任务ID，确保操作的有序性：

**处理逻辑**：
```javascript
const unlockedTaskIds = await taskIds.reduce(async (previousPromise, taskId) => {
  const acc = await previousPromise;
  // 处理单个任务...
  return [...acc, taskId];
}, Promise.resolve([]));
```

**为什么使用顺序执行**：
- 避免并发更新导致的死锁问题
- 确保日志记录的顺序性
- 便于问题追踪和调试

#### 步骤6: 查询任务并加锁

对每个任务ID执行带锁查询：

**查询条件**：
- `where: { id: taskId }` - 按任务ID查询
- `transaction` - 使用当前事务
- `lock: transaction.LOCK.UPDATE` - 行级更新锁

**加锁目的**：
- 防止其他并发操作同时修改该任务
- 确保读取到的数据在事务内不会被其他事务修改

#### 步骤7: 任务存在性判断

判断任务是否存在于数据库中：

**存在判断**：
```javascript
if (!task) {
  return acc; // 任务不存在，忽略该任务，继续处理下一个
}
```

**容错设计**：
- 不存在的任务会被静默忽略
- 不会抛出错误，不影响其他任务的处理
- 最终返回结果中只包含实际释放成功的任务ID

#### 步骤8: 更新任务锁定状态

释放任务的排程锁定：

**更新字段**：
- `scheduleLockedUntil`: 设置为 `null`（表示未锁定）
- `updatedBy`: 设置为当前操作人的用户ID

**更新操作**：
```javascript
await task.update(
  {
    scheduleLockedUntil: null,
    updatedBy: operatorId,
  },
  { transaction }
);
```

**字段说明**：
- `scheduleLockedUntil`：排程锁定截止时间，`null` 表示未锁定
- `updatedBy`：记录最后更新该任务的操作人

#### 步骤9: 记录操作日志

将释放操作记录到任务日志表（`annealing_task_logs`）：

**日志信息**：
- `taskId`：任务ID
- `action`：操作类型（SYNCED - 同步/更新操作）
- `description`：操作描述（"任务排程锁定已释放"）
- `originalValue`：原始值（包含原 scheduleLockedUntil 值）
- `newValue`：新值（scheduleLockedUntil 为 null）
- `operatorId`：操作人用户ID
- `operatorName`：操作人姓名
- `operatorIp`：操作人IP地址
- `operationContext`：操作上下文（包含 action: 'unlock'）

**日志作用**：
- 操作审计和追溯
- 问题排查和数据恢复
- 合规性要求

#### 步骤10: 添加到已释放列表

将成功释放的任务ID添加到结果数组：

```javascript
return [...acc, taskId];
```

#### 步骤11: 提交事务

所有任务处理完成后，提交数据库事务：

```javascript
await transaction.commit();
```

**提交时机**：
- 所有任务都处理完成（包括更新和日志记录）
- 没有发生任何异常

**提交效果**：
- 所有数据库更改永久生效
- 释放事务持有的所有锁

#### 步骤12: 记录系统日志

使用 logger 记录成功操作的信息：

```javascript
logger.info(`释放任务排程锁定: 成功=${unlockedTaskIds.length}, 操作人ID=${operatorId}`);
```

**日志级别**：INFO

**日志用途**：
- 系统运维和监控
- 性能分析
- 操作统计

#### 步骤13: 返回成功结果

构造并返回成功响应数据：

**返回对象**：
- `unlockedCount`：成功释放的任务数量
- `unlockedTaskIds`：成功释放的任务ID列表

**HTTP状态码**：200 OK

### 异常处理流程

如果在处理过程中发生任何异常：

```
异常发生
   ↓
回滚事务 (transaction.rollback())
   ↓
记录错误日志 (logger.error)
   ↓
抛出异常给上层处理
   ↓
返回错误响应 (HTTP 500)
```

**错误日志包含**：
- taskIds：请求的任务ID列表
- error.message：错误消息
- operatorId：操作人ID

## 使用示例

### 场景1: 排程失败后释放任务

**业务需求**: 排程算法执行失败，需要释放已锁定的任务，以便重新排程

**操作步骤**：
1. 排程模块调用"锁定任务用于排程"接口锁定了一批任务

## 常见问题

### Q1: 释放不存在的任务会报错吗？

**答**：不会。系统采用容错设计，不存在的任务ID会被自动忽略，不影响其他有效任务的释放。最终返回的 `unlockedCount` 和 `unlockedTaskIds` 只包含实际存在并成功释放的任务。

**原因**：
- 任务可能在锁定后被删除
- 前端缓存可能包含已删除任务的ID
- 容错设计提高了系统的健壮性

### Q2: 可以释放未锁定的任务吗？

**答**：可以，但不会有任何副作用。如果任务的 `scheduleLockedUntil` 已经是 `null`（未锁定状态），再次释放不会改变任何数据，仍然会返回成功。

**说明**：
- 接口具有幂等性
- 重复释放不会导致错误
- 可以安全地重试操作

### Q3: 一次最多可以释放多少个任务？

**答**：最多100个任务。这是为了防止单次操作时间过长，导致数据库事务超时或系统性能问题。

**处理建议**：
- 如果需要释放超过100个任务，请分批调用
- 前端可以实现批量操作的队列机制
- 每次操作完成后再发起下一批

### Q4: 释放操作会影响正在执行的任务吗？

**答**：不会。本接口只操作处于待排程状态（`pending-schedule`）的任务。正在执行的任务（`in-progress`等状态）不应该被锁定用于排程，因此不会受到影响。

**注意**：
- 确保只锁定待排程状态的任务
- 不要锁定已开始执行的任务
- 执行中的任务有独立的状态管理机制

### Q5: 释放操作失败会怎样？

**答**：如果释放操作失败（如数据库错误），整个事务会回滚，所有任务的锁定状态都不会改变。

**失败场景**：
- 数据库连接中断
- 事务超时
- 系统内部错误

**处理建议**：
- 检查服务器日志定位具体错误
- 确认数据库服务正常
- 可以重试操作（幂等性保证）
- 必要时联系技术支持

### Q6: 如何知道哪些任务被释放了？

**答**：响应数据中的 `unlockedTaskIds` 字段包含了所有成功释放的任务ID列表。前端可以根据这个列表更新UI状态或执行后续操作。

**使用建议**：
- 对比请求的 `taskIds` 和响应的 `unlockedTaskIds`
- 如果数量不一致，说明部分任务不存在或已释放
- 可以在前端显示释放结果摘要

### Q7: 权限不足会有什么提示？

**答**：如果当前用户没有 `prod.annealing-task.schedule` 权限，会返回 HTTP 403 错误，错误码为 `FORBIDDEN`，错误消息为"无权限执行此操作"。

**解决方法**：
- 联系系统管理员
- 申请排程管理权限（`prod.annealing-task.schedule`）
- 确认账号所属角色是否包含该权限

### Q8: 如何避免重复提交？

**答**：接口具有幂等性，重复调用不会产生副作用。但为了减少不必要的服务器负载，建议：

**前端实现**：
- 提交后禁用按钮，避免用户重复点击
- 使用请求去重机制
- 显示加载状态

**后端保证**：
- 事务机制确保操作原子性
- 已释放的任务再次释放不会报错
- 操作日志记录所有请求

### Q9: 释放操作会记录日志吗？

**答**：会。每个成功释放的任务都会在任务日志表（`annealing_task_logs`）中记录一条日志，包含：

**日志内容**：
- 操作类型：SYNCED
- 操作描述："任务排程锁定已释放"
- 原始值：释放前的 `scheduleLockedUntil` 值
- 新值：`scheduleLockedUntil` 为 null
- 操作人信息：ID、姓名、IP地址
- 操作时间：记录创建时间

**日志用途**：
- 操作审计
- 问题追踪
- 数据恢复参考

## 附录

### 任务锁定状态说明

| 字段名              | 类型     | 说明                                                  |
| ------------------- | -------- | ----------------------------------------------------- |
| scheduleLockedUntil | datetime | 排程锁定截止时间，NULL表示未锁定                      |
| isScheduleLocked    | boolean  | 是否被锁定（虚拟字段），根据 scheduleLockedUntil 计算 |

**锁定判断逻辑**：
- 如果 `scheduleLockedUntil` 为 `null`，则未锁定
- 如果 `scheduleLockedUntil` 大于当前时间，则已锁定
- 如果 `scheduleLockedUntil` 小于等于当前时间，则锁定已过期（视为未锁定）
