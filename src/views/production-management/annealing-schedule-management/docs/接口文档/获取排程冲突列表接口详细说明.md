## 功能概述

### 所有功能

获取排程冲突列表（Get Schedule Plan Conflicts）是退火炉排程管理模块中的冲突检测功能，用于获取指定排程方案在生成或调整过程中检测到的所有冲突信息，以支持调度员识别问题、优化排程方案的业务场景。

该接口提供完整的冲突检测结果，包括冲突类型、严重程度、受影响的任务、解决建议等信息，帮助调度员快速定位问题并采取相应的调整措施。

### 关键特性

- ✅ **实时冲突查询**：获取排程方案最新的冲突检测结果，包括算法运行后和手动调整时的冲突
- ✅ **多维度筛选**：支持按严重程度（low/medium/high/critical）和冲突类型筛选，快速定位关键问题
- ✅ **详细冲突信息**：每个冲突包含类型、描述、受影响任务ID列表、解决建议等完整信息
- ✅ **严重程度分级**：自动区分致命冲突（阻止发布）和非致命冲突（允许发布），指导决策
- ✅ **可操作建议**：每个冲突都提供具体的解决建议，降低调整难度
- ✅ **追踪检测时间**：记录冲突检测的时间戳，便于问题追溯和分析

---

### 使用前提

- ✅ 排程方案必须已创建且处于 `generated`（已生成）或 `published`（已发布）状态
- ✅ 用户必须具备 `prod.scheduling.view` 权限
- ✅ 排程方案必须已经过冲突检测（算法运行完成或手动调整后）
- ✅ 提供有效的排程方案ID（UUID格式）

### 不适用场景

- ❌ 方案处于 `draft`（草稿）状态时，尚未运行算法，不存在冲突检测结果
- ❌ 方案处于 `computing`（运算中）状态时，冲突检测尚未完成，无法获取结果
- ❌ 方案已被 `cancelled`（取消）后，冲突信息已失效

### 详细步骤说明

#### 步骤1: 接收请求
- 从路径参数中提取排程方案ID（UUID格式）
- 从查询参数中提取可选的筛选条件：
  - `severityLevel`: 严重程度筛选（low/medium/high/critical）
  - `conflictType`: 冲突类型筛选（time-conflict、capacity-exceeded等）
- 验证参数格式的有效性

#### 步骤2: 方案状态校验
- 根据方案ID查询排程方案是否存在
- 如果方案不存在，返回 `404 Not Found` 错误
- 验证当前用户是否具备 `prod.scheduling.view` 权限
- 如果无权限，返回 `403 Forbidden` 错误
- 检查方案状态：
  - `draft` 或 `computing` 状态：提示冲突检测尚未完成
  - `cancelled` 状态：提示方案已取消，冲突信息已失效
  - `generated` 或 `published` 状态：允许查询

#### 步骤3: 构建查询条件
- 基础条件：`schedulePlanId = :id`
- 如果提供了 `severityLevel` 参数：添加 `severityLevel = :severityLevel` 条件
- 如果提供了 `conflictType` 参数：添加 `conflictType = :conflictType` 条件
- 设置排序规则：按严重程度优先（critical > high > medium > low），再按检测时间倒序

#### 步骤4: 查询冲突数据
- 从 `SchedulePlanConflicts` 表中查询符合条件的冲突记录
- 关联查询受影响的任务信息（通过 `affectedTaskIds` 数组）
- 获取每个冲突的完整字段：
  - id: 冲突记录ID
  - schedulePlanId: 所属排程方案ID
  - conflictType: 冲突类型代码
  - severityLevel: 严重程度
  - description: 冲突描述
  - affectedTaskIds: 受影响的任务ID数组
  - suggestion: 解决建议
  - detectedAt: 检测时间

#### 步骤5: 格式化响应数据
- 转换时间字段为ISO 8601格式
- 确保 `affectedTaskIds` 为数组格式
- 按照统一响应格式组装数据：
  - `success: true`
  - `data: [冲突列表]`
  - `message: "获取排程冲突列表成功"`
  - `meta`: 包含时间戳、请求ID、版本号

#### 步骤6: 返回冲突列表
- 返回HTTP状态码 `200 OK`
- 返回格式化后的JSON响应
- 记录操作日志（用户ID、方案ID、筛选条件、返回冲突数量）

## 接口文档

### 基本信息

**接口路径**: `GET /v1/prod/schedule-plans/:id/conflicts`

**功能描述**: 获取指定排程方案的冲突检测结果，支持按严重程度和冲突类型筛选，帮助调度员快速识别和解决排程冲突问题。

**认证要求**: Bearer Token 认证，需要 `prod.scheduling.view` 权限

## 使用示例

### 场景1: 算法执行完成后查看所有冲突

**业务需求**: 调度员运行排程算法后，需要查看所有检测到的冲突，评估排程质量。

**操作步骤**:

1. 创建排程方案并运行算法
2. 等待算法执行完成（方案状态变为 `generated`）
3. 调用冲突列表接口查看所有冲突
4. 根据冲突严重程度决定下一步操作

**响应分析**:

- 返回4个冲突：2个致命冲突（critical）、1个高级冲突（high）、1个中级冲突（medium）
- 致命冲突必须解决，否则无法发布
- 高级和中级冲突可以选择性处理

### 场景2: 只查看致命冲突，快速识别阻塞问题

**业务需求**: 调度员在发布方案前，只想查看会阻止发布的致命冲突，优先解决这些问题。

**操作步骤**:

1. 使用 `severityLevel=critical` 参数筛选致命冲突
2. 逐个查看冲突详情和解决建议
3. 针对性地进行手动调整

**处理策略**:

- 冲突1（时间重叠）：将任务2延后2小时或转移到TH-02炉子
- 冲突2（容量超限）：将重量最小的任务转移到其他炉子

### 场景3: 查看特定类型冲突，分析某类问题

**业务需求**: 发现排程中频繁出现工艺不兼容的混炉冲突，需要专门分析这类问题并优化混炉策略。

## 常见问题

### Q1: 为什么查询冲突列表返回空数组？

**A**: 可能的原因：

1. **排程方案没有冲突** - 算法生成的排程方案质量很高，所有约束都得到满足
2. **方案状态不正确** - 如果方案处于 `draft`（草稿）或 `computing`（运算中）状态，冲突检测尚未完成
3. **筛选条件过于严格** - 使用了 `severityLevel` 或 `conflictType` 参数，但该类型的冲突不存在
4. **冲突已被解决** - 之前存在的冲突已通过手动调整解决

**处理建议**:

- 检查方案状态是否为 `generated` 或 `published`
- 去掉筛选条件，查询所有冲突
- 查看算法执行日志，确认是否运行成功

### Q2: 冲突检测是实时的吗？

**A**: 冲突检测的时机：

1. **算法执行完成时** - 自动进行全面冲突检测，检测所有类型的冲突
2. **手动调整后** - 实时检测调整是否产生新冲突或解决旧冲突
3. **发布前验证** - 发布接口会再次执行致命冲突检查，确保安全

**检测速度**: 通常在1秒内完成，对于复杂方案（100+任务）可能需要2-3秒

**实时性保证**: 每次手动调整任务时，后端会立即重新运行冲突检测，确保冲突列表始终反映最新状态

### Q3: 什么是致命冲突（critical）？为什么不能发布？

**A**: 致命冲突类型及原因：

| 冲突类型 | 为什么是致命的                                     | 后果                       |
| -------- | -------------------------------------------------- | -------------------------- |
| 时间冲突 | 同一炉子不能同时执行两个任务，物理上不可行         | 生产无法执行，系统逻辑错误 |
| 容量超限 | 超出炉子最大容量，存在安全风险和设备损坏风险       | 安全事故、设备损坏         |
| 维护冲突 | 设备维护期间不能使用，强行使用可能导致维护计划冲突 | 设备故障、维护延误         |

**非致命冲突（high/medium/low）** 可以通过以下方式处理：

- `high` 级冲突：可以使用 `forcePublish=true` 参数强制发布（需要管理员权限）
- `medium/low` 级冲突：可以直接发布，但会记录警告日志

### Q4: 如何根据冲突建议进行调整？

**A**: 每个冲突的 `suggestion` 字段提供了可操作的解决建议，常见调整方式：

**时间冲突解决**:

```
建议: "将任务AT-20251010-0002延后至12:00执行，或转移到TH-02炉子"

操作1: 延后时间
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "scheduledLoadTime": "2025-10-11T12:00:00.000Z" }

操作2: 更换炉子
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "furnaceCode": "TH-02" }
```

**容量超限解决**:

```
建议: "将重量最小的任务AT-20251010-0005（3.8吨）转移到TH-01炉子"

操作: 转移任务到其他炉子
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "furnaceCode": "TH-01" }
```

**工艺不兼容解决**:

```
建议: "建议取消混炉安排，单独排程"

操作: 取消混炉标记
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "isMixed": false }
```

### Q5: 手动调整后，冲突数量反而增加了，怎么办？

**A**: 这是正常现象，可能的原因：

1. **解决了一个冲突，产生了新冲突** - 例如将任务转移到TH-02炉子后，TH-02炉子可能产生新的容量超限
2. **连锁反应** - 调整一个任务的时间可能影响后续任务的排程

**处理策略**:

1. **回退调整** - 撤销最近的调整，尝试其他解决方案
2. **整体优化** - 考虑重新运行算法，而不是手动逐个调整
3. **分步解决** - 先解决致命冲突，再处理非致命冲突
4. **参考建议** - 严格按照系统提供的 `suggestion` 进行调整

### Q6: 冲突列表中的 `affectedTaskIds` 如何使用？

**A**: `affectedTaskIds` 的用途：

1. **快速定位** - 点击冲突记录后，前端可以高亮显示甘特图中受影响的任务块
2. **批量调整** - 对于涉及多个任务的冲突（如混炉不兼容），可以批量选中这些任务进行调整
3. **关联查询** - 调用任务详情接口，查看这些任务的完整信息（产品编码、工艺参数等）

### Q7: 不同严重程度的冲突，应该如何优先处理？

**A**: 处理优先级建议：

| 优先级 | 严重程度 | 处理策略             | 是否阻止发布   | 建议处理时间 |
| ------ | -------- | -------------------- | -------------- | ------------ |
| P0     | critical | 必须立即解决         | ✅ 是           | 发布前       |
| P1     | high     | 强烈建议解决         | ❌ 否（可强制） | 发布前       |
| P2     | medium   | 评估后决定是否解决   | ❌ 否           | 可发布后处理 |
| P3     | low      | 可忽略，记录日志即可 | ❌ 否           | 可忽略       |

**实际工作流程**:

```
1. 查询所有冲突
   GET /v1/prod/schedule-plans/:id/conflicts

2. 优先处理致命冲突（critical）
   GET /v1/prod/schedule-plans/:id/conflicts?severityLevel=critical
   → 必须全部解决，否则无法发布

3. 评估高级冲突（high）
   GET /v1/prod/schedule-plans/:id/conflicts?severityLevel=high
   → 评估业务影响，决定是否解决或强制发布

4. 中低级冲突可选择性处理
   → 不影响发布，可以后续优化
```

### Q8: 如何监控排程冲突的趋势？

**A**: 冲突趋势分析建议：

**分析指标**:

- **冲突率** = 有冲突的方案数 / 总方案数
- **平均冲突数** = 总冲突数 / 总方案数
- **冲突解决时间** = 方案发布时间 - 方案生成时间
- **最常见冲突类型** = 各类型冲突的占比

**优化策略**:

- 如果 `time-conflict` 频繁出现 → 优化算法的时间分配策略
- 如果 `capacity-exceeded` 频繁出现 → 调整混炉规则或增加炉子资源
- 如果 `process-incompatible` 频繁出现 → 优化混炉兼容性判断规则

### 冲突解决策略参考

#### 1. 时间冲突（time-conflict）

**冲突场景**: 炉号为 `TH-01` 的炉子在 `2025-10-11 08:00-12:00` 已排程任务A，又分配了 `10:00-14:00` 的任务B

**解决策略**:

- **策略1**: 延后任务B的开始时间到12:00
- **策略2**: 将任务B转移到其他空闲炉子（如TH-02）
- **策略3**: 提前任务A的开始时间，为任务B腾出空间
- **策略4**: 重新运行算法，优化整体时间分配

**调整接口**:

```bash
# 策略1: 延后任务B
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "scheduledLoadTime": "2025-10-11T12:00:00.000Z" }

# 策略2: 转移任务B到TH-02
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "furnaceCode": "TH-02" }
```

#### 2. 容量超限（capacity-exceeded）

**冲突场景**: TH-01炉最大容量42吨，但排程了任务A（20吨）、任务B（15吨）、任务C（10吨），总计45吨

**解决策略**:

- **策略1**: 将重量最小的任务C转移到其他炉子
- **策略2**: 取消部分任务的混炉安排，单独排程
- **策略3**: 调整任务组合，寻找更优的混炉方案
- **策略4**: 拆分重量较大的任务（如果允许）

**调整接口**:

```bash
# 策略1: 转移任务C到TH-02
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "furnaceCode": "TH-02" }

# 策略2: 取消任务C的混炉
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "isMixed": false }
```

#### 3. 工艺不兼容（process-incompatible）

**冲突场景**: 任务A（1060合金，380°C）与任务B（8011合金，340°C）被安排混炉，但合金牌号不同且温度差40°C

**解决策略**:

- **策略1**: 取消混炉，单独排程两个任务
- **策略2**: 寻找工艺参数更接近的任务进行混炉
- **策略3**: 评估业务影响后强制发布（需要审批）
- **策略4**: 调整算法的混炉兼容性规则

**调整接口**:

```bash
# 策略1: 取消混炉
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "isMixed": false }

# 策略3: 强制发布（发布时使用）
POST /v1/prod/schedule-plans/:id/publish
{ "forcePublish": true, "reason": "业务紧急，工艺不兼容可接受" }
```

#### 4. 物料未就绪（material-not-ready）

**冲突场景**: 任务A的物料预计11:00到达，但排程的装炉时间为10:00

**解决策略**:

- **策略1**: 推迟装炉时间到11:30，留出30分钟缓冲时间
- **策略2**: 联系物流部门提前物料到达时间
- **策略3**: 评估影响后直接发布（中级冲突可发布）
- **策略4**: 将该任务与其他任务调换顺序

**调整接口**:

```bash
# 策略1: 推迟装炉时间
PATCH /v1/prod/schedule-plans/:id/items/:itemId
{ "scheduledLoadTime": "2025-10-11T11:30:00.000Z" }
```

### 冲突检测算法说明

#### 时间冲突检测算法

```
对于每个炉子：
  获取该炉子的所有排程任务
  按装炉时间排序
  for i = 0 to 任务数量-2:
    任务A = 排程任务[i]
    任务B = 排程任务[i+1]
    if 任务A.出炉时间 > 任务B.装炉时间:
      记录时间冲突(任务A, 任务B)
```

#### 容量超限检测算法

```
对于每个炉次（混炉的任务组）：
  计算总重量 = sum(任务.重量)
  if 总重量 < 炉子最小容量(35吨):
    记录容量不足警告
  else if 总重量 > 炉子最大容量(42吨):
    记录容量超限冲突(致命)
```

#### 工艺兼容性检测算法

```
对于每个混炉任务组：
  if 任务数量 > 1:
    for 任务A, 任务B in 任务组的所有配对:
      if 任务A.产品编码 == 任务B.产品编码:
        兼容 ✅
      else if 任务A.合金牌号 == 任务B.合金牌号:
        温度差 = abs(任务A.退火温度 - 任务B.退火温度)
        if 温度差 <= 20:
          兼容 ✅
        else:
          记录工艺不兼容冲突
      else:
        记录工艺不兼容冲突
```
