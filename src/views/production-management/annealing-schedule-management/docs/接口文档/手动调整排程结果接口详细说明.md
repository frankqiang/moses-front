## 功能概述

### 所有功能

手动调整排程结果（Manual Schedule Adjustment）是退火排程管理模块中的核心操作之一，用于对已生成的排程结果进行精细化调整，以支持现场实际生产需求变化、设备状态调整、紧急插单等业务场景。该接口提供灵活的排程优化能力，确保排程方案与实际生产情况保持高度匹配。

### 关键特性

- ✅ **严格冲突校验**：系统自动检测时间冲突、设备冲突、容量超限等问题，**阻止任何导致冲突的调整操作**，确保排程准确性
- ✅ **多维度调整支持**：支持炉号更换、装炉时间调整、出炉时间修改等多种调整操作
- ✅ **智能约束校验**：自动验证调整后的排程是否满足工艺要求、设备容量、时间逻辑等业务约束
- ✅ **原子性操作**：单次调整操作保证数据一致性，避免部分更新导致的数据异常
- ✅ **详细日志记录**：完整记录调整操作的用户、时间、原因等信息，便于追溯和分析
- ✅ **灵活参数配置**：支持单字段或多字段组合调整，满足不同的调整需求
- ✅ **详细错误反馈**：当调整不通过时，提供具体的冲突任务信息和时间段，帮助用户快速定位问题

---

### 使用前提

- ✅ 排程方案必须存在且处于草稿状态（未发布）
- ✅ 用户具备 `prod.scheduling.adjust` 权限
- ✅ 目标排程结果项必须存在且未被其他操作锁定
- ✅ 至少提供一个需要调整的字段（炉号、装炉时间、出炉时间或备注）

### 不适用场景

- ❌ 已发布的排程方案无法调整，需要先取消发布
- ❌ 不支持跨排程方案的批量调整操作

### 详细步骤说明

#### 步骤1: 接收调整请求
- 解析路径参数中的排程方案ID和排程结果项ID
- 提取请求体中的调整字段（炉号、时间、备注等）
- 验证至少包含一个有效的调整字段

#### 步骤2: 验证权限和参数
- 校验JWT Token的有效性
- 确认用户具备 `prod.scheduling.adjust` 权限
- 验证请求参数格式和业务规则（如出炉时间必须晚于装炉时间）

#### 步骤3: 查找排程方案
- 根据方案ID查询排程方案记录
- 验证方案状态为草稿状态（未发布）
- 确认方案未被删除且用户有访问权限

#### 步骤4: 查找排程结果项
- 根据项目ID查询对应的排程结果项
- 验证该项目属于指定的排程方案
- 确认项目未被其他操作锁定

#### 步骤5: 执行字段更新
- 在数据库事务中更新指定的字段值
- 保持其他字段不变，确保数据完整性
- 更新最后修改时间和操作人信息

#### 步骤6: 冲突检测分析
- 检测时间冲突：相同炉号的时间重叠
- 检测容量冲突：炉子装载量超出容量限制
- 检测工艺冲突：不兼容工艺的同炉排程
- 检测维护计划冲突：是否与设备维护时间冲突
- **如发现任何冲突，立即回滚事务并返回错误响应**

#### 步骤7: 记录调整日志
- 记录调整前后的字段值变化
- 保存调整原因和操作人信息
- 记录冲突检测结果用于后续分析

#### 步骤8: 返回调整结果
- 返回更新后的排程结果项数据
- 包含完整的冲突检测结果列表
- 提供操作成功确认和后续建议

## 接口文档

### 基本信息

**接口路径**: `PATCH /v1/prod/schedule-plans/:id/items/:itemId`

**功能描述**: 手动调整已生成的排程结果，支持炉号更换、时间调整等操作，并实时进行冲突检测

**认证要求**: Bearer Token 认证，需要 `prod.scheduling.adjust` 权限

所有错误的 API 调用都会返回以下统一格式：


**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null

- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

```

Content-Type: application/json
```

## 常见问题

### Q1: 调整后出现冲突怎么办？
**A**: 系统采用严格校验模式，如果调整后的排程与已有排程存在冲突（如时间重叠、容量超限等），系统会**拒绝本次调整操作**并返回详细的冲突信息。您需要根据返回的冲突详情（包括冲突的任务编号、时间段等）重新选择合适的炉号或时间段，确保无冲突后再次提交调整。这种设计可以避免排程混乱，确保生产计划的准确性。

### Q2: 为什么无法调整已发布的排程？
**A**: 已发布的排程方案已经同步到生产执行系统，为保证数据一致性，需要先取消发布再进行调整。

### Q3: 调整操作是否可以撤销？
**A**: 系统会保留调整前的原始数据（originalFurnaceCode等字段），可以通过再次调整来恢复原始状态。

### Q4: 调整后是否需要重新发布？
**A**: 是的，任何调整都需要重新发布排程方案才能同步到生产执行系统。

### Q5: 如何处理调整失败的情况？
**A**: 调整失败时，系统会返回详细的错误信息，包括具体的冲突任务编号（taskCode）和时间段。您需要根据这些信息重新规划调整方案，例如选择其他时间段或其他炉号，确保不会产生冲突后再次提交。

### 冲突类型枚举

| 冲突类型代码      | 中文名称 | 说明                                 |
| ----------------- | -------- | ------------------------------------ |
| time-conflict     | 时间冲突 | 相同炉号存在时间重叠，操作将被拒绝   |
| capacity-conflict | 容量冲突 | 炉子装载量超出容量限制，操作将被拒绝 |
| process-conflict  | 工艺冲突 | 不兼容工艺的同炉排程，操作将被拒绝   |
| resource-conflict | 资源冲突 | 所需资源不足或被占用，操作将被拒绝   |

**说明**: 系统采用严格校验模式，任何类型的冲突都会导致调整操作被拒绝，不存在"允许冲突但给出警告"的情况。

### 炉号规范

炉号命名规范：`TH-XX`，其中：
- `TH`: 表示退火炉（Thermal furnace）
- `XX`: 两位数字编号，01-20
