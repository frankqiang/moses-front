## 🔔 最新更新（2025-10-25）

### ✨ 响应结构优化

#### 结构变更
- ✅ **扁平化响应结构**: 所有排程方案字段直接在 `data` 下，不再嵌套在 `data.plan` 对象中
- ✅ **日志字段重命名**: `logs` 改为 `changeLogs`，更准确反映其含义
- ✅ **用户信息增强**: 同时返回 `createdBy`/`updatedBy` UUID 和 `creator`/`updater` 用户对象，避免额外请求

#### 新增字段
- ✅ **`statusLabel`**: 方案状态中文名称（如"已生成"、"已发布"），模型自动生成，无需前端映射
- ✅ **`algorithmTypeLabel`**: 算法类型中文名称（如"规则算法"），模型自动生成，无需前端映射
- ✅ **`creator/updater/deleter`**: 创建人/更新人/删除人用户对象，包含 id、name、email，方便前端直接使用
- ✅ **`items[].creator/updater`**: 排程结果项的创建人/更新人用户对象，方便追踪操作人信息
- ✅ **`changeLogs[].operator`**: 变更日志的操作人用户对象，完整展示操作人信息
- ✅ **`items[].schedulePlanId`**: 排程方案ID，便于关联查询
- ✅ **`items[].adjustmentCount`**: 手动调整次数，追踪排程调整历史
- ✅ **`items[].lastAdjustedAt`**: 最后调整时间
- ✅ **`items[].lastAdjustedBy`**: 最后调整人ID
- ✅ **`changeLogs[].schedulePlanId`**: 排程方案ID，便于日志关联查询

#### 字段类型调整
- ✅ **数值字段字符串化**: `scheduleWeight` 和 `plannedWeight` 从数值改为字符串格式（如 `"850.50"`），保留精度

#### 升级影响
- 前端需要调整数据访问路径：`data.plan.xxx` → `data.xxx`
- 前端可直接使用 `statusLabel` 和 `algorithmTypeLabel`，减少枚举映射代码
- 日志访问路径调整：`data.logs` → `data.changeLogs`
- 用户信息全面结构化：
  - 方案级别：可直接使用 `creator.name`、`updater.name`
  - 排程结果项：可直接使用 `item.creator.name`、`item.updater.name`
  - 变更日志：可直接使用 `log.operator.name`
  - 同时保留 UUID 字段（`createdBy`、`operatorId` 等）用于数据操作
- 重量字段作为字符串处理，避免精度丢失

## 功能概述

### 所有功能

获取排程方案详情（Get Schedule Plan Detail）是退火排程管理模块中的核心查询接口之一，用于获取指定排程方案的完整详细信息，以支持排程方案查看、调整、分析决策的业务场景。

### 关键特性

- ✅ **完整信息展示**：返回排程方案的基本信息、算法参数、评分结果、状态信息等全部详情
- ✅ **排程结果查看**：提供方案中所有排程结果项的详细信息，包含任务、炉号、时间安排等
- ✅ **冲突检测结果**：展示排程过程中检测到的所有冲突信息及其严重程度
- ✅ **变更日志跟踪**：提供方案的完整变更历史记录（最近 20 条），支持审计追溯
- ✅ **用户信息完整**：同时返回用户 UUID 和用户对象（id、name、email），无需额外请求
- ✅ **关联数据加载**：包含关联的退火任务详情、设备信息等
- ✅ **状态实时展示**：准确反映方案当前状态和各阶段时间节点
- ✅ **中文标签自动生成**：自动提供状态和算法类型的中文名称，无需前端映射

---

### 使用前提

- ✅ 用户已通过身份认证并具备有效的访问令牌
- ✅ 用户拥有 `prod.scheduling.view` 权限
- ✅ 提供的排程方案ID必须存在且有效
- ✅ 排程方案未被删除（软删除状态下不可访问）

### 不适用场景

- ❌ 批量查询多个排程方案（应使用排程方案列表接口）
- ❌ 仅需要基本信息而不需要详细数据的轻量级查询场景

### 详细步骤说明

#### 步骤1: 接收请求参数
- 从路径参数中提取排程方案ID
- 验证ID格式是否为有效的UUID
- 检查用户认证状态和访问权限

#### 步骤2: 参数验证校验
- 校验用户是否具备 `prod.scheduling.view` 权限
- 验证排程方案ID格式是否符合UUID规范
- 确认请求头中包含有效的认证令牌

#### 步骤3: 查询排程方案基本信息
- 根据ID查询排程方案主表数据
- 检查方案是否存在且未被删除
- 获取方案编号、名称、状态、时间范围等基础信息

#### 步骤4: 关联查询排程结果项列表
- 查询该方案下所有的排程结果项
- 包含任务ID、炉号、计划时间、持续时长等
- 按序号或时间排序返回有序列表

#### 步骤5: 关联查询冲突检测结果
- 查询方案相关的所有冲突记录
- 按严重程度分类展示冲突信息
- 提供冲突描述和解决建议

#### 步骤6: 关联查询操作日志记录
- 获取方案的操作历史记录
- 包含创建、调整、发布、取消等操作
- 按时间倒序返回最近的操作记录

#### 步骤7: 关联查询用户信息
- 同时返回用户 UUID（`createdBy`、`updatedBy`）和用户对象（`creator`、`updater`）
- 用户对象包含 id、name、email 等基本信息
- 避免前端额外请求，提升用户体验

#### 步骤8: 组装响应数据并返回结果
- 将所有查询结果组装成统一的数据结构
- 对敏感字段进行过滤处理
- 返回符合API规范的JSON响应

## 接口文档

### 基本信息

**接口路径**: `GET /v1/prod/schedule-plans/:id`

**功能描述**: 获取指定排程方案的详细信息，包含排程结果、冲突记录、操作日志等完整数据

**认证要求**: Bearer Token认证，需要 `prod.scheduling.view` 权限

## 统一响应格式说明

### 成功响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
```

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号


**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

| 字段名              | 类型   | 说明                                        | 示例值  |
| ------------------- | ------ | ------------------------------------------- | ------- |

| furnaceMaxCapacity  | number | 该炉子的最大容量（吨，来自设备主数据）      | 42      |
| furnaceMinCapacity  | number | 该炉子的最小装载量（吨，maxCapacity × 80%） | 33.6    |

**说明**：
- `furnaceMaxCapacity` 和 `furnaceMinCapacity` 是 P0 阶段新增字段
- 每个炉子的容量限制独立计算，支持多炉容量不一致的场景
- `capacityUtilization = (totalWeight / furnaceMaxCapacity) × 100%`

**重量计算逻辑**（智能选择策略）：
- ✅ **优先使用实际重量**：任务已绑定物料时，使用 `actualWeight`（物料实际重量合计）
- ✅ **降级使用计划重量**：任务未绑定物料时，使用 `plannedWeight`（预估重量）
- ✅ **混料场景累加**：混炉时，totalWeight 为该炉次所有任务的重量合计
- 📌 **业务影响**：已备料任务的排程结果基于真实重量，提高准确性和容量利用率
- 📌 **最佳实践**：推荐在排程前完成物料绑定（先备料后排程）

## 常见问题

### Q1: 为什么获取不到排程方案详情？

**A1**: 可能的原因包括：
- 排程方案ID不存在或格式错误
- 方案已被删除（软删除）
- 用户没有查看权限
- 认证令牌已过期

建议检查ID格式、确认权限配置、更新访问令牌。

### Q2: 响应数据量很大，如何优化加载性能？

**A2**: 该接口返回完整详情，数据量较大是正常的。优化建议：
- 仅在需要详细信息时调用该接口
- 考虑使用分页加载操作日志
- 前端实现数据缓存机制
- 必要时可联系后端团队提供轻量级查询接口

### Q3: 排程结果项的关联任务信息不完整怎么办？

**A3**: 如果任务详情不足，可能是：
- 关联的退火任务被删除或状态异常
- 数据库关联关系存在问题
- 权限限制导致部分字段被过滤

建议检查任务状态，必要时联系技术支持。

### Q4: 冲突检测结果如何理解和处理？

**A4**: 冲突检测结果说明：
- `severity` 为 `critical` 的冲突必须处理才能发布
- `high` 和 `medium` 级别的冲突建议处理
- `low` 级别的冲突可以接受
- 查看 `resolutionSuggestion` 获取处理建议

### Q5: 变更日志记录不全或缺失？

**A5**: 变更日志（`changeLogs`）默认返回最近的 20 条记录，如需完整历史：
- 检查日志记录的时间范围
- 确认操作是否正确触发了日志记录
- 部分旧版本操作可能没有完整日志
- 可通过审计模块查询更详细的历史记录
- 接口限制返回 20 条是为了性能优化，如需更多历史记录请联系后端团队

### Q6: 响应结构与之前文档不一致怎么办？

**A6**: 当前文档已更新为实际的响应结构（扁平化 + 用户对象增强），如果您的前端代码还在使用旧的嵌套结构，需要进行以下调整：

**旧的访问方式（已废弃）**：
```javascript
const planCode = response.data.plan.planCode;
const status = response.data.plan.status;
const items = response.data.items;
const logs = response.data.logs;
```

**新的访问方式（当前实际结构）**：
```javascript
const planCode = response.data.planCode;
const status = response.data.status;
const statusLabel = response.data.statusLabel; // 新增：中文标签
const creatorName = response.data.creator?.name; // 新增：直接获取创建人姓名
const creatorEmail = response.data.creator?.email; // 新增：直接获取创建人邮箱

// 排程结果项也有用户对象
const items = response.data.items;
items.forEach(item => {
  console.log(`任务 ${item.taskCode} 由 ${item.creator?.name} 创建`);
});

// 变更日志也有操作人对象
const changeLogs = response.data.changeLogs; // 注意：改名
changeLogs.forEach(log => {
  console.log(`${log.operator?.name} 在 ${log.operatedAt} 执行了 ${log.action}`);
});
```

**主要变更点**：
- 所有方案字段直接在 `data` 下，去掉 `plan` 嵌套
- `logs` 改名为 `changeLogs`
- 新增 `statusLabel` 和 `algorithmTypeLabel` 中文标签字段
- 用户信息全面结构化：
  - 方案级别有 `creator`/`updater`/`deleter` 对象
  - 排程结果项有 `creator`/`updater` 对象
  - 变更日志有 `operator` 对象
- 同时保留 UUID 字段（如 `createdBy`、`operatorId`），用于数据比较和更新
