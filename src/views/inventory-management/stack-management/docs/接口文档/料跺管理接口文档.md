# Moses API 料垛管理模块接口文档

## 概述

本文档详细说明了 Moses API 料垛管理模块的所有接口，包括请求方法、路径、参数、请求和响应数据结构、功能描述、错误码和返回示例。**本文档严格基于实际代码实现编写**，确保前端开发人员能够准确对接。

## 🚨 **重要提醒**

**本文档基于代码分析编写，在前端集成前必须通过实际调用接口验证所有响应结构和字段！**

### API 基础信息

- **基础 URL**: `http://localhost:3000/v1` (开发环境)
- **API 版本**: v1
- **认证方式**: JWT Bearer Token
- **数据格式**: JSON
- **字符编码**: UTF-8
- **Content-Type**: application/json

### Swagger 文档

项目已集成 Swagger 文档，可通过以下地址访问：

- **开发环境**: http://localhost:3000/v1/docs
- **在线文档**: 提供完整的 API 接口说明、参数定义和示例

### 权限约定

- **inv.stack.manage**: 料垛管理权限，可执行组垛、拆垛等写操作
- **inv.stack.view**: 料垛查看权限，可执行料垛列表查询、详情查询、成员料框查询等读操作

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
```

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

## 料垛业务流程说明

### 料垛生命周期概述

```
步骤1：料框准备 → 确保所有料框满足组垛条件
   ↓
步骤2：组垛操作 → 将多个料框堆叠成料垛，状态：活动中
   ↓
步骤3：料垛作为整体 → 在物流、退火等环节中作为一个单元进行管理
   ↓
步骤4：拆垛操作 → 解除料垛与料框的关联，状态：已拆垛
   ↓
步骤5：料框独立 → 料框恢复独立状态，可重新组垛或单独使用
```

### 料垛状态列表

⚠️ **重要说明**：接口传参和返回时使用**中文状态值**，而非英文枚举常量名！

| 状态值（接口使用） | 常量名（仅供参考） | 说明                 |
| ------------------ | ------------------ | -------------------- |
| 活动中             | ACTIVE             | 料垛正常使用中       |
| 已拆垛             | DESTACKED          | 料垛已解除，不再使用 |

### 组垛规则

**料框必须满足以下条件才能组垛**：

1. **规格一致性**: 所有料框必须具有相同的料框规格
2. **产品一致性**: 所有料框必须具有相同的产品代码
3. **批次一致性**: 所有料框必须具有相同的批次号（如果批次号不为空）
4. **状态一致性**: 所有料框必须处于相同的状态
5. **数量要求**: 至少需要2个料框
6. **堆叠层数限制**: 料框数量不得超过规格定义的最大堆叠层数
7. **独立性要求**: 所有料框必须尚未组垛（stackId为null）

## 料垛接口详细说明

### 1. 组垛

**接口路径**: `POST /v1/inv/stacks`

**功能描述**: 将符合条件的料框堆叠成料垛。要求所有料框具有相同的料框规格、产品代码、批次号和状态。堆叠层数不得超过规格的最大堆叠层数限制。料垛编号格式为：LD-YYYYMMDD-XXXX（如：LD-20250110-0001）。

**认证要求**: 需要 Bearer Token

**权限要求**: `inv.stack.manage`

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

**请求参数**:

| 参数名    | 类型   | 必填 | 限制                             | 描述                       | 示例                             |
| --------- | ------ | ---- | -------------------------------- | -------------------------- | -------------------------------- |
| stackCode | string | 否   | 格式：LD-YYYYMMDD-XXXX，长度1-50 | 料垛编号，不提供则自动生成 | LD-20250110-0001                 |
| binIds    | array  | 是   | UUID数组，至少2个，不能重复      | 料框ID列表                 | ["123e4567-...", "223e4567-..."] |
| remarks   | string | 否   | 长度最大500字符                  | 备注                       | 组垛备注                         |

**请求示例**:

```bash
curl -X POST http://localhost:3000/v1/inv/stacks \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." \

      "123e4567-e89b-12d3-a456-426614174003"
    ],

```

### 2. 拆垛

**接口路径**: `POST /v1/inv/stacks/:id/destack`

**功能描述**: 解除料垛与成员料框的关联关系。拆垛后，料垛状态变为"已拆垛"（DESTACKED），成员料框的stackId清空，恢复独立状态。拆垛操作会记录拆垛时间和操作员信息。

**认证要求**: 需要 Bearer Token

**权限要求**: `inv.stack.manage`

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

**路径参数**:

| 参数名 | 类型   | 必填 | 描述           | 示例                                 |
| ------ | ------ | ---- | -------------- | ------------------------------------ |
| id     | string | 是   | 料垛ID（UUID） | 554e4422-beac-48bd-a22b-43b38a3c212b |

**请求参数**:

| 参数名  | 类型   | 必填 | 限制            | 描述     | 示例         |
| ------- | ------ | ---- | --------------- | -------- | ------------ |
| remarks | string | 否   | 长度最大500字符 | 拆垛原因 | 检验需要拆垛 |

**请求示例**:

```bash
curl -X POST http://localhost:3000/v1/inv/stacks/554e4422-beac-48bd-a22b-43b38a3c212b/destack \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." \
  -d '{
    "remarks": "检验需要拆垛"
  }'
```

**成功响应** (HTTP 200):

```json
{
  "success": true,
  "data": {
    "stackId": "554e4422-beac-48bd-a22b-43b38a3c212b",
    "stackCode": "LD-20250110-0001",
    "destackedBinCount": 3,
    "remainingBinCount": 0,
    "destackedBinCodes": [
      "LK-20250110-0001",
      "LK-20250110-0002",
      "LK-20250110-0003"
    ],
    "isFullDestack": true
  },
  "message": "拆垛成功",
  "meta": {
    "timestamp": "2025-01-10T14:00:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**:

| 字段名            | 类型    | 描述                         | 示例                                   |
| ----------------- | ------- | ---------------------------- | -------------------------------------- |
| stackId           | string  | 料垛ID                       | "554e4422-beac-48bd-a22b-43b38a3c212b" |
| stackCode         | string  | 料垛编号                     | "LD-20250110-0001"                     |
| destackedBinCount | number  | 本次拆垛的料框数量           | 3                                      |
| remainingBinCount | number  | 剩余的料框数量（部分拆垛时） | 0                                      |
| destackedBinCodes | array   | 拆垛的料框编号列表           | ["LK-20250110-0001", ...]              |
| isFullDestack     | boolean | 是否完全拆垛                 | true                                   |

**字段说明**：
- `destackedBinCount`: 本次拆垛操作解除关联的料框数量
- `remainingBinCount`: 如果是部分拆垛，剩余仍在料垛中的料框数量；完全拆垛时为0
- `destackedBinCodes`: 被拆垛的料框编号数组，方便追踪
- `isFullDestack`: true表示料垛已完全拆解，false表示还有料框未拆（部分拆垛）

**错误响应**:

| HTTP状态码 | 错误码                    | 错误消息                | 说明                         | 处理建议                           |
| ---------- | ------------------------- | ----------------------- | ---------------------------- | ---------------------------------- |
| 400        | VALIDATION_ERROR          | 请求参数验证失败        | 料垛ID格式不正确             | 确保ID为有效的UUID格式             |
| 400        | STACK_ALREADY_DESTACKED   | 料垛已拆垛              | 该料垛已经拆垛               | 检查料垛状态                       |
| 400        | STACK_DESTACK_NOT_ALLOWED | 不允许拆垛              | 当前状态不允许拆垛           | 检查业务规则和料垛状态             |
| 401        | UNAUTHORIZED              | 未授权，Token无效或过期 | 未提供认证Token或Token已失效 | 重新登录获取有效Token              |
| 403        | FORBIDDEN                 | 无权限执行此操作        | 当前用户没有料垛管理权限     | 联系管理员分配inv.stack.manage权限 |
| 404        | STACK_NOT_FOUND           | 料垛不存在              | 指定ID的料垛不存在或已删除   | 检查料垛ID是否正确                 |
| 500        | STACK_DESTACK_FAILED      | 拆垛失败                | 服务器内部错误，拆垛操作失败 | 查看日志定位问题或联系技术支持     |

### 3. 料垛列表查询

**接口路径**: `GET /v1/inv/stacks`

**认证要求**: 需要 Bearer Token

**权限要求**: `inv.stack.view`

**请求头**:

```
Authorization: Bearer <access_token>
```

### 错误处理最佳实践

1. **统一错误处理**: 前端应根据错误码进行统一处理，而不是依赖 HTTP 状态码

2. **错误码模式识别**: 建议根据错误码前缀进行模式识别处理
   - `STACK_`: 料垛相关错误，根据具体错误码处理
   - `INV_`: 库存管理通用错误，可能影响多个模块
   - `UNAUTHORIZED/FORBIDDEN`: 认证授权错误，需要处理登录和权限问题

3. **错误消息展示**: 直接使用 `error.message` 字段的内容，无需前端硬编码错误消息

4. **重试机制**: 对于包含 `retryAfter` 字段的错误，应按照指定时间后重试

5. **日志记录**: 使用 `traceId` 进行错误追踪和问题排查

## 数据模型

### 料垛模型

料垛是多个料框的堆叠组合，作为一个物流单元进行管理。

```json
{
  "id": "string (UUID)",
  "stackCode": "string",
  "binSpecificationCode": "string",
  "productCode": "string",
  "batchNumber": "string | null",
  "totalWeight": "number",
  "binCount": "number",
  "stackLayers": "number",
  "status": "string (枚举)",
  "currentLocationId": "string (UUID) | null",
  "stackedAt": "string (ISO日期)",
  "stackedBy": "string (UUID) | null",
  "destackedAt": "string (ISO日期) | null",
  "destackedBy": "string (UUID) | null",
  "remarks": "string | null",
  "isDeleted": "boolean",
  "createdBy": "string (UUID) | null",
  "updatedBy": "string (UUID) | null",
  "createdAt": "string (ISO日期)",
  "updatedAt": "string (ISO日期)"
}
```

### 字段说明

**主要字段**:
- `id`: 料垛唯一标识
- `stackCode`: 料垛编号，格式：LD-YYYYMMDD-XXXX，自动转换为大写
- `binSpecificationCode`: 料框规格代码，冗余存储便于查询，自动转换为大写
- `productCode`: 产品代码，冗余存储便于查询，自动转换为大写
- `batchNumber`: 批次号
- `totalWeight`: 总重量(kg)，所有料框重量之和，DECIMAL类型，响应时自动转换为number
- `binCount`: 料框数量
- `stackLayers`: 堆叠层数，不得超过规格的最大堆叠层数
- `status`: 料垛状态，枚举值：ACTIVE（活动中）/ DESTACKED（已拆垛）

**位置和关联**:
- `currentLocationId`: 当前位置ID，可为null

**时间和操作员**:
- `stackedAt`: 组垛时间
- `stackedBy`: 组垛操作员ID
- `destackedAt`: 拆垛时间，未拆垛时为null
- `destackedBy`: 拆垛操作员ID，未拆垛时为null
- `createdAt`: 数据库记录创建时间
- `updatedAt`: 数据库记录更新时间
- `createdBy`: 创建人ID
- `updatedBy`: 最后更新人ID

**其他**:
- `remarks`: 备注信息
- `isDeleted`: 软删除标志，false表示正常，true表示已删除

**日期时间格式**:
- 所有日期时间字段均使用 ISO 8601 格式：`YYYY-MM-DDTHH:mm:ss.sssZ`
- 示例：`"2025-01-10T10:30:00.000Z"`

## 附录：料框与料垛关系说明

### 数据关联

- 料框（Bin）模型包含 `stackId` 字段，指向所属的料垛
- 料垛（Stack）模型通过一对多关系关联料框
- 组垛时，料框的 `stackId` 被设置为料垛ID
- 拆垛时，料框的 `stackId` 被清空（设为null）

### 状态联动

- 组垛不影响料框的业务状态（status字段），料框保持原有状态
- 料垛作为整体参与物流和退火流程
- 拆垛后，料框恢复独立状态，可继续参与业务流程

### 操作限制

- 已组垛的料框不能再次组垛（必须先拆垛）
- 已组垛的料框不能单独更新某些属性
- 料垛拆垛后状态变为DESTACKED，不能再执行组垛操作
