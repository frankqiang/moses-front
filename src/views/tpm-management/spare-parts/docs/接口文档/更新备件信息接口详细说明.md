## 功能概述

### 所有功能

更新备件信息（Update Spare Part Information）是备件管理模块中的核心操作之一，用于修改已创建备件的基础信息、供应商信息、价格策略和库存管理配置，以适应业务需求变化和持续优化的场景。该接口支持部分更新（PATCH），允许只提交需要修改的字段，未提交的字段保持原值不变。

### 关键特性

- ✅ **部分字段更新**：支持PATCH语义，仅更新提交的字段，未提交字段保持原值，避免覆盖未修改的数据
- ✅ **编码保护机制**：备件编码作为业务唯一标识，创建后不允许修改，确保数据可追溯性和一致性
- ✅ **库存策略校验**：自动校验库存上限不能小于库存下限，防止配置错误导致的库存管理混乱
- ✅ **供应商信息管理**：支持更新结构化的供应商信息（名称、联系人、电话、邮箱），便于供应商变更和信息维护
- ✅ **审计信息记录**：自动记录更新人和更新时间，保留完整的操作审计轨迹
- ✅ **实时数据同步**：更新成功后返回完整的备件信息（包含库存、创建人、更新人），确保前端数据一致性

---

### 使用前提

- ✅ 用户已通过认证获得有效的 Bearer Token
- ✅ 用户具有 `mdm.tpm.spare-part.manage` 权限
- ✅ 备件ID必须存在且未被软删除
- ✅ 如修改库存上下限，需确保新的上限 ≥ 新的下限（或保持原值）

### 不适用场景

- ❌ 不能修改备件编码（sparePartCode），编码在创建后即锁定
- ❌ 不能通过此接口修改库存数量，应使用入库/出库接口操作库存
- ❌ 不支持批量更新多个备件，需要逐个调用接口更新
- ❌ 不能更新已软删除的备件，应先恢复备件后再更新

### 详细步骤说明

#### 步骤1: 接收更新备件请求

**操作内容**：
- 从路径参数中提取备件ID
- 从请求体中提取需要更新的字段
- 验证Authorization Header中的JWT Token

**路径参数**：
- `id`: 备件的唯一标识（UUID格式）

**请求体**：
- 包含需要更新的字段（JSON格式）
- 所有字段均为可选
- 只需提供需要修改的字段

**注意事项**：
- sparePartCode字段即使提交也会被忽略（不允许修改）
- 空字符串和null的处理不同：空字符串表示清空该字段，不提交表示保持原值

#### 步骤2: 验证请求参数

**操作内容**：
- 使用Joi验证器验证请求参数
- 验证备件ID格式（必须是有效的UUID）
- 验证请求体中各字段的格式和类型

**验证规则**（Joi Schema）：
- `sparePartName`: 字符串，1-200字符
- `specification`: 字符串，最多200字符
- `applicableEquipmentTypes`: 字符串，最多500字符
- `supplierInfo`: 对象，包含name、contact、phone、email字段
- `unitPrice`: 数字，>=0，最多2位小数
- `unit`: 字符串，1-50字符
- `maxStock`: 整数，>=0
- `minStock`: 整数，>=0
- `safetyStock`: 整数，>=0
- `leadTimeDays`: 整数，>=0
- `storageLocation`: 字符串，最多100字符
- `shelfLifeMonths`: 整数，>=0
- `remark`: 字符串，无限制

**错误处理**：
- 验证失败返回400错误
- 错误信息包含具体的字段名和验证失败原因

#### 步骤3: 验证备件是否存在

**操作内容**：
- 根据ID在数据库中查询备件
- 检查备件是否存在
- 检查备件是否已被软删除（isDeleted=false）

**错误处理**：
- 备件不存在或已删除 → 返回404错误（TPM_SPARE_001：备件不存在）

#### 步骤4: 业务规则验证

**操作内容**：
- 验证库存上下限的合理性
- 验证数值类型字段的非负性
- 验证邮箱格式（如果supplierInfo.email有值）

**错误处理**：
- 库存上限 < 库存下限 → 返回400错误（TPM_SPARE_014：库存上限不能小于库存下限）
- 数值为负数 → 返回400错误（VALIDATION_ERROR：请求参数验证失败）

#### 步骤5: 数据预处理

**特殊处理**：
- unitPrice转换为数字类型（存储为DECIMAL）
- supplierInfo序列化为JSON字符串（存储为JSONB）

#### 步骤6: 开启数据库事务

**操作内容**：
- 创建Sequelize事务对象
- 后续数据库操作在事务内执行
- 确保数据一致性（原子性操作）

**事务隔离级别**：
- READ_COMMITTED（PostgreSQL默认）

**事务范围**：
- 更新备件主数据
- 查询完整数据（关联查询）

#### 步骤7: 更新备件主数据

**操作内容**：
- 在spare_parts表中更新备件记录
- 只更新请求体中提交的字段
- 自动更新updatedBy和updatedAt字段

**返回结果**：
- 受影响的行数（应为1）

**错误处理**：
- 更新失败 → 回滚事务，返回500错误（TPM_SPARE_009：更新备件失败）

#### 步骤8: 关联查询完整数据

**操作内容**：
- 查询更新后的备件主数据
- 关联查询库存信息（spare_part_inventories表）
- 关联查询创建人信息（users表）
- 关联查询更新人信息（users表）

#### 步骤9: 提交事务

**操作内容**：
- 提交数据库事务
- 释放数据库锁
- 持久化所有更改

**错误处理**：
- 提交失败 → 自动回滚，返回500错误

#### 步骤10: 组装响应数据

**操作内容**：
- 格式化为统一响应结构
- 添加响应元数据（timestamp、requestId、version）
- 确保数据类型正确（如unitPrice格式化为字符串）


#### 步骤11: 返回成功响应

**操作内容**：
- HTTP状态码：200 OK
- Content-Type: application/json
- 返回完整的备件详情数据（更新后）

**性能优化**：
- 使用单个事务避免中间状态
- 使用Sequelize的 `include` 机制一次性关联查询
- 数据库层面建立必要的索引

## 接口文档

### 基本信息

**接口路径**: `PATCH /v1/mdm/tpm/spare-parts/:id`

**功能描述**: 更新指定备件的基础信息，支持部分字段更新（PATCH语义）。不允许修改备件编码，如果修改库存上下限会自动校验合理性。更新成功后返回完整的备件信息（包含库存、创建人、更新人）。

**认证要求**: JWT Bearer Token，需要 `mdm.tpm.spare-part.manage` 权限

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",

      "field": "发生错误的字段名（可选）",

    "requestId": "req-1234567890-abcdef",
    "version": "v1"

```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null

- `error.details`: 可选的错误详细信息

**请求头**:

```
Authorization: Bearer <access_token>

```

## 常见问题

### Q1: 能否修改备件编码？

**A**: 不能。备件编码（sparePartCode）在创建后不允许修改，因为它是业务唯一标识，用于系统内的数据关联和追溯。如果确实需要更换编码，建议创建新备件并将旧备件软删除。

### Q2: 如果只更新一个字段，其他字段会被清空吗？

**A**: 不会。本接口采用PATCH语义，支持部分更新。只有请求体中提交的字段会被更新，未提交的字段保持原值不变。

**示例**:
```json
// 只更新单价
{
  "unitPrice": 200.00
}
```
执行后，只有unitPrice字段更新为200.00，其他所有字段（名称、规格、库存配置等）保持不变。

### Q3: 如何正确更新库存上下限？

**A**: 系统会自动校验库存上限不能小于库存下限。更新时需注意：

**场景1：同时更新上下限** - 确保请求中的 maxStock >= minStock
```json
{
  "maxStock": 100,
  "minStock": 20
}
```

**场景2：只更新上限** - 新的上限必须 >= 现有的下限
```json
{
  "maxStock": 150  // 假设现有minStock=20，则150 >= 20，合法
}
```

**场景3：只更新下限** - 新的下限必须 <= 现有的上限
```json
{
  "minStock": 30  // 假设现有maxStock=100，则30 <= 100，合法
}
```

如果校验失败，会返回400错误（TPM_SPARE_014：库存上限不能小于库存下限）。

### Q4: 更新supplierInfo时，能否只修改部分字段？

**A**: supplierInfo是作为整体对象更新的。如果提交supplierInfo对象，建议包含所有子字段（name、contact、phone、email），否则未提交的子字段会被清空（设为NULL）。

**不推荐**（会导致联系人和电话被清空）:

### Q5: 如何清空某个可选字段（如remark）？

**A**: 提交空字符串即可清空该字段。

```json
{
  "remark": ""  // 清空备注
}
```

**注意区别**：
- 提交空字符串 `""` → 清空字段
- 不提交字段 → 保持原值不变
- 提交 `null` → 清空字段（等同于空字符串）

### Q6: 更新后如何确认数据已生效？

**A**: 更新成功后，接口会返回更新后的完整备件信息，包括：
- 所有更新后的字段值
- 自动更新的 `updatedAt` 时间戳
- 自动更新的 `updater` 信息（当前登录用户）

前端可直接使用响应数据刷新界面，无需再次调用查询接口。

### Q7: 更新备件信息会影响库存数量吗？

**A**: 不会。更新备件信息只修改备件的基础信息和库存策略配置（如上下限、安全库存），不会改变实际库存数量（currentQuantity）。

要修改库存数量，需使用专门的入库/出库接口：
- 增加库存：`POST /v1/mdm/tpm/spare-parts/:id/in-stock`
- 减少库存：`POST /v1/mdm/tpm/spare-parts/:id/out-stock`

### Q8: 如果更新过程中发生错误，会部分更新吗？

**A**: 不会。更新操作在数据库事务中执行，遵循原子性原则：
- 成功：所有字段都更新成功
- 失败：所有字段都回滚到更新前的状态

确保数据一致性，不会出现部分字段更新成功、部分失败的情况。

### Q9: 能否同时更新多个备件？

**A**: 本接口不支持批量更新。如需更新多个备件，需要逐个调用接口。

### 库存策略字段说明

| 字段名       | 中文名称   | 作用                                         | 推荐配置策略         |
| ------------ | ---------- | -------------------------------------------- | -------------------- |
| maxStock     | 库存上限   | 库存数量的最大值，超过时可能过度占用库存成本 | 根据历史消耗量设定   |
| minStock     | 库存下限   | 库存数量的最小值，低于时应及时采购           | 根据采购周期设定     |
| safetyStock  | 安全库存   | 触发预警的阈值，低于时系统会发出低库存预警   | 通常设为 minStock/2  |
| leadTimeDays | 采购提前期 | 从下单到到货的天数，用于计算何时启动采购流程 | 根据供应商交货期设定 |

**配置建议**:
- safetyStock <= minStock <= maxStock
- safetyStock通常设置为 (leadTimeDays × 日均消耗量)
- minStock 通常设置为 (leadTimeDays × 1.5 × 日均消耗量)
- maxStock 根据存储空间和资金占用平衡设定
