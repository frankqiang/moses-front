## 功能概述

### 所有功能

查询单个备件详情（Get Spare Part Detail）是备件管理模块中的核心查询操作之一，用于根据备件ID获取备件的完整详细信息，以支持备件信息查看、出入库操作前确认、库存管理和维护任务规划的业务场景。

该接口返回备件的所有基础信息（编码、名称、规格、供应商等）、实时库存状态（当前库存、在途数量、预留数量）以及审计信息（创建人、更新人、时间戳），为业务人员提供全面的备件数据视图。

### 关键特性

- ✅ **完整信息返回**：一次调用获取备件主数据、库存状态、人员信息，无需多次请求
- ✅ **实时库存查询**：返回当前最新的库存数量、在途数量、预留数量，支持库存决策
- ✅ **低库存状态判断**：自动计算并返回可用库存，支持前端进行低库存预警提示
- ✅ **供应商信息展示**：包含完整的供应商联系信息（名称、联系人、电话、邮箱），便于快速联系采购
- ✅ **审计信息追溯**：提供创建人、更新人的完整信息（ID、姓名、邮箱），支持操作追溯和责任确认
- ✅ **安全删除保护**：自动过滤已软删除的备件，确保查询结果的有效性

---

### 使用前提

- ✅ 用户已登录并持有有效的认证Token
- ✅ 用户拥有 `mdm.tpm.spare-part.view` 权限（查看备件权限）
- ✅ 备件ID必须存在且未被软删除
- ✅ 备件ID必须为有效的UUID格式

### 不适用场景

- ❌ 批量查询多个备件信息（应使用备件列表接口 `GET /v1/mdm/tpm/spare-parts`）
- ❌ 仅需要库存信息（应使用专用库存接口 `GET /v1/mdm/tpm/spare-parts/:id/inventory`）
- ❌ 查询出入库历史记录（应使用出入库记录接口 `GET /v1/mdm/tpm/spare-parts/transactions`）
- ❌ 修改备件信息（应使用更新接口 `PATCH /v1/mdm/tpm/spare-parts/:id`）

### 详细步骤说明

#### 步骤1: 身份认证和权限验证

**操作内容**：
- 验证请求头中的 JWT Bearer Token 是否有效
- 检查Token是否过期
- 验证用户是否拥有 `mdm.tpm.spare-part.view` 权限

**验证规则**：
- Token格式：`Authorization: Bearer <access_token>`
- Token必须未过期且签名有效
- 用户角色必须包含查看备件的权限

**失败处理**：
- Token无效或过期：返回 401 Unauthorized
- 缺少权限：返回 403 Forbidden

#### 步骤2: 路径参数验证

**操作内容**：
- 验证路径参数 `id` 是否为有效的UUID格式
- 使用Joi验证器进行格式校验

**验证规则**：
- id必须符合UUID v4格式（如：`a1b2c3d4-e5f6-7890-abcd-ef1234567890`）
- 不允许空值或其他格式的字符串

**失败处理**：
- 格式错误：返回 400 Bad Request，错误码 VALIDATION_ERROR

#### 步骤3: 查询备件主数据

**操作内容**：
- 使用Sequelize ORM查询 `spare_parts` 表
- 根据id精确匹配查询
- 自动过滤 `isDeleted = false` 的记录（软删除保护）

**查询SQL（等效）**：
```sql
SELECT * FROM spare_parts
WHERE id = :id AND is_deleted = false;
```

**数据包含**：
- 备件编码、名称、规格
- 供应商信息（JSON对象）
- 价格、单位、库存配置
- 存储位置、保质期等

**失败处理**：
- 备件不存在或已删除：返回 404 Not Found，错误码 TPM_SPARE_001

#### 步骤4: 关联查询库存信息

**操作内容**：
- JOIN查询 `spare_part_inventories` 表
- 获取备件的实时库存状态
- 一对一关联（一个备件对应一条库存记录）

**查询SQL（等效）**：
```sql
SELECT
  current_quantity,
  in_transit_quantity,
  reserved_quantity,
  last_updated_at
FROM spare_part_inventories
WHERE spare_part_id = :id;
```

**返回字段**：
- `currentQuantity`: 当前实际可用库存
- `inTransitQuantity`: 采购在途数量
- `reservedQuantity`: 已预留未领用数量
- `lastUpdatedAt`: 库存最后更新时间

**计算逻辑**：
- 可用库存 = currentQuantity - reservedQuantity（前端计算）
- 低库存判断 = currentQuantity <= safetyStock（前端判断）

#### 步骤5: 关联查询创建人信息

**操作内容**：
- JOIN查询 `users` 表
- 根据 `createdBy` 字段关联
- 获取创建人的基本信息

**查询SQL（等效）**：
```sql
SELECT id, name, email
FROM users
WHERE id = spare_parts.created_by;
```

**返回对象**（creator）：
- `id`: 创建人的用户ID
- `name`: 创建人姓名
- `email`: 创建人邮箱

**特殊情况**：
- 如果创建人已被删除，createdBy为NULL，则creator对象为null

#### 步骤6: 关联查询更新人信息

**操作内容**：
- JOIN查询 `users` 表
- 根据 `updatedBy` 字段关联
- 获取最后更新人的基本信息

**查询SQL（等效）**：
```sql
SELECT id, name, email
FROM users
WHERE id = spare_parts.updated_by;
```

**返回对象**（updater）：
- `id`: 更新人的用户ID
- `name`: 更新人姓名
- `email`: 更新人邮箱

**特殊情况**：
- 如果更新人已被删除，updatedBy为NULL，则updater对象为null
- 如果备件从未被更新，updater与creator相同

#### 步骤7: 组装响应数据

**操作内容**：
- 合并备件主数据、库存信息、人员信息
- 格式化为统一响应结构
- 添加响应元数据（timestamp、requestId、version）

**数据结构**：
```javascript
{
  success: true,
  data: {
    // 备件主数据（flatten）
    id, sparePartCode, sparePartName, ...
    // 库存信息（nested object）
    inventory: { currentQuantity, ... },
    // 人员信息（nested objects）
    creator: { id, name, email },
    updater: { id, name, email }
  },
  message: "获取备件详情成功",
  meta: { timestamp, requestId, version }
}
```

#### 步骤8: 返回成功响应

**操作内容**：
- HTTP状态码：200 OK
- Content-Type: application/json
- 返回完整的备件详情数据

**性能优化**：
- 使用Sequelize的 `include` 机制一次性关联查询，避免N+1问题
- 数据库层面建立必要的索引（id主键、外键索引）
- 响应数据已过滤敏感信息（如密码等）

## 接口文档

### 基本信息

**接口路径**: `GET /v1/mdm/tpm/spare-parts/:id`

**功能描述**: 根据备件ID返回备件的完整详细信息，包括基础信息、实时库存状态和审计信息。如果备件不存在或已被软删除，则返回404错误。

**认证要求**: JWT Bearer Token，需要 `mdm.tpm.spare-part.view` 权限

## 使用示例

### 场景1: 查询备件详情用于信息展示

**业务需求**: 仓库管理员在备件管理界面点击某个备件，查看完整的备件信息，包括规格、供应商、库存状态等。

**展示逻辑**:
- 显示备件编码、名称、规格等基础信息
- 显示当前库存、在途数量、可用库存
- 如果 `currentQuantity <= safetyStock`，显示低库存警告标记
- 显示供应商联系信息，点击可拨打电话或发送邮件
- 显示创建人、更新人和时间戳用于审计追溯

### 场景2: 出库前查询备件库存充足性

**业务需求**: 维护工程师在执行维护任务时需要领用备件，领用前先查询备件详情，确认库存是否充足。

### 场景3: 批量查询备件详情用于对比

**业务需求**: 采购部门需要对比多个备件的供应商和价格信息，为采购决策提供依据。

### 场景4: 移动端扫码查询备件信息

**业务需求**: 仓库管理员使用移动设备扫描备件条形码/二维码，快速查看备件详情和库存状态。

### 场景5: 审计追溯查询创建人和修改历史

**业务需求**: 管理员需要查看备件的创建人和最后修改人信息，进行操作审计和责任追溯。

## 常见问题

### Q1: 为什么返回的unitPrice是字符串而不是数字？

**回答**:
为了保持精度，价格字段使用 `decimal(10,2)` 数据库类型存储，API返回时为字符串格式（如 `"150.00"`）。这样可以避免浮点数运算的精度问题。

### Q2: 如何判断备件是否处于低库存状态？

**回答**:
低库存判断逻辑为：`currentQuantity <= safetyStock`

### Q3: creator或updater字段为null是什么情况？

**回答**:
以下情况会导致创建人或更新人信息为null：
1. 创建人/更新人账户已被删除（外键约束为SET NULL）
2. 数据迁移过程中未关联用户信息
3. 系统自动创建的数据（如批量导入）

### Q4: 如何计算可用库存？

**回答**:
可用库存 = 当前库存 - 预留数量

**公式**: `availableStock = currentQuantity - reservedQuantity`

### Q5: supplierInfo字段可能为空吗？

**回答**:
是的，`supplierInfo` 字段是可选的JSONB类型，可能的值包括：
- 完整的供应商对象：`{ name, contact, phone, email }`
- 部分字段对象：`{ name: "供应商A" }` （其他字段未填写）
- 空对象：`{}`
- null值：`null`

### Q6: 查询已删除的备件会返回什么？

**回答**:
查询已软删除的备件（`isDeleted = true`）会返回 **404错误**，错误码为 `TPM_SPARE_001`。

系统自动过滤已删除的记录，确保前端不会获取到无效数据。

### Q7: 如何区分备件是否被修改过？

**回答**:
对比 `createdAt` 和 `updatedAt` 字段：
- 如果 `createdAt === updatedAt`，表示从未被修改
- 如果 `updatedAt > createdAt`，表示已被修改

### Q8: 接口是否支持批量查询？

**回答**:
本接口仅支持查询单个备件详情。如需批量查询，有以下选择：

1. **使用列表接口** `GET /v1/mdm/tpm/spare-parts`，通过筛选条件查询多个备件
2. **并发请求**：前端发起多个并发请求查询多个备件详情（参见使用示例场景3）

## 附录

### 备件状态枚举

备件本身没有状态字段，但可以根据库存和时间计算出以下逻辑状态：

| 状态   | 判断条件                         | 说明         |
| ------ | -------------------------------- | ------------ |
| 正常   | `currentQuantity > safetyStock`  | 库存充足     |
| 低库存 | `currentQuantity <= safetyStock` | 需要采购补货 |
| 缺货   | `currentQuantity === 0`          | 无可用库存   |
| 有在途 | `inTransitQuantity > 0`          | 有采购在途   |
| 有预留 | `reservedQuantity > 0`           | 有备件被预留 |
| 已删除 | `isDeleted === true`             | 已软删除     |
