## 功能概述

### 所有功能

备件出库（SparePart Out-Stock）是备件管理模块中的核心操作之一，用于执行备件领用、退库、报废等减少库存的业务操作，以支持设备维护备件的精细化管理和使用追溯的业务场景。

### 关键特性

- ✅ **智能库存校验**：出库前自动校验库存充足性，避免超出库存数量的出库操作
- ✅ **多类型支持**：支持领用、退库、报废三种出库类型，满足不同业务场景需求
- ✅ **强制关联追溯**：领用时必须关联维护任务或故障单，确保备件使用可追溯
- ✅ **智能单号生成**：支持手动提供出库单号或系统自动生成（格式：SP-OUT/RET/SCR-时间戳）
- ✅ **事务保护机制**：使用数据库事务确保出库记录创建和库存扣减的原子性操作
- ✅ **实时库存反馈**：接口响应同时返回出库记录详情和更新后的最新库存状态

---

### 使用前提

- ✅ 备件主数据必须已存在（需要先通过创建备件接口创建备件）
- ✅ 用户必须拥有 `mdm.tpm.spare-part.manage` 权限
- ✅ 备件当前库存必须充足（库存数量 >= 出库数量）
- ✅ 出库数量必须为正整数（≥ 1）
- ✅ 领用类型出库时，必须关联维护任务ID或故障单ID（至少提供一个）
- ✅ 如果手动提供出库单号，该单号在系统中必须唯一

### 不适用场景

- ❌ 备件采购入库操作（应使用备件入库接口）
- ❌ 修改已创建的出库记录（出库记录创建后不可修改，只能查询）
- ❌ 备件主数据的创建或更新（应使用相应的备件管理接口）
- ❌ 库存不足时强制出库（系统会拦截并返回库存不足错误）

### 详细步骤说明

#### 步骤1: 参数验证
- **验证内容**：
  - 检查出库数量是否为正整数（≥ 1）
  - 验证出库类型是否为允许的值（领用/退库/报废）
  - 检查UUID格式的字段（备件ID、任务ID、故障单ID）
  - 验证出库单号格式（如果手动提供）
- **验证规则**：使用Joi验证器进行参数格式和取值范围验证
- **失败处理**：返回400错误和VALIDATION_ERROR错误码

#### 步骤2: 备件存在性验证
- **验证内容**：
  - 根据路径参数中的备件ID查询备件主数据
  - 检查备件是否存在且未被软删除（isDeleted = false）
- **查询范围**：仅查询有效的备件记录
- **失败处理**：备件不存在时返回404错误和TPM_SPARE_001错误码

#### 步骤3: 库存充足性验证
- **验证内容**：
  - 查询备件的当前库存记录
  - 比较当前库存数量与出库数量
  - 验证公式：`currentQuantity >= 出库数量`
- **验证逻辑**：必须确保库存充足，否则禁止出库
- **失败处理**：
  - 库存记录不存在：返回404错误和TPM_SPARE_004错误码
  - 库存不足：返回400错误和TPM_SPARE_011错误码

#### 步骤4: 业务规则校验
- **适用条件**：仅当出库类型为"领用"时执行此步骤
- **校验内容**：
  - 检查是否提供了relatedTaskId或relatedFailureId（至少一个）
  - 如果提供了relatedTaskId，验证维护任务是否存在
  - 如果提供了relatedFailureId，验证故障单是否存在
- **业务意义**：确保领用的备件有明确的使用去向，便于后续追溯
- **失败处理**：
  - 未提供关联信息：返回400错误和TPM_SPARE_017错误码
  - 维护任务不存在：返回404错误和MAINTENANCE_TASK_002错误码
  - 故障单不存在：返回404错误和EQUIPMENT_FAILURE_002错误码

#### 步骤5: 出库单号处理
- **自动生成逻辑**：
  - 如果未提供transactionCode，根据出库类型自动生成
  - 领用：`SP-OUT-${timestamp}`
  - 退库：`SP-RET-${timestamp}`
  - 报废：`SP-SCR-${timestamp}`
- **唯一性验证**：
  - 如果手动提供出库单号，查询是否已存在
  - 单号重复时返回400错误和TPM_SPARE_015错误码
- **单号转换**：手动提供的单号会自动转换为大写

#### 步骤6: 创建出库记录
- **记录内容**：
  - 出库单号（transactionCode）
  - 备件ID（sparePartId）
  - 出库类型（transactionType：出库/退库/报废）
  - 出库数量（quantity）
  - 出库时间（transactionTime：当前时间）
  - 经手人ID（operatorId：当前登录用户ID）
  - 关联维护任务ID（relatedTaskId：可选）
  - 关联故障单ID（relatedFailureId：可选）
  - 用途说明（purpose：可选）
  - 备注（remark：可选）
  - 创建人/更新人（createdBy/updatedBy：当前登录用户ID）
- **数据保存**：写入SparePartTransaction表，生成UUID作为主键
- **事务保护**：在数据库事务中执行，确保与库存更新的原子性

#### 步骤7: 扣减库存数量
- **更新操作**：
  - 当前库存数量减少：`currentQuantity = currentQuantity - 出库数量`
  - 更新库存最后更新时间：`lastUpdatedAt = 当前时间`
- **事务保护**：与出库记录创建在同一事务中执行
- **失败回滚**：如果更新失败，事务自动回滚，出库记录不会保存

#### 步骤8: 查询更新后库存
- **查询内容**：
  - 重新查询备件库存记录（获取最新库存数据）
  - 关联查询备件基础信息（编码、名称、单位、库存配置）
- **计算字段**：
  - 可用库存：`availableQuantity = currentQuantity - reservedQuantity`
  - 低库存状态：`isLowStock = currentQuantity <= safetyStock`
- **数据完整性**：确保返回给用户的库存数据是最新、准确的

#### 步骤9: 返回响应结果
- **响应结构**：
  - `success`: true
  - `data`: 包含transaction（出库记录）和inventory（更新后库存）
  - `message`: "备件出库成功"
  - `meta`: 包含时间戳、请求ID、版本号
- **HTTP状态码**：201 Created
- **业务价值**：用户一次请求即可获得出库记录和最新库存状态，无需二次查询

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/spare-parts/:id/out-stock`

**功能描述**: 备件出库操作，支持领用、退库、报废等类型。系统会自动校验库存充足性，如果库存不足则无法出库。**领用时必须关联维护任务或故障单**。出库单号可以手动提供，也可以由系统自动生成（格式：SP-OUT/RET/SCR-时间戳）。出库成功后返回出库记录详情和更新后的库存信息。

**认证要求**: JWT Bearer Token，需要 `mdm.tpm.spare-part.manage` 权限

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号


**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 路径参数

| 参数名 | 类型   | 必填 | 限制     | 描述   | 示例                                   |
| ------ | ------ | ---- | -------- | ------ | -------------------------------------- |
| id     | string | 是   | UUID格式 | 备件ID | "a1b2c3d4-e5f6-7890-abcd-ef1234567890" |

### 请求参数

| 参数名           | 类型    | 必填 | 限制                       | 描述                                                                    | 示例                 |
| ---------------- | ------- | ---- | -------------------------- | ----------------------------------------------------------------------- | -------------------- |
| transactionCode  | string  | 否   | 1-100字符，自动转大写      | 出库单号，不提供则自动生成                                              | "SP-OUT-20240121001" |
| quantity         | integer | 是   | >=1，不超过当前库存        | 出库数量                                                                | 2                    |
| transactionType  | string  | 否   | 领用/退库/报废，默认"领用" | 出库类型                                                                | "领用"               |
| relatedTaskId    | string  | 否   | UUID格式，领用时可选       | 关联维护任务ID（领用时必须提供relatedTaskId或relatedFailureId至少一个） | "task-uuid-1234"     |
| relatedFailureId | string  | 否   | UUID格式，领用时可选       | 关联故障单ID（领用时必须提供relatedTaskId或relatedFailureId至少一个）   | "failure-uuid-1234"  |
| purpose          | string  | 否   | 无限制                     | 出库用途说明                                                            | "设备维护使用"       |
| remark           | string  | 否   | 无限制                     | 备注                                                                    | "紧急维修"           |

**⚠️ 重要说明**：
- 当`transactionType`为"领用"时，**必须**提供`relatedTaskId`或`relatedFailureId`至少一个，否则会返回错误码TPM_SPARE_017
- 当`transactionType`为"退库"或"报废"时，可以不提供关联信息
- 出库数量不能超过当前库存数量，否则会返回错误码TPM_SPARE_011

## 常见问题

### Q1: 领用时必须关联维护任务或故障单吗？

**A**: 是的，当`transactionType`为"领用"时，**必须**提供`relatedTaskId`或`relatedFailureId`至少一个。这是业务规则要求，目的是确保每一次备件领用都有明确的使用去向，便于后续追溯和成本核算。

如果都不提供，接口会返回400错误：

**解决方案**:
- 正常维护场景：提供`relatedTaskId`（维护任务ID）
- 故障抢修场景：提供`relatedFailureId`（故障单ID）
- 也可以同时提供两者（某些故障单可能关联到计划维护任务）

---

### Q2: 退库和报废需要关联任务或故障单吗？

**A**: 不需要。只有`transactionType`为"领用"时才强制要求关联维护任务或故障单。退库和报废操作可以不提供关联信息。
---

### Q3: 出库数量超过库存会怎么样？

**A**: 系统会自动校验库存充足性，如果出库数量超过当前库存数量，操作会失败并返回400错误：
**解决方案**:
1. 减少出库数量，不超过当前库存
2. 先进行入库操作，增加库存后再出库
3. 检查是否有预留库存（reservedQuantity），可用库存 = 当前库存 - 预留数量

---

### Q4: 出库单号如何生成？手动提供还是自动生成？

**A**: 支持两种方式，推荐使用自动生成。

**方式1: 自动生成（推荐）**
- 不提供`transactionCode`字段
- 系统根据出库类型自动生成：
  - 领用：`SP-OUT-${timestamp}`
  - 退库：`SP-RET-${timestamp}`
  - 报废：`SP-SCR-${timestamp}`

**方式2: 手动提供**
- 提供`transactionCode`字段（1-100字符）
- 系统会自动转换为大写
- 必须确保单号全局唯一，否则返回TPM_SPARE_015错误

系统会转换为：`MY-CUSTOM-OUT-20240121`

---

### Q5: 出库后如何查看库存变化？

**A**: 出库成功后，响应中已经包含了更新后的库存信息，无需二次查询。

响应结构包含两部分：
1. `transaction`: 出库记录详情
2. `inventory`: **更新后**的最新库存信息
---
### Q6: 如何判断出库后是否触发低库存预警？

**A**: 查看响应中的`inventory.isLowStock`字段。

**建议**:
- 前端可以根据`isLowStock`字段显示库存预警图标
- 当`isLowStock = true`时，提示采购人员及时补货
- 结合`availableQuantity`判断是否还能继续出库

---

### Q7: 退库操作为什么也使用出库接口？

**A**: 虽然退库实际上是增加库存，但从业务流程角度，它仍然是一种"出库"操作类型。

**设计理由**:
1. **统一管理**: 所有库存变动操作（领用、退库、报废）都记录在同一张出入库流水表中
2. **便于追溯**: 可以通过`transactionType`字段区分操作类型，完整追溯备件流转历史
3. **业务语义**: "退库"本质上是"从使用现场出库并返回仓库"的反向操作

**区分方式**:
- 通过`transactionType`字段区分：
  - `"领用"`: 减少库存
  - `"退库"`: **增加库存**（特殊的出库类型）
  - `"报废"`: 减少库存

**⚠️ 注意**: 如果业务上需要纯粹的"入库"操作（如采购入库），应使用入库接口：
```
POST /v1/mdm/tpm/spare-parts/:id/in-stock
```

### Q8: 出库时关联了错误的维护任务怎么办？

**A**: 出库记录一旦创建**不可修改**，这是为了保证数据的完整性和可追溯性。

**解决方案**:
1. **预防措施**: 出库前仔细确认维护任务ID或故障单ID
2. **错误处理**: 如果已经出库且关联错误，需要：
   - 联系系统管理员或技术支持
   - 在备注中说明实际情况
   - 必要时可以软删除错误记录（需要管理员权限）

**建议**:
- 前端在提交前显示确认弹窗，展示维护任务或故障单的详细信息
- 实现任务/故障单的搜索和选择功能，避免手动输入UUID

### Q10: 出库接口的性能如何？会不会很慢？

**A**: 出库接口使用了事务保护和多表关联查询，但性能经过优化，通常在100-300ms内完成。

**性能优化措施**:
1. **数据库索引**: 在关键字段（sparePartId、transactionCode等）建立了索引
2. **事务范围控制**: 事务仅包含必要的写操作，查询操作在事务外执行
3. **按需关联查询**: 响应中的关联数据（备件信息）仅查询必要字段

**性能建议**:
- 避免在短时间内大量并发出库（如有批量需求，可联系后端提供批量接口）
- 合理设置前端请求超时时间（建议30秒）
- 监控`isLowStock`状态，避免库存不足导致的频繁失败重试

### 库存计算公式

| 计算字段          | 计算公式                           | 说明                           |
| ----------------- | ---------------------------------- | ------------------------------ |
| availableQuantity | currentQuantity - reservedQuantity | 可用库存 = 当前库存 - 预留数量 |
| isLowStock        | currentQuantity <= safetyStock     | 当前库存是否低于或等于安全库存 |

**⚠️ 注意**:
- `availableQuantity`和`isLowStock`是服务层计算字段，不存储在数据库中
- 出库时仅校验`currentQuantity`，不考虑`reservedQuantity`
- 低库存预警基于`currentQuantity`和`safetyStock`比较

### 出库操作状态转换

虽然出库操作本身没有状态流转（一次性操作），但会影响库存状态：

```
库存正常 (currentQuantity > safetyStock)
  │
  │ 出库操作
  ▼
库存充足判断 (currentQuantity >= 出库数量)
  │
  ├─ YES → 执行出库 → 扣减库存
  │                    │
  │                    ▼
  │              判断库存状态
  │                    │
  │                    ├─ currentQuantity > safetyStock → 库存正常
  │                    └─ currentQuantity <= safetyStock → 低库存预警
  │
  └─ NO → 返回库存不足错误 (TPM_SPARE_011)
```
