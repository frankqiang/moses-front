## 功能概述

### 所有功能

获取维护工作量统计（Maintenance Workload Statistics）是设备TPM管理模块中TPM统计分析子模块的核心接口之一，用于统计维护人员的工作量分布，支持按人员、设备类型、维护类型等维度分组统计，以支持维护资源优化配置、工作负荷均衡评估、绩效考核分析等业务场景。

该接口通过多维度的工作量分析，帮助管理者全面了解维护人员的工作负荷情况、任务完成质量、工时分布趋势，实现维护资源的科学配置和高效利用，从而提升整体维护管理水平。

### 关键特性

- ✅ **多维度分组统计**：支持按维护人员（assignee）、设备类型（equipmentType）、维护类型（maintenanceType）三种维度进行分组统计，满足不同管理视角的分析需求
- ✅ **灵活时间范围**：支持自定义时间范围统计，可以按日、周、月、年等不同时间粒度查看工作量趋势变化
- ✅ **全面工作量指标**：提供总任务数、已完成任务数、总工时、平均工时、完成率等多项核心指标，全方位评估工作量
- ✅ **趋势分析能力**：按时间段展示工作量变化趋势，帮助识别工作量波动规律，支持工作计划优化
- ✅ **精确筛选功能**：支持按维护人员ID、设备类型筛选，快速定位特定对象的工作量数据
- ✅ **统计汇总展示**：提供整体工作量汇总信息，包括总任务数、总工时、活跃人员数、整体完成率等关键指标

---

### 使用前提

- ✅ **权限要求**：用户需具备 `mdm.tpm.statistics.view` 权限，能够查看TPM统计数据
- ✅ **认证要求**：请求必须携带有效的JWT Bearer Token进行身份认证
- ✅ **数据要求**：系统中需要有维护任务记录、工时记录等历史数据，并且维护任务已正确分配给维护人员
- ✅ **时间范围**：必须提供有效的开始日期和结束日期，且结束日期不能早于开始日期

### 不适用场景

- ❌ **实时工时追踪**：本接口提供的是统计分析数据，不适用于实时工时记录和追踪，请使用维护任务管理接口
- ❌ **详细任务清单**：如需查看具体任务明细和执行过程，请使用维护任务列表接口，本接口仅提供统计汇总

### 详细步骤说明

#### 步骤1: 接收查询请求与权限验证

**功能描述**：
- 接收客户端发送的GET请求
- 验证JWT Token的有效性
- 检查用户是否具备 `mdm.tpm.statistics.view` 权限

**校验规则**：
- Token必须有效且未过期
- 用户必须拥有查看TPM统计数据的权限

**异常处理**：
- Token无效或过期：返回401 UNAUTHORIZED
- 权限不足：返回403 FORBIDDEN

#### 步骤2: 参数验证

**功能描述**：
- 验证必填参数和可选参数的格式、取值范围
- 设置默认值

**参数验证规则**：
- `startDate`：必填，必须是有效的ISO日期格式（YYYY-MM-DD）
- `endDate`：必填，必须是有效的ISO日期格式，且不能早于startDate
- `assigneeId`：如提供必须是有效的UUID格式
- `equipmentType`：如提供必须是枚举值之一（退火炉/行车/自动料车/备料台）
- `timePeriod`：如提供必须是枚举值之一（日/周/月/年），默认"月"
- `groupBy`：如提供必须是枚举值之一（assignee/equipmentType/maintenanceType），默认"assignee"

**日期范围校验**：
- 检查endDate是否大于等于startDate
- 建议时间范围不超过1年，避免查询性能问题

**异常处理**：
- 参数格式错误：返回400 VALIDATION_ERROR
- 参数取值超出范围：返回400 VALIDATION_ERROR
- 缺少必填参数：返回400 VALIDATION_ERROR

#### 步骤3: 查询维护任务

**功能描述**：
- 根据时间范围和筛选条件查询维护任务记录
- 关联查询维护人员、设备、工时等相关信息

**查询逻辑**：
- 查询指定时间范围内的所有维护任务
- 如指定assigneeId，则只查询该维护人员的任务
- 如指定equipmentType，则只查询该类型设备的维护任务
- 包含任务的工时记录、完成状态等信息

**数据库操作**：
```sql
SELECT
  mt.*,
  u.name as assigneeName,
  e.type as equipmentType,
  mt.workHours
FROM maintenance_tasks mt
LEFT JOIN users u ON mt.assigneeId = u.id
LEFT JOIN equipment e ON mt.equipmentId = e.id
WHERE
  mt.plannedStartDate >= :startDate
  AND mt.plannedStartDate <= :endDate
  AND (mt.assigneeId = :assigneeId OR :assigneeId IS NULL)
  AND (e.type = :equipmentType OR :equipmentType IS NULL)
ORDER BY mt.plannedStartDate
```

#### 步骤4: 开启事务

**功能描述**：
- 开启数据库事务确保数据一致性
- 为后续的多表查询和统计计算提供事务保护

**事务特性**：
- 隔离级别：READ COMMITTED
- 事务范围：包括所有统计查询和计算操作

#### 步骤5: 计算整体汇总

**功能描述**：
- 基于查询到的维护任务数据，计算整体统计指标

**汇总指标计算**：

##### 5.1 总任务数（totalTasks）
- 统计指定时间范围内的维护任务总数
- 包括所有状态的任务（待执行、执行中、已完成、已延期、已取消）

##### 5.2 已完成任务数（completedTasks）
- 统计状态为"已完成"的维护任务数量
- 用于计算任务完成率

##### 5.3 总工时（totalWorkHours）
- 累加所有维护任务的实际工时
- 对于未完成的任务，使用计划工时估算
- 精确到0.1小时

##### 5.4 活跃维护人员数（activeAssignees）
- 统计在时间范围内至少承担1个维护任务的人员数量
- 去重统计不同的维护人员

##### 5.5 完成率（completionRate）
- 计算公式：completionRate = (completedTasks / totalTasks) × 100%
- 精确到小数点后2位
- 以百分比形式展示（不带%符号）

**计算示例**：
```javascript
// 示例数据
totalTasks = 150
completedTasks = 135
totalWorkHours = 720.5
activeAssignees = 8

// 完成率计算
completionRate = (135 / 150) × 100 = 90.00%
```

#### 步骤6: 按分组维度统计

**功能描述**：
- 根据groupBy参数指定的维度对数据进行分组统计

**分组维度说明**：

##### 6.1 按维护人员分组（groupBy=assignee）
- 按维护人员（assigneeId）分组
- 统计每个维护人员的工作量指标
- 返回字段包含：assigneeId、assigneeName

##### 6.2 按设备类型分组（groupBy=equipmentType）
- 按设备类型分组
- 统计每种设备类型的维护工作量
- 返回字段包含：equipmentType

##### 6.3 按维护类型分组（groupBy=maintenanceType）
- 按维护类型分组（预防性维护、纠正性维护、改善性维护等）
- 统计不同维护类型的工作量分布
- 返回字段包含：maintenanceType

**每个分组的统计指标**：
- totalTasks：该分组的总任务数
- completedTasks：该分组的已完成任务数
- totalWorkHours：该分组的总工时
- avgWorkHours：该分组的平均单任务工时（totalWorkHours / totalTasks）
- completionRate：该分组的任务完成率

**排序规则**：
- 默认按totalWorkHours降序排列
- 工时相同时按totalTasks降序排列

#### 步骤7: 生成趋势数据

**功能描述**：
- 根据timePeriod参数指定的时间粒度，生成工作量趋势数据

**时间粒度处理**：

##### 7.1 按日统计（timePeriod=日）
- 按自然日分组
- period为当天0点时间戳
- 适用于短期（1周-1月）工作量分析

##### 7.2 按周统计（timePeriod=周）
- 按自然周分组（周一到周日）
- period为该周周一0点时间戳
- 适用于中期（1月-3月）工作量分析

##### 7.3 按月统计（timePeriod=月）
- 按自然月分组
- period为当月1日0点时间戳
- 适用于长期（3月-1年）工作量分析
- 默认时间粒度

##### 7.4 按年统计（timePeriod=年）
- 按自然年分组
- period为当年1月1日0点时间戳
- 适用于多年度工作量对比

**趋势数据指标**：
- period：时间段起始时间（ISO 8601格式）
- totalTasks：该时间段的总任务数
- completedTasks：该时间段的已完成任务数
- totalWorkHours：该时间段的总工时

**生成逻辑**：
```javascript
// 伪代码示例
趋势数据 = []
当前时间点 = startDate

while (当前时间点 <= endDate) {
  时间段数据 = {
    period: 当前时间点,
    totalTasks: 统计该时间段的任务数,
    completedTasks: 统计该时间段的已完成任务数,
    totalWorkHours: 统计该时间段的总工时
  }
  趋势数据.push(时间段数据)
  当前时间点 += 时间粒度
}
```

#### 步骤8: 数据聚合和排序

**功能描述**：
- 对分组统计结果和趋势数据进行最终聚合
- 按照业务规则排序

**聚合操作**：
- 确保所有分组的统计指标格式一致
- 数值精度处理（工时保留1位小数，完成率保留2位小数）
- 处理空值和边界情况

**排序规则**：
- 分组统计：按totalWorkHours降序
- 趋势数据：按period升序（时间正序）

#### 步骤9: 提交事务

**功能描述**：
- 提交数据库事务
- 释放数据库连接和资源

**事务提交条件**：
- 所有查询和计算完成
- 无异常发生

#### 步骤10: 返回统计结果

**功能描述**：
- 将统计汇总、分组统计和趋势数据封装为统一响应格式
- 返回给客户端

**响应内容**：
- summary：整体工作量统计汇总
- workloadByGroup：按指定维度分组的工作量统计
- workloadTrend：按时间粒度的工作量趋势数据

## 接口文档

### 基本信息

**接口路径**: `GET /v1/mdm/tpm/statistics/maintenance-workload`

**功能描述**: 统计指定时间段内维护人员的工作量分布，支持按人员、设备类型、维护类型等维度分组统计，提供工作量趋势和分组统计，帮助管理者了解维护人员的工作负荷，优化资源分配。

**认证要求**: JWT Bearer Token，需要 `mdm.tpm.statistics.view` 权限

### 查询参数

| 参数名        | 类型   | 必填 | 限制                                         | 描述                       | 默认值   | 示例                                 |
| ------------- | ------ | ---- | -------------------------------------------- | -------------------------- | -------- | ------------------------------------ |
| startDate     | string | 是   | ISO日期格式                                  | 开始日期                   | 无       | 2024-01-01                           |
| endDate       | string | 是   | ISO日期格式，不能早于开始日期                | 结束日期                   | 无       | 2024-03-31                           |
| assigneeId    | string | 否   | UUID格式                                     | 维护人员ID筛选             | null     | 123e4567-e89b-12d3-a456-426614174000 |
| equipmentType | string | 否   | 枚举：退火炉/行车/自动料车/备料台            | 设备类型筛选               | null     | 退火炉                               |
| timePeriod    | string | 否   | 枚举：日/周/月/年                            | 时间粒度，用于趋势数据分组 | 月       | 月                                   |
| groupBy       | string | 否   | 枚举：assignee/equipmentType/maintenanceType | 分组字段                   | assignee | assignee                             |

**查询参数说明**：

- **startDate**：统计的开始日期，必填，用于界定统计时间范围的起点
- **endDate**：统计的结束日期，必填，用于界定统计时间范围的终点
- **assigneeId**：指定维护人员ID时，只统计该人员的工作量；不指定时统计所有人员
- **equipmentType**：按设备类型筛选，只统计该类型设备的维护工作量
- **timePeriod**：时间粒度，用于趋势数据的时间分组
  - `日`：按天统计，适用于短期分析（1周-1月）
  - `周`：按周统计，适用于中期分析（1月-3月）
  - `月`：按月统计，适用于长期分析（3月-1年），默认值
  - `年`：按年统计，适用于多年度对比
- **groupBy**：分组维度，决定workloadByGroup数据的分组方式
  - `assignee`：按维护人员分组，默认值
  - `equipmentType`：按设备类型分组
  - `maintenanceType`：按维护类型分组

## 常见问题

### Q1: startDate和endDate参数应该如何设置？

**A**: 时间范围设置建议：

| 分析场景       | 建议时间范围 | 推荐timePeriod | 示例                                     |
| -------------- | ------------ | -------------- | ---------------------------------------- |
| 短期工作量分析 | 1周-1月      | 日             | startDate=2024-10-01, endDate=2024-10-31 |
| 中期工作量分析 | 1月-3月      | 周             | startDate=2024-07-01, endDate=2024-09-30 |
| 长期工作量分析 | 3月-1年      | 月             | startDate=2024-01-01, endDate=2024-12-31 |
| 多年度对比分析 | 1年以上      | 年             | startDate=2023-01-01, endDate=2024-12-31 |

**注意事项**：
- 时间范围不宜过长（建议不超过1年），避免影响查询性能
- endDate必须大于等于startDate
- 日期格式必须为ISO标准格式（YYYY-MM-DD）

### Q2: groupBy参数应该如何选择？

**A**: 根据业务场景选择合适的分组方式：

| 业务场景             | 推荐groupBy     | 说明                               |
| -------------------- | --------------- | ---------------------------------- |
| 维护人员绩效考核     | assignee        | 查看每个维护人员的工作量和完成情况 |
| 维护资源配置         | assignee        | 识别工作负荷过重或过轻的人员       |
| 设备类型维护成本分析 | equipmentType   | 了解不同设备类型的维护工作量投入   |
| 维护预算编制         | equipmentType   | 为不同设备类型编制维护预算         |
| TPM策略评估          | maintenanceType | 分析预防性维护和纠正性维护的比例   |
| 维护类型资源优化     | maintenanceType | 评估不同维护类型的资源需求         |

**提示**：
- 不同的groupBy会返回不同的workloadByGroup字段结构
- 可以结合多次调用，使用不同groupBy进行多维度分析

### Q3: 如何理解和使用workloadTrend趋势数据？

**A**: workloadTrend提供按时间段的工作量趋势，用于识别工作量变化规律：

**字段含义**：
- `period`：时间段起始时间
- `totalTasks`：该时间段的总任务数
- `completedTasks`：该时间段的已完成任务数
- `totalWorkHours`：该时间段的总工时

**使用建议**：
1. **识别波动规律**：通过趋势数据识别工作量的周期性波动
2. **预测未来需求**：基于历史趋势预测未来工作量
3. **对比同比环比**：对比不同时期的工作量变化
4. **评估计划合理性**：工作量平稳表示计划合理，波动大表示需要优化

**前端展示**：
- 折线图：展示工作量的时间趋势
- 面积图：展示累计工作量的增长趋势
- 柱状图：对比不同时间段的工作量

### Q4: avgWorkHours（平均工时）指标如何解读？

**A**: avgWorkHours表示平均单任务工时，计算公式为：

```
avgWorkHours = totalWorkHours / totalTasks
```

**解读建议**：

| avgWorkHours范围 | 工作效率评价 | 可能原因                   | 改善建议                   |
| ---------------- | ------------ | -------------------------- | -------------------------- |
| < 3小时          | 高效         | 任务简单或人员经验丰富     | 维持现状，总结最佳实践     |
| 3-6小时          | 正常         | 任务复杂度适中，符合预期   | 继续保持                   |
| 6-10小时         | 偏慢         | 任务复杂或经验不足         | 提供培训，优化流程         |
| > 10小时         | 低效         | 任务极其复杂或存在流程问题 | 深入分析原因，制定改善计划 |

**影响因素**：
- 任务复杂度
- 人员技能水平
- 备件可得性
- 维护流程效率
- 设备状况

### Q5: completionRate（完成率）较低应该如何改善？

**A**: 完成率低可能有多种原因，需要分析具体情况：

**常见原因及改善措施**：

| 可能原因       | 分析方法                     | 改善措施                           |
| -------------- | ---------------------------- | ---------------------------------- |
| 任务分配过多   | 对比各人员的totalTasks       | 优化任务分配，实现工作量均衡       |
| 任务复杂度过高 | 查看avgWorkHours是否过高     | 分解复杂任务，提供技术支持         |
| 备件供应不及时 | 分析延期任务的原因           | 优化备件库存管理，建立紧急采购机制 |
| 计划不合理     | 查看timePeriod的峰谷分布     | 合理安排任务时间，避免扎堆         |
| 人员能力不足   | 对比不同人员的completionRate | 提供培训，技能提升                 |
| 流程效率低     | 分析任务执行周期             | 优化维护流程，减少等待时间         |

**目标设定**：
- 优秀水平：completionRate >= 95%
- 良好水平：completionRate >= 90%
- 需要改善：completionRate < 90%

**配合使用建议**：

| 配合接口           | 分析目的                       | 业务价值                   |
| ------------------ | ------------------------------ | -------------------------- |
| 获取故障汇总统计   | 分析故障与维护工作量的关系     | 评估预防性维护的有效性     |
| 获取MTTR趋势分析   | 对比工作量与修复时间的关系     | 识别影响修复效率的因素     |
| 获取维护计划执行率 | 对比计划与实际工作量           | 评估计划的准确性和可执行性 |
| 获取备件消耗分析   | 分析备件消耗与维护工作量的关系 | 优化备件库存和维护资源配置 |
| 获取设备健康度评分 | 关联设备健康与维护投入         | 评估维护投入的有效性和ROI  |

**综合分析示例**：
1. 通过工作量统计发现某人员工作量过高
2. 结合MTTR分析发现该人员修复时间较长
3. 再结合故障统计发现该人员负责的设备故障率较高
4. 最后查看设备健康度评分，发现该人员负责的设备健康度较低
5. **结论**：需要增加对这些设备的预防性维护投入，减少故障维护工作量

### Q7: 接口返回的工作量数据是实时的吗？

**A**: 工作量统计数据不是严格意义上的实时数据，但具有较高的时效性：

**数据时效性说明**：
- **数据来源**：基于维护任务表和工时记录表的历史数据
- **统计范围**：包括指定时间范围内创建或计划的所有维护任务
- **更新频率**：随着维护任务状态更新而实时更新
- **延迟情况**：如果维护人员未及时更新任务状态或记录工时，数据会有延迟

**建议**：
- 对于管理驾驶舱展示，建议每5-10分钟刷新一次
- 对于报表分析，建议使用已完成周期的历史数据
- 确保维护人员及时更新任务状态和工时记录

### Q8: 如何处理跨年度的工作量统计？

**操作建议**：

```bash
  &endDate=2024-12-31

  &groupBy=assignee
```

**方式2：分年度查询再合并（推荐用于多年度对比）**

```bash
# 查询2023年
GET /v1/mdm/tpm/statistics/maintenance-workload
  ?startDate=2023-01-01
  &endDate=2023-12-31
  &timePeriod=月
  &groupBy=assignee

# 查询2024年
GET /v1/mdm/tpm/statistics/maintenance-workload
  ?startDate=2024-01-01
  &endDate=2024-12-31
  &timePeriod=月
  &groupBy=assignee
```

**数据解读注意事项**：
- 注意人员变动影响（如离职、入职、调岗）
- 考虑设备数量变化的影响
- 考虑业务量变化的影响
- 使用人均工作量指标进行同比对比更合理

### 工作量指标计算公式

| 指标名称        | 计算公式                            | 单位 | 精度说明    |
| --------------- | ----------------------------------- | ---- | ----------- |
| totalTasks      | COUNT(维护任务)                     | 个   | 整数        |
| completedTasks  | COUNT(维护任务 WHERE 状态='已完成') | 个   | 整数        |
| totalWorkHours  | SUM(维护任务.workHours)             | 小时 | 保留1位小数 |

| completionRate  | (completedTasks / totalTasks) × 100 | %    | 保留2位小数 |
| activeAssignees | COUNT(DISTINCT 维护任务.assigneeId) | 人   | 整数        |

### 技术参考

#### 数据统计范围

- **任务统计**：包括指定时间范围内计划开始日期在范围内的所有维护任务
- **工时统计**：已完成任务使用实际工时，未完成任务使用计划工时
- **人员统计**：按维护任务的assigneeId进行统计
- **设备统计**：按维护任务关联的设备类型进行统计
- **类型统计**：按维护任务的类型进行统计

#### 性能指标

- **接口响应时间**：平均200-500ms（取决于时间范围和数据量）
- **并发支持**：支持30 QPS
- **数据量限制**：建议时间范围不超过1年
- **查询超时**：15秒

#### 数据精度

- **工时数据**：保留1位小数（如220.5）
- **完成率**：保留2位小数（如93.33）
- **平均工时**：保留1位小数（如5.2）

#### 缓存策略

- **数据时效性**：基于实时数据库查询，无缓存
- **建议刷新频率**：
  - 管理驾驶舱：每5-10分钟刷新
  - 报表分析：使用历史数据无需频繁刷新
  - 绩效考核：按考核周期查询即可
