## 功能概述

### 所有功能

获取故障汇总统计（Failure Summary Statistics）是TPM统计分析模块中的核心功能之一,用于多维度统计分析设备故障情况,以支持故障预防、问题设备识别、维修效率评估等业务场景。该接口提供按时间段、按故障类型、按设备三个维度的全面统计分析,帮助管理者识别故障模式和高风险设备,为故障预防和改进提供数据支持。

### 关键特性

- ✅ **多维度统计**：提供时间维度、类型维度、设备维度三个角度的故障统计分析
- ✅ **故障等级分布**：按时间段统计I级严重、II级重大、III级一般、IV级轻微故障的数量分布
- ✅ **类型分析**：统计机械、电气、液压、控制、其他五种故障类型的发生频率
- ✅ **问题设备识别**：自动识别故障频发的TOP 10设备,并计算各设备的平均修复时间
- ✅ **灵活筛选**：支持按设备ID、设备类型、故障类型进行精准筛选
- ✅ **时间粒度可调**：支持按日/周/月/年四种时间粒度统计,适应不同分析场景

---

### 使用前提

- ✅ 用户必须具有`mdm.tpm.statistics.view`权限才能访问接口
- ✅ 必须提供有效的开始日期和结束日期,且结束日期不能早于开始日期
- ✅ 系统中已有设备故障记录数据
- ✅ 请求需要携带有效的JWT Bearer Token进行身份认证

### 不适用场景

- ❌ 实时故障监控预警（本接口为统计分析,非实时监控）
- ❌ 单个故障详情查询（应使用故障详情查询接口）
- ❌ 故障记录的创建、更新、删除操作（本接口仅提供只读统计）
- ❌ 超过1年的大跨度查询（建议分批查询以确保性能）

### 详细步骤说明

#### 步骤1: 接收查询请求
- 接收客户端发起的GET请求
- 提取查询参数：startDate、endDate、timePeriod、equipmentId、equipmentType、failureType
- 记录操作日志,包含操作人ID和查询参数

#### 步骤2: 参数验证
**日期验证**：
- 验证startDate和endDate为必填参数
- 检查日期格式是否符合ISO 8601标准（YYYY-MM-DD）
- 校验endDate不能早于startDate

**枚举值验证**：
- equipmentType必须在[退火炉, 行车, 自动料车, 备料台]范围内
- failureType必须在[机械, 电气, 液压, 控制, 其他]范围内
- timePeriod必须在[日, 周, 月, 年]范围内,默认值为"月"

**UUID格式验证**：
- 如果提供equipmentId,验证其为有效的UUIDv4格式

#### 步骤3: 构建查询条件
**时间范围筛选**：
- 将日期字符串转换为Date对象
- 构建failureTime字段的BETWEEN条件
- 示例：`failureTime BETWEEN '2024-01-01' AND '2024-03-31'`

**设备筛选条件**：
- 如果提供equipmentId,直接筛选该设备
- 如果提供equipmentType,通过关联Equipment表筛选设备类型
- 两个条件可独立或组合使用

**故障类型筛选**：
- 如果提供failureType,添加故障类型筛选条件
- 示例：`failureType = '电气'`

**软删除过滤**：
- 所有查询自动添加`isDeleted = false`条件

#### 步骤4: 执行数据库查询 - 按时间段统计
**查询目标**：统计每个时间段内的故障数量和各等级分布

**SQL逻辑**：
```sql
SELECT
  DATE_TRUNC(timePeriod, failure_time) AS period,
  COUNT(*) AS failureCount,
  COUNT(CASE WHEN failure_level = 'I级-严重' THEN 1 END) AS severeCounts,
  COUNT(CASE WHEN failure_level = 'II级-重大' THEN 1 END) AS majorCounts,
  COUNT(CASE WHEN failure_level = 'III级-一般' THEN 1 END) AS normalCounts,
  COUNT(CASE WHEN failure_level = 'IV级-轻微' THEN 1 END) AS minorCounts
FROM equipment_failures
WHERE [筛选条件]
GROUP BY DATE_TRUNC(timePeriod, failure_time)
ORDER BY period ASC
```

**时间分组规则**：
- 日粒度：`DATE_TRUNC('day', failure_time)` - 按天分组
- 周粒度：`DATE_TRUNC('week', failure_time)` - 按周一分组
- 月粒度：`DATE_TRUNC('month', failure_time)` - 按月1号分组
- 年粒度：`DATE_TRUNC('year', failure_time)` - 按年1月1号分组

**数据处理**：
- 将查询结果转换为整数类型
- 按时间升序排列

#### 步骤5: 执行数据库查询 - 按故障类型统计
**查询目标**：统计每种故障类型的发生次数

**SQL逻辑**：
```sql
SELECT
  failure_type AS failureType,
  COUNT(*) AS failureCount
FROM equipment_failures
WHERE [筛选条件]
GROUP BY failure_type
ORDER BY COUNT(*) DESC
```

**数据处理**：
- 按故障数量降序排列
- 将计数结果转换为整数类型
- 展示所有存在的故障类型（不限制数量）

#### 步骤6: 执行数据库查询 - 按设备统计（TOP 10）
**查询目标**：识别故障频发的设备并计算平均修复时间

**SQL逻辑**：
```sql
SELECT
  equipment.equipment_code AS equipmentCode,
  equipment.name AS equipmentName,
  COUNT(*) AS failureCount,
  AVG(EXTRACT(EPOCH FROM (repair_completion_time - repair_start_time)) / 3600) AS avgMTTR
FROM equipment_failures
INNER JOIN equipment ON equipment_failures.equipment_id = equipment.id
WHERE [筛选条件]
GROUP BY equipment.equipment_code, equipment.name, equipment.id
ORDER BY COUNT(*) DESC
LIMIT 10
```

**MTTR计算规则**：
- MTTR（平均修复时间）= (修复完成时间 - 修复开始时间) / 3600秒
- 转换为小时单位,保留2位小数
- 如果没有修复时间记录,则显示"0.00"

**数据处理**：
- 仅返回前10个故障最多的设备
- 按故障数量降序排列
- 显示设备编码、设备名称、故障次数、平均MTTR

#### 步骤7: 执行数据库查询 - 总体统计
**查询目标**：计算统计期内的总体故障情况

**SQL逻辑**：
```sql
SELECT
  COUNT(*) AS totalFailures,
  COUNT(CASE WHEN failure_level = 'I级-严重' THEN 1 END) AS severeFailures
FROM equipment_failures
WHERE [筛选条件]
```

**数据处理**：
- 统计故障总数
- 统计I级严重故障数量（用于风险评估）
- 转换为整数类型

#### 步骤8: 数据格式化处理
**数值类型转换**：
- 所有计数字段使用`parseInt()`转换为整数
- MTTR使用`parseFloat().toFixed(2)`保留2位小数

**响应结构组装**：
```javascript
{
  summary: {
    totalFailures: 整数,
    severeFailures: 整数,
    timePeriod: 字符串
  },
  timeStatistics: [时间段统计数组],
  typeStatistics: [类型统计数组],
  equipmentStatistics: [设备统计数组]
}
```

**空值处理**：
- 如果没有数据,返回0或空数组
- 避免null值返回,确保数据类型一致

#### 步骤9: 记录日志并返回响应
**成功日志**：
- 记录查询成功信息
- 包含筛选条件和结果数量
- 日志级别：INFO

**错误处理**：
- 捕获数据库查询异常
- 记录错误堆栈信息
- 抛出ApiError,错误码STATISTICS_001
- 日志级别：ERROR

**返回响应**：
- 使用统一响应格式sendSuccess
- 包含success、data、message、meta字段
- HTTP状态码200

## 接口文档

### 基本信息

**接口路径**: `GET /v1/mdm/tpm/statistics/failure-summary`

**功能描述**: 统计指定时间段内的故障汇总信息,支持按设备、故障类型、时间粒度筛选。该接口提供多维度的故障数据分析,包括按时间段、按故障类型、按设备的统计,帮助识别故障模式和高风险设备。

**认证要求**: JWT Bearer Token认证,需要 `mdm.tpm.statistics.view` 权限

## 常见问题

### Q1: 为什么设备统计只返回TOP 10,不能返回所有设备?

**回答**: 设计限制为TOP 10是基于以下考虑：
1. **性能优化**: 避免返回过多数据影响接口性能
2. **关注重点**: 故障最多的10个设备已经覆盖了主要问题
3. **用户体验**: 过多数据不利于快速识别重点

**解决方案**:
- 如需查看特定设备,使用equipmentId参数精准查询
- 如需完整设备列表,可使用设备健康度评分接口

### Q2: timeStatistics中某些时间段没有数据,是否正常?

**回答**: 完全正常。如果某个时间段内没有故障记录,该时间段不会出现在结果中。这是预期行为,表示该时段没有故障发生。

**注意事项**:
- 前端展示时需要处理时间段不连续的情况
- 可以用0填充缺失的时间段,或在图表中显示空白
- 不要将数据缺失理解为接口错误

### Q3: avgMTTR为什么是字符串类型而不是数字类型?

**回答**: 为了保持精度和格式一致性：
1. **精度控制**: 字符串格式固定保留2位小数,如"8.50"
2. **避免精度丢失**: 数字类型可能导致精度问题,如8.50变为8.5
3. **格式统一**: 前端展示时格式一致,便于对齐显示

**使用建议**:
- 前端直接展示字符串值即可
- 如需数值计算,使用`parseFloat(avgMTTR)`转换

### Q4: 查询1年以上的数据会有性能问题吗?

**回答**: 查询时间跨度过大可能导致性能问题：
1. **数据量大**: 1年以上数据量可能很大,查询耗时长
2. **内存占用**: 大量数据会占用较多内存
3. **超时风险**: 可能触发接口超时

**建议方案**:
- 单次查询不超过1年
- 长期趋势分析使用年度粒度（timePeriod="年"）
- 大数据量查询考虑分批次进行
- 历史数据分析可以生成离线报告

### Q5: 如何理解故障等级的分布?

**回答**: 故障等级反映故障的严重程度：
- **I级-严重**: 导致设备完全停机,严重影响生产,需立即处理
- **II级-重大**: 显著影响设备性能,需要尽快处理
- **III级-一般**: 影响设备正常运行,但可暂缓处理
- **IV级-轻微**: 对生产影响较小,可计划性处理

**分析建议**:
- 重点关注I级和II级故障的数量和趋势
- 如果轻微故障转变为严重故障,说明预防措施不足
- 严重故障比例过高,需要加强预防性维护

### Q6: equipmentType和equipmentId能同时使用吗?

**回答**: 可以同时使用,但通常没有必要：
- **同时使用**: 接口支持同时传入两个参数,会同时生效
- **实际意义**: 因为equipmentId已经唯一确定设备,equipmentType会被自动满足
- **建议用法**:
  - 查询单个设备时,只传equipmentId
  - 查询某类设备时,只传equipmentType
  - 通常不需要同时传入

### Q7: 返回的故障数据是实时的还是有延迟?

**回答**: 数据是实时查询的,没有缓存延迟：
1. **实时计算**: 每次请求都实时从数据库查询计算
2. **最新数据**: 反映的是请求时刻的最新故障记录
3. **无延迟**: 故障记录一旦创建,立即可以在统计中体现

**注意事项**:
- 高频调用会增加数据库压力
- 报表类应用建议适当缓存结果
- 实时监控可以定期（如每5分钟）调用一次

### Q8: 为什么有些设备的avgMTTR是"0.00"?

**可能原因**:
1. **未记录修复时间**: 该设备的故障记录中没有repairStartTime或repairCompletionTime
2. **故障未完成修复**: 故障还在处理中,还没有完成修复
3. **数据录入问题**: 维护人员未及时记录修复时间

**解决方案**:
- 加强故障记录的完整性管理
- 培训维护人员及时记录修复时间
- 在业务流程中强制要求填写修复时间
- 对于"0.00"的情况,前端可以显示"未记录"或"-"

### 性能优化建议

1. **索引优化**:
   - equipmentId字段应有索引
   - failureTime字段应有索引
   - failureType字段可考虑索引
   - 组合索引：(equipmentId, failureTime, isDeleted)

   - 避免查询超过1年的数据
   - 合理使用equipmentType筛选减少数据量
   - 时间范围尽量精确,避免无效数据扫描

   - 历史数据（上月及以前）可以缓存30分钟
   - 当月数据建议实时查询或短期缓存（5分钟）
   - 报表类应用可以使用离线生成策略

4. **并发控制**:
   - 避免同一用户高频调用（建议间隔 ≥ 30秒）
   - 大批量查询建议在低峰期进行
   - 考虑使用队列机制处理大量统计请求
