## 功能概述

### 所有功能

任务接单（Accept Maintenance Task）是设备TPM管理模块中的核心执行操作之一，用于执行人员接收派发给自己的维护任务，或自主接单未派工的任务，以支持灵活的维护任务分配和执行的业务场景。

该接口允许维护人员主动承接维护任务，标志着任务进入"已接单"状态（由系统自动关联执行人）。任务接单是任务生命周期中的重要环节，连接了任务分配和任务执行两个阶段。

### 关键特性

- ✅ **灵活的接单方式**：支持派工后接单和自主接单两种方式，满足不同的组织管理模式
- ✅ **自动身份关联**：接单时自动将当前登录用户与任务关联，无需手动指定执行人
- ✅ **状态自动迁移**：接单成功后，任务状态自动从"待执行"变为"待执行"（标记已接单）
- ✅ **权限严格控制**：只能接收派工给自己的任务，或接单未派工的任务，防止权限混乱
- ✅ **完整的审计跟踪**：自动记录接单时间、接单人等关键审计信息
- ✅ **实时数据更新**：接单成功后立即返回更新后的完整任务信息

## 业务场景

### 适用场景

1. **派工后接单场景**
   - 管理员已将任务派工给指定的维护人员
   - 维护人员登录系统后，查看"我的任务"列表
   - 维护人员通过任务接单接口确认接收任务
   - 例如：管理员派工给张三的"退火炉日常维护"任务，张三登录后点击接单按钮

2. **自主接单场景**
   - 管理员创建了任务但未指定执行人员（permitOpen = true）
   - 任何具有执行权限的维护人员都可以自主接单
   - 有利于提高任务响应速度和人员的主动性
   - 例如：系统发布了"应急抢修"任务，多个维护人员可以竞争接单

3. **多人轮转维护场景**
   - 一个维护任务涉及多个维护阶段
   - 第一阶段的人员完成后将任务转交给下一个人员
   - 下一个人员通过接单接口接收任务

4. **跨班次交接场景**
   - 前一班班长为下一班分配维护任务
   - 下一班的维护人员接班后通过接单接口确认任务

### 使用前提

- ✅ 维护任务必须处于"待执行"状态
- ✅ 如果任务已派工给其他人，只有被派工的人员才能接单
- ✅ 如果任务未派工，任何具有执行权限的人员都可以接单
- ✅ 操作人员必须具有 `mdm.tpm.maintenance-task.execute` 权限

### 不适用场景

- ❌ 任务已处于执行中、已完成、已取消等终止状态时无法接单
- ❌ 任务已派工给其他人，当前用户不是派工对象时无法接单
- ❌ 当前用户没有执行维护任务的权限时无法接单

### 详细步骤说明

#### 步骤1: 验证请求参数
- **验证内容**：检查路径参数taskId是否为有效的UUID格式
- **失败响应**：HTTP 400，错误码 `VALIDATION_ERROR`
- **特殊说明**：taskId为路径参数，必填

#### 步骤2: 查询维护任务
- **操作内容**：根据taskId查询任务记录，检查任务是否存在且未被删除
- **技术实现**：执行SQL查询 `SELECT * FROM maintenance_tasks WHERE id = ? AND isDeleted = false`
- **失败情况**：任务不存在时返回HTTP 404，错误码 `TPM_TASK_001`

#### 步骤3: 验证任务状态
- **校验规则**：检查任务的当前status是否为"待执行"，其他状态不允许接单
- **失败响应**：HTTP 400，错误码 `TPM_TASK_011`，错误消息为"只有待执行状态的任务才能接单"

#### 步骤4: 检查权限
- **派工情况判断**：
  - 若任务已派工给用户（assignedTo == currentUserId），当前用户可以接单
  - 若任务未派工（assignedTo == null），当前用户也可以接单
  - 若任务已派工给其他人，当前用户无法接单
- **失败响应**：HTTP 403，错误码 `TPM_TASK_016`，错误消息为"只能接收派工给自己的任务"

#### 步骤5: 更新任务状态
- **操作内容**：在事务中更新任务的关键字段
- **更新字段**：
  - status: "待执行"（保持不变，但标记为已接单）
  - updatedBy: 当前登录用户ID
  - updatedAt: 当前时间

#### 步骤6: 关联执行人员
- **关联逻辑**：如果任务未派工（assignedTo为null），则更新assignedTo为当前用户ID
- **技术实现**：使用UPDATE语句更新assignedTo字段

#### 步骤7: 记录接单日志
- **记录内容**：记录任务接单操作，包含操作人ID、操作时间、操作类型（ACCEPT）
- **日志级别**：INFO级别
- **日志格式**：`用户接单维护任务成功 - 任务ID: {taskId}, 执行人: {userId}`

#### 步骤8: 返回更新后的任务信息
- **返回内容**：返回接单成功的任务完整信息，包含关联的设备、维护计划、执行人员等
- **数据结构**：符合统一响应格式，包含success、data、message、meta字段

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/maintenance-tasks/:taskId/accept`

**功能描述**: 执行人员接收派发给自己的维护任务，或自主接单未派工的任务。只有待执行状态的任务才能接单。接单成功后，如果任务未派工则自动关联当前用户为执行人。

**认证要求**: JWT Bearer Token，需要 `mdm.tpm.maintenance-task.execute` 权限

**请求头**:

```
Authorization: Bearer <access_token>
```

### 路径参数

| 参数名 | 类型   | 必填 | 限制     | 描述       | 示例                                   |
| ------ | ------ | ---- | -------- | ---------- | -------------------------------------- |
| taskId | string | 是   | UUID格式 | 维护任务ID | "d4e5f6a7-b8c9-0123-def0-234567890123" |

### 请求示例

#### cURL 命令

```bash
curl -X POST http://localhost:3000/v1/mdm/tpm/maintenance-tasks/d4e5f6a7-b8c9-0123-def0-234567890123/accept \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

#### 说明

此接口为无请求体的纯REST操作，只需提供taskId作为路径参数和有效的授权token即可。

## 使用示例

### 场景1: 派工后接单

**业务需求**: 管理员已将"退火炉日常维护"任务派工给张三，张三登录系统后需要确认接单

**前置条件**:
- 任务ID: "d4e5f6a7-b8c9-0123-def0-234567890123"
- 任务状态: 待执行
- 派工人员: 张三 (ID: c3d4e5f6-a7b8-9012-cdef-123456789012)
- 张三已登录获得有效token

**请求**:
```bash
curl -X POST http://localhost:3000/v1/mdm/tpm/maintenance-tasks/d4e5f6a7-b8c9-0123-def0-234567890123/accept \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

**预期结果**:
- HTTP 200
- 任务状态保持"待执行"
- updatedBy变更为张三的ID
- updatedAt更新为当前时间
- 前端显示"接单成功"提示

**预期结果**:
- HTTP 200

## 常见问题

### Q1: 任务接单后立即可以开始执行吗？

**A**: 不一定。接单后任务状态仍为"待执行"，需要调用"开始执行任务"接口才能将状态变为"执行中"。这样的设计允许执行人员有时间做好准备。

### Q2: 未派工的任务多人可以接单吗？

**A**: 每个任务只能被一个人接单。当第一个人接单成功后，系统会自动关联该执行人，其他人再尝试接单会失败（权限验证失败）。

### Q3: 能否取消已接单的任务？

**A**: 可以。接单只是确认了任务的执行人，任务仍处于"待执行"状态，可以通过"取消任务"接口取消。

### Q4: 接单是否支持批量操作？

**A**: 当前接口只支持单任务接单。如需批量操作，需要前端循环调用此接口。

### Q5: 接单后任务信息如何快速刷新？

**A**: 接单接口返回的就是最新的完整任务信息，前端可以直接使用返回的数据更新UI，无需再次查询。

## 附录

### 任务状态机

```
[待执行]
   │
   ├─→ 接单操作 → 保持[待执行]（已标记为接单）
   │
   ├─→ 开始执行 → 转变为[执行中]
   │
   ├─→ 延期申请 → 转变为[已延期]
   │
   └─→ 取消任务 → 转变为[已取消]
```

### 派工状态与接单权限矩阵

| 派工状态           | 派工对象 | 当前用户 | 能否接单 | 说明                     |
| ------------------ | -------- | -------- | -------- | ------------------------ |
| 已派工给用户A      | 张三     | 张三     | ✓ 是     | 派工对象可以接单         |
| 已派工给用户A      | 张三     | 李四     | ✗ 否     | 其他用户无法接单         |
| 未派工             | null     | 任何人   | ✓ 是     | 任何人都可以接单         |
| 已接单（状态变更） | 张三     | 张三     | ✗ 否     | 状态已变更，无法重复接单 |

### 相关权限常量

| 权限代码                         | 说明         | 必需 |
| -------------------------------- | ------------ | ---- |
| mdm.tpm.maintenance-task.execute | 执行维护任务 | 是   |

### 相关错误码常量

| 错误码       | HTTP状态码 | 说明                         |
| ------------ | ---------- | ---------------------------- |
| TPM_TASK_001 | 404        | 维护任务不存在               |
| TPM_TASK_011 | 400        | 只有待执行状态的任务才能接单 |
| TPM_TASK_016 | 403        | 只能接收派工给自己的任务     |
| UNAUTHORIZED | 401        | 未授权                       |
| FORBIDDEN    | 403        | 无权限                       |

### 时间字段说明

所有时间字段使用ISO 8601格式：`YYYY-MM-DDTHH:mm:ss.sssZ`

示例: `"2024-01-20T06:05:00.000Z"`

- `T` 分隔日期和时间
- `Z` 表示UTC时区
- 毫秒精度：`.sss`

### 与其他接口的联动

1. **接单前**: 查询"我的任务"接口（GET /v1/mdm/tpm/maintenance-tasks/my-tasks）获取待接单任务列表
2. **接单后**: 可立即调用"开始执行任务"接口（POST /v1/mdm/tpm/maintenance-tasks/:taskId/start）开始执行
3. **执行中**: 如需延期，调用"任务延期申请"接口（POST /v1/mdm/tpm/maintenance-tasks/:taskId/postpone）
4. **完成时**: 调用"完成任务"接口（POST /v1/mdm/tpm/maintenance-tasks/:taskId/complete）
