## 功能概述

### 所有功能

任务负载分析（Task Workload Analysis）是设备TPM管理模块中的核心统计分析接口之一，用于对维护任务进行多维度的负载统计和分析，支持按维护人员或设备两种方式分组统计各类型任务的分布情况，以便管理层了解维护工作量分配情况、优化资源配置、识别瓶颈和改进工作效率的业务场景。

该接口能够统计不同状态的任务数量（待执行、执行中、已完成、已延期），为系统提供可视化的负载分析数据基础。

### 关键特性

- ✅ **多维度分组统计**：支持按维护人员（assignee）或设备（equipment）两种分组方式进行负载统计
- ✅ **全面的任务状态分类**：统计待执行、执行中、已完成、已延期等各类型任务的数量
- ✅ **时间范围灵活过滤**：支持按开始和结束日期进行时间范围过滤，可精确到日期级别
- ✅ **完整的关联信息**：返回人员名称、设备编码、设备名称等关联信息，无需前端二次查询
- ✅ **高效的数据聚合**：在后端完成数据聚合计算，减少前端数据处理复杂度
- ✅ **实时数据反映**：基于当前数据库状态实时统计，确保数据准确性

### 使用前提

- ✅ 用户必须通过JWT认证，拥有有效的access token
- ✅ 用户必须具有 `mdm.tpm.maintenance-task.view` 权限
- ✅ 数据库中必须存在维护任务记录
- ✅ 时间参数若指定必须为有效的ISO 8601格式

### 不适用场景

- ❌ 未进行身份认证或Token无效时无法访问
- ❌ 当系统中未创建任何维护任务时返回空数据
- ❌ 使用无效的时间格式会导致参数验证失败
- ❌ groupBy参数只接受assignee或equipment，其他值会返回错误

## 业务场景

### 适用场景

1. **维护负载均衡分析场景**
   - 管理层需要了解每个维护人员的任务分配情况
   - 按"assignee"分组查看各人员的任务总数和各状态任务数
   - 例如：查看张三、李四、王五各自有多少待执行、执行中、已完成的任务
   - 用于优化人员配置和工作量平衡

2. **设备维护需求分析场景**
   - 需要分析各设备的维护工作量和需求
   - 按"equipment"分组查看各设备的任务分布
   - 例如：查看退火炉、加热炉、冷却塔各自有多少维护任务和完成进度
   - 用于制定设备维护计划和预算

3. **特定时间段的工作分析场景**
   - 需要统计特定时间内（如某周或某月）的维护工作量
   - 通过startDate和endDate参数精确过滤时间范围
   - 例如：统计2024年1月1日至2024年1月31日的负载分布
   - 用于性能分析、效率评估和工作总结

4. **实时仪表板数据展示场景**
   - 前端仪表板需要实时显示负载统计信息
   - 通过定期调用此接口获取最新的统计数据
   - 例如：显示当前各人员任务状态的柱状图或饼图
   - 用于管理层快速了解系统运行状态

5. **任务分配决策支持场景**
   - 派工人员需要了解各个维护人员当前的工作量
   - 在分配新任务前调用此接口查看各人员的待执行和执行中任务数
   - 例如：发现李四只有3个待执行任务，而王五有8个，优先将新任务分配给李四
   - 用于实现更智能的负载均衡分配

### 详细步骤说明

#### 步骤1: 接收HTTP GET请求
- **操作内容**：系统接收到GET请求，包含可选的查询参数
- **查询参数**：可包含 startDate、endDate、groupBy 三个参数
- **技术实现**：Express 框架接收HTTP请求

#### 步骤2: JWT认证验证
- **验证内容**：检查请求头中的Authorization: Bearer Token是否有效
- **验证规则**：Token必须是有效的JWT格式，且未过期
- **失败响应**：HTTP 401，错误码 `UNAUTHORIZED`
- **特殊说明**：如果Token无效或过期，需重新登录获取新Token

#### 步骤3: 权限验证
- **验证内容**：检查当前用户是否具有 `mdm.tpm.maintenance-task.view` 权限
- **技术实现**：auth中间件在验证Token后进行权限检查
- **失败响应**：HTTP 403，错误码 `FORBIDDEN`
- **特殊说明**：即使Token有效，如果无权限仍然会被拒绝

#### 步骤4: 参数验证
- **验证内容**：使用Joi验证器验证查询参数
- **验证规则**：
  - startDate：可选，必须为ISO 8601格式的日期
  - endDate：可选，必须为ISO 8601格式的日期，且不早于startDate
  - groupBy：可选，默认值为"assignee"，只能是"assignee"或"equipment"
- **失败响应**：HTTP 400，返回验证错误信息
- **技术实现**：maintenanceTaskValidation.getTaskWorkloadAnalysis中间件

#### 步骤5: 查询维护任务列表
- **操作内容**：从数据库查询维护任务记录
- **查询条件**：
  - isDeleted = false（未软删除）
  - 若指定startDate，则 plannedStartTime >= startDate
  - 若指定endDate，则 plannedStartTime <= endDate
- **关联查询**：同时关联查询Equipment（设备）和User（分配人员）
- **技术实现**：
  ```
  MaintenanceTask.findAll({
    where: { isDeleted: false, ... },
    include: [
      { model: Equipment },
      { model: User, as: 'assignee' }
    ]
  })
  ```

#### 步骤6: 数据聚合处理
- **按assignee分组时**：
  - 遍历所有任务，按assignedTo (人员ID) 分组
  - 为每个人员统计：总任务数、待执行任务数、执行中任务数、已完成任务数、已延期任务数
  - 获取人员名称用于返回
- **按equipment分组时**：
  - 遍历所有任务，按equipmentId (设备ID) 分组
  - 为每个设备统计：总任务数、待执行任务数、执行中任务数、已完成任务数、已延期任务数
  - 获取设备编码和名称用于返回
- **状态分类**：
  - 待执行 → pendingTasks
  - 执行中 → inProgressTasks
  - 已完成 → completedTasks
  - 已延期 → delayedTasks

#### 步骤7: 组装响应数据
- **响应结构**：包含groupBy字段和data数组
- **data数组项**：当按assignee分组时，每项包含 assigneeId、assigneeName、totalTasks等；当按equipment分组时，包含 equipmentId、equipmentCode、equipmentName、totalTasks等
- **技术实现**：使用sendSuccess方法统一格式化响应

#### 步骤8: 返回成功响应
- **HTTP状态码**：200 OK
- **响应格式**：标准的成功响应格式（success、data、message、meta）
- **返回时间**：通常在几百毫秒内完成

## 接口文档

### 基本信息

**接口路径**: `GET /v1/mdm/tpm/maintenance-tasks/workload`

**功能描述**: 统计分析维护任务的负载情况，支持按维护人员或设备分组统计各类型任务的分布，用于工作量分析、资源配置优化和性能评估。

**认证要求**: JWT Bearer Token，需要 `mdm.tpm.maintenance-task.view` 权限

## 统一响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
```

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",

    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

| 参数名    | 类型   | 必填 | 限制                                            | 描述                                                          | 默认值     | 示例         |

## 使用示例

### 场景1: 管理员查看当前维护人员负载情况

**业务需求**: 管理员在仪表板上需要实时显示所有维护人员的工作量分布，用于了解当前的人员配置是否均衡，是否有人员超负荷或空闲。

### 场景2: 统计某月份的设备维护工作量

**业务需求**: 财务部门需要统计2024年1月份各设备的维护任务数量，用于设备维护成本核算和工作量统计。

### 场景3: 派工系统中的智能负载均衡

**业务需求**: 管理层需要对比1月和2月的维护工作量变化，分析是否有明显的季节性波动。

**业务需求**: 监控中心的仪表板需要每5分钟自动刷新一次，显示最新的负载分布情况。

## 常见问题

### Q1: groupBy参数可以同时支持两种分组方式吗？

**A**: 不可以。groupBy参数一次只能指定一个值，要么是"assignee"，要么是"equipment"。如果需要同时查看两种分组方式的数据，需要调用两次接口。

### Q2: 时间参数只支持日期级别吗？可以精确到时间吗？

**A**: 时间参数支持完整的ISO 8601格式，包括年月日时分秒。例如可以使用"2024-01-21T09:00:00Z"来精确到时分秒。但通常情况下使用日期级别就足够了，例如"2024-01-21"。

### Q3: 任务状态有哪些？为什么返回的任务数对不上？

**A**: 维护任务的状态包括：待执行（待执行）、执行中（执行中）、已完成（已完成）、已延期（已延期）、已取消（已取消）。已取消的任务不会被统计，只有前四种状态的任务会计入各类统计。另外，已软删除的任务也不会被统计。

### Q4: 返回的人员名称显示为"未分配"是什么意思？

**A**: 当任务的assignedTo字段为null或未指定维护人员时，系统会将其分组为"未分配"，assigneeId显示为字符串"unassigned"。这表示该任务还没有分配给具体的维护人员。

### Q5: 如果没有指定时间参数，接口会统计所有的历史任务吗？

**A**: 是的。如果不指定startDate和endDate，接口会统计数据库中所有未被软删除的维护任务记录，包括历史上的任务。这可能会导致数据量很大。建议在使用时总是指定合理的时间范围。

### Q6: 接口响应时间是多久？大数据量下会不会很慢？

**A**: 通常情况下响应时间在几百毫秒以内。如果系统中有数万条维护任务记录，响应时间可能会延长到1-2秒。建议定期对历史任务进行归档处理，或在数据库中为equipmentId、assignedTo、plannedStartTime等字段建立索引以优化查询性能。

### Q7: 是否支持权限过滤？不同权限的用户看到的数据会不同吗？

**A**: 当前接口不支持权限级别的数据过滤。所有有权限访问该接口的用户都会看到相同的数据。如果需要实现权限级别的数据隔离（例如部门管理员只能看到所属部门的负载信息），需要在业务层额外实现。

### Q8: groupBy="equipment"时，如果设备编码为null会显示什么？

**A**: 系统会显示"未知"作为设备编码，"未知设备"作为设备名称。这通常表示设备记录可能被删除或数据不完整。建议检查数据完整性。

### 任务状态枚举

| 状态码/代码 | 中文名称    | 说明                                   |
| ----------- | ----------- | -------------------------------------- |
| 待执行      | PENDING     | 任务已创建，等待执行人员接单或开始执行 |
| 执行中      | IN_PROGRESS | 执行人员已开始执行，任务正在进行中     |
| 已完成      | COMPLETED   | 执行人员已完成任务，任务进入已完成状态 |
| 已延期      | DELAYED     | 任务因某种原因需要延期，等待后续处理   |
| 已取消      | CANCELLED   | 任务已被取消，不再执行（统计时不计入） |

### groupBy参数可选值

| 参数值    | 中文含义   | 说明                                         |
| --------- | ---------- | -------------------------------------------- |
| assignee  | 按人员分组 | 统计结果按维护人员分组，显示每个人的负载分布 |
| equipment | 按设备分组 | 统计结果按设备分组，显示每个设备的维护工作量 |



### 如何理解负载分析

负载分析是通过统计维护任务的数量和分布情况来评估维护工作的繁忙程度。例如：

- **按人员分组**：显示每个维护人员有多少个待执行任务、执行中的任务等，用于评估人员工作量
- **按设备分组**：显示每个设备有多少个待执行任务、执行中的任务等，用于评估设备的维护需求

通过这些数据，管理层可以：
- 识别超负荷的人员，进行人员调配或加班安排
- 识别闲置的人员，进行工作分配或岗位优化
- 识别高维护需求的设备，进行预防性维护或设备升级
- 对比不同时期的负载，分析工作量趋势
