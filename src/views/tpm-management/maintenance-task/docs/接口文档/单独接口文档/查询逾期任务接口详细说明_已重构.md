## 功能概述

### 所有功能

**查询逾期任务**（Overdue Tasks Query）是维护任务管理模块中的重要查询功能，用于快速识别和查看所有逾期的维护任务（计划开始时间早于当前时间，且状态为待执行或执行中），帮助管理员和维护人员及时发现延迟任务并采取相应措施，以支持维护计划管理、任务调度优化和工作效率提升的业务场景。

逾期任务查询是维护任务运营管理的关键功能，通过及时发现和处理逾期任务，可以确保设备维护的连续性和有效性。该接口支持灵活的筛选条件，支持按设备、执行人员等维度进行筛选，同时支持分页查询，能够适应不同规模的维护任务场景。

### 关键特性

- ✅ **实时逾期识别**：自动计算当前时间与计划开始时间的差异，准确识别逾期任务，无需人工干预
- ✅ **智能状态过滤**：只返回待执行或执行中状态的任务，自动排除已完成和已取消的任务
- ✅ **灵活的筛选条件**：支持按设备、执行人员等多个维度进行筛选，满足不同查询场景
- ✅ **分页查询支持**：支持标准分页参数（page、limit），可处理大量逾期任务场景
- ✅ **完整的任务信息**：返回逾期任务的完整详情，包含设备、执行人、计划时间等关键信息
- ✅ **高效的数据查询**：通过优化的数据库查询实现，支持大数据量场景下的快速响应

### 使用前提

- ✅ 用户已完成身份认证，持有有效的JWT令牌
- ✅ 用户令牌未过期且有效
- ✅ 系统中存在已创建的维护任务数据
- ✅ 任务的计划开始时间早于当前系统时间
- ✅ 任务状态为"待执行"或"执行中"之一

### 不适用场景

- ❌ 查询已完成的任务——逾期查询只返回活跃任务，已完成任务应使用历史查询接口
- ❌ 查询已取消的任务——逾期查询不包含已取消的任务，取消任务查询需单独查询
- ❌ 查询未来计划的任务——逾期查询仅识别计划开始时间早于当前时间的任务

### 详细步骤说明

#### 步骤1: 用户身份验证
- **验证内容**：检查请求头中的JWT令牌，验证令牌的有效性和未过期状态
- **失败处理**：令牌无效或过期返回 401 错误（UNAUTHORIZED）
- **说明**：确保只有经过认证的用户才能查询任务

#### 步骤2: 筛选条件应用
- **自动条件**：
  - 任务状态必须为"待执行"或"执行中"
  - 计划开始时间必须早于当前系统时间
  - 任务必须未被删除（isDeleted=false）
- **可选条件**：
  - equipmentId：按设备筛选逾期任务
  - assignedTo：按执行人筛选逾期任务
- **说明**：确保只返回真正逾期的活跃任务

#### 步骤3: 数据库查询执行
- **查询逻辑**：
  - 使用 WHERE 子句应用所有筛选条件
  - 按 plannedStartTime 升序排序（最逾期的任务在前）
  - 按照 page 和 limit 参数进行分页
- **关联数据加载**：
  - 左连接设备表获取设备信息
  - 左连接用户表获取执行人信息
  - 左连接维护计划表获取计划信息
- **说明**：一次查询加载所有需要的关联数据，避免 N+1 问题

#### 步骤4: 响应数据构建
- **返回字段**：
  - results：逾期任务数组
  - page：当前页码
  - limit：每页数量
  - totalPages：总页数（基于实际逾期任务总数）
  - totalResults：逾期任务总数
- **说明**：返回结构与查询任务列表接口一致，便于前端统一处理

## 接口文档

### 基本信息

**接口路径**: `GET /v1/mdm/tpm/maintenance-tasks/overdue`

**功能描述**: 查询所有逾期的维护任务，即计划开始时间早于当前时间且状态为待执行或执行中的任务。支持按设备、执行人等条件筛选，返回分页结果。

**认证要求**: JWT Bearer Token 认证，无需特定权限


**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null

```
Authorization: Bearer <access_token>
```

## 常见问题

### Q1: 为什么查询结果中没有已完成的任务？
**A**: 逾期任务查询的设计初衷是识别需要处理的活跃任务。已完成的任务已进入最终状态，不存在"逾期"的问题。如需查询已完成的历史任务，请使用"查询维护任务列表"接口并按状态筛选。

### Q2: 接口如何判断任务是否逾期？
**A**: 系统通过对比任务的"计划开始时间"（plannedStartTime）与当前系统时间（now）来判断。如果 `plannedStartTime < now` 且任务状态为"待执行"或"执行中"，则视为逾期任务。

### Q3: 任务完成后会不会还出现在逾期列表中？
**A**: 不会。任务状态变为"已完成"后，会被自动排除在逾期查询之外。只有"待执行"和"执行中"状态的任务才会出现在逾期列表中。

### Q4: 可以按任务状态筛选吗？
**A**: 不能。逾期任务查询默认只返回"待执行"和"执行中"状态的任务。如需按特定状态筛选所有任务，请使用"查询维护任务列表"接口。

### Q5: 如何快速看到最紧急的逾期任务？
**A**: 逾期任务默认按"计划开始时间"升序排列，最早计划开始的任务（最逾期的）会显示在最前面，这样可以快速识别最紧急的任务。

### Q6: limit参数为什么有100的限制？
**A**: 为了保护服务器性能和防止大量数据传输，系统设置了单次查询的最大限制。如需查询超过100条记录，建议使用分页方式多次查询。

### Q7: 如何获取某个用户的所有逾期任务总数？
**A**: 调用接口时指定 `assignedTo` 参数，响应结果中的 `totalResults` 字段就是该用户的逾期任务总数，无需逐页计算。

### Q8: 时区如何处理？
**A**: 系统统一使用 UTC 时间戳（ISO 8601格式）存储和返回。前端应根据用户的本地时区进行转换展示。

### 逾期判断时间差

逾期任务查询会根据当前时间自动计算逾期天数。以下是常见的逾期时间段：

| 逾期时长 | 紧急程度 | 处理建议                       |
| -------- | -------- | ------------------------------ |
| 0-1天    | 轻微     | 如非必要，应尽快处理           |
| 1-3天    | 中等     | 应列为近期工作重点             |
| 3-7天    | 较高     | 应立即重新评估并加速处理       |
| 7天以上  | 严重     | 应上报管理层，评估是否调整计划 |
