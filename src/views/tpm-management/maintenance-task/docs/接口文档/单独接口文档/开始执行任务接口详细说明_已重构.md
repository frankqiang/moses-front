## 功能概述

### 所有功能

开始执行任务（Start Maintenance Task）是设备TPM管理模块中的核心执行操作之一，用于执行人员正式开始执行维护任务。当执行人员点击"开始执行"时，系统将任务状态变更为"执行中"，记录任务的实际开始时间，并同时将对应的设备状态同步更新为"维护中"，以防止在设备维护期间被其他操作占用。这支持了精细化的设备状态管理和维护任务执行追踪的业务场景。

### 关键特性

- ✅ **状态自动迁移**：任务状态从"待执行"或"已延期"自动转变为"执行中"
- ✅ **时间自动记录**：系统自动记录任务的实际开始时间，用于后续统计分析
- ✅ **设备状态同步**：关联设备状态自动更新为"维护中"，防止冲突操作
- ✅ **执行人身份校验**：严格验证只有任务的执行人才能开始执行，防止权限混乱
- ✅ **完整的审计跟踪**：记录开始执行的时间、执行人等关键审计信息
- ✅ **事务一致性保证**：任务状态更新和设备状态更新在事务中原子执行

## 业务场景

### 适用场景

1. **正式开始维护作业场景**
   - 执行人员已接单任务并做好准备
   - 现在需要正式开始维护作业
   - 点击"开始执行"按钮，任务进入"执行中"状态
   - 例如：张三接单了"退火炉日常维护"任务，准备工具完毕后点击开始执行

2. **设备维护期间的状态管理场景**
   - 设备在维护期间不能执行其他操作
   - 通过更新设备状态为"维护中"来标识当前状态
   - 防止其他业务系统对该设备的并发操作
   - 例如：设备状态从"空闲"变为"维护中"，自动生成设备状态变更日志

3. **维护数据统计和分析场景**
   - 需要追踪每项维护任务的实际执行时间
   - 记录actualStartTime用于计算工作效率
   - 例如：根据actualStartTime计算任务的等待时长

4. **任务重新执行场景**
   - 任务已延期（状态为"已延期"）
   - 延期期限已到，可以重新开始执行
   - 点击"开始执行"按钮继续执行任务
   - 例如：因零件延货延期的任务，零件到货后可以重新开始执行

### 使用前提

- ✅ 维护任务必须处于"待执行"或"已延期"状态
- ✅ 当前登录用户必须是任务的执行人（assignedTo == currentUserId）
- ✅ 操作人员必须具有 `mdm.tpm.maintenance-task.execute` 权限
- ✅ 关联的设备必须存在且处于可维护状态

### 不适用场景

- ❌ 任务已处于"执行中"状态时无法再次开始执行
- ❌ 任务已完成、已取消等终止状态时无法开始执行
- ❌ 当前用户不是任务的执行人时无法开始执行
- ❌ 当前用户没有执行维护任务的权限时无法开始执行

### 详细步骤说明

#### 步骤1: 验证请求参数
- **验证内容**：检查路径参数taskId是否为有效的UUID格式
- **失败响应**：HTTP 400，错误码 `VALIDATION_ERROR`
- **特殊说明**：taskId为路径参数，必填

#### 步骤2: 查询维护任务
- **操作内容**：根据taskId查询任务记录，检查任务是否存在且未被删除
- **技术实现**：执行SQL查询 `SELECT * FROM maintenance_tasks WHERE id = ? AND isDeleted = false`
- **失败情况**：任务不存在时返回HTTP 404，错误码 `MAINTENANCE_TASK_002`

#### 步骤3: 验证任务状态
- **校验规则**：检查任务的当前status是否为"待执行"或"已延期"，其他状态不允许开始执行
- **允许的状态**：["待执行", "已延期"]
- **失败响应**：HTTP 400，错误码 `MAINTENANCE_TASK_006`，错误消息为"只有待执行或已延期状态的任务才能开始执行"

#### 步骤4: 验证执行人
- **验证逻辑**：检查task.assignedTo是否等于当前用户ID
- **失败场景**：用户不是执行人时无法开始执行
- **失败响应**：HTTP 403，错误码 `MAINTENANCE_TASK_007`，错误消息为"只有任务执行人才能开始执行任务"

#### 步骤5: 验证用户有效性
- **验证内容**：检查执行用户是否存在且处于激活状态
- **技术实现**：调用integrationService.validateUserId进行校验
- **失败情况**：用户不存在或已禁用时抛出错误

#### 步骤6: 更新任务状态
- **操作内容**：在事务中更新任务的关键字段
- **更新字段**：
  - status: "执行中"（状态变更）
  - actualStartTime: 当前时间戳（新增）
  - updatedBy: 当前登录用户ID
  - updatedAt: 当前时间

#### 步骤7: 更新设备状态
- **操作内容**：将关联设备状态更新为"维护中"
- **技术实现**：调用integrationService.setEquipmentToMaintenance
- **关键参数**：设备ID、任务ID、操作人ID、事务对象

#### 步骤8: 记录操作日志
- **记录内容**：记录任务开始执行操作，包含操作人ID、操作时间、设备信息
- **日志级别**：INFO级别
- **日志格式**：`维护任务开始执行: {taskCode}, taskId: {taskId}, userId: {userId}`

#### 步骤9: 返回更新后的任务信息
- **返回内容**：返回开始执行成功的任务完整信息，包含关联的设备、维护计划、执行人员等
- **数据结构**：符合统一响应格式，包含success、data、message、meta字段

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/maintenance-tasks/:taskId/start`

**功能描述**: 执行人员开始执行维护任务。当任务状态为"待执行"或"已延期"时，点击此接口后任务状态变为"执行中"，同时记录实际开始时间，设备状态同步更新为"维护中"。

**认证要求**: JWT Bearer Token，需要 `mdm.tpm.maintenance-task.execute` 权限

**请求头**:

```
Authorization: Bearer <access_token>
```

### 路径参数

| 参数名 | 类型   | 必填 | 限制     | 描述       | 示例                                   |
| ------ | ------ | ---- | -------- | ---------- | -------------------------------------- |
| taskId | string | 是   | UUID格式 | 维护任务ID | "d4e5f6a7-b8c9-0123-def0-234567890123" |

### 请求示例

#### cURL 命令

```bash
curl -X POST http://localhost:3000/v1/mdm/tpm/maintenance-tasks/d4e5f6a7-b8c9-0123-def0-234567890123/start \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

#### 说明

此接口为无请求体的纯REST操作，只需提供taskId作为路径参数和有效的授权token即可。

## 使用示例

### 场景1: 任务从待执行状态开始执行

**业务需求**: 张三已接单"退火炉日常维护"任务，现在准备好了开始执行任务

**前置条件**:
- 任务ID: "d4e5f6a7-b8c9-0123-def0-234567890123"
- 任务状态: 待执行
- 执行人员: 张三 (ID: c3d4e5f6-a7b8-9012-cdef-123456789012)
- 张三已登录获得有效token
- 设备状态: 空闲

**请求**:
```bash
curl -X POST http://localhost:3000/v1/mdm/tpm/maintenance-tasks/d4e5f6a7-b8c9-0123-def0-234567890123/start \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

**预期结果**:
- HTTP 200
- 任务状态变更为"执行中"
- actualStartTime更新为当前时间

## 常见问题

### Q1: 开始执行任务后能否取消任务？

**A**: 可以。任务开始执行后（状态为"执行中"），仍然可以通过"取消任务"接口取消。当任务被取消时，关联的设备状态会自动恢复为"空闲"。

### Q2: 设备状态是否会自动恢复？

**A**: 不会自动恢复。设备会保持"维护中"状态，直到以下情况之一发生：
- 任务完成：设备状态恢复为"空闲"
- 任务取消：设备状态恢复为"空闲"
- 手动通过设备管理接口修改设备状态

### Q3: 如果我不是执行人能否调用此接口？

**A**: 不能。系统会进行严格的执行人校验，只有task.assignedTo与当前登录用户ID相同时才能调用此接口。如需变更执行人，需要通过"任务派工"接口重新派工。

### Q4: actualStartTime什么时候被记录？

**A**: actualStartTime在调用此接口时被记录为当前服务器时间。该时间用于后续统计任务执行的等待时长、执行耗时等指标。

### Q5: 能否在延期后立即开始执行？

**A**: 可以。当任务状态为"已延期"时，仍然可以通过此接口开始执行，系统不强制要求等待延期时间到达。

### Q6: 此接口是否支持批量操作？

**A**: 当前接口只支持单任务操作。如需批量启动多个任务，需要前端循环调用此接口。

### Q7: 是否支持幂等性操作？

**A**: 不完全支持。当任务已处于"执行中"状态时，再次调用会返回错误。建议前端实现防止重复提交的机制（如按钮禁用）。

### Q8: 如何追踪任务的执行时间？

**A**: 可以通过以下字段计算：
- 等待时长 = actualStartTime - plannedStartTime
- 执行耗时 = actualEndTime - actualStartTime
- 总耗时 = actualEndTime - createdAt

## 附录

### 任务状态机（包含开始执行流程）

```
[待执行]
   │
   ├─→ 开始执行 → 转变为[执行中] ──→ 完成任务 → 转变为[已完成] → 生成维护记录
   │                      │
   │                      ├─→ 延期申请 → 转变为[已延期]
   │                      │
   │                      └─→ 取消任务 → 转变为[已取消]
   │
   ├─→ 接单操作 → 保持[待执行]
   │
   ├─→ 派工操作 → 保持[待执行]
   │
   ├─→ 延期申请 → 转变为[已延期]
   │
   └─→ 取消任务 → 转变为[已取消]

[已延期]
   │
   ├─→ 开始执行 → 转变为[执行中]
   │
   ├─→ 取消任务 → 转变为[已取消]
   │
   └─→ 延期申请 → 保持[已延期]（更新延期原因/时间）
```

### 任务与设备状态对应关系

| 任务状态 | 设备状态 | 说明                       |
| -------- | -------- | -------------------------- |
| 待执行   | 空闲     | 任务未开始，设备正常可用   |
| 执行中   | 维护中   | 任务正在执行，设备被占用   |
| 已完成   | 空闲     | 任务完成，设备恢复可用     |
| 已延期   | 空闲     | 任务延期等待，设备正常可用 |
| 已取消   | 空闲     | 任务取消，设备恢复可用     |

### 设备状态枚举值

| 状态码 | 中文名称 | 说明             |
| ------ | -------- | ---------------- |
| 空闲   | idle     | 设备处于空闲状态 |
| 维护中 | maintain | 设备正在维护中   |
| 故障   | fault    | 设备故障，不可用 |
| 停用   | offline  | 设备已停用       |

### 时间字段说明

所有时间字段使用ISO 8601格式：`YYYY-MM-DDTHH:mm:ss.sssZ`

示例: `"2024-01-20T08:15:00.000Z"`

- `T` 分隔日期和时间
- `Z` 表示UTC时区
- 毫秒精度：`.sss`

### 与其他接口的联动

1. **开始执行前**：确保任务处于"待执行"或"已延期"状态
   - 可通过"查询任务详情"接口获取当前状态
   - 接口：GET /v1/mdm/tpm/maintenance-tasks/:taskId

2. **开始执行后**：可进行的后续操作
   - **完成任务**：POST /v1/mdm/tpm/maintenance-tasks/:taskId/complete
   - **取消任务**：POST /v1/mdm/tpm/maintenance-tasks/:taskId/cancel
   - **申请延期**：POST /v1/mdm/tpm/maintenance-tasks/:taskId/postpone

3. **事前准备**：开始执行前通常需要
   - 接单任务：POST /v1/mdm/tpm/maintenance-tasks/:taskId/accept
   - 查询任务详情：GET /v1/mdm/tpm/maintenance-tasks/:taskId
   - 查询设备信息：GET /v1/mdm/equipment/:equipmentId

4. **状态查询**：
   - 查询我的任务：GET /v1/mdm/tpm/maintenance-tasks/my-tasks?status=待执行,已延期
   - 查询所有任务：GET /v1/mdm/tpm/maintenance-tasks?status=待执行
   - 查询逾期任务：GET /v1/mdm/tpm/maintenance-tasks/overdue
