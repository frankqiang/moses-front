## 功能概述

### 所有功能

**完成任务**（Task Completion）是维护任务管理模块中的关键操作之一，用于维护执行人员提交维护任务的完成信息，标记任务为"已完成"状态，同时自动恢复设备状态和创建维护记录，以支持完整的维护工作流和追踪管理的业务场景。

完成任务操作是维护任务生命周期中的最后执行阶段，连接了任务执行和维护历史记录两个重要环节。通过完成操作，系统能够准确记录维护工作内容、工时、使用备件等详细信息，为后续的维护分析和设备维护历史查询提供完整的数据基础。

### 关键特性

- ✅ **智能状态流转**：只有执行中状态的任务才能完成，确保任务状态流转的正确性和业务规则的完整性
- ✅ **完整的维护信息记录**：支持记录维护内容、发现问题、处理措施、使用备件、工时等丰富的维护数据
- ✅ **自动维护记录创建**：完成任务时自动生成维护记录，包含任务信息、设备信息、维护人员等关联数据
- ✅ **设备状态自动恢复**：任务完成后自动恢复设备状态为"空闲"，同时清除维护标记
- ✅ **执行人员权限校验**：确保只有任务的执行人才能完成任务，保护数据完整性和业务安全性
- ✅ **原子性操作**：完成操作在事务保护下执行，确保任务状态、维护记录、设备状态的一致性

### 使用前提

- ✅ 维护任务存在且ID有效（需为有效的UUID格式）
- ✅ 维护任务当前状态为"执行中"（状态为其他值时完成会失败）
- ✅ 执行人员是当前登录的操作用户且已被设置为任务的 assignedTo
- ✅ 执行人员用户状态为"激活"（inactive用户无法完成任务）
- ✅ 必须提供维护内容详情信息（maintenanceContent必填）
- ✅ 持有有效的JWT认证令牌，且令牌未过期

### 不适用场景

- ❌ 任务处于待执行状态的完成——应先接单或派工，再开始执行后才能完成
- ❌ 任务已完成或已取消的完成——这些是终态，不允许再次操作
- ❌ 非执行人员的完成操作——只有任务的执行人员才能完成任务
- ❌ 未开始执行的任务完成——需要先调用开始执行接口

### 详细步骤说明

#### 步骤1: 用户身份验证
- **验证内容**：检查当前登录用户是否有效且状态为激活
- **失败处理**：用户无效或已禁用返回 404 错误（USER_001）
- **说明**：确保操作者是有效的系统用户

#### 步骤2: 任务查询与状态验证
- **验证内容**：查询指定ID的维护任务，验证任务存在且状态为"执行中"
- **失败处理**：
  - 任务不存在：返回 404 错误（TPM_TASK_002）
  - 任务状态不是执行中：返回 400 错误（TPM_TASK_008）
- **说明**：只有执行中的任务才符合完成条件

#### 步骤3: 执行人权限验证
- **验证内容**：检查当前操作用户是否是任务的执行人（assignedTo 字段）
- **失败处理**：不是执行人返回 403 错误（TPM_TASK_009）
- **说明**：确保只有任务执行人才能完成任务

#### 步骤4: 事务开启
- **内容**：开启数据库事务，确保完成操作的原子性
- **说明**：如果完成过程中发生异常，事务会自动回滚，保证数据一致性

#### 步骤5: 任务状态更新
- **更新字段**：
  - `status`：设置为"已完成"
  - `actualEndTime`：设置为当前时间
  - `confirmedBy`：设置为当前操作用户ID
  - `confirmedAt`：设置为当前时间
  - `remark`：可选，更新任务备注
  - `updatedBy`：设置为当前操作用户ID
- **说明**：记录任务完成信息和时间戳

#### 步骤6: 设备状态恢复
- **内容**：调用集成服务恢复设备状态
- **处理**：设备状态从"维护"恢复为"空闲"，清除维护标记
- **说明**：确保设备可用性管理的准确性

#### 步骤7: 维护记录创建
- **内容**：自动创建新的维护记录
- **关键字段**：
  - 维护记录编码（自动生成）
  - 关联任务ID和设备ID
  - 维护内容、问题描述、处理措施
  - 使用的备件清单
  - 工时统计
  - 执行人和确认人信息
- **说明**：维护记录是维护历史的重要凭证

#### 步骤8: 事务提交
- **内容**：提交数据库事务，确保所有更新操作持久化
- **说明**：事务提交成功后，完成操作不可逆

#### 步骤9: 数据查询与响应
- **内容**：查询更新后的完整任务信息，包括关联的设备、执行人、确认人等
- **说明**：返回的完整信息可供前端直接展示，无需额外查询

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/maintenance-tasks/:taskId/complete`

**功能描述**: 执行人员完成维护任务，标记任务为"已完成"状态，自动创建维护记录，并恢复设备状态。只有执行中状态的任务且由任务执行人才能完成。

**认证要求**: JWT Bearer Token 认证（无需特定权限，但操作人必须是任务的执行人）

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 路径参数

| 参数名 | 类型   | 必填 | 限制     | 描述       | 示例                                   |
| ------ | ------ | ---- | -------- | ---------- | -------------------------------------- |
| taskId | string | 是   | UUID格式 | 维护任务ID | "d4e5f6a7-b8c9-0123-def0-234567890123" |

### 请求参数

| 参数名                    | 类型   | 必填 | 限制        | 描述               | 示例                                           |
| ------------------------- | ------ | ---- | ----------- | ------------------ | ---------------------------------------------- |
| maintenanceContent        | string | 是   | 最大500字符 | 维护内容详情       | "检查加热元件，清洁炉体，测试温控系统运行正常" |
| problemFound              | string | 否   | 最大500字符 | 发现问题描述       | "加热管积垢较厚"                               |

| sparePartsUsed            | array  | 否   | 见下方结构  | 使用备件清单       | 见下方结构说明                                 |

#### JavaScript/axios 示例

```javascript
import axios from 'axios';

const api = axios.create({
  baseURL: 'http://localhost:3000/v1',
  headers: {
    'Content-Type': 'application/json',
  },
});

async function completeMaintenanceTask(taskId, completionData, token) {
  try {
    const response = await api.post(
      `/mdm/tpm/maintenance-tasks/${taskId}/complete`,
      completionData,
      {
        headers: {
          Authorization: `Bearer ${token}`,
        },
      }
    );

    console.log('任务完成成功:', response.data.data);
    return response.data.data;
  } catch (error) {
    console.error('任务完成失败:', error.response.data);
    throw error;
  }
}

// 使用示例
const completionData = {
  maintenanceContent: '检查加热元件、清洁炉体、测试温控系统',

    },
  ],
  workHours: 2.5,
  equipmentStatusBefore: '高温告警，制温不稳定',
  equipmentStatusAfter: '恢复正常，温度稳定',

};

completeMaintenanceTask('d4e5f6a7-b8c9-0123-def0-234567890123', completionData, token);
```

## 常见问题

### Q1: 完成任务后，维护记录会自动创建吗？

**A**: 是的，完成任务时会自动创建对应的维护记录。系统会：
- 将完成任务时提交的所有维护数据写入维护记录
- 关联设备ID和任务ID
- 记录执行人和确认人信息
- 生成维护记录编码

这意味着无需单独调用维护记录创建接口。

### Q2: 完成任务后，设备状态如何变化？

**A**: 设备状态变化流程：
1. 任务开始执行时，设备状态变为"维护"
2. 任务完成时，设备状态自动恢复为"空闲"
3. 如果设备在维护过程中发生异常，状态可能变为"故障"，完成时不会改变故障状态

因此，不需要单独调用设备状态更新接口。

### Q3: 非执行人员能否代替执行人完成任务？

**A**: 不能。系统有严格的权限控制：
- 只有任务的执行人（assignedTo 字段指定的用户）才能完成任务
- 如果其他人员尝试完成任务，会返回 403 Forbidden 错误
- 管理员也无法代替执行人完成任务，这是设计考虑

如果需要转移责任，应该先取消原任务，再创建新任务并派工给其他人员。

### Q4: 能否多次完成同一个任务？

**A**: 不能。任务完成后状态变为"已完成"，这是最终状态：
- 已完成的任务无法再完成
- 再次调用完成接口会返回 TPM_TASK_008 错误
- 如果需要重新开始工作，应该创建新的任务

### Q5: 完成任务时，maintenanceContent 字段为什么必填？

**A**: maintenanceContent 是维护记录的核心信息：
- 它记录了具体的维护工作内容
- 是维护历史和工作量统计的重要依据
- 便于后续的维护分析和设备评估

即使维护内容简单，也应该填写简要说明。

### Q6: 是否必须填写所有维护字段？

**A**: 不必须。完成任务只有一个必填字段：
- **必填**：maintenanceContent（维护内容）

其他字段都是可选的：
- problemFound：只在发现问题时填写
- solutionApplied：只在处理了问题时填写
- sparePartsUsed：只在使用了备件时填写
- workHours：可根据实际工时填写
- equipmentStatusBefore/After：用于记录设备状态变化

### Q7: 如何记录使用的备件信息？

**A**: 通过 sparePartsUsed 数组记录：
- 每个备件项应包含备件名称和数量
- 可选包含备件ID或编码
- 系统不会自动从库存扣减，仅记录使用信息

示例：
```javascript
sparePartsUsed: [
  { sparePartName: '加热管', quantity: 2 },
  { sparePartName: '密封条', quantity: 1 },
]
```

### Q8: 完成任务失败后能否重试？

**A**: 可以，根据不同的失败原因处理：
- **VALIDATION_ERROR**：检查请求参数，修正后重试
- **TPM_TASK_008**：确保任务状态为"执行中"，必要时刷新页面获取最新状态
- **TPM_TASK_009**：确保当前用户是任务执行人
- **USER_001**：用户状态异常，联系管理员处理
- **UNAUTHORIZED**：重新登录获取新Token
- **INTERNAL_ERROR**：稍后重试或联系技术支持

### Q9: 完成任务时可否修改任务的其他信息？

**A**: 不能。完成任务接口只能更新以下字段：
- 任务状态（变为"已完成"）
- 实际完成时间
- 确认人和确认时间
- 任务备注（remark）

其他字段（任务标题、描述、计划时间等）无法通过此接口修改。如需修改，应该在任务完成前进行。

### Q10: 完成任务的响应中，为什么需要返回完整的任务信息？

**A**: 返回完整信息有几个好处：
- 前端可以直接刷新显示，无需额外查询
- 确认设备状态已正确恢复
- 验证维护记录是否已创建
- 提供完整的操作审计信息

这样设计符合 REST 最佳实践。

### 日期时间格式说明

所有涉及时间的字段都使用 ISO 8601 标准格式：

- **格式**: `YYYY-MM-DDTHH:mm:ss.sssZ`
- **示例**: `2024-01-20T10:35:00.000Z`
- **说明**: Z 表示 UTC 时区，即零时区
- **时区转换**: 前端需要根据本地时区显示时间
