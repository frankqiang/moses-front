## 功能概述

### 所有功能

按组织架构筛选维护人员（Get Maintenance Personnel by Organization Structure）是维护任务管理模块中的重要辅助接口，用于根据部门、岗位、角色等组织架构信息筛选出符合条件的维护人员，以支持任务派工、人员选择等业务场景。

该接口主要应用在以下场景：
- 创建维护任务时选择执行人员
- 任务派工时按组织架构筛选可用人员
- 按部门查看该部门所有维护人员
- 按岗位查看具备特定技能的维护人员
- 按角色查看具有特定权限的维护人员

### 关键特性

- ✅ **灵活的组织架构筛选**：支持按部门、岗位、角色等多维度组合筛选
- ✅ **只返回活跃用户**：自动过滤非活跃状态的用户，确保人员可用性
- ✅ **完整的组织信息**：返回用户的部门、岗位等详细组织架构信息
- ✅ **自定义排序**：支持按姓名等字段自定义排序方式
- ✅ **数量限制**：支持限制返回结果数量，优化性能和用户体验
- ✅ **关联查询优化**：使用高效的数据库关联查询，一次性获取完整信息

---

### 使用前提

- ✅ **认证要求**：必须提供有效的 JWT Bearer Token
- ✅ **用户状态**：只返回状态为 `active` 的活跃用户
- ✅ **组织架构数据**：系统中已存在部门、岗位、角色等组织架构数据
- ✅ **用户档案完整性**：用户必须有完整的档案信息（UserProfile）

### 不适用场景

- ❌ **查询所有系统用户**：本接口专门用于筛选维护人员，不适合查询全部系统用户
- ❌ **查询已离职人员**：本接口只返回活跃用户，不包含非活跃或已离职人员
- ❌ **不需要组织架构信息**：如果只需要用户基本信息，建议使用用户管理模块的接口

### 详细步骤说明

#### 步骤1: 接收查询请求

接收客户端传入的筛选条件，包括：
- `departmentId`: 部门ID（可选）
- `positionId`: 岗位ID（可选）
- `roleIds`: 角色ID列表，逗号分隔（可选）
- `limit`: 返回结果数量限制，默认50（可选）
- `sortBy`: 排序字段和方向，默认name:asc（可选）

#### 步骤2: 参数解析与验证

**参数验证**：
- 验证 UUID 格式的参数（departmentId、positionId）
- 解析角色ID列表（支持逗号分隔的多个角色ID）
- 验证并解析分页和排序参数

**默认值处理**：
- limit 默认值：50
- sortBy 默认值：name:asc
- 所有筛选条件都是可选的

#### 步骤3: 构建基础查询条件

**固定条件**：
- 用户状态必须为 `active`（活跃状态）

**关联查询配置**：
- 必须关联 `UserProfile`（用户档案）
- 必须关联 `Department`（部门信息）
- 必须关联 `Position`（岗位信息）

#### 步骤4: 按部门筛选（可选）

如果提供了 `departmentId`：
- 在 `UserProfile` 关联条件中添加 `departmentId` 筛选
- 只返回该部门下的用户

#### 步骤5: 按岗位筛选（可选）

如果提供了 `positionId`：
- 在 `UserProfile` 关联条件中添加 `positionId` 筛选
- 只返回该岗位的用户

#### 步骤6: 按角色筛选（可选）

如果提供了 `roleIds`：
- 解析逗号分隔的角色ID列表
- 添加 `userRoles` 关联查询
- 只返回拥有指定角色的用户
- 支持多角色条件（用户拥有其中任意一个角色即可）

#### 步骤7: 执行数据库查询

使用 Sequelize ORM 执行联表查询：

```javascript
User.findAll({
  where: { status: 'active' },
  include: [
    {
      model: UserProfile,
      as: 'profile',
      required: true,
      where: { /* 部门/岗位筛选条件 */ },
      include: [
        { model: Department, as: 'department' },
        { model: Position, as: 'position' }
      ]
    },
    // 如果有角色筛选
    {
      association: 'userRoles',
      where: { roleId: roleIds },
      required: true
    }
  ],
  order: [/* 排序规则 */],
  limit: limit
})
```

**查询特点**：
- 使用 `required: true` 确保只返回有档案信息的用户
- 一次性加载所有关联数据，避免 N+1 查询问题
- 支持复杂的多表联查和条件组合

#### 步骤8: 返回人员列表

返回符合条件的维护人员列表，每个用户包含：
- 用户基本信息（id、name、username、email、status）
- 用户档案信息（profile）
- 所属部门信息（department）
- 所属岗位信息（position）

## 接口文档

### 基本信息

**接口路径**: `GET /v1/mdm/tpm/maintenance-tasks/personnel`

**功能描述**: 根据部门、岗位、角色等组织架构信息筛选可用的维护人员，用于任务派工时选择执行人员。该接口只返回状态为活跃的用户，并包含完整的组织架构信息。

**认证要求**: 需要 Bearer Token 认证

### 查询参数

| 参数名       | 类型   | 必填 | 限制                  | 描述                         | 默认值     | 示例                                   |
| ------------ | ------ | ---- | --------------------- | ---------------------------- | ---------- | -------------------------------------- |
| departmentId | string | 否   | UUID格式              | 部门ID筛选                   | null       | "a1b2c3d4-e5f6-7890-abcd-ef1234567890" |
| positionId   | string | 否   | UUID格式              | 岗位ID筛选                   | null       | "b2c3d4e5-f6a7-8901-bcde-f12345678901" |
| roleIds      | string | 否   | 逗号分隔的UUID列表    | 角色ID列表，支持多个角色筛选 | null       | "role-id-1,role-id-2"                  |
| limit        | number | 否   | 最小值1，最大值100    | 限制返回结果数量             | 50         | 50                                     |
| sortBy       | string | 否   | 格式：字段名:asc/desc | 排序字段和方向               | "name:asc" | "name:asc"                             |

**查询参数说明**：

- **departmentId**: 按部门筛选，只返回该部门下的用户
- **positionId**: 按岗位筛选，只返回该岗位的用户
- **roleIds**: 按角色筛选，支持多个角色用逗号分隔（用户拥有其中任意一个角色即返回）
- **limit**: 限制返回数量，防止一次返回过多数据
- **sortBy**: 支持多字段排序，逗号分隔，格式为 `字段名:排序方向`
- 所有筛选条件都是可选的，不提供筛选条件时返回所有活跃维护人员（受limit限制）

### 场景1: 任务派工时选择本部门的维护人员

**业务需求**: 管理员创建了一个维护任务，需要将任务派发给设备维护部的工程师。

**步骤**：
1. 获取当前部门ID（例如：设备维护部）
2. 调用接口筛选该部门的维护人员
3. 在前端显示人员列表供管理员选择
4. 选择执行人员后调用任务派工接口

**请求示例**：

```bash
curl -X GET "http://localhost:3000/v1/mdm/tpm/maintenance-tasks/personnel?departmentId=dept-maintenance-001&limit=50&sortBy=name:asc" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

**响应示例**：

```json
{
  "success": true,
  "data": [
    {
      "id": "user-001",
      "name": "张三",
      "username": "zhangsan",
      "email": "zhangsan@example.com",
      "status": "active",
      "profile": {
        "department": {
          "id": "dept-maintenance-001",
          "name": "设备维护部",
          "code": "DEPT001"
        },
        "position": {
          "name": "维护工程师",
          "code": "POS001"
        }
      }

  ],
  "message": "查询维护人员成功"
```

**步骤**：

### 场景3: 按角色筛选有特定权限的人员

## 常见问题

### Q1: 为什么查询结果为空？

**可能原因**：
1. 指定的部门/岗位下没有活跃用户
2. 指定的角色没有分配给任何用户
3. 用户状态不是 `active`（已离职或禁用）
4. 用户没有关联的 UserProfile（档案信息不完整）
5. 筛选条件组合过于严格，没有用户同时满足所有条件

**解决方案**：
- 检查组织架构数据是否正确
- 确认用户是否有完整的档案信息
- 尝试放宽筛选条件或单独测试每个筛选条件
- 检查用户状态是否为活跃

### Q2: 如何实现分页查询？

**回答**：
本接口暂不支持标准的分页（page参数），但支持通过 `limit` 参数限制返回数量。

**推荐做法**：
- 使用合理的 `limit` 值（建议 20-100）
- 结合筛选条件缩小结果集
- 如果需要完整分页功能，建议联系后端开发团队扩展接口

### Q3: roleIds 支持多角色筛选吗？

**回答**：
支持。`roleIds` 参数可以传入多个角色ID（用逗号分隔），用户只要拥有其中任意一个角色即会被返回。

**示例**：
```
?roleIds=role-id-1,role-id-2,role-id-3
```

这将返回拥有 `role-id-1` **或** `role-id-2` **或** `role-id-3` 的所有用户。

### Q4: 如何按姓名排序？

**回答**：
使用 `sortBy` 参数指定排序规则。

**示例**：
- 姓名升序：`?sortBy=name:asc`（默认）
- 姓名降序：`?sortBy=name:desc`
- 多字段排序：`?sortBy=name:asc,username:desc`

### Q5: 返回的用户信息包含密码吗？

**回答**：
不包含。User 模型已配置 `toJSON` 方法自动过滤敏感字段（如密码、token等），确保数据安全。

### Q6: 如何筛选特定技能的维护人员？

**回答**：
可以通过以下方式：
1. **按岗位筛选**：不同技能对应不同岗位（如"电气工程师"、"机械工程师"）
2. **按角色筛选**：为不同技能创建对应角色
3. **组合筛选**：同时使用部门和岗位筛选

**建议**：
如果需要更细粒度的技能筛选，建议在系统中建立技能标签体系，并扩展本接口支持技能标签筛选。

### Q7: 接口性能如何？查询速度慢怎么办？

**性能优化建议**：
1. **使用筛选条件**：避免不带条件查询全部用户
2. **限制返回数量**：合理设置 `limit` 值
3. **数据库索引**：确保 User、UserProfile、Department、Position 表有合适的索引
4. **缓存优化**：对于不常变化的组织架构数据，可以在前端缓存

**性能指标参考**：
- 带筛选条件的查询：< 200ms
- 不带条件查询全部：< 500ms（取决于用户总数）

## 附录

### 用户状态枚举

| 状态值   | 中文名称 | 说明                                       |
| -------- | -------- | ------------------------------------------ |
| active   | 活跃     | 正常使用中的用户（**本接口只返回此状态**） |
| inactive | 未激活   | 账号创建但未激活                           |
| disabled | 已禁用   | 账号被管理员禁用                           |
| deleted  | 已删除   | 账号被软删除                               |

**注意**: 本接口只返回 `status = 'active'` 的用户。

### sortBy 支持的排序字段

| 字段名   | 类型   | 说明     | 示例            |
| -------- | ------ | -------- | --------------- |
| name     | string | 用户姓名 | `name:asc`      |
| username | string | 用户名   | `username:desc` |
| email    | string | 邮箱     | `email:asc`     |

**排序方向**：
- `asc`: 升序（默认）
- `desc`: 降序

**多字段排序**：
支持多字段排序，使用逗号分隔：
```
?sortBy=name:asc,username:desc
```

### 数据库模型关系

```
User (用户)
  │
  ├─ UserProfile (用户档案) [1:1]
  │    │
  │    ├─ Department (部门) [N:1]
  │    │
  │    └─ Position (岗位) [N:1]
  │
  └─ UserRoles (用户角色关联) [N:M]
       │
       └─ Role (角色) [N:1]
```

**关系说明**：
- 每个用户有且只有一个用户档案（UserProfile）
- 每个用户档案关联一个部门（Department）
- 每个用户档案关联一个岗位（Position）
- 每个用户可以拥有多个角色（通过 UserRoles 中间表）

## 总结

本接口是维护任务管理中的重要辅助接口，主要用于任务派工时选择合适的维护人员。

### 核心功能

1. **灵活的筛选**：支持按部门、岗位、角色等多维度筛选
2. **完整的信息**：返回用户的组织架构信息，方便前端展示
3. **性能优化**：支持结果数量限制和自定义排序
4. **数据安全**：只返回活跃用户，自动过滤敏感信息

### 使用建议

- 根据实际业务需求选择合适的筛选条件
- 合理设置 `limit` 参数，避免一次返回过多数据
- 对于不常变化的数据，可以在前端进行缓存
- 结合其他接口（如任务派工接口）使用，形成完整的业务流程

### 注意事项

- 本接口只返回 `status = 'active'` 的用户
- 用户必须有完整的 UserProfile 档案信息
- 所有筛选条件都是可选的，支持任意组合
- 暂不支持标准的分页查询（page/offset），但支持 limit 限制
