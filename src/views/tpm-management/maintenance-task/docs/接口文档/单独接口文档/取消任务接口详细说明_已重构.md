## 功能概述

### 所有功能

**取消任务**（Cancel Maintenance Task）是维护任务管理模块中的重要操作之一，用于取消已创建的维护任务，使任务进入"已取消"状态，同时自动恢复关联设备状态为"空闲"，并记录任务取消的相关信息，以支持灵活的维护任务管理和异常处理的业务场景。

取消任务操作允许管理员或任务创建者在任务尚未完成时进行撤销，确保系统内维护任务的清晰性和准确性。通过取消操作，系统能够准确记录哪些任务被取消及其原因，为后续的任务管理分析和工作流审计提供完整的数据基础。

### 关键特性

- ✅ **灵活的任务撤销**：支持在任务不同阶段（待执行、执行中、已延期）进行取消，仅终态任务无法取消
- ✅ **自动设备状态恢复**：取消任务时自动恢复设备状态为"空闲"，确保设备资源的准确性
- ✅ **完整的取消信息记录**：支持记录取消原因和详细说明，为任务管理提供完整审计
- ✅ **操作权限校验**：严格验证操作权限，仅管理员或拥有权限的操作者才能取消任务
- ✅ **原子性操作**：取消操作在事务保护下执行，确保任务状态和设备状态的一致性
- ✅ **规范的状态迁移**：任务状态明确从活跃状态转换为"已取消"终态，防止歧义

### 使用前提

- ✅ 维护任务存在且ID有效（需为有效的UUID格式）
- ✅ 维护任务当前状态为"待执行"、"执行中"或"已延期"（其他状态无法取消）
- ✅ 操作用户具有 `mdm.tpm.maintenance-task.manage` 权限或为任务的创建者
- ✅ 操作用户状态为"激活"（inactive用户无法执行取消操作）
- ✅ 持有有效的JWT认证令牌，且令牌未过期

### 不适用场景

- ❌ 任务已完成的取消——已完成的任务是终态，不允许再次操作
- ❌ 任务已取消的取消——已取消的任务无法重复取消
- ❌ 非授权人员的取消操作——只有具有权限的操作者才能取消任务
- ❌ 无权限用户的取消——需要具有管理维护任务的权限

### 详细步骤说明

#### 步骤1: 用户身份验证
- **验证内容**：检查当前登录用户是否有效且状态为激活
- **失败处理**：用户无效或已禁用返回 404 错误（USER_001）
- **说明**：确保操作者是有效的系统用户

#### 步骤2: 任务查询与状态验证
- **验证内容**：查询指定ID的维护任务，验证任务存在且处于可取消状态
- **失败处理**：
  - 任务不存在：返回 404 错误（TPM_TASK_002）
  - 任务处于终态（已完成/已取消）：返回 400 错误（TPM_TASK_010）
- **说明**：只有处于活跃状态的任务才符合取消条件

#### 步骤3: 权限检验
- **验证内容**：检查当前操作用户是否具有 `mdm.tpm.maintenance-task.manage` 权限或为任务创建者
- **失败处理**：无权限返回 403 错误（FORBIDDEN）
- **说明**：确保只有授权人员才能取消任务

#### 步骤4: 事务开启
- **内容**：开启数据库事务，确保取消操作的原子性
- **说明**：如果取消过程中发生异常，事务会自动回滚，保证数据一致性

#### 步骤5: 任务状态更新
- **更新字段**：
  - `status`：设置为"已取消"
  - `cancelReason`：设置为取消原因
  - `cancelRemarks`：设置为取消详细说明
  - `cancelledBy`：设置为当前操作用户ID
  - `cancelledAt`：设置为当前时间
  - `updatedBy`：设置为当前操作用户ID
  - `updatedAt`：设置为当前时间
- **说明**：记录任务取消信息和时间戳

#### 步骤6: 设备状态恢复
- **内容**：调用集成服务恢复设备状态
- **处理**：设备状态恢复为"空闲"，清除维护标记
- **说明**：确保设备可用性管理的准确性

#### 步骤7: 事务提交
- **内容**：提交数据库事务，确保所有更新操作持久化
- **说明**：事务提交成功后，取消操作不可逆

#### 步骤8: 数据查询与响应
- **内容**：查询更新后的完整任务信息，包括关联的设备、操作人员等
- **说明**：返回的完整信息可供前端直接展示，无需额外查询

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/maintenance-tasks/:taskId/cancel`

**功能描述**: 取消维护任务，将任务状态变更为"已取消"，自动恢复设备状态为"空闲"。仅管理员或拥有权限的操作者才能取消处于待执行、执行中或已延期状态的任务。

**认证要求**: JWT Bearer Token 认证，需要 `mdm.tpm.maintenance-task.manage` 权限

所有错误的 API 调用都会返回以下统一格式：

```json

    "code": "ERROR_CODE",

    "version": "v1"
  }

```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

  baseURL: 'http://localhost:3000/v1',
  headers: {

  },
});

async function cancelMaintenanceTask(taskId, cancelData, token) {
  try {
    const response = await api.post(
      `/mdm/tpm/maintenance-tasks/${taskId}/cancel`,
      cancelData,
      {
        headers: {
          Authorization: `Bearer ${token}`,
        },

    );

    return response.data.data;
  } catch (error) {
    console.error('任务取消失败:', error.response.data);
    throw error;
  }
}

  cancelReason: '设备故障，无法维护',

## 常见问题

### Q1: 取消任务后能否撤销取消操作？

**A**: 不能。一旦任务被取消并确认，取消操作无法撤销。如果需要重新执行维护工作，应该创建新的任务。

### Q2: 取消任务是否会删除任务记录？

**A**: 不会删除。取消操作只是改变任务状态为"已取消"，任务记录会完整保留在系统中，便于后续查询、统计和审计。

### Q3: 任务取消时，设备状态会如何变化？

**A**: 设备状态会自动恢复为"空闲"。无论设备当前处于什么维护状态（维护中、延期等），取消任务后都会恢复为可用状态。

### Q4: 非管理员能否取消任务？

**A**: 不能。系统要求操作用户必须具有 `mdm.tpm.maintenance-task.manage` 权限，这是为了保证取消操作的权威性和安全性。普通员工无法取消任务。

### Q5: 哪些状态的任务可以取消？

**A**: 以下状态的任务可以取消：
- 待执行：任务还未开始执行
- 执行中：任务正在执行中
- 已延期：任务处于延期状态

以下状态的任务不能取消：
- 已完成：任务已完成，无法取消
- 已取消：任务已取消，无法再次取消

### Q6: cancelReason 和 cancelRemarks 有什么区别？

**A**:
- **cancelReason**：取消原因（必填），应简洁说明为什么取消，如"设备故障"、"优先级调整"等
- **cancelRemarks**：取消详细说明（可选），可提供更详细的背景信息，如"预计下周一重新安排"等

### Q7: 取消任务是否会影响执行人的工作计划？

**A**: 是的。任务被取消后，执行人可以被释放去执行其他任务。建议在取消之前通知相关人员。

### Q8: 能否批量取消多个任务？

**A**: 当前接口只支持单任务取消。如需批量取消，需要前端循环调用此接口。

### Q9: 取消操作是否支持幂等性？

**A**: 不支持。当任务已处于"已取消"状态时，再次调用会返回错误。建议前端实现防止重复提交的机制。

### Q10: 取消任务时是否需要提供特殊权限令牌？

**A**: 不需要。只需提供有效的JWT Token，系统会在Token中验证用户权限。如果用户不具有 `mdm.tpm.maintenance-task.manage` 权限，请求会被拒绝。

```
[待执行]
   │
   ├─→ 接单操作 → 保持[待执行]
   │
   ├─→ 派工操作 → 保持[待执行]

   ├─→ 延期申请 → 转变为[已延期]
   │

[执行中]
   │
   ├─→ 完成任务 → 转变为[已完成] ← 终态
   │
   ├─→ 延期申请 → 转变为[已延期]
   │
   └─→ 取消任务 → 转变为[已取消] ← 终态

[已延期]
   │
   ├─→ 开始执行 → 转变为[执行中]
   │
   ├─→ 延期申请 → 保持[已延期]（更新延期原因）
   │
   └─→ 取消任务 → 转变为[已取消] ← 终态

[已取消] ← 终态，无任何操作可转出
[已完成] ← 终态，无任何操作可转出
```

### 日期时间格式说明

所有涉及时间的字段都使用 ISO 8601 标准格式：

- **格式**: `YYYY-MM-DDTHH:mm:ss.sssZ`
- **示例**: `2024-01-20T07:30:00.000Z`

- **时区转换**: 前端需要根据本地时区显示时间
