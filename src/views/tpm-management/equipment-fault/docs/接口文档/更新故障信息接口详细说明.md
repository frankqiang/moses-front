## 功能概述

### 所有功能

更新故障信息（Update Equipment Failure）是设备故障管理模块中的核心操作之一,用于修正或补充已创建的故障报告基本信息,以支持故障信息维护、信息纠错、补充完善等业务场景。

此接口专门用于更新故障的基本信息字段,如故障描述、故障等级、故障类型、初步原因分析等。**注意**：故障处理相关的状态变更操作（如开始处理、完成处理、验证、关闭等）需要使用专用的操作接口,不通过此接口进行。

### 关键特性

- ✅ **灵活更新**：支持更新故障的所有基本信息字段,至少提供一个字段即可
- ✅ **数据验证**：自动验证关联数据的有效性（设备、报告人等）
- ✅ **唯一性保证**：更新故障编码时自动验证唯一性,避免编码冲突
- ✅ **事务保护**：使用数据库事务确保数据一致性,更新失败自动回滚
- ✅ **完整返回**：返回更新后的完整故障信息,包括所有关联数据
- ✅ **审计追踪**：自动记录更新人和更新时间,保留操作审计记录

---

### 使用前提

- ✅ 故障记录必须存在且未被软删除
- ✅ 用户必须具有 `mdm.tpm.equipment-failure.manage` 权限
- ✅ 更新的设备ID和报告人ID必须是系统中的有效数据
- ✅ 更新故障编码时不能与其他故障记录的编码重复

### 不适用场景

- ❌ 故障状态变更操作（需使用开始处理、完成处理、验证、关闭等专用接口）
- ❌ 更新处理人员、验证人员（由相应的处理流程接口自动设置）
- ❌ 记录处理措施和使用备件（需通过完成处理接口操作）
- ❌ 更新MTTR（系统在完成处理时自动计算）

### 详细步骤说明

#### 步骤1: 接收更新请求

- 接收客户端发送的 PATCH 请求
- 从路径参数中提取 `failureId`
- 从请求体中提取要更新的字段信息
- 从认证信息中获取当前操作用户ID

#### 步骤2: 验证路径参数

- **验证故障ID**:
  - 必须是有效的UUID格式
  - 不能为空
- 验证失败返回 400 错误

#### 步骤3: 验证请求体参数

- **至少提供一个字段**: 请求体不能为空,必须包含至少一个要更新的字段
- **字段格式验证**:
  - `failureCode`: 字符串,最大100字符
  - `equipmentId`: UUID格式
  - `failureTime`: ISO 8601日期时间格式
  - `reporterId`: UUID格式
  - `failureDescription`: 字符串,不能为空
  - `failureLevel`: 枚举值（I级-严重/II级-重大/III级-一般/IV级-轻微）
  - `impactDegree`: 枚举值（停机/性能下降/无影响）
  - `failureType`: 枚举值（机械/电气/液压/控制/其他）
  - `failureCausePreliminary`: 字符串,可为空
  - `failureCauseDetailed`: 字符串,可为空
- 验证失败返回 400 错误

#### 步骤4: 开启数据库事务

- 创建数据库事务
- 确保后续所有数据库操作的原子性
- 任何错误发生时自动回滚

#### 步骤5: 查询故障记录

- **查询条件**:
  - 故障ID = failureId
  - isDeleted = false（未软删除）
- **查询失败处理**:
  - 记录不存在: 抛出 404 错误（错误码: EQUIPMENT_FAILURE_002）
  - 事务自动回滚

#### 步骤6: 验证关联数据

- **如果更新设备ID**:
  - 查询设备是否存在
  - 不存在则抛出 404 错误（错误码: EQUIPMENT_001）
- **如果更新报告人ID**:
  - 查询用户是否存在
  - 不存在则抛出 404 错误（错误码: USER_001）
- 验证失败时事务自动回滚

#### 步骤7: 验证编码唯一性

- **如果更新故障编码**:
  - 将编码转为大写并去除空格
  - 查询是否存在相同编码的其他故障记录（排除当前记录）
  - 存在重复则抛出 400 错误（错误码: EQUIPMENT_FAILURE_001）
- 验证失败时事务自动回滚

#### 步骤8: 执行更新操作

- **更新字段**: 将请求体中的所有字段更新到数据库
- **自动设置**: updatedBy = 当前用户ID
- **自动设置**: updatedAt = 当前时间戳
- **字符串处理**:
  - `failureCode`: 自动转为大写
  - `failureDescription`: 自动去除首尾空格
  - `failureCausePreliminary`: 自动去除首尾空格
  - `failureCauseDetailed`: 自动去除首尾空格

#### 步骤9: 提交事务

- 所有更新操作成功执行后提交事务
- 将数据持久化到数据库
- 记录操作日志

#### 步骤10: 查询完整信息

- 重新查询更新后的故障记录
- **包含关联数据**:
  - 设备信息（equipment）
  - 报告人信息（reporter）
  - 处理人信息（repairer）
  - 验证人信息（verifier）
  - 创建人信息（creator）
  - 更新人信息（updater）

#### 步骤11: 返回更新结果

- 封装为统一响应格式
- HTTP状态码: 200
- 返回完整的故障信息
- 包含成功消息: "更新故障信息成功"

## 接口文档

### 基本信息

**接口路径**: `PATCH /v1/mdm/tpm/equipment-failures/{failureId}`

**功能描述**: 更新故障的基本信息。可以更新故障描述、等级、类型、初步原因分析等字段。注意：故障处理相关的操作（如开始处理、完成处理等）需要使用专用的操作接口。

**认证要求**: Bearer Token认证,需要 `mdm.tpm.equipment-failure.manage` 权限

## 统一响应格式说明

### 成功响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
    // 具体的业务数据,根据接口而不同
  },
  "message": "操作成功的描述信息",
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值,表示请求是否成功
- `data`: 成功时包含业务数据,失败时为 null
- `error`: 失败时包含错误信息,成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码,用于程序化处理
- `error.message`: 用户友好的错误描述,可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息,包含时间戳、请求 ID 和版本号

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

## 常见问题

### Q1: 为什么不能通过此接口修改故障状态？

**A**: 故障状态的变更涉及复杂的业务流程和验证规则，例如：
- 开始处理需要分配处理人员并记录开始时间
- 完成处理需要填写处理措施和使用备件
- 验证需要检查验证人不能是处理人
- 关闭需要处理设备状态恢复

这些操作都有专门的接口来处理，确保业务逻辑的完整性和数据一致性。如需变更状态，请使用：
- 开始处理：`POST /v1/mdm/tpm/equipment-failures/:failureId/start-repair`
- 完成处理：`POST /v1/mdm/tpm/equipment-failures/:failureId/complete-repair`
- 验证处理：`POST /v1/mdm/tpm/equipment-failures/:failureId/verify`
- 关闭故障：`POST /v1/mdm/tpm/equipment-failures/:failureId/close`

---

### Q2: 更新故障信息后，为什么返回的数据包含所有关联信息？

**A**: 返回完整的故障信息（包括设备、报告人、处理人等关联数据）是为了：
1. **前端状态同步**: 前端可以直接使用返回的数据更新界面，无需再次查询
2. **数据完整性**: 确保前端获取到最新的完整数据，包括关联数据可能的变更
3. **减少请求**: 避免前端在更新后再发起一次详情查询请求
4. **一致性保证**: 返回的数据与查询详情接口格式一致，便于前端处理

如果只需要更新后的基本字段，前端可以只使用 `data` 中的核心字段，忽略关联对象。

---

### Q3: 更新故障编码时为什么会被转换为大写？

**A**: 故障编码统一转换为大写是为了：
1. **一致性**: 确保所有故障编码格式统一，避免因大小写差异导致的编码冲突
2. **可读性**: 大写字母在编码中更加醒目，便于识别
3. **唯一性验证**: 统一格式后，唯一性验证更加准确（避免 "GZ-001" 和 "gz-001" 被视为不同编码）

例如，提交 "gz-2024-001" 会自动转换为 "GZ-2024-001" 并存储。

---

### Q4: 更新关联数据（设备ID、报告人ID）时会发生什么？

**A**: 更新关联数据时，系统会：

1. **验证有效性**:
   - 查询新的设备ID是否存在于设备表中
   - 查询新的报告人ID是否存在于用户表中
   - 如果不存在，返回 404 错误

2. **更新关联**:
   - 成功验证后，更新外键关联
   - 返回的数据中会包含新关联对象的完整信息

3. **保持历史**:
   - 创建人（createdBy）保持不变
   - 更新人（updatedBy）记录为当前操作用户
   - 创建时间（createdAt）保持不变
   - 更新时间（updatedAt）更新为当前时间

**注意**: 更新设备ID可能会影响故障统计和设备故障历史，请谨慎操作。

---

### Q5: 至少提供一个字段是什么意思？

**A**: 此接口要求请求体中至少包含一个要更新的字段，原因是：

1. **避免空更新**: 如果请求体为空 `{}`，不会更新任何数据，这样的请求没有意义
2. **明确意图**: 要求至少一个字段确保开发者明确知道要更新什么
3. **性能考虑**: 避免无效的数据库操作和事务开销

**正确示例**:
```json
{
  "failureLevel": "II级-重大"
}
```

**错误示例**:
```json
{}
```

如果提交空对象，会收到 400 错误：`"至少需要提供一个更新字段"`

---

### Q6: 更新操作失败后数据会发生什么？

**A**: 更新操作使用数据库事务保护，确保数据一致性：

1. **事务回滚**: 任何验证失败或错误发生时，所有数据库操作自动回滚
2. **原子性**: 要么全部更新成功，要么全部不更新，不会出现部分更新的情况
3. **数据不变**: 失败后，数据库中的数据保持更新前的状态
4. **错误提示**: 返回详细的错误信息，说明失败原因

例如，如果同时更新故障编码和设备ID，而设备ID无效，整个更新操作都会回滚，故障编码也不会被修改。

---

### Q7: 更新时可以清空某个字段的值吗？

**A**: 取决于字段的必填性：

**可以清空的字段**（可选字段）:
- `failureCausePreliminary`: 传空字符串 `""` 或 `null`
- `failureCauseDetailed`: 传空字符串 `""` 或 `null`

**不能清空的字段**（必填字段）:
- `failureDescription`: 不能为空，会返回验证错误
- `failureLevel`: 必须是枚举值之一
- `impactDegree`: 必须是枚举值之一
- `failureType`: 必须是枚举值之一

---

### Q8: 如何处理更新时的并发问题？

**A**: 系统通过以下机制处理并发更新：

1. **数据库事务隔离**: 使用数据库事务确保隔离性
2. **乐观锁机制**: 通过 `updatedAt` 时间戳判断数据是否被修改
3. **唯一性约束**: 数据库层面的唯一性约束（如故障编码）

**最佳实践**:
- 更新前先查询最新数据，获取当前的 `updatedAt` 值
- 如果其他用户先更新了数据，当前更新会成功，但建议前端提示用户刷新数据
- 对于编码等唯一字段，如果冲突会返回明确的错误提示

**并发场景示例**:
- 用户A和用户B同时查询故障详情
- 用户A先更新故障等级为"II级-重大"
- 用户B后更新故障描述
- 两次更新都会成功，最终数据包含两次更新的内容
