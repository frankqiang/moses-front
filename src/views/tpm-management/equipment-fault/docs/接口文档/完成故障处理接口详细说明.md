## 功能概述

### 所有功能

完成故障处理（Complete Repair）是设备故障管理模块中的核心流程操作，用于记录故障处理完成情况，将故障从"处理中"状态转入"已解决"状态，以支持故障全生命周期管理和维修质量追溯的业务场景。

当维修人员完成故障处理后，通过此接口记录详细的处理措施、使用的备件清单和详细原因分析。系统自动记录处理完成时间，计算MTTR（平均修复时间），为后续的设备可靠性分析和维修效率评估提供准确数据。

### 关键特性

- ✅ **处理措施记录**：详细记录故障处理过程和采取的措施，形成维修知识库
- ✅ **备件清单管理**：记录使用的备件及数量，支持成本核算和库存管理
- ✅ **自动时间记录**：系统自动记录处理完成时间，确保时间数据准确性
- ✅ **MTTR自动计算**：自动计算平均修复时间（处理完成时间 - 处理开始时间），为KPI统计提供数据
- ✅ **处理人权限校验**：确保只有故障处理人员本人才能完成处理，防止越权操作
- ✅ **详细原因分析**：支持补充完善故障原因分析，为根本原因分析和预防措施制定提供依据

---

### 使用前提

- ✅ **故障记录存在**：故障记录必须已创建且在系统中存在
- ✅ **状态符合要求**：故障当前状态必须为"处理中"
- ✅ **处理人权限**：只有故障的处理人员本人才能完成处理
- ✅ **管理权限**：需要 `mdm.tpm.equipment-failure.manage` 权限
- ✅ **已开始处理**：故障必须已经通过"开始处理"接口分配处理人员并记录处理开始时间

### 不适用场景

- ❌ **故障未开始处理**：状态为"待处理"的故障需先调用"开始处理"接口
- ❌ **非处理人操作**：不是故障处理人员本人不能完成处理（防止越权）
- ❌ **故障已解决**：已经完成处理的故障不能重复完成（需先返工）
- ❌ **故障已关闭**：已关闭的故障不能完成处理

### 详细步骤说明

#### 步骤1: 维修人员诊断并处理故障

**维修过程**：
- **故障诊断**：检查故障部位，确认故障原因
- **制定方案**：根据故障情况确定处理方案
- **执行维修**：
  - 拆卸故障部件
  - 更换或维修故障零件
  - 使用备件进行更换
  - 调整相关参数
- **功能测试**：
  - 试运行设备
  - 检查设备各项功能
  - 确认故障已消除
  - 验证设备性能恢复

#### 步骤2: 整理处理信息

**处理措施总结**（必填）：
- 详细描述处理过程和步骤
- 记录采取的技术措施
- 说明调整的参数和设置
- 记录测试验证结果
- 示例："拆解主轴，更换磨损轴承，添加润滑油，调整轴承间隙至标准值0.05mm，试运行2小时无异常"

**使用备件统计**（可选）：
- 记录每种使用的备件
- 统计使用数量
- 记录备件编码和名称
- 用于成本核算和库存扣减

**详细原因分析**（可选）：
- 在初步原因基础上深入分析
- 确认故障根本原因
- 分析故障发生机理
- 识别故障诱因
- 示例："主轴承使用时间已达8000小时，超过额定寿命；润滑系统自动加油功能失效导致润滑不足，加速了轴承磨损"

#### 步骤3: 调用完成处理接口

**必填信息**：
- `repairActions`：故障处理措施，不能为空，建议详细描述

**可选信息**：
- `sparePartsUsed`：使用备件清单（JSONB数组格式）
  - 每个备件包含：sparePartId、sparePartCode、sparePartName、quantity
- `failureCauseDetailed`：详细故障原因分析

#### 步骤4: 权限验证

**验证要点**：
- 操作用户必须具有 `mdm.tpm.equipment-failure.manage` 权限
- 确保只有授权人员才能完成故障处理
- 权限不足返回 403 Forbidden 错误

#### 步骤5: 故障记录验证

**验证内容**：
- 故障ID（failureId）对应的记录是否存在
- 使用数据库查询验证故障记录存在性
- 验证故障记录未被软删除（isDeleted = false）

**验证失败处理**：
- 故障不存在返回 404 Not Found
- 错误码：EQUIPMENT_FAILURE_002
- 提示故障ID无效

#### 步骤6: 状态验证

**允许的起始状态**：
- **处理中**：正常流程，处理完成后的状态变更（唯一允许状态）

**不允许的起始状态**：
- **待处理**：尚未开始处理，需先调用"开始处理"接口
- **已解决**：已经完成处理，不能重复完成
- **已验证**：已验证通过，正常流程应关闭
- **已关闭**：已关闭，流程结束

**验证失败处理**：
- 返回 400 Bad Request
- 错误码：EQUIPMENT_FAILURE_003
- 提示："当前状态不允许完成处理，只有"处理中"状态才能完成处理"

#### 步骤7: 处理人身份验证

**验证逻辑**：
```javascript
// 获取当前操作用户ID
const currentUserId = req.user.id;

// 获取故障记录的处理人员ID
const failure = await EquipmentFailure.findByPk(failureId);
const repairerId = failure.repairerId;

// 验证是否为处理人员本人
if (currentUserId !== repairerId) {
  throw new ApiError(403, 'EQUIPMENT_FAILURE_004', '只有故障处理人员才能完成处理');
}
```

**验证意义**：
- **防止越权操作**：确保其他人不能代替处理人员完成
- **责任明确**：处理人员对自己的处理结果负责
- **数据准确性**：确保处理信息由实际处理人填写
- **审计追踪**：明确处理责任人

**验证失败处理**：
- 返回 403 Forbidden
- 错误码：EQUIPMENT_FAILURE_004
- 提示："只有故障处理人员才能完成处理"
- details中包含当前处理人员信息

#### 步骤8: 参数验证

**处理措施验证**（必填）：
- `repairActions` 字段不能为空
- 必须是字符串类型
- 建议至少包含20个字符以确保描述完整
- 使用 Joi 验证器验证：`Joi.string().required().trim().min(1)`

**备件清单验证**（可选）：
- 如果提供，必须是数组格式
- 数组元素结构验证：
  - `sparePartId`: 必填，字符串
  - `sparePartCode`: 必填，字符串
  - `sparePartName`: 必填，字符串
  - `quantity`: 必填，正整数（> 0）

**详细原因验证**（可选）：
- 如果提供，必须是字符串类型
- 允许为空字符串或null

**验证失败处理**：
- 返回 400 Bad Request
- 错误码：VALIDATION_ERROR
- 提示具体的验证错误信息
- details中包含错误字段名称

#### 步骤9: 开启数据库事务

**事务保护内容**：
- 故障记录更新（处理措施、备件清单、详细原因、完成时间、MTTR、状态）
- 确保所有字段同时更新成功

**事务失败回滚**：
- 如任一操作失败，全部回滚
- 保证数据一致性

#### 步骤10: 记录处理完成时间

**时间记录**：
- 使用系统当前时间：`new Date()`
- 存储为 `repairEndTime` 字段
- 格式：ISO 8601（`2024-01-20T15:30:00.000Z`）

**时间准确性保证**：
- 使用服务器时间，不依赖客户端时间
- 确保时区一致性
- 为MTTR计算提供准确的结束时间点

#### 步骤11: 计算MTTR

**计算公式**：
```javascript
const repairStartTime = failure.repairStartTime; // 开始处理时记录的时间
const repairEndTime = new Date(); // 当前系统时间
const mttrMilliseconds = repairEndTime - repairStartTime;
const mttrHours = mttrMilliseconds / (1000 * 60 * 60); // 转换为小时
const mttrHoursRounded = Math.round(mttrHours * 100) / 100; // 保留2位小数
```

**MTTR说明**：
- **MTTR定义**：Mean Time To Repair（平均修复时间）
- **计算单位**：小时（hours）
- **精度**：保留2位小数
- **用途**：
  - 设备可靠性评估
  - 维修效率分析
  - 维修人员绩效评估
  - 备件需求预测

**示例**：
- 处理开始时间：2024-01-20 11:00:00
- 处理完成时间：2024-01-20 15:30:00
- MTTR = 4.5 小时

#### 步骤12: 更新故障记录

**更新字段**：
```javascript
{
  repairActions: "更换主轴承，添加润滑油...",      // 处理措施
  sparePartsUsed: [...],                         // 使用备件清单（JSONB）
  failureCauseDetailed: "主轴承磨损严重...",     // 详细原因分析
  repairEndTime: new Date(),                     // 处理完成时间
  mttrHours: 4.5,                                // 平均修复时间
  status: "已解决",                              // 状态变更
  updatedBy: req.user.id,                        // 更新人ID
  updatedAt: new Date()                          // 更新时间
}
```

**数据库操作**：
- 使用 Sequelize ORM 的 `update` 方法
- 在事务中执行
- 更新成功后重新查询完整记录（包含关联数据）

#### 步骤13: 提交事务

**成功提交**：
- 故障记录更新成功
- 返回更新后的完整故障记录（包含关联的设备、人员信息）
- 状态已变更为"已解决"
- MTTR已计算并保存

**失败回滚**：
- 任一更新失败，全部回滚
- 返回错误信息，故障状态保持"处理中"
- 可重新调用完成处理接口

#### 步骤14: 通知质检人员验证（预留功能）

**未来扩展**：
- 发送站内消息通知质检人员
- 发送邮件或短信提醒
- 推送移动端通知
- 自动分配验证人员

**当前处理**：
- 仅更新数据库记录
- 质检人员需主动查看待验证的故障列表

#### 步骤15: 返回更新后的故障记录

**返回内容**：
- HTTP 状态码：200 OK
- 包含完整的故障记录信息
- 包含关联的设备信息、处理人员信息
- 包含新记录的处理措施、备件清单、MTTR
- 包含操作结果消息："故障处理已完成"

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/equipment-failures/{failureId}/complete-repair`

**功能描述**: 完成指定故障的处理。记录详细的处理措施、使用的备件清单和详细原因分析，将故障状态从"处理中"更新为"已解决"。系统自动记录处理完成时间并计算MTTR（平均修复时间）。只有故障的处理人员本人才能完成处理。

**认证要求**: Bearer Token 认证，需要 `mdm.tpm.equipment-failure.manage` 权限

## 统一响应格式说明

### 成功响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
    // 具体的业务数据，根据接口而不同
  },
  "message": "操作成功的描述信息",
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号


**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

## 常见问题

### Q1: 完成处理后发现遗漏信息，如何补充？

**A**: 有两种方式补充信息：

**方式1：使用更新故障接口（推荐）**

- 接口：`PATCH /v1/mdm/tpm/equipment-failures/:failureId`
- 可更新的字段：
  - `failureCauseDetailed`：补充详细原因分析
  - `sparePartsUsed`：补充遗漏的备件
  - 其他非核心字段
- 优点：不影响MTTR和处理完成时间
- 适用场景：处理完成后发现信息遗漏

**方式2：通过根本原因分析接口补充**

- 接口：`POST /v1/mdm/tpm/equipment-failures/:failureId/root-cause-analysis`
- 补充：`rootCauseAnalysis`、`preventiveMeasures`
- 优点：专门用于深入分析
- 适用场景：后续进行根本原因分析时补充

**不能补充的信息**：
- `repairActions`：处理措施是核心信息，完成后一般不建议修改
- `repairEndTime`：系统自动记录，不能手动修改
- `mttrHours`：自动计算值，不能手动修改

---

### Q2: 处理过程中使用了很多备件，如何全部记录？

**A**: `sparePartsUsed` 数组没有数量限制，可以记录所有使用的备件。

**建议**：
- **完整记录**：即使是小件（如螺栓、密封圈），也应记录
- **准确数量**：确保数量准确，用于库存扣减
- **备件信息完整**：包含备件ID、编码、名称，便于追溯
- **分类记录**：按备件类型分组记录，便于阅读

### Q5: MTTR是如何计算的？计算有误怎么办？

**A**: MTTR由系统自动计算，公式如下：

**计算公式**：
```
MTTR（小时）= (处理完成时间 - 处理开始时间) / (1000 * 60 * 60)
```

**计算示例**：
- 处理开始时间：2024-01-20 11:00:00
- 处理完成时间：2024-01-20 15:30:00
- 时间差：4.5小时
- MTTR = 4.5（保留2位小数）

**MTTR计算有误的情况**：

**情况1：处理开始时间记录错误**
- 原因：开始处理时时间记录不准确
- 解决：需要联系管理员手动修正处理开始时间，系统不提供接口修改

**情况2：中间暂停未计入**
- 示例：等待备件采购，实际停工2小时
- 当前限制：系统不支持暂停/恢复，MTTR包含等待时间
- 未来扩展：可增加暂停时间段记录功能

**情况3：跨天处理**
- 示例：今天开始，明天完成
- 计算方式：仍按实际时间差计算，MTTR可能很大（如20小时）
- 说明：这是真实的修复时间，反映了实际情况

**建议**：
- 准确记录处理开始时间
- 在处理措施中说明等待时间
- 如确实需要修正MTTR，可通过工单联系技术支持

### Q6: 其他人可以代替处理人员完成处理吗？

**A**: **不能**。系统强制要求只有处理人员本人才能完成处理。

**验证规则**：
```javascript
if (currentUserId !== repairerId) {
  throw new ApiError(403, 'EQUIPMENT_FAILURE_004', '只有故障处理人员才能完成处理');
}
```

**设计原因**：
1. **责任明确**：处理人员对自己的处理结果负责
2. **信息准确**：只有实际处理人才最清楚处理过程
3. **防止越权**：防止他人代填或篡改处理信息
4. **审计追踪**：确保操作人和记录人一致

**特殊情况处理**：

**情况1：处理人员离职**
- 解决：使用更新故障接口先更换处理人员
- 新处理人员接手后完成处理

**情况2：协作处理**
- 主处理人员：由其完成处理
- 协助人员：在 `repairActions` 中注明参与人员

**情况3：处理人员请假**
- 短期请假：等待处理人员返回后完成
- 长期请假：先更换处理人员

### Q7: 完成处理后，设备状态会自动恢复吗？

**A**: **不会自动恢复**。设备状态恢复需要在"验证处理"环节。

**状态变化流程**：

1. **开始处理**（影响程度=停机）：
   - 故障状态：待处理 → 处理中
   - 设备状态：启用 → **维修中**

2. **完成处理**：
   - 故障状态：处理中 → 已解决
   - 设备状态：**维修中**（保持不变）

3. **验证处理**：
   - 故障状态：已解决 → 已验证
   - 设备状态：维修中 → **启用**（恢复）

**设计原因**：
- 处理完成不代表质量合格
- 需要质检人员验证处理结果
- 验证通过后才能恢复生产使用
- 防止处理不彻底导致二次故障

**手动恢复**：
- 如确需立即恢复，可调用设备更新接口手动修改设备状态
- 但不建议这样做，应遵循正常验证流程

### Q8: 处理措施应该写多详细？

**A**: 建议遵循 **STAR原则**（Situation-Task-Action-Result）。

**建议详细程度**：

**最低要求**（通过验证）：
- 简要描述处理步骤
- 至少20个字符
- 示例："更换主轴承，添加润滑油，测试正常"

**推荐详细度**（最佳实践）：
- **Situation（情况）**：发现的具体问题
- **Task（任务）**：确定的处理方案
- **Action（行动）**：具体执行步骤
- **Result（结果）**：处理后的验证结果

**示例**：

**简单描述**（最低要求）：
```
"更换主轴承，添加润滑油，调整间隙，测试正常"
```

**详细描述**（推荐）：
```
"经检查发现主轴承严重磨损，内圈有裂纹（Situation）；
决定更换新轴承并全面检查润滑系统（Task）；
拆解主轴，更换2个主轴承，添加5L润滑油，调整轴承间隙至标准值0.05mm，
检查润滑系统自动加油功能并修复（Action）；
试运行2小时，温度正常，无异响，振动值在标准范围内（Result）"
```

**包含的关键信息**：
- ✅ 具体操作步骤
- ✅ 更换的备件及规格
- ✅ 调整的参数及数值
- ✅ 测试验证方法和结果
- ✅ 处理时长分布（可选）

**不建议**：
- ❌ 过于简单："已修好"
- ❌ 没有结果："更换轴承"（缺少验证）
- ❌ 没有细节："维修完成"

### Q9: 可以先完成处理，后续再补充备件清单吗？

**A**: 可以，但**不推荐**。

**可以的方式**：

**方式1：完成处理时不填备件**

**方式2：后续通过更新接口补充**

**不推荐的原因**：
1. **成本统计不准**：延迟记录导致统计时点不准确
2. **库存管理混乱**：备件使用和库存扣减不同步
3. **容易遗忘**：后续可能忘记补充
4. **数据不完整**：影响维修报告的完整性

**推荐做法**：
- 处理完成前整理好备件使用清单
- 一次性完整填写所有信息
- 如确实遗漏，尽快补充

### Q10: 完成处理接口调用失败，会影响数据吗？

**A**: 不会。系统使用数据库事务保证数据一致性。

**保证**：
- ✅ 如果接口返回成功（HTTP 200），所有数据已正确保存
- ✅ 如果接口返回失败（HTTP 4xx/5xx），所有数据保持原样，无任何变化
- ✅ 不会出现部分字段更新、部分字段未更新的不一致情况

**失败处理**：
1. 查看错误响应中的错误码和错误消息
2. 根据错误提示修正问题
3. 重新调用完成处理接口
4. 可多次重试，不会造成数据混乱

**常见失败原因**：
- 权限验证失败：检查是否为处理人员本人
- 状态验证失败：检查故障是否为"处理中"状态
- 参数验证失败：检查处理措施是否填写
- 网络超时：重新调用即可

- 供应商评估：统计备件来源和质量

### MTTR计算说明

**MTTR定义**：
- Mean Time To Repair（平均修复时间）
- 衡量设备故障维修效率的关键指标

**计算公式**：
```
MTTR（小时）= (处理完成时间 - 处理开始时间) / (1000 * 60 * 60)
```

**计算示例**：
- 处理开始：2024-01-20 11:00:00
- 处理完成：2024-01-20 15:30:00
- 时间差：16,200,000 毫秒
- MTTR = 16,200,000 / (1000 * 60 * 60) = 4.5 小时

**精度**：保留2位小数

**用途**：
- 设备可靠性评估
- 维修效率分析
- 维修人员绩效考核
- 备件需求预测
- 维护计划优化
