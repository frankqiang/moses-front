## 功能概述

### 所有功能

创建故障报告（Create Equipment Failure）是设备故障管理模块中的核心操作之一，用于记录设备发生的故障事件，以支持故障跟踪、处理流程管理和设备可靠性分析的业务场景。

当设备发生故障时，由发现人或报告人提交故障信息，系统自动生成故障编码并记录故障详情。支持故障等级、影响程度、故障类型等多维度分类，为后续的故障处理和统计分析提供基础数据。

### 关键特性

- ✅ **自动编码生成**：支持自动生成唯一故障编码（格式：EF-设备编码-时间戳），也可手动指定编码
- ✅ **多维度分类**：支持按故障等级（I-IV级）、影响程度（停机/性能下降/无影响）、故障类型（机械/电气/液压/控制/其他）进行分类
- ✅ **设备状态联动**：当影响程度为"停机"时，自动将关联设备状态设置为"维修中"
- ✅ **实时故障报告**：支持现场人员快速创建故障报告，记录故障发生的准确时间点
- ✅ **初步原因记录**：允许报告人填写初步故障原因分析，为后续处理提供参考
- ✅ **数据完整性验证**：自动验证设备和报告人的有效性，确保数据关联准确

---

### 使用前提

- ✅ **设备存在**：关联的设备必须在系统中存在且有效
- ✅ **报告人有效**：报告人必须是系统中的有效用户
- ✅ **权限要求**：需要 `mdm.tpm.equipment-failure.manage` 权限
- ✅ **必填信息完整**：设备ID、故障时间、报告人ID、故障描述、故障等级、影响程度、故障类型必须填写

### 不适用场景

- ❌ **预防性维护记录**：不用于记录计划内的预防性维护，应使用维护记录管理模块
- ❌ **设备保养记录**：不用于记录日常保养活动，应使用维护记录管理模块
- ❌ **设备巡检记录**：不用于记录日常巡检，巡检发现问题后才创建故障报告

### 详细步骤说明

#### 步骤1: 现场人员发现设备故障

- 操作人员、维修人员或巡检人员在日常工作中发现设备异常
- 确认是需要记录的故障事件（非日常保养或巡检）
- 准备创建故障报告

#### 步骤2: 填写故障报告信息

**必填信息**：
- **设备ID**：选择发生故障的设备，必须是系统中存在的设备
- **故障时间**：记录故障实际发生的时间点（ISO 8601格式）
- **报告人ID**：当前用户或发现人的用户ID
- **故障描述**：详细描述故障现象，包括故障表现、异常声音、温度、震动等
- **故障等级**：根据故障严重程度选择（I级-严重、II级-重大、III级-一般、IV级-轻微）
- **影响程度**：选择对生产的影响（停机、性能下降、无影响）
- **故障类型**：选择故障类别（机械、电气、液压、控制、其他）

**可选信息**：
- **故障编码**：通常不填写，由系统自动生成
- **初步原因分析**：报告人可填写初步判断的故障原因

#### 步骤3: 参数验证

系统自动进行以下验证：

**设备验证**：
- 检查equipmentId是否为有效的UUID格式
- 查询设备是否在数据库中存在
- 验证失败返回错误码：`EQUIPMENT_001`（设备不存在）

**报告人验证**：
- 检查reporterId是否为有效的UUID格式
- 查询用户是否在数据库中存在
- 验证失败返回错误码：`USER_001`（用户不存在）

**必填字段验证**：
- 验证所有必填字段是否提供
- 验证故障描述不为空
- 验证失败返回错误码：`VALIDATION_ERROR`

**枚举值验证**：
- 验证故障等级是否为有效值（I级-严重、II级-重大、III级-一般、IV级-轻微）
- 验证影响程度是否为有效值（停机、性能下降、无影响）
- 验证故障类型是否为有效值（机械、电气、液压、控制、其他）
- 验证失败返回错误码：`VALIDATION_ERROR`

#### 步骤4: 开启数据库事务

- 使用Sequelize事务机制确保数据一致性
- 后续所有数据库操作在同一事务中执行
- 发生错误时自动回滚所有操作

#### 步骤5: 生成或验证故障编码

**自动生成编码**（未提供failureCode）：
- 获取关联设备的设备编码
- 生成时间戳
- 拼接格式：`EF-{设备编码}-{时间戳}`
- 示例：`EF-EQ-001-1704038400000`

**手动指定编码**（提供failureCode）：
- 验证编码格式（1-100字符）
- 查询数据库检查编码唯一性
- 验证失败返回错误码：`EQUIPMENT_FAILURE_001`（故障编码已存在）

#### 步骤6: 创建故障记录

在事务中执行插入操作，保存以下信息：

**必填字段**：
- failureCode（生成或指定的编码）
- equipmentId（设备ID）
- failureTime（故障时间）
- reporterId（报告人ID）
- failureDescription（故障描述）
- failureLevel（故障等级）
- impactDegree（影响程度）
- failureType（故障类型）

**默认值字段**：
- status：默认为"待处理"
- isRepeatFailure：默认为false
- isDeleted：默认为false
- createdBy：当前用户ID
- createdAt：当前时间

**空值字段**：
- failureCausePreliminary（如未提供）
- failureCauseDetailed（null）
- repairStartTime（null）
- repairEndTime（null）
- repairActions（null）
- sparePartsUsed（空数组）
- repairerId（null）
- verifierId（null）
- rootCauseAnalysis（null）
- preventiveMeasures（null）
- mttrHours（null）

#### 步骤7: 判断影响程度并更新设备状态

**如果影响程度 = "停机"**：
- 查询关联设备的当前状态
- 将设备状态更新为"维修中"
- 更新设备的updatedAt和updatedBy字段
- 所有操作在同一事务中完成

**如果影响程度 = "性能下降" 或 "无影响"**：
- 保持设备当前状态不变
- 不执行设备状态更新操作

#### 步骤8: 提交事务

- 验证所有操作都成功执行
- 提交数据库事务，持久化所有更改
- 如发生任何错误，自动回滚事务

#### 步骤9: 返回成功响应

- HTTP状态码：201 Created
- 返回创建成功的完整故障记录
- 包含所有字段信息和关联数据
- 返回统一响应格式

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/equipment-failures`

**功能描述**: 创建新的设备故障报告。当设备发生故障时，由发现人或报告人提交故障信息，系统自动生成故障编码并记录故障详情。支持故障等级、影响程度、故障类型等多维度分类，为后续的故障处理和统计分析提供基础数据。

**认证要求**: Bearer Token 认证，需要 `mdm.tpm.equipment-failure.manage` 权限

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 请求参数

| 参数名                  | 类型   | 必填 | 限制                                          | 描述                | 示例                       |
| ----------------------- | ------ | ---- | --------------------------------------------- | ------------------- | -------------------------- |
| failureCode             | string | 否   | 1-100字符，不提供则自动生成                   | 故障编码            | "GZ-2024-001"              |
| equipmentId             | string | 是   | UUID格式                                      | 关联设备ID          | "f47ac10b-58cc-4372-..."   |
| failureTime             | string | 是   | ISO 8601日期时间格式                          | 故障发生时间        | "2024-01-20T10:30:00.000Z" |
| reporterId              | string | 是   | UUID格式                                      | 故障发现人/报告人ID | "a1b2c3d4-e5f6-7890-..."   |
| failureDescription      | string | 是   | 不能为空                                      | 故障现象描述        | "设备异响，温度过高"       |
| failureLevel            | string | 是   | 枚举: I级-严重/II级-重大/III级-一般/IV级-轻微 | 故障等级            | "I级-严重"                 |
| impactDegree            | string | 是   | 枚举: 停机/性能下降/无影响                    | 影响程度            | "停机"                     |
| failureType             | string | 是   | 枚举: 机械/电气/液压/控制/其他                | 故障类型分类        | "机械"                     |
| failureCausePreliminary | string | 否   | -                                             | 初步故障原因分析    | "轴承磨损严重"             |

### 错误响应

| HTTP状态码 | 错误码                | 错误消息       | 说明                   | 处理建议               |
| ---------- | --------------------- | -------------- | ---------------------- | ---------------------- |

| 400        | EQUIPMENT_FAILURE_001 | 故障编码已存在 | 手动指定的故障编码重复 | 使用自动生成的编码     |

## 使用示例

### 场景1: 设备停机紧急故障报告

**业务需求**: 退火炉主电机突然停机，需要立即创建紧急故障报告，通知维修团队处理。

**特点**:
- 故障等级为"I级-严重"，表示紧急故障
- 影响程度为"停机"，系统会自动将设备状态设为"维修中"
- 详细描述故障现象，包括声音、温度、电流等关键信息
- 填写初步原因分析，为维修团队提供参考

### 场景2: 设备性能下降故障报告

**业务需求**: 冷轧机运行速度下降20%，生产效率受影响，但设备可继续运行。

**特点**:
- 故障等级为"III级-一般"，表示非紧急故障
- 影响程度为"性能下降"，设备状态保持不变
- 可以安排计划性维修，不影响其他生产
- 提供详细的性能数据对比

### 场景3: 液压系统泄漏故障报告

**业务需求**: 液压压机发现液压油泄漏，暂时不影响生产，但需要尽快处理防止扩大。

**特点**:
- 故障等级为"II级-重大"，虽然暂时无影响但需要重视
- 影响程度为"无影响"，当前不影响生产
- 需要尽快安排维修，防止故障扩大
- 提供泄漏速度等关键数据

### 场景4: PLC控制系统故障报告

**业务需求**: 自动化生产线PLC控制系统出现间歇性通讯中断，导致生产不稳定。

**特点**:
- 故障类型为"控制"，属于自动化系统故障
- 详细记录故障频率和时长
- 为电气工程师提供诊断依据
- 影响生产稳定性，需要及时处理

### 场景5: 使用手动指定的故障编码

**业务需求**: 部分企业有自己的故障编码规则，需要手动指定故障编码而非使用系统自动生成。

**特点**:
- 手动指定故障编码"GZ-2024-0120-001"，符合企业编码规范
- 系统会验证编码唯一性
- 故障等级为"IV级-轻微"，属于小故障
- 不填写初步原因分析（可选字段）

## 常见问题

### Q1: 故障编码是如何生成的？

**A**: 系统提供两种方式：
1. **自动生成（推荐）**：不提供failureCode参数，系统自动生成格式为 `EF-{设备编码}-{时间戳}` 的唯一编码
2. **手动指定**：提供failureCode参数，系统会验证编码唯一性，如果已存在会返回错误

**建议**：通常使用自动生成，除非企业有特殊的编码规范要求。

### Q2: 影响程度选择"停机"后，设备状态会如何变化？

**A**: 当影响程度选择"停机"时，系统会自动执行以下操作：
1. 创建故障记录
2. 将关联设备的状态自动更新为"维修中"
3. 后续通过"验证故障处理"或"关闭故障单"操作，设备状态会恢复为"启用"

**注意**：如果选择"性能下降"或"无影响"，设备状态保持不变。

### Q3: 故障等级应该如何选择？

**A**: 根据故障的严重程度和影响范围选择：
- **I级-严重**：导致生产停机，影响交付，需要立即处理（如设备停机、重大安全隐患）
- **II级-重大**：严重影响生产效率（产能下降50%以上），需要优先处理
- **III级-一般**：影响生产但可继续运行（产能下降50%以下），可安排计划性维修
- **IV级-轻微**：轻微影响或无影响，不影响正常生产，可计划性处理

### Q4: 创建故障报告时必须填写初步原因分析吗？

**A**: 不是必须的。`failureCausePreliminary`（初步故障原因分析）是可选字段。
- **建议填写**：如果报告人能够初步判断故障原因，填写初步分析有助于维修人员快速定位问题
- **可以不填**：如果无法判断，可以不填写，由专业维修人员在处理时进行分析

### Q5: 如果选错了设备或报告人，创建后还能修改吗？

**A**: 可以修改。创建故障报告后，可以使用更新接口（`PATCH /v1/mdm/tpm/equipment-failures/:failureId`）修改除ID外的所有字段，包括设备ID和报告人ID。

**注意**：修改时系统会重新验证设备和人员的有效性。

### Q6: 故障时间可以填写未来的时间吗？

**A**: 技术上可以，但不建议。故障时间应该是故障实际发生的时间点。如果填写未来时间，虽然系统不会报错，但会影响后续的统计分析（如MTTR计算、故障趋势分析）。

**建议**：准确记录故障发生的时间，如果无法确定精确时间，使用发现故障的时间。

### Q7: 创建故障报告失败，提示"设备不存在"，如何处理？

**A**: 这个错误说明提供的equipmentId在系统中不存在或已被删除。处理步骤：
1. 检查equipmentId是否正确（UUID格式）
2. 使用设备查询接口确认设备是否存在
3. 如果设备不存在，需要先在设备管理模块中创建设备
4. 确保设备未被软删除（isDeleted=false）

### Q8: 权限不足无法创建故障报告，如何解决？

**A**: 创建故障报告需要 `mdm.tpm.equipment-failure.manage` 权限。解决方案：
1. 联系系统管理员
2. 检查当前用户的角色权限配置
3. 管理员在角色管理中为用户角色分配该权限
4. 重新登录使权限生效

### Q9: 可以为同一设备同时创建多个故障报告吗？

**A**: 可以。一个设备可以有多个故障报告，系统不限制同一设备的故障报告数量。这是合理的，因为：
1. 设备可能同时存在多个不同的故障问题
2. 一个故障处理完成后，可能又出现新的故障
3. 重复故障需要单独记录每次发生

**建议**：创建前先查询该设备是否有未关闭的故障报告，避免重复报告同一问题。

### Q10: 如何判断一个故障是否是重复故障？

**A**: 创建故障报告时，`isRepeatFailure` 字段默认为 `false`。重复故障的判断和标记通常在后续流程中进行：
1. 创建时默认不是重复故障
2. 维修人员在处理过程中，通过查询历史故障记录判断是否为重复故障
3. 使用更新接口将 `isRepeatFailure` 设置为 `true`
4. 需要进行根本原因分析，制定预防措施

**系统提供重复故障查询接口**，可以筛选出所有标记为重复故障的记录，用于专项分析和改进。
