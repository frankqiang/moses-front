## 功能概述

### 所有功能

验证故障处理（Verify Repair）是设备故障管理模块中的质量控制环节，用于确认故障处理结果是否符合要求，将故障从"已解决"状态转入"已验证"状态，以支持故障处理质量管理和设备维修质量追溯的业务场景。

当维修人员完成故障处理后，由质检人员或设备管理员对处理结果进行验证。系统记录验证人员和验证时间，确保故障处理质量可控、可追溯。验证通过后，故障可以关闭并恢复设备正常使用；验证不通过时，可以将故障返工重新处理。

### 关键特性

- ✅ **质量验证**：确保故障处理符合标准，防止处理不彻底导致故障复发
- ✅ **验证人记录**：记录验证人员信息，明确质量责任人
- ✅ **自动时间记录**：系统自动记录验证时间，完善处理全流程时间轴
- ✅ **状态流转控制**：自动将故障状态从"已解决"更新为"已验证"
- ✅ **设备状态准备**：为设备恢复正常使用做准备，验证后可关闭故障单
- ✅ **质量追溯**：完整记录处理人员和验证人员，支持质量问题追溯

---

### 使用前提

- ✅ **故障记录存在**：故障记录必须已创建且在系统中存在
- ✅ **状态符合要求**：故障当前状态必须为"已解决"
- ✅ **已完成处理**：故障必须已记录处理措施和处理完成时间
- ✅ **验证人有效**：指定的验证人员必须是系统中的有效用户
- ✅ **权限要求**：需要 `mdm.tpm.equipment-failure.manage` 权限

### 不适用场景

- ❌ **故障未处理完成**：状态为"待处理"或"处理中"的故障需先完成处理
- ❌ **故障已验证**：已验证的故障不能重复验证
- ❌ **故障已关闭**：已关闭的故障不能验证
- ❌ **验证人是处理人**：验证人员不能是故障的处理人员本人（避免自己验证自己的工作）

### 详细步骤说明

#### 步骤1: 故障处理完成

**前置状态**：
- 维修人员已完成故障处理
- 故障状态为"已解决"
- 已记录处理措施、使用备件、处理完成时间
- MTTR已自动计算

**触发条件**：
- 处理完成后自动进入待验证状态
- 质检人员主动查看待验证故障列表

#### 步骤2: 质检人员查看待验证故障列表

**查询条件**：
- 使用故障列表查询接口
- 筛选条件：`status=已解决`
- 可按故障等级、设备、时间等进一步筛选

**优先级判断**：
- I级-严重故障：优先验证
- 停机故障：优先验证，尽快恢复设备
- 按处理完成时间排序，先完成先验证

#### 步骤3: 现场检查验证

**验证内容**：

**1. 设备运行状况检查**
- 启动设备，观察运行状态
- 检查设备各项参数是否正常
- 确认故障现象是否消除
- 检查是否有新的异常情况

**2. 设备功能测试**
- 测试设备各项功能
- 进行负载测试（如适用）
- 验证性能指标是否达标
- 确认设备可正常投入生产

**3. 故障消除确认**
- 对照故障描述，确认症状消失
- 检查故障部位，确认处理到位
- 验证初步原因分析和详细原因是否合理
- 确认处理措施是否针对根本原因

**4. 处理质量检查**
- 检查维修工艺是否规范
- 检查使用备件是否合格
- 检查安装调试是否符合标准
- 检查是否有遗留问题

**验证结果判断**：

**验证通过标准**：
- ✅ 故障现象完全消除
- ✅ 设备运行正常，参数达标
- ✅ 功能测试全部通过
- ✅ 处理质量符合要求
- ✅ 无遗留问题

**验证不通过情况**：
- ❌ 故障现象仍存在或部分存在
- ❌ 设备运行异常或参数不达标
- ❌ 功能测试不通过
- ❌ 处理质量不符合要求
- ❌ 存在新的问题或隐患

**验证不通过处理**：
- 不调用验证接口
- 使用更新故障接口或开始处理接口将故障返工
- 重新分配处理人员（可能是原处理人或更有经验的工程师）
- 记录验证不通过的原因（在故障备注中）

#### 步骤4: 调用验证处理接口

**必填信息**：
- `verifierId`：验证人员ID，必须提供

**验证通过后操作**：
- 调用验证处理接口
- 记录验证人员和验证时间
- 故障状态变更为"已验证"

#### 步骤5: 权限验证

**验证要点**：
- 操作用户必须具有 `mdm.tpm.equipment-failure.manage` 权限
- 确保只有授权人员才能验证故障处理结果
- 权限不足返回 403 Forbidden 错误

#### 步骤6: 故障记录验证

**验证内容**：
- 故障ID（failureId）对应的记录是否存在
- 使用数据库查询验证故障记录存在性
- 验证故障记录未被软删除（isDeleted = false）

**验证失败处理**：
- 故障不存在返回 404 Not Found
- 错误码：EQUIPMENT_FAILURE_002
- 提示故障ID无效

#### 步骤7: 状态验证

**允许的起始状态**：
- **已解决**：故障处理完成，待验证（唯一允许状态）

**不允许的起始状态**：
- **待处理**：尚未开始处理，需先处理
- **处理中**：尚未完成处理，需先完成
- **已验证**：已经验证通过，不能重复验证
- **已关闭**：已关闭，流程结束

**验证失败处理**：
- 返回 400 Bad Request
- 错误码：EQUIPMENT_FAILURE_005
- 提示："当前状态不允许验证，只有"已解决"状态才能验证"

#### 步骤8: 验证人员验证

**验证逻辑**：

**1. 验证人员存在性**
```javascript
// 验证验证人员是否存在
const verifier = await User.findByPk(verifierId);
if (!verifier) {
  throw new ApiError(404, 'USER_001', '指定的验证人员不存在');
}
```

**2. 验证人不能是处理人**
```javascript
// 获取故障记录
const failure = await EquipmentFailure.findByPk(failureId);
const repairerId = failure.repairerId;

// 验证验证人不能是处理人本人
if (verifierId === repairerId) {
  throw new ApiError(400, 'EQUIPMENT_FAILURE_006', '验证人员不能是故障处理人员本人');
}
```

**业务规则说明**：
- **独立验证原则**：验证人员必须独立于处理人员
- **质量控制要求**：避免自己验证自己的工作
- **责任分离**：处理责任和验证责任由不同人员承担
- **客观性保证**：确保验证结果的客观性和公正性

**验证失败处理**：
- 验证人不存在：返回 404 Not Found，错误码 USER_001
- 验证人是处理人：返回 400 Bad Request，错误码 EQUIPMENT_FAILURE_006
- 提示错误原因和处理人员信息

#### 步骤9: 开启数据库事务

**事务保护内容**：
- 故障记录更新（验证人、验证时间、状态）
- 确保所有字段同时更新成功

**事务失败回滚**：
- 如任一操作失败，全部回滚
- 保证数据一致性

#### 步骤10: 更新故障记录

**更新字段**：
```javascript
{
  verifierId: "c3d4e5f6-g7h8-9012-cdef-gh1234567890",  // 验证人员ID
  verificationTime: new Date(),                         // 验证时间（新增字段）
  status: "已验证",                                     // 状态变更
  updatedBy: req.user.id,                               // 更新人ID
  updatedAt: new Date()                                 // 更新时间
}
```

**数据库操作**：
- 使用 Sequelize ORM 的 `update` 方法
- 在事务中执行
- 更新成功后重新查询完整记录（包含关联数据）

#### 步骤11: 提交事务

**成功提交**：
- 故障记录更新成功
- 返回更新后的完整故障记录（包含关联的设备、人员信息）
- 状态已变更为"已验证"
- 验证人员和验证时间已记录

**失败回滚**：
- 任一更新失败，全部回滚
- 返回错误信息，故障状态保持"已解决"
- 可重新调用验证处理接口

#### 步骤12: 通知相关人员（预留功能）

**未来扩展**：
- 通知处理人员验证结果
- 通知设备管理员可以关闭故障单
- 通知生产调度可以恢复设备使用
- 记录验证备注和质量评价

**当前处理**：
- 仅更新数据库记录
- 相关人员需主动查看故障状态

#### 步骤13: 返回更新后的故障记录

**返回内容**：
- HTTP 状态码：200 OK
- 包含完整的故障记录信息
- 包含关联的设备信息、处理人员信息、验证人员信息
- 包含操作结果消息："故障处理验证通过"

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/equipment-failures/{failureId}/verify`

**功能描述**: 验证指定故障的处理结果。由质检人员或设备管理员对处理完成的故障进行现场验证，确认故障是否已正确处理、设备是否可正常使用。验证通过后，将故障状态从"已解决"更新为"已验证"，记录验证人员和验证时间。验证人员不能是故障的处理人员本人。

**认证要求**: Bearer Token 认证，需要 `mdm.tpm.equipment-failure.manage` 权限

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",

      "value": "错误的字段值（可选）",

    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号


**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

**业务需求**: 质检工程师对I级严重故障的处理结果进行现场验证，确认设备恢复正常，验证通过。

- 故障状态变更为"已验证"

## 常见问题

### Q1: 为什么验证人员不能是处理人员本人？

**A**: 这是质量管理的基本原则，确保验证的独立性和客观性。

**原因**：

**1. 质量控制要求**
- 避免自己验证自己的工作
- 防止主观判断导致质量问题
- 确保维修质量标准统一

**2. 责任分离**
- 处理责任：处理人员负责
- 验证责任：质检人员负责
- 责任明确，便于追溯

**3. 独立性原则**
- 验证人员独立于处理过程
- 客观评价处理结果
- 发现处理过程中的遗漏问题

**4. 组织要求**
- 符合ISO质量管理体系要求
- 符合TPM全员生产维护体系
- 符合内部质量控制流程

**特殊情况**：
- 如果团队人员不足，至少应由班组长或主管验证
- 紧急情况下可暂时放宽，但需事后补充正式验证
- 系统层面强制要求验证人≠处理人

---

### Q2: 验证不通过如何处理？

**A**: 验证不通过时，**不要调用验证接口**，应将故障返工重新处理。

**处理流程**：

**方式1：使用更新故障接口**
- 接口：`PATCH /v1/mdm/tpm/equipment-failures/:failureId`
- 更新字段：添加备注说明验证不通过的原因
- 保持状态"已解决"，等待重新处理

**方式2：重新开始处理（推荐）**
- 将故障状态改回"处理中"或使用开始处理接口
- 重新分配处理人员（可能是原处理人或更有经验的工程师）
- 记录返工原因和验证不通过的具体问题

**方式3：使用专门的返工接口（未来扩展）**
- 系统可扩展专门的返工接口
- 自动记录返工次数和原因
- 统计分析返工率，用于质量改进

**记录要求**：
- 详细说明验证不通过的原因
- 记录发现的具体问题
- 明确需要重新处理的内容
- 更新处理措施要求

---

### Q3: 验证通过后，设备状态会自动恢复吗？

**A**: 不会自动恢复。设备状态恢复需要在"关闭故障单"环节。

**状态变化流程**：

1. **开始处理**（影响程度=停机）：
   - 故障状态：待处理 → 处理中
   - 设备状态：启用 → **维修中**

2. **完成处理**：
   - 故障状态：处理中 → 已解决
   - 设备状态：**维修中**（保持不变）

3. **验证处理**（当前接口）：
   - 故障状态：已解决 → 已验证
   - 设备状态：**维修中**（保持不变）

4. **关闭故障单**：
   - 故障状态：已验证 → 已关闭
   - 设备状态：维修中 → **启用**（恢复）

**设计原因**：
- 验证通过只是确认处理质量
- 关闭故障单才是正式结束维修
- 给生产调度预留准备时间
- 可能还需要其他准备工作（如清洁、调试）

**手动恢复**：
- 如需立即恢复设备，可在验证后直接调用关闭故障单接口
- 也可手动更新设备状态（不推荐，应遵循正常流程）

---

### Q4: 可以验证其他质检人员验证过的故障吗？

**A**: 系统层面允许，但业务上不推荐。

**系统限制**：
- 只验证状态为"已解决"的故障
- 已验证的故障状态为"已验证"，不符合条件
- 系统会返回状态验证失败错误

**如需二次验证**：

**情况1：验证结果有争议**
- 使用更新故障接口将状态改回"已解决"
- 由主管或更高级别质检人员重新验证

**情况2：发现新问题**
- 不应重新验证，而应重新开始处理
- 可能标记为重复故障
- 分析根本原因，制定预防措施

---

### Q5: 验证时间是如何记录的？

**A**: 系统自动记录验证时间，使用服务器时间。

**记录方式**：
- 后端自动记录，前端无需传入
- 使用数据库服务器时间：`new Date()`
- 记录字段：可能是 `verificationTime` 或使用 `updatedAt`

**时间用途**：
- 完善故障处理全流程时间轴
- 统计验证效率
- 分析处理质量（返工率）
- 计算完整的故障处理周期时间

**时间准确性**：
- 使用服务器时间，避免客户端时间不准
- 确保时间记录的权威性
- 支持跨时区的时间统一

---

### Q6: 如何查询待验证的故障列表？

**A**: 使用故障列表查询接口，筛选状态为"已解决"的故障。

**查询示例**：

```bash
GET /v1/mdm/tpm/equipment-failures?status=已解决&sortBy=repairEndTime:asc
```

**常用筛选条件**：
- `status=已解决`：必选筛选条件
- `sortBy=repairEndTime:asc`：按处理完成时间升序，先完成先验证
- `failureLevel=I级-严重`：优先验证严重故障
- `impactDegree=停机`：优先验证停机故障
- `equipmentId=xxx`：按设备筛选

**高级筛选**：
- 按处理人员筛选：`repairerId=xxx`
- 按时间范围：`startDate=xxx&endDate=xxx`
- 组合条件：同时使用多个筛选条件

---

### Q7: 验证接口调用失败会有什么影响？

**A**: 不会有任何影响。系统使用数据库事务保证数据一致性。

**保证**：
- ✅ 接口返回成功（HTTP 200）：故障记录已正确更新
- ✅ 接口返回失败（HTTP 4xx/5xx）：所有数据保持原样
- ✅ 不会出现部分字段更新、部分字段未更新的情况

**失败处理**：
1. 查看错误响应中的错误码和错误消息
2. 根据错误提示修正问题（如更换验证人员）
3. 重新调用验证处理接口
4. 可多次重试，不会造成数据混乱

**常见失败原因**：
- 权限验证失败：检查是否有管理权限
- 状态验证失败：检查故障是否为"已解决"状态
- 验证人就是处理人：更换验证人员
- 验证人不存在：检查验证人员ID
- 网络超时：重新调用即可

---

### Q8: 质检人员不在岗时，可以由其他人验证吗？

**A**: 可以。系统只验证验证人员不是处理人员，不限制特定质检人员。

**灵活分配**：
- 任何有管理权限的用户都可以验证
- 验证人员只需不是处理人员本人即可
- 可以是：
  - 专职质检人员
  - 设备管理员
  - 维修主管
  - 班组长

**建议做法**：
- 优先由专职质检人员验证
- 质检人员不在时，由主管代为验证
- 建立质检人员轮班制度
- 紧急情况可由设备管理员验证

**权限要求**：
- 需要 `mdm.tpm.equipment-failure.manage` 权限
- 角色权限管理中配置

---

### Q9: 验证通过后发现问题，如何处理？

**A**: 验证通过后发现问题，建议创建新的故障记录。

**原因**：
- 原故障已验证通过并关闭
- 重新打开原故障会破坏时间线完整性
- 新问题应作为新故障或重复故障处理

**处理流程**：

**情况1：立即发现（验证后几小时内）**
- 可以暂不关闭原故障
- 使用更新故障接口将状态改回"已解决"
- 重新开始处理，修正问题
- 重新验证

**情况2：延后发现（验证后数小时或数天）**
- 创建新的故障记录
- 标记为重复故障（`isRepeatFailure: true`）
- 关联原故障记录（在描述中说明）
- 进行根本原因分析，制定预防措施

**质量改进**：
- 分析为什么验证时未发现
- 改进验证标准和流程
- 加强质检人员培训
- 完善验证检查清单

---

### Q10: 夜班和白班的验证工作如何衔接？

**A**: 建议尽量当班完成验证，特殊情况可跨班交接。

**推荐做法**：

**当班验证**：
- 处理完成后立即验证
- 减少等待时间
- 快速恢复设备使用
- 验证质量更好（问题更易发现）

**跨班验证**：
- 处理人：夜班维修工程师
- 验证人：白班质检工程师
- 需做好交接记录
- 白班验证时可联系夜班处理人

**紧急故障**：
- 夜班处理完成
- 夜班主管直接验证
- 白班质检人员补充验证（可选）

**质检排班**：
- 建议质检人员与维修人员同班次
- 或建立质检人员待命制度
- 确保各时段有人验证
