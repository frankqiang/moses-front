## 功能概述

### 所有功能

开始处理故障（Start Repair）是设备故障管理模块中的核心流程操作，用于启动故障处理流程，将故障从"待处理"状态转入"处理中"状态，以支持故障全生命周期管理和处理进度追踪的业务场景。

当故障报告创建后，由维修主管或设备管理员分配专业维修人员开始处理故障。系统自动记录处理开始时间，并根据故障影响程度自动更新设备状态，确保故障处理过程的可追溯性和设备状态的准确性。

### 关键特性

- ✅ **处理人员分配**：支持分配具有相应技能的维修人员，记录责任人信息
- ✅ **自动时间记录**：系统自动记录处理开始时间，为MTTR计算提供准确数据
- ✅ **状态自动流转**：自动将故障状态从"待处理"更新为"处理中"
- ✅ **设备状态联动**：当故障影响程度为"停机"时，自动将设备状态设置为"维修中"
- ✅ **处理进度追踪**：记录处理开始时间点，便于跟踪维修进度和计算处理时长
- ✅ **权限验证**：确保只有具备管理权限的人员才能分配和启动故障处理

---

### 使用前提

- ✅ **故障记录存在**：故障记录必须已创建且在系统中存在
- ✅ **状态符合要求**：故障当前状态必须为"待处理"或"已解决"（返工场景）
- ✅ **处理人有效**：分配的处理人员必须是系统中的有效用户
- ✅ **权限要求**：需要 `mdm.tpm.equipment-failure.manage` 权限

### 不适用场景

- ❌ **故障已在处理中**：如果故障状态已是"处理中"，不能重复开始处理
- ❌ **故障已关闭**：已关闭的故障不能重新开始处理，需先更改状态
- ❌ **故障已验证**：已验证的故障正常流程是关闭，不应开始处理（除非需要返工）

### 详细步骤说明

#### 步骤1: 维修主管查看待处理故障

- 维修主管或设备管理员查看待处理故障列表
- 根据故障等级、类型、影响程度确定处理优先级
- I级-严重故障（停机）：最高优先级，立即处理
- II级-重大故障：高优先级，尽快安排
- III级-一般故障和IV级-轻微故障：按计划安排

#### 步骤2: 根据故障类型选择处理人员

**选择原则**：
- **故障类型匹配**：根据故障类型选择对应专业的维修人员
  - 机械故障 → 机械维修工程师
  - 电气故障 → 电气工程师
  - 液压故障 → 液压系统工程师
  - 控制故障 → 自动化工程师
  - 其他故障 → 根据具体情况确定
- **技能水平匹配**：根据故障等级选择相应经验的人员
- **工作负荷平衡**：考虑维修人员当前工作量
- **紧急程度考虑**：严重故障优先分配最有经验的人员

#### 步骤3: 权限验证

**验证要点**：
- 操作用户必须具有 `mdm.tpm.equipment-failure.manage` 权限
- 确保只有授权人员才能分配故障处理任务
- 权限不足返回 403 Forbidden 错误

#### 步骤4: 状态验证

**允许的起始状态**：
- **待处理**：故障刚创建，首次开始处理（正常流程）
- **已解决**：验证不通过需要返工，重新开始处理（返工流程）

**不允许的起始状态**：
- **处理中**：已有人在处理，不能重复开始
- **已验证**：已验证通过，应关闭或返工
- **已关闭**：已关闭，流程结束

**验证失败处理**：
- 返回 400 Bad Request
- 错误码：EQUIPMENT_FAILURE_003
- 提示当前状态和允许的操作

#### 步骤5: 验证处理人员

**验证内容**：
- 处理人员ID（repairerId）必须提供
- 处理人员必须是系统中存在的有效用户
- 通过查询用户表验证用户有效性

**验证失败处理**：
- 用户不存在返回 404 Not Found
- 错误码：USER_001
- 提示用户ID无效

#### 步骤6: 开启数据库事务

**事务保护内容**：
- 故障记录更新（处理人、开始时间、状态）
- 设备状态更新（如果影响程度为停机）
- 确保两个操作的原子性

**事务失败回滚**：
- 如任一操作失败，全部回滚
- 保证数据一致性

#### 步骤7: 更新故障记录

**更新字段**：
- `repairerId`：设置为分配的处理人员ID
- `repairStartTime`：记录当前系统时间作为处理开始时间
- `status`：更新为"处理中"
- `updatedBy`：记录操作人ID
- `updatedAt`：记录更新时间

**自动处理**：
- 系统自动获取当前时间，无需前端传入
- 确保时间记录准确，用于MTTR计算

#### 步骤8: 判断故障影响程度并更新设备状态

**判断逻辑**：
```javascript
if (failure.impactDegree === '停机') {
  // 更新设备状态为"维修中"
  await Equipment.update(
    { status: '维修中' },
    { where: { id: failure.equipmentId } }
  );
}
```

**设备状态联动说明**：
- **影响程度=停机**：设备状态自动设为"维修中"
  - 表示设备当前不可用
  - 生产调度系统不会分配任务给该设备
  - 设备列表中显示维修状态
- **其他影响程度**：设备状态保持不变
  - 性能下降：设备可继续使用，状态不变
  - 无影响：设备正常运行，状态不变

#### 步骤9: 提交事务

**成功提交**：
- 故障记录和设备状态同时更新成功
- 返回更新后的完整故障记录

**失败回滚**：
- 任一更新失败，全部回滚
- 返回错误信息，故障状态保持原样

#### 步骤10: 通知处理人员（预留功能）

**未来扩展**：
- 发送站内消息通知处理人员
- 发送邮件或短信提醒
- 推送移动端通知

**当前处理**：
- 仅记录数据库，处理人员需主动查看任务

#### 步骤11: 返回更新后的故障记录

**返回内容**：
- HTTP 状态码：200 OK
- 包含完整的故障记录信息
- 包含关联的设备信息、处理人员信息
- 包含操作结果消息

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/equipment-failures/{failureId}/start-repair`

**功能描述**: 开始处理指定的设备故障。分配处理人员，记录处理开始时间，将故障状态从"待处理"更新为"处理中"。如果故障影响程度为"停机"，同时将关联设备状态设置为"维修中"。

**认证要求**: Bearer Token 认证，需要 `mdm.tpm.equipment-failure.manage` 权限

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }

  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号


**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

## 使用示例

### 场景1: 严重故障快速响应

**业务需求**: 生产线设备突然停机，报告了I级严重故障，维修主管立即分配最有经验的机械工程师处理。

**操作步骤**:

1. 维修主管查看待处理故障列表，找到刚创建的故障记录
2. 确认故障等级为"I级-严重"，影响程度为"停机"
3. 选择资深机械工程师"李工"作为处理人员
4. 调用开始处理接口

**业务效果**:
- 故障状态立即变更为"处理中"
- 设备状态自动更新为"维修中"，生产调度系统不再分配任务
- 李工可以在系统中看到分配给自己的故障任务
- 系统记录处理开始时间，为后续MTTR计算提供数据

---

### 场景2: 电气故障专业分配

**业务需求**: 发现设备控制柜显示异常，创建了II级电气故障，需要分配给电气工程师处理。

**操作步骤**:

1. 设备管理员查看新创建的电气类故障
2. 根据故障类型"电气"，选择电气工程师"张工"
3. 调用开始处理接口，分配任务

**业务效果**:
- 电气工程师张工被分配处理该故障
- 因影响程度为"性能下降"，设备状态保持"启用"，可继续使用
- 张工可以合理安排处理时间，不影响正常生产

---

### 场景3: 返工场景处理

**业务需求**: 故障处理完成并验证后，发现问题复发，需要重新开始处理（返工）。

**操作步骤**:

1. 质量工程师发现故障复发，将故障状态改回"已解决"（或系统支持"返工"操作）
2. 维修主管重新分配处理人员（可能是原处理人或更有经验的工程师）
3. 调用开始处理接口，重新开始处理流程


**业务效果**:
- 系统记录新的处理开始时间
- 分配更有经验的工程师处理
- 可能标记为重复故障，用于后续分析改进

**操作步骤**:

2. 选择工作负荷较轻的维修人员
3. 按故障类型和人员技能匹配，分配故障

**业务效果**:
- 合理分配工作任务，避免某个人负荷过重
- 各维修人员可以看到自己的任务列表
- 提高整体维修效率

## 常见问题

### Q1: 如果分配的处理人员不在岗怎么办？

**A**: 系统层面只验证处理人员是否为有效用户，不验证是否在岗。业务上建议：

1. **分配前确认**：维修主管在分配前确认人员在岗状态
2. **支持重新分配**：如果处理人员无法及时响应，可通过更新故障接口重新分配处理人员
3. **通知机制**：未来可扩展通知功能，处理人员收到分配后确认接受任务
4. **建立待命制度**：建立维修人员待命制度，确保各时段有人响应

---

### Q2: 开始处理后发现分配错了人员，如何修改？

**A**: 有两种方式修改处理人员：

**方式1：使用更新故障接口（推荐）**

- 优点：保留原处理开始时间，只更换处理人员
- 适用场景：已开始处理不久，只是人员分配错误

**方式2：修改故障状态后重新开始**

- 优点：重新记录处理开始时间，MTTR计算更准确
- 适用场景：原人员尚未实际开始处理，或需要完全重新开始

---

### Q3: 故障状态为"处理中"时能否重复调用开始处理接口？

**A**: 不能。系统会返回错误：

**原因**：
- 避免重复记录处理开始时间
- 防止意外覆盖处理人员
- 保证MTTR计算准确性

**如需修改处理人员**：使用更新故障接口（见Q2）

---

### Q4: 为什么开始处理后设备状态变成了"维修中"？

**A**: 这是业务规则的自动联动机制：

**联动规则**：
- 当故障影响程度为"**停机**"时，开始处理自动将设备状态设为"**维修中**"
- 当故障影响程度为"性能下降"或"无影响"时，设备状态**不变**

**业务意义**：
- **停机故障**：设备完全不可用，必须标记为维修中
  - 生产调度系统不会分配任务给该设备
  - 设备列表中明确显示维修状态
  - 防止误操作尝试使用该设备
- **性能下降**：设备可继续使用，只是效率降低
  - 设备保持原状态，可继续生产
  - 维修人员利用生产间隙处理
- **无影响**：完全不影响设备运行
  - 设备正常使用，计划性维修

**设备状态恢复**：
- 验证处理完成后，设备状态会自动恢复为"启用"
- 也可手动更新设备状态

---

### Q5: 处理开始时间是由前端传入还是后端自动记录？

**A**: **后端自动记录**，前端无需传入。

**原因**：
- **时间准确性**：使用服务器时间，避免客户端时间不准确
- **防止篡改**：防止恶意修改处理开始时间
- **简化调用**：前端只需传入处理人员ID
- **MTTR计算依据**：确保MTTR计算基于准确的服务器时间

**记录时机**：
- 接口调用成功，数据库事务提交前记录
- 使用数据库服务器时间：`new Date()` 或 `CURRENT_TIMESTAMP`

---

### Q6: 可以同时开始处理多个故障吗？

**A**: 可以。一个维修人员可以同时被分配多个故障任务。

**系统层面**：
- 没有限制一个人同时处理的故障数量
- 支持并行处理多个故障

**业务建议**：
- **优先级管理**：按故障等级确定处理顺序
  - I级-严重：最高优先级，立即处理
  - II级-重大：高优先级
  - III级-一般、IV级-轻微：按计划处理
- **工作负荷控制**：维修主管需考虑人员负荷，避免分配过多任务
- **时间管理**：处理人员合理安排各故障的处理时间
- **进度跟踪**：定期检查各故障的处理进度

---

### Q7: 开始处理接口调用失败，设备状态会改变吗？

**A**: 不会。系统使用数据库事务保证数据一致性。

**保证**：
- 如果接口返回成功，故障记录和设备状态都已正确更新
- 如果接口返回失败，所有数据保持原样，无任何变化
- 不会出现故障状态已更新但设备状态未更新的不一致情况

---

### Q8: 如何查询某个维修人员当前处理中的所有故障？

**A**: 使用查询故障列表接口，按处理人员和状态筛选：

**其他筛选**：
- 查询某人的所有历史故障：`?repairerId=ID`（不限状态）
- 查询某人今天开始处理的故障：`?repairerId=ID&status=处理中&startDate=2024-01-20`
- 查询某人处理的严重故障：`?repairerId=ID&failureLevel=I级-严重`

---

### Q9: 夜班开始处理的故障，白班接手如何操作？

**A**: 使用更新故障接口更换处理人员：

**场景**：夜班工程师开始处理但未完成，白班工程师接手继续处理

**建议**：
- **优先使用方式1**：保留原处理开始时间，MTTR计算更准确
- **交接记录**：在故障记录中添加备注说明交接情况（使用更新接口的备注字段）
- **协作模式**：如果是协作处理，保持原处理人员，在处理措施中注明参与人员

---

### Q10: 系统如何防止错误地将"已验证"或"已关闭"的故障重新开始处理？

**A**: 系统通过状态流转验证规则防止：

- ✅ "待处理"：正常首次开始处理

- ❌ "处理中"：已有人在处理

- ❌ "已关闭"：流程已结束

### 备件清单数据格式

使用的备件清单（`sparePartsUsed`）是JSONB格式，结构如下：

```json
[
  {
    "sparePartId": "备件ID（UUID）",
    "sparePartCode": "备件编码",
    "sparePartName": "备件名称",
    "quantity": 2
  },
  {
    "sparePartId": "备件ID（UUID）",
    "sparePartCode": "SP-002",
    "sparePartName": "润滑油",
    "quantity": 5
  }
]
```

**说明**：
- 开始处理时，`sparePartsUsed` 为空数组 `[]`
- 完成处理时填写使用的备件清单
- 用于成本统计和库存管理
