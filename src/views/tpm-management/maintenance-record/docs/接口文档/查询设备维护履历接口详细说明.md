## 功能概述

### 所有功能

查询设备维护履历（Query Equipment Maintenance History）是维护记录管理模块中的专项查询接口，用于查询指定设备的完整维护历史记录，按维护日期倒序排列，支持分页查询。该接口返回设备基本信息和维护记录列表，用于设备健康档案管理、维护历史追溯、设备状态评估等业务场景。

该接口是设备维护档案管理的核心入口，为设备维护历史查看、设备健康分析、故障追溯等功能提供完整的数据支撑。

### 关键特性

- ✅ **设备维护档案**：查询指定设备的完整维护历史记录，形成设备维护档案
- ✅ **时间倒序排列**：维护记录按维护日期倒序排列，最新维护记录优先展示
- ✅ **设备信息展示**：返回设备基本信息（编码、名称、类型），方便快速了解设备概况
- ✅ **分页查询支持**：支持自定义页码和每页数量，优化大数据量场景下的查询性能
- ✅ **关联数据加载**：自动关联查询设备、维护任务、执行人员、确认人员等相关信息
- ✅ **完整记录信息**：包含维护类型、内容、问题、处理措施、备件使用、工时等完整信息

---

### 使用前提

- ✅ 用户已通过认证，持有有效的 JWT Token
- ✅ 用户具有查看维护记录的权限（当前版本需认证即可）
- ✅ 提供的设备ID必须存在且格式正确（UUID格式）
- ✅ 设备未被软删除

### 不适用场景

- ❌ 需要查询多个设备的维护记录（应使用维护记录列表接口 `/v1/mdm/tpm/maintenance-records`）
- ❌ 需要按特定条件筛选维护记录（应使用维护记录列表接口的筛选功能）
- ❌ 需要聚合统计设备维护数据（应使用统计分析接口 `/v1/mdm/tpm/maintenance-records/statistics`）
- ❌ 需要查询已软删除的维护记录（本接口只返回未删除记录）

### 详细步骤说明

#### 步骤1: 接收查询请求
- **输入**：设备ID（路径参数）和分页参数（查询参数）
- **内容**：Controller 层接收 HTTP GET 请求，提取路径参数 `equipmentId` 和查询参数 `page`、`limit`
- **验证**：初步检查参数是否存在

#### 步骤2: 验证请求参数
- **设备ID验证**：
  - 检查 `equipmentId` 是否为有效的 UUID 格式
  - 如果格式无效，返回 400 错误（VALIDATION_ERROR）
- **分页参数验证**：
  - `page`：必须为大于等于1的整数，默认值为1
  - `limit`：必须为1-100之间的整数，默认值为10
  - 如果参数无效，返回 400 错误（VALIDATION_ERROR）

#### 步骤3: 查询设备信息
- **查询操作**：
  - 根据 `equipmentId` 查询设备表（Equipment）
  - 检查设备是否存在
  - 检查设备的 `isDeleted` 标记是否为 false
- **错误处理**：
  - 如果设备不存在或已删除，返回 404 错误（EQP_008 - 设备不存在）
  - 记录查询日志
- **数据提取**：
  - 提取设备的 id、equipmentCode、name、equipmentType 等基本信息
  - 这些信息将在响应中作为设备基本信息返回

#### 步骤4: 构建查询条件
- **主要条件**：
  - `equipmentId = :equipmentId`（等于请求的设备ID）
  - `isDeleted = false`（排除已软删除的记录）
- **查询范围**：
  - 只查询该设备的维护记录
  - 不限制维护类型、时间范围等其他条件

#### 步骤5: 计算分页参数
- **偏移量计算**：
  - `offset = (page - 1) * limit`
  - 例如：第2页，每页10条 → offset = (2-1) * 10 = 10
- **限制数量**：
  - `limit = 查询参数limit` （默认10，最大100）
- **分页策略**：
  - 使用 OFFSET-LIMIT 方式进行分页
  - 确保分页参数在合理范围内

#### 步骤6: 执行数据库查询
- **查询主表**：
  - 查询维护记录表（MaintenanceRecord）
  - 应用查询条件（equipmentId、isDeleted）
  - 应用分页参数（offset、limit）
- **关联查询**：
  - **LEFT JOIN Equipment**：关联设备信息（id、equipmentCode、name、equipmentType）
  - **LEFT JOIN MaintenanceTask**：关联维护任务信息（id、taskCode、taskTitle、taskType）
  - **LEFT JOIN User AS executor**：关联执行人员信息（id、name、email）
  - **LEFT JOIN User AS confirmer**：关联确认人员信息（id、name、email）
  - **LEFT JOIN User AS creator**：关联创建人信息（id、name、email）
  - **LEFT JOIN User AS updater**：关联更新人信息（id、name、email）
- **排序规则**：
  - 一级排序：`maintenanceDate DESC`（维护日期倒序，最新维护记录在前）
  - 二级排序：`id DESC`（记录ID倒序，保证排序稳定性）
- **性能优化**：
  - 使用数据库索引（equipmentId、isDeleted、maintenanceDate）
  - 避免 N+1 查询问题
  - 一次性加载所有关联数据

#### 步骤7: 计算分页元数据
- **总记录数查询**：
  - 执行 COUNT 查询获取符合条件的总记录数
  - 查询条件与主查询相同（equipmentId、isDeleted）
- **总页数计算**：
  - `totalPages = Math.ceil(totalResults / limit)`
  - 例如：总记录35条，每页10条 → 总页数 = Math.ceil(35/10) = 4页
- **元数据字段**：
  - `page`：当前页码
  - `limit`：每页记录数
  - `totalPages`：总页数
  - `totalResults`：总记录数

#### 步骤8: 格式化响应数据
- **设备信息**：
  - 提取设备的 id、equipmentCode、name、equipmentType
  - 组装为 `equipment` 对象
- **维护记录列表**：
  - 将查询结果转换为 JSON 格式
  - 包含所有维护记录字段和关联对象
  - 组装为 `results` 数组
- **分页元数据**：
  - 组装 page、limit、totalPages、totalResults 字段
- **响应结构**：
  ```json
  {
    "equipment": { ... },
    "results": [ ... ],
    "page": 1,
    "limit": 10,
    "totalPages": 4,
    "totalResults": 35
  }
  ```

#### 步骤9: 返回成功响应
- **HTTP 状态码**：200 OK
- **响应格式**：使用统一的成功响应格式
  ```json
  {
    "success": true,
    "data": { ... },
    "message": "获取设备维护履历成功",
    "meta": { ... }
  }
  ```
- **日志记录**：
  - 记录成功查询日志
  - 包含设备ID、查询用户、返回记录数等信息

## 接口文档

### 基本信息

**接口路径**: `GET /v1/mdm/tpm/maintenance-records/by-equipment/:equipmentId`

**功能描述**: 查询指定设备的完整维护履历，按维护日期倒序排列，支持分页查询。返回设备基本信息和维护记录列表，用于设备健康档案和维护历史追溯。

**认证要求**: Bearer Token 认证，需要有效的 JWT Token

**请求头**:

```
Authorization: Bearer <access_token>
```

### 路径参数

| 参数名      | 类型   | 必填 | 限制     | 描述                         | 示例                                   |
| ----------- | ------ | ---- | -------- | ---------------------------- | -------------------------------------- |
| equipmentId | string | 是   | UUID格式 | 设备ID，必须是有效的UUID格式 | "660e8400-e29b-41d4-a716-446655440001" |

### 查询参数

| 参数名 | 类型   | 必填 | 限制  | 描述                                   | 默认值 | 示例 |
| ------ | ------ | ---- | ----- | -------------------------------------- | ------ | ---- |
| page   | number | 否   | >=1   | 页码，从1开始                          | 1      | 1    |
| limit  | number | 否   | 1-100 | 每页记录数，最小1条，最大100条，默认10 | 10     | 10   |

### 请求示例

#### cURL 命令

```bash
curl -X GET "http://localhost:3000/v1/mdm/tpm/maintenance-records/by-equipment/660e8400-e29b-41d4-a716-446655440001?page=1&limit=10" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

#### JavaScript (Axios)

```javascript
const axios = require('axios');

const getEquipmentMaintenanceHistory = async (equipmentId, page = 1, limit = 10) => {
  try {
    const response = await axios.get(
      `http://localhost:3000/v1/mdm/tpm/maintenance-records/by-equipment/${equipmentId}`,
      {
        params: { page, limit },
        headers: {
          'Authorization': 'Bearer YOUR_ACCESS_TOKEN'
        }
      }
    );
    console.log('设备维护履历:', response.data);
    return response.data;
  } catch (error) {
    console.error('查询失败:', error.response?.data);
    throw error;
  }
};

// 调用示例
getEquipmentMaintenanceHistory('660e8400-e29b-41d4-a716-446655440001', 1, 10);
```

## 使用示例

### 场景1: 查询设备的完整维护履历（第一页）

**业务需求**: 设备管理员需要查看"退火炉1号"的完整维护历史记录，了解设备的健康状况和维护频率。

**业务价值**:
- 快速了解设备的维护频率和维护质量
- 发现设备的常见故障模式和问题趋势
- 为设备健康评估和维护计划制定提供依据

### 场景2: 分页查询大量维护记录

**业务需求**: 某台设备已运行多年，维护记录达到100多条，需要分页查询以优化性能。
**业务价值**:
- 优化大数据量场景下的查询性能
- 减少网络传输数据量，提升用户体验
- 支持前端实现无限滚动或分页导航

### 场景3: 设备故障追溯分析

**业务需求**: 某设备出现故障，技术人员需要查看历史维护记录，分析故障原因和处理措施。

**输出示例**:
```
设备信息: 退火炉1号 (AF001)
总维护记录: 35条
维护类型分布: { '日常保养': 20, '定期保养': 10, '故障维修': 5 }
故障维修记录: 5条
最近故障: {
  日期: '2024-02-07T10:00:00.000Z',
  问题: '温度传感器故障，导致温度显示异常',

  执行人: '张三'
}
平均维护工时: 2.85小时
```

**业务价值**:
- 快速定位设备历史故障模式
- 分析故障频率和处理效果
- 为预防性维护提供数据支持

### 场景4: 设备健康档案导出

**业务需求**: 质量部门需要导出设备的完整维护档案，用于设备健康评估和审计。

**业务价值**:
- 形成完整的设备健康档案
- 支持质量审计和合规检查
- 为设备资产管理提供数据支持

### 场景5: 设备维护频率监控

**业务需求**: 维护主管需要监控设备的维护频率，判断是否符合维护计划要求。
