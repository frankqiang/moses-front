## 功能概述

### 所有功能

创建维护记录（Create Maintenance Record）是设备TPM管理中的核心操作之一，用于记录设备维护保养的完整过程和结果，以支持设备健康档案管理和维护历史追溯的业务场景。该接口支持手工创建维护记录和补录历史维护信息。

### 关键特性

- ✅ **自动编码生成**：如果不提供记录编码，系统将自动生成格式为 `MR-{设备编码}-{时间戳}` 的唯一编码
- ✅ **完整记录信息**：支持记录维护内容、发现问题、处理措施、使用备件、维护工时等完整信息
- ✅ **任务关联支持**：可选关联维护任务ID，用于任务完成后生成记录的场景
- ✅ **备件清单管理**：支持记录使用的备件清单（备件ID、编码、名称、数量）
- ✅ **状态对比记录**：支持记录维护前后设备状态，便于效果评估
- ✅ **关联数据返回**：创建成功后自动返回关联的设备、任务、执行人、确认人等完整信息

---

### 使用前提

- ✅ 用户已通过JWT认证，持有有效的Bearer Token
- ✅ 关联的设备必须已在系统中存在
- ✅ 执行人员必须已在系统中存在
- ✅ 如果指定确认人员，确认人员必须已在系统中存在
- ✅ 如果关联维护任务，任务必须已在系统中存在

### 不适用场景

- ❌ 设备尚未导入系统 - 应先创建设备主数据
- ❌ 执行人员不存在 - 应先创建用户账号
- ❌ 任务驱动的自动记录生成 - 应使用任务完成接口，由系统自动创建记录

### 详细步骤说明

#### 步骤1: 接收创建请求

- **说明**：接收客户端发送的POST请求
- **请求内容**：JSON格式的维护记录数据
- **必需头部**：Authorization Bearer Token, Content-Type: application/json

#### 步骤2: 参数验证

- **验证器**：使用Joi验证器进行参数验证
- **必填字段**：
  - `equipmentId`（设备ID，UUID格式）
  - `maintenanceDate`（维护日期时间，ISO 8601格式）
  - `maintenanceType`（维护类型，枚举值）
  - `maintenanceContent`（维护内容，非空字符串）
  - `executorId`（执行人员ID，UUID格式）
- **可选字段**：
  - `recordCode`（记录编码，最大100字符）
  - `taskId`（关联任务ID）
  - `problemFound`（发现问题描述）
  - `solutionApplied`（处理措施）
  - `sparePartsUsed`（备件清单数组）
  - `workHours`（维护工时，≥0）
  - `confirmerId`（确认人员ID）
  - `equipmentStatusBefore`（维护前设备状态）
  - `equipmentStatusAfter`（维护后设备状态）
  - `nextMaintenanceSuggestion`（下次维护建议）
- **特殊验证**：
  - `maintenanceType` 必须是：日常保养、定期检查、大修、专项维护之一
  - `workHours` 如果提供必须≥0
  - `sparePartsUsed` 如果提供，每个备件对象必须包含 sparePartId、sparePartCode、sparePartName、quantity

#### 步骤3: 关联数据验证

- **设备验证**：
  - 根据 `equipmentId` 查询设备表
  - 如果设备不存在，抛出 404 错误（错误码：EQP_008）
- **执行人员验证**：
  - 根据 `executorId` 查询用户表
  - 如果用户不存在，抛出 404 错误（错误码：USER_001）
- **确认人员验证**（如果提供）：
  - 根据 `confirmerId` 查询用户表
  - 如果用户不存在，抛出 404 错误（错误码：USER_001）
- **任务验证**（如果提供）：
  - 根据 `taskId` 查询维护任务表
  - 如果任务不存在，抛出 404 错误（错误码：TPM_TASK_001）

#### 步骤4: 编码处理

- **自动生成逻辑**：
  - 如果未提供 `recordCode`，系统自动生成
  - 生成规则：`MR-{设备编码}-{时间戳}`
  - 示例：`MR-AF001-1705737600000`
- **手动编码验证**：
  - 如果提供了 `recordCode`，检查数据库中是否已存在
  - 如果编码已存在，抛出 400 错误（错误码：TPM_RECORD_002）
- **唯一性保证**：通过数据库唯一约束和应用层验证双重保证

#### 步骤5: 开启事务

- **事务范围**：创建维护记录、查询关联数据
- **隔离级别**：使用默认隔离级别
- **目的**：确保数据一致性，出错时可回滚

#### 步骤6: 创建维护记录

- **数据库操作**：向 `maintenance_records` 表插入新记录
- **自动填充字段**：
  - `id`：系统生成的UUID
  - `recordCode`：已生成或验证的编码
  - `createdBy`：当前用户ID（从JWT Token获取）
  - `updatedBy`：当前用户ID（从JWT Token获取）
  - `createdAt`：当前时间戳
  - `updatedAt`：当前时间戳
  - `isDeleted`：默认false
  - `attachmentUrls`：默认空数组
- **JSONB字段处理**：
  - `sparePartsUsed`：以JSON格式存储备件清单
  - `attachmentUrls`：初始化为空数组
- **数据类型转换**：
  - `workHours`：转换为DECIMAL类型存储

#### 步骤7: 查询关联数据

- **查询内容**：
  - 设备信息（id, equipmentCode, name, equipmentType, status）
  - 维护任务信息（id, taskCode, taskTitle, taskType）- 如果关联了任务
  - 执行人员信息（id, name, email）
  - 确认人员信息（id, name, email）- 如果指定了确认人
  - 创建人信息（id, name, email）
  - 更新人信息（id, name, email）
- **查询方式**：使用Sequelize的include关联查询
- **目的**：一次性返回完整的记录信息，减少客户端的额外请求

#### 步骤8: 提交事务

- **成功提交**：所有操作成功完成，提交事务
- **失败回滚**：任何步骤出错，自动回滚所有数据库操作
- **日志记录**：记录创建操作日志，包含用户ID、操作结果等

#### 步骤9: 返回完整记录信息

- **响应格式**：统一的成功响应格式
- **响应内容**：
  - 维护记录的所有字段
  - 关联的设备、任务、人员信息
  - 操作元数据（时间戳、请求ID、版本号）
- **HTTP状态码**：201 Created

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/maintenance-records`

**功能描述**: 创建新的维护保养记录，记录设备维护的完整过程和结果。支持关联维护任务、使用备件清单、附件信息等完整的维护记录信息。如果不提供记录编码，系统将自动生成格式为 `MR-{设备编码}-{时间戳}` 的编码。适用于手工创建维护记录和补录历史维护信息的场景。

**认证要求**: JWT Bearer Token 认证，需要 `mdm.tpm.maintenance-record.manage` 权限

### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }

    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号


**请求头**:

```
Authorization: Bearer <access_token>

```

## 常见问题

### Q1: 如何自动生成记录编码？

**A**: 不提供 `recordCode` 参数即可。系统会自动生成格式为 `MR-{设备编码}-{时间戳}` 的唯一编码。

**示例**:
```json
{
  "equipmentId": "660e8400-e29b-41d4-a716-446655440001",
  // 不提供 recordCode
  "maintenanceDate": "2024-01-20T14:30:00.000Z",
  ...
}
```

**系统生成**: `MR-AF001-1705737600000`

---

### Q2: 如何处理备件清单？

**A**: `sparePartsUsed` 是一个对象数组，每个对象包含备件的完整信息。如果没有使用备件，可以不提供该字段或提供空数组。

**示例**:
```json
{
  "sparePartsUsed": [
    {
      "sparePartId": "990e8400-e29b-41d4-a716-446655440004",
      "sparePartCode": "SP-001",
      "sparePartName": "液压油密封圈",
      "quantity": 2
    },
    {
      "sparePartId": "990e8400-e29b-41d4-a716-446655440005",
      "sparePartCode": "SP-002",
      "sparePartName": "液压油滤芯",
      "quantity": 1
    }
  ]
}
```

**注意事项**:
- 每个备件对象的所有字段都是必填的
- `quantity` 必须大于0
- 系统会将数据以JSONB格式存储

---

### Q3: 维护类型有哪些可选值？

**A**: `maintenanceType` 必须是以下四个值之一：

- `日常保养`：日常定期保养
- `定期检查`：定期检查维护
- `大修`：设备大修
- `专项维护`：专项维护任务

**错误示例**:
```json
{
  "maintenanceType": "临时维护" // ❌ 错误，不是有效的枚举值
}
```

**正确示例**:
```json
{
  "maintenanceType": "日常保养" // ✅ 正确
}
```

---

### Q4: 如何补录历史维护记录？

**A**: 可以手动指定 `recordCode` 和历史的 `maintenanceDate`。

**示例**:
```json
{
  "recordCode": "MR-AF001-HISTORY-001",
  "maintenanceDate": "2023-12-15T10:00:00.000Z", // 历史日期
  "equipmentId": "660e8400-e29b-41d4-a716-446655440001",
  "maintenanceType": "大修",
  "maintenanceContent": "历史大修记录",
  "executorId": "770e8400-e29b-41d4-a716-446655440002"
}
```

**注意事项**:
- 确保 `recordCode` 唯一，避免与现有记录冲突
- `maintenanceDate` 可以是历史日期
- 用于完善设备维护履历

---

### Q5: 创建记录后如何上传附件？

**A**: 创建记录时 `attachmentUrls` 初始化为空数组。创建成功后，使用"上传维护记录附件"接口添加附件。

**步骤**:
1. 创建维护记录，获得记录ID
2. 调用 `POST /v1/mdm/tpm/maintenance-records/:recordId/attachments` 上传附件

**参考**: 详见"上传维护记录附件接口文档"

---

### Q6: 如果关联的设备或用户不存在会怎样？

**A**: 系统会在创建前验证所有关联数据的有效性，如果不存在会返回404错误。

**错误响应示例**:
```json
{
  "success": false,
  "error": {
    "code": "EQP_008",
    "message": "设备不存在",
    "details": {
      "field": "equipmentId",
      "value": "invalid-equipment-id"
    }
  }
}
```

**处理建议**:
- 确保设备已在系统中创建
- 确保执行人员和确认人员已注册
- 如果关联任务，确保任务已创建

---

### Q7: workHours 字段返回的是字符串还是数字？

**A**: 由于数据库使用 DECIMAL 类型存储工时，响应中 `workHours` 以字符串形式返回，保持精度。

**请求时**（number类型）:
```json
{
  "workHours": 2.5
}
```

**响应时**（string类型）:
```json
{
  "workHours": "2.50"
}
```

**前端处理**:
```javascript
const hours = parseFloat(record.workHours);
```

---

### Q8: 能否创建记录时不指定执行人员？

**A**: 不能。`executorId` 是必填字段，必须指定执行维护的人员。

**原因**:
- 维护记录必须明确责任人
- 用于工作量统计和追溯
- 符合设备管理规范

---

### Q9: 创建记录是否需要权限？

**A**: 是的，需要 `mdm.tpm.maintenance-record.manage` 权限。

**权限验证**:
- 系统会检查当前用户的Token
- 验证是否具有管理维护记录的权限
- 无权限会返回 403 错误

---

### Q10: 如何查看创建的维护记录？

**A**: 创建成功后，响应中包含完整的记录信息。也可以使用以下接口查询：

- 查询单个记录：`GET /v1/mdm/tpm/maintenance-records/:recordId`
- 查询设备履历：`GET /v1/mdm/tpm/maintenance-records/by-equipment/:equipmentId`
- 查询记录列表：`GET /v1/mdm/tpm/maintenance-records`

## 附录

### 维护类型枚举值

| 状态码   | 中文名称 | 说明                     | 适用场景                   |
| -------- | -------- | ------------------------ | -------------------------- |
| 日常保养 | 日常保养 | 设备日常清洁、润滑等保养 | 每日或每周例行维护         |
| 定期检查 | 定期检查 | 按计划进行的设备检查     | 月检、季检、年检           |
| 大修     | 大修     | 设备全面拆解检修         | 设备运行一定时间后进行大修 |
| 专项维护 | 专项维护 | 针对特定部件的专项维护   | 发现特定问题或执行专项改造 |

### 记录编码规则

**自动生成格式**: `MR-{设备编码}-{时间戳}`

**示例**:
- `MR-AF001-1705737600000`
- `MR-EQ-002-1705823400000`

**说明**:
- `MR`: Maintenance Record 的缩写
- 设备编码：从设备主数据中获取
- 时间戳：创建时的Unix时间戳（毫秒）

**手动指定**:
- 可以手动指定编码，但必须保证唯一性
- 建议采用有意义的编码规则
- 适用于补录历史记录

### 备件清单数据格式

**JSONB格式存储**:

```json
[
  {
    "sparePartId": "uuid",
    "sparePartCode": "SP-001",
    "sparePartName": "轴承",
    "quantity": 2
  },
  {
    "sparePartId": "uuid",
    "sparePartCode": "SP-002",
    "sparePartName": "润滑油",
    "quantity": 5
  }
]
```

**字段说明**:
- `sparePartId`: 备件的唯一标识（UUID格式）
- `sparePartCode`: 备件编码（用于库存管理系统）
- `sparePartName`: 备件名称（便于识别）
- `quantity`: 使用数量（必须>0）

### 附件列表数据格式

**JSONB格式存储**:

```json
[
  {
    "url": "https://example.com/files/photo1.jpg",
    "fileName": "维护现场照片1.jpg",
    "fileType": "image/jpeg"
  },
  {
    "url": "https://example.com/files/report.pdf",
    "fileName": "检测报告.pdf",
    "fileType": "application/pdf"
  }
]
```

**字段说明**:
- `url`: 附件的访问URL
- `fileName`: 文件名（含扩展名）
- `fileType`: MIME类型

**创建记录时**: `attachmentUrls` 初始化为空数组，需要通过附件管理接口上传。

### 日期时间格式

**ISO 8601 格式**: `YYYY-MM-DDTHH:mm:ss.sssZ`

**示例**:
- `2024-01-20T14:30:00.000Z`
- `2024-01-21T09:00:00.000Z`

**说明**:
- 使用UTC时区（Z表示零时区）
- 包含毫秒精度
- JavaScript 可以使用 `new Date().toISOString()` 生成
