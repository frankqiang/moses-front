## 功能概述

### 所有功能

删除维护记录附件（Delete Maintenance Record Attachment）是设备TPM管理中的重要辅助功能，用于从维护记录中移除指定的附件文件（如错误上传的照片、过时的报告、重复的文档等），以支持维护记录附件管理、错误纠正和数据优化的业务场景。该接口通过附件索引精确定位并删除单个附件，删除后会重新返回完整的维护记录信息。

### 关键特性

- ✅ **精确删除**：通过附件索引（attachmentId）精确定位要删除的附件，避免误删
- ✅ **事务保护**：使用数据库事务确保删除操作的原子性，失败时自动回滚
- ✅ **索引验证**：严格验证attachmentId的有效性，防止越界访问
- ✅ **完整响应**：删除成功后返回包含最新附件列表的完整维护记录信息
- ✅ **操作日志**：记录详细的删除操作日志，包括操作人、删除的附件信息等
- ✅ **关联更新**：自动更新维护记录的updatedBy和updatedAt字段

---

### 使用前提

- ✅ 用户已通过JWT认证，持有有效的Bearer Token
- ✅ 维护记录必须已在系统中存在且未被删除
- ✅ 维护记录必须包含至少一个附件
- ✅ 提供的attachmentId必须在有效范围内（0到附件数量-1）

### 不适用场景

- ❌ 维护记录不存在或已被删除 - 需先确认记录存在
- ❌ 维护记录没有任何附件 - 无可删除的附件
- ❌ attachmentId超出索引范围 - 会返回附件不存在错误
- ❌ 需要删除多个附件 - 应多次调用此接口或使用更新接口

### 详细步骤说明

#### 步骤1: 接收删除请求
- Controller层接收DELETE请求
- 从路径参数中提取recordId（维护记录ID）
- 从路径参数中提取attachmentId（附件索引）
- 从认证信息中获取当前用户ID（操作人）

#### 步骤2: 参数验证
使用Joi验证器进行参数校验：
- **recordId验证**：必须是有效的UUID格式
- **attachmentId验证**：必须是非负整数（0或正整数）
- 如果验证失败，返回400错误（VALIDATION_ERROR）

**验证规则示例**：
```javascript
{
  params: Joi.object().keys({
    recordId: Joi.string().uuid().required(),
    attachmentId: Joi.number().integer().min(0).required()
  })
}
```

#### 步骤3: 查询维护记录
- 根据recordId查询维护记录
- 验证记录存在且isDeleted为false
- 如果记录不存在，抛出404错误（MAINTENANCE_RECORD_002）

#### 步骤4: 验证附件列表
- 检查维护记录的attachmentUrls字段
- 验证attachmentUrls不为null且不为空数组
- 如果没有附件，抛出404错误（MAINTENANCE_RECORD_003）

**验证逻辑**：
```javascript
if (!record.attachmentUrls || record.attachmentUrls.length === 0) {
  throw new ApiError(404, ERROR_CODES.MAINTENANCE_RECORD_003);
}
```

#### 步骤5: 验证附件索引
- 将attachmentId转换为整数类型
- 验证attachmentId >= 0 且 < 附件数组长度
- 如果索引越界，抛出404错误（MAINTENANCE_RECORD_003）

**索引验证逻辑**：
```javascript
const index = parseInt(attachmentId, 10);
if (index < 0 || index >= record.attachmentUrls.length) {
  throw new ApiError(404, ERROR_CODES.MAINTENANCE_RECORD_003);
}
```

#### 步骤6: 开启事务
- 启动数据库事务
- 确保后续所有数据库操作的原子性
- 如果任何步骤失败，所有更改将回滚

#### 步骤7: 获取现有附件列表
- 读取维护记录的attachmentUrls字段
- 创建附件数组的副本，避免直接修改原数组
- 保存要删除的附件信息用于日志记录

**代码示例**：
```javascript
const updatedAttachments = [...record.attachmentUrls];
const deletedAttachment = updatedAttachments[index];
```

#### 步骤8: 删除指定附件
- 使用数组的splice方法移除指定索引的附件
- 删除后数组长度减1，后续元素索引前移

**删除操作**：
```javascript
updatedAttachments.splice(index, 1);
```

#### 步骤9: 更新维护记录
更新维护记录的以下字段：
- `attachmentUrls`：更新为删除后的附件列表
- `updatedBy`：设置为当前操作人ID
- `updatedAt`：自动更新为当前时间戳

#### 步骤10: 提交事务
- 如果所有操作成功，提交事务
- 所有更改永久保存到数据库
- 如果过程中有异常，自动回滚事务

#### 步骤11: 记录操作日志
使用logger记录删除操作信息：
```javascript
logger.info('维护记录附件删除成功', {
  recordId: record.id,
  recordCode: record.recordCode,
  attachmentId: index,
  deletedAttachment: {
    fileName: deletedAttachment.fileName,
    fileType: deletedAttachment.fileType
  },
  userId: operatorId
});
```

#### 步骤12: 查询完整记录信息
- 重新查询维护记录，包含所有关联数据：
  - 设备信息（equipment）
  - 维护任务信息（maintenanceTask）
  - 执行人信息（executor）
  - 确认人信息（confirmer）
  - 创建人信息（creator）
  - 更新人信息（updater）

#### 步骤13: 返回成功响应
- 返回HTTP 200状态码
- 使用统一响应格式返回完整的维护记录信息
- 包含success标志、data数据、message消息和meta元信息

## 接口文档

### 基本信息

**接口路径**: `DELETE /v1/mdm/tpm/maintenance-records/:recordId/attachments/:attachmentId`

**功能描述**: 删除指定维护记录中的单个附件。通过维护记录ID和附件索引精确定位要删除的附件，删除后返回包含最新附件列表的完整维护记录信息。

**认证要求**: Bearer Token认证，需要登录后获取的JWT令牌

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 统一响应格式

#### 成功响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
    // 具体的业务数据，根据接口而不同
  },
  "message": "操作成功的描述信息",
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

#### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

### 路径参数

| 参数名       | 类型    | 必填 | 限制             | 描述                                     | 示例                                   |
| ------------ | ------- | ---- | ---------------- | ---------------------------------------- | -------------------------------------- |
| recordId     | string  | 是   | UUID格式         | 维护记录ID，用于定位记录                 | "aaa11111-e29b-41d4-a716-446655440000" |
| attachmentId | integer | 是   | 非负整数（>= 0） | 附件索引，attachmentUrls数组中的索引位置 | 0                                      |

**attachmentId说明**：
- attachmentId是附件在attachmentUrls数组中的索引（从0开始）
- 第一个附件的索引为0，第二个为1，以此类推
- 必须在有效范围内：0 <= attachmentId < 附件总数
- 删除后，后续附件的索引会自动前移

```bash
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
```

#### JavaScript (Axios)

```javascript
const axios = require('axios');

const recordId = 'aaa11111-e29b-41d4-a716-446655440000';
const attachmentId = 0; // 删除第一个附件

axios.delete(`/v1/mdm/tpm/maintenance-records/${recordId}/attachments/${attachmentId}`, {
  headers: {
    'Authorization': `Bearer ${accessToken}`,
    'Content-Type': 'application/json'
  }
})
.then(response => {
  console.log('删除成功，最新附件列表:', response.data.data.attachmentUrls);
})
.catch(error => {
  console.error('删除失败:', error.response.data);
});
```

#### JavaScript (Fetch)

```javascript
const recordId = 'aaa11111-e29b-41d4-a716-446655440000';
const attachmentId = 1; // 删除第二个附件

fetch(`/v1/mdm/tpm/maintenance-records/${recordId}/attachments/${attachmentId}`, {
  method: 'DELETE',
  headers: {
    'Authorization': `Bearer ${accessToken}`,
    'Content-Type': 'application/json'
  }
})
.then(response => response.json())
.then(data => {
  if (data.success) {
    console.log('删除成功，剩余附件数量:', data.data.attachmentUrls.length);
  } else {
    console.error('删除失败:', data.error.message);
  }
});
```

## 使用示例

### 场景1: 删除错误上传的照片

**业务需求**: 维护人员误将其他设备的照片上传到当前维护记录，需要删除该照片

**实现步骤**:

2. 使用DELETE接口删除指定索引的附件

**业务价值**:
- 及时纠正上传错误
- 保持维护记录的准确性
- 避免误导后续审查人员

### 场景2: 删除过期的维护报告

**实现步骤**:

1. 上传正式报告作为新附件
2. 删除临时报告附件
3. 验证最终附件列表只包含正式报告

**业务价值**:
- 确保记录中只保留最新版本
- 减少存储空间占用

### 场景3: 批量清理重复附件

**实现步骤**:

1. 获取所有附件列表
2. 识别重复的附件
3. 按索引从大到小依次删除重复项（避免索引变化）

**业务价值**:
- 清理冗余数据
- 优化存储空间
- 提高数据质量

**重要提示**：删除多个附件时，必须从索引大的开始删除，否则删除第一个后，后续附件的索引会发生变化，导致删除错误的附件。

## 常见问题

### Q1: 删除附件后，后续附件的索引会变化吗？

**A**: 会。删除附件使用数组的splice方法，删除后后续元素会自动前移。

**示例**：
- 原始附件列表：[A(0), B(1), C(2), D(3)]
- 删除索引1（附件B）后：[A(0), C(1), D(2)]
- 原来索引为2的C，删除B后索引变为1
- 原来索引为3的D，删除B后索引变为2

**重要**：如果需要删除多个附件，必须从索引大的开始删除，避免索引变化导致错误。

### Q2: 能否同时删除多个附件？

**A**: 当前接口不支持批量删除，需要多次调用。

**替代方案**：
- 使用更新维护记录接口（PATCH），直接传入删除后的完整附件数组
- 这种方式更适合大量删除操作

### Q3: 删除附件后，文件存储服务中的文件也会被删除吗？

**A**: 不会。此接口只删除数据库中的附件记录，不会删除文件存储服务（如OSS、S3）中的实际文件。

**文件清理建议**：
1. 实施定期的文件清理脚本，检查数据库中未引用的文件
2. 使用文件存储服务的生命周期管理功能
3. 记录删除操作日志，用于后续文件清理
4. 考虑实现逻辑删除，将附件移至"回收站"

### Q4: 删除失败后如何处理？

**A**: 所有操作在事务中执行，失败时会自动回滚，不会产生脏数据。

**常见失败原因**：
1. **维护记录不存在（404）**：检查recordId是否正确
2. **附件不存在（404）**：检查attachmentId是否在有效范围内
3. **索引越界（404）**：附件数量为3时，有效索引为0-2，不能使用3或更大的值
4. **未授权（401）**：Token过期或无效，需要重新登录

### Q5: 如何获取有效的attachmentId范围？

**A**: 先调用查询附件列表接口，获取所有附件

### Q6: 删除操作可以撤销吗？

**A**: 不能。删除操作是永久性的，不支持撤销。

**预防措施**：
1. **前端实现二次确认**：删除前弹出确认对话框
2. **显示附件预览**：让用户确认要删除的内容
3. **实施权限控制**：限制删除操作的权限
4. **记录操作日志**：保存删除记录用于审计

### Q7: 删除最后一个附件后会发生什么？

**A**: 删除最后一个附件后，attachmentUrls会变为空数组`[]`，这是正常状态。

**业务影响**：
- 维护记录仍然存在，只是没有附件
- 可以随时通过上传接口添加新附件
- 某些业务规则可能要求必须包含附件（需在业务层面验证）

### Q8: attachmentId参数可以是字符串吗？

**A**: 可以，但会被转换为整数。

**参数处理逻辑**：
```javascript
// URL中的 /attachments/2 和 /attachments/"2" 都会被接受
const index = parseInt(attachmentId, 10);

// 但以下情况会失败
// /attachments/abc -> parseInt('abc') = NaN -> 验证失败
// /attachments/2.5 -> parseInt('2.5') = 2 -> 转为整数2
```

**建议**：前端始终传递整数，避免类型转换问题。

### Q9: 如何实现"删除所有附件"功能？

**方式1：循环删除（从大到小）**

**推荐**：批量删除时使用方式2更高效，只需一次API调用。

### Q10: 删除操作对维护记录的其他字段有影响吗？

**A**: 只影响以下字段：

| 字段名         | 变化               | 说明         |
| -------------- | ------------------ | ------------ |

- ✅ 创建时间和创建人
- ✅ 其他所有业务字段

### 附件索引计算规则

#### 索引的含义

attachmentId是附件在`attachmentUrls`数组中的位置索引：

```javascript
attachmentUrls: [
  { url: '...', fileName: '照片1.jpg', fileType: 'image/jpeg' },  // 索引 0
  { url: '...', fileName: '照片2.jpg', fileType: 'image/jpeg' },  // 索引 1
  { url: '...', fileName: '报告.pdf', fileType: 'application/pdf' } // 索引 2
]
```

#### 有效索引范围

- **最小值**：0（第一个附件）
- **最大值**：附件数量 - 1
- **示例**：3个附件时，有效索引为 0, 1, 2

#### 删除后索引变化

**场景示例**：
```
原始状态:
索引 0: 照片1.jpg
索引 1: 照片2.jpg
索引 2: 报告.pdf
索引 3: 数据.xlsx

删除索引1后:
索引 0: 照片1.jpg (不变)
索引 1: 报告.pdf (原索引2，前移)
索引 2: 数据.xlsx (原索引3，前移)
```
