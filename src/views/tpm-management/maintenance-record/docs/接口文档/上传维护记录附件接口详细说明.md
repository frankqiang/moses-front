## 功能概述

### 所有功能

上传维护记录附件（Upload Maintenance Record Attachments）是设备TPM管理中的重要辅助功能，用于为维护记录添加相关的附件文件（如现场照片、维护报告、检测数据等），以支持维护过程可视化记录和证据归档的业务场景。该接口支持批量上传多个附件，新附件会追加到现有附件列表中，不会覆盖原有附件。

### 关键特性

- ✅ **批量上传支持**：单次请求可上传多个附件，提高操作效率
- ✅ **追加模式**：新附件追加到现有附件列表末尾，保留所有历史附件
- ✅ **多格式支持**：支持图片（JPEG、PNG等）、文档（PDF、Word等）、数据文件等多种格式
- ✅ **完整信息记录**：每个附件包含URL、文件名和文件类型三项完整信息
- ✅ **事务保护**：使用数据库事务确保附件信息更新的原子性
- ✅ **完整响应返回**：上传成功后返回包含所有附件的完整维护记录信息

---

### 使用前提

- ✅ 用户已通过JWT认证，持有有效的Bearer Token
- ✅ 维护记录必须已在系统中存在且未被删除
- ✅ 附件文件已通过独立的文件上传服务上传到存储系统，获得了URL
- ✅ 至少提供一个附件信息（attachments数组不能为空）

### 不适用场景

- ❌ 维护记录不存在或已被删除 - 需先确认记录存在
- ❌ 文件尚未上传到存储系统 - 需先使用文件上传服务获取URL
- ❌ 需要替换现有附件 - 应先使用删除附件接口，再上传新附件
- ❌ 需要更新附件元信息 - 应使用更新维护记录接口修改attachmentUrls字段

### 详细步骤说明

#### 步骤1: 接收上传请求
- Controller层接收POST请求
- 从路径参数中提取recordId（维护记录ID）
- 从请求体中提取attachments数组（附件信息）
- 从认证信息中获取当前用户ID（操作人）

#### 步骤2: 参数验证
使用Joi验证器进行参数校验：
- **recordId验证**：必须是有效的UUID格式
- **attachments验证**：必须是数组且至少包含1个元素
- **附件对象验证**：每个附件必须包含：
  - `url`：必须是有效的URI格式
  - `fileName`：文件名，必填字符串
  - `fileType`：文件类型（MIME类型），必填字符串

#### 步骤3: 查询维护记录
- 根据recordId查询维护记录
- 验证记录存在且isDeleted为false
- 如果记录不存在，抛出404错误（TPM_RECORD_001）

#### 步骤4: 开启事务
- 启动数据库事务
- 确保后续所有数据库操作的原子性
- 如果任何步骤失败，所有更改将回滚

#### 步骤5: 获取现有附件列表
- 读取维护记录的attachmentUrls字段
- 如果attachmentUrls为null或undefined，初始化为空数组
- 保留所有现有附件信息

#### 步骤6: 合并附件列表
- 使用数组扩展运算符合并：`[...existingAttachments, ...newAttachments]`
- 新附件追加到现有附件列表末尾
- 不对现有附件做任何修改或删除

#### 步骤7: 更新维护记录
更新维护记录的以下字段：
- `attachmentUrls`：更新为合并后的附件列表
- `updatedBy`：设置为当前操作人ID
- `updatedAt`：自动更新为当前时间戳

#### 步骤8: 提交事务
- 如果所有操作成功，提交事务
- 所有更改永久保存到数据库
- 如果过程中有异常，自动回滚事务

#### 步骤9: 记录操作日志
使用logger记录操作信息：
```javascript
logger.info('维护记录附件上传成功', {
  recordId: record.id,
  recordCode: record.recordCode,
  attachmentCount: attachments.length,
  userId: operatorId
});
```

#### 步骤10: 查询完整记录信息
- 重新查询维护记录，包含所有关联数据：
  - 设备信息（equipment）
  - 维护任务信息（maintenanceTask）
  - 执行人信息（executor）
  - 确认人信息（confirmer）
  - 创建人信息（creator）
  - 更新人信息（updater）

#### 步骤11: 返回成功响应
- 返回HTTP 200状态码
- 使用统一响应格式返回完整的维护记录信息
- 包含success标志、data数据、message消息和meta元信息

## 接口文档

### 基本信息

**接口路径**: `POST /v1/mdm/tpm/maintenance-records/:recordId/attachments`

**功能描述**: 为指定的维护记录上传附件文件信息。支持批量上传多个附件，新附件会追加到现有附件列表中，不会覆盖原有附件。附件信息包括URL、文件名和文件类型。

**认证要求**: Bearer Token认证，需要登录后获取的JWT令牌

**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 统一响应格式

#### 成功响应格式

所有成功的 API 调用都会返回以下统一格式：

```json
{
  "success": true,
  "data": {
    // 具体的业务数据，根据接口而不同
  },
  "message": "操作成功的描述信息",
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

#### 错误响应格式

所有错误的 API 调用都会返回以下统一格式：

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",
    "details": {
      "field": "发生错误的字段名（可选）",
      "value": "错误的字段值（可选）",
      "retryAfter": 300,
      "traceId": "req-1234567890-abcdef"
    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号

### 路径参数

| 参数名   | 类型   | 必填 | 限制     | 描述                     | 示例                                   |
| -------- | ------ | ---- | -------- | ------------------------ | -------------------------------------- |
| recordId | string | 是   | UUID格式 | 维护记录ID，用于定位记录 | "aaa11111-e29b-41d4-a716-446655440000" |

### 请求参数

| 参数名      | 类型  | 必填 | 限制        | 描述                       | 示例           |
| ----------- | ----- | ---- | ----------- | -------------------------- | -------------- |
| attachments | array | 是   | 至少1个元素 | 附件信息数组，支持批量上传 | 见下方结构说明 |

### 附件对象结构

每个附件对象包含以下字段：

| 参数名   | 类型   | 必填 | 限制        | 描述                                     | 示例                                                |
| -------- | ------ | ---- | ----------- | ---------------------------------------- | --------------------------------------------------- |
| url      | string | 是   | 有效URI格式 | 附件URL，文件在存储系统中的访问地址      | "https://example.com/files/maintenance-photo-1.jpg" |
| fileName | string | 是   | -           | 文件名，用于显示和下载时的文件名         | "维护现场照片1.jpg"                                 |
| fileType | string | 是   | -           | 文件类型（MIME类型），用于文件识别和预览 | "image/jpeg"                                        |

**说明**：
- `url`：应先通过独立的文件上传服务将文件上传到存储系统（如OSS、S3等），获得文件的访问URL后再调用此接口
- `fileName`：建议使用有意义的文件名，便于后续查看和管理
- `fileType`：常见的MIME类型包括：
  - 图片：`image/jpeg`、`image/png`、`image/gif`等
  - 文档：`application/pdf`、`application/msword`、`application/vnd.openxmlformats-officedocument.wordprocessingml.document`等
  - 表格：`application/vnd.ms-excel`、`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`等

## 常见问题

### Q1: 上传附件会覆盖原有附件吗？

**A**: 不会。此接口采用追加模式，新附件会添加到现有附件列表的末尾，不会删除或覆盖原有附件。如果需要删除某个附件，应使用专门的删除附件接口。

### Q2: 附件文件是直接上传到此接口吗？

**A**: 不是。此接口只接收附件的元信息（URL、文件名、文件类型），不处理文件本身的上传。正确的流程是：
1. 先使用独立的文件上传服务（如OSS、S3等）上传文件
2. 获得文件的访问URL
3. 再调用此接口将附件信息关联到维护记录

### Q3: 单次最多可以上传多少个附件？

**A**: 接口要求attachments数组至少包含1个元素，理论上没有明确的上限限制。但考虑到请求大小和性能，建议：
- 常规场景：单次上传1-10个附件
- 批量场景：单次上传不超过50个附件
- 如果附件数量很多，建议分批上传

### Q4: 支持哪些文件类型？

**A**: 接口本身不限制文件类型，只要提供有效的URL、文件名和文件类型（MIME类型）即可。常见的文件类型包括：
- **图片**：image/jpeg、image/png、image/gif、image/bmp等
- **文档**：application/pdf、application/msword、application/vnd.openxmlformats-officedocument.wordprocessingml.document等
- **表格**：application/vnd.ms-excel、application/vnd.openxmlformats-officedocument.spreadsheetml.sheet等
- **压缩包**：application/zip、application/x-rar-compressed等
- **视频**：video/mp4、video/avi等

### Q5: 附件URL必须是公网可访问的吗？

**A**: 不一定。URL的可访问性取决于您的文件存储方案：
- **公网存储**：如果使用公开的OSS桶，URL可以是公网可访问的
- **私有存储**：如果使用私有存储，URL可以是带签名的临时访问链接
- **内网存储**：如果系统部署在内网，URL可以是内网地址

关键是确保需要访问附件的用户（通过系统前端）能够访问到这些URL。

### Q6: 上传失败后如何处理？

**A**: 如果上传失败，接口会返回相应的错误信息：
1. **维护记录不存在（404）**：检查recordId是否正确，或记录是否已被删除
2. **参数验证失败（400）**：检查attachments数组格式，确保每个附件包含必填字段
3. **URL格式错误（400）**：确保URL是有效的URI格式（通常以http://或https://开头）
4. **未授权（401）**：检查Token是否有效，必要时重新登录

所有操作都在事务中执行，失败时会自动回滚，不会产生脏数据。

### Q7: 如何删除已上传的附件？

**A**: 使用专门的删除附件接口：
```
DELETE /v1/mdm/tpm/maintenance-records/:recordId/attachments/:attachmentId
```
其中attachmentId是附件在attachmentUrls数组中的索引（从0开始）。

### Q8: 可以更新已上传附件的信息吗？

**A**: 此接口不支持直接更新附件信息。如果需要修改附件的文件名或文件类型，需要：
1. 使用删除附件接口删除原附件
2. 重新调用此接口上传修改后的附件信息

或者，可以使用更新维护记录接口，直接修改整个attachmentUrls数组。

### Q9: 附件URL失效后怎么办？

**A**: 如果文件存储服务中的文件被删除或URL过期，系统中保存的附件信息不会自动更新。建议：
- 使用稳定的文件存储方案，避免文件被误删
- 如果使用临时URL（如签名URL），确保有效期足够长
- 定期检查附件URL的可访问性
- 重要文件考虑使用永久存储

### Q10: 如何查看维护记录的所有附件？

**A**: 有两种方式：
1. **查询单个维护记录**：`GET /v1/mdm/tpm/maintenance-records/:recordId`，响应中包含完整的attachmentUrls数组
2. **专门的附件查询接口**：`GET /v1/mdm/tpm/maintenance-records/:recordId/attachments`，返回该记录的所有附件信息

### 最佳实践

1. **文件存储选择**
   - 生产环境建议使用专业的对象存储服务（OSS、S3等）
   - 确保存储服务的高可用性和数据安全性
   - 使用CDN加速附件访问

2. **文件命名规范**
   - 使用有意义的文件名，便于识别和管理
   - 建议格式：`{功能}-{设备编码}-{日期}-{序号}.{扩展名}`
   - 示例：`维护照片-AF001-20240120-001.jpg`

3. **附件大小控制**
   - 建议单个附件文件不超过10MB
   - 大文件建议压缩后上传
   - 视频文件建议使用专门的视频存储方案

4. **安全性考虑**
   - 上传文件前进行病毒扫描
   - 验证文件类型，防止恶意文件上传
   - 使用HTTPS协议传输
   - 敏感文件使用签名URL，控制访问权限

5. **错误处理**
   - 实现重试机制，处理网络不稳定情况
   - 提供清晰的错误提示，帮助用户定位问题
   - 记录操作日志，便于问题追溯

6. **用户体验优化**
   - 提供上传进度提示
   - 支持批量选择文件
   - 提供附件预览功能
   - 支持拖拽上传
