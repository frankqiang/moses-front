## 功能概述

### 所有功能

查询单个维护记录（Get Maintenance Record）是设备TPM管理中的核心查询操作之一，用于根据维护记录ID获取完整的维护记录详情，包括维护基本信息、关联的设备信息、维护任务信息、执行人员、确认人员、创建人、更新人等完整信息，以支持维护记录详情查看、维护履历追溯、设备健康档案等业务场景。

### 关键特性

- ✅ **完整数据返回**：返回维护记录的所有字段信息，包括基本信息、问题描述、解决方案、备件使用、附件等
- ✅ **关联对象加载**：自动加载关联的设备、维护任务、执行人员、确认人员、创建人、更新人等对象信息
- ✅ **软删除过滤**：自动过滤已软删除的维护记录，确保只返回有效数据
- ✅ **格式化输出**：工时等数值字段自动格式化为标准格式，日期时间使用ISO 8601格式
- ✅ **权限验证**：需要有效的JWT Token，确保数据访问安全
- ✅ **404处理**：记录不存在时返回标准化的404错误响应

---

### 使用前提

- ✅ 用户已通过认证，持有有效的JWT Token
- ✅ 提供的维护记录ID必须是有效的UUID格式
- ✅ 维护记录必须存在且未被软删除（isDeleted=false）
- ✅ 关联的设备、用户等实体信息在数据库中存在

### 不适用场景

- ❌ 批量查询多个维护记录（应使用列表查询接口）
- ❌ 只需要部分字段信息（当前接口返回完整数据，无字段筛选功能）
- ❌ 查询已删除的维护记录（软删除记录无法通过此接口获取）

### 详细步骤说明

#### 步骤1: 接收请求
- 接收GET请求，路径格式为 `/v1/mdm/tpm/maintenance-records/:recordId`
- 提取路径参数 `recordId`
- 准备进行认证和验证流程

#### 步骤2: 验证JWT Token
- 从请求头的 `Authorization` 字段提取Bearer Token
- 验证Token的有效性和完整性
- 提取Token中的用户信息，用于后续的权限验证和日志记录
- Token无效时返回401错误

#### 步骤3: 验证路径参数
- 验证 `recordId` 是否为有效的UUID格式
- 使用Joi验证器进行格式校验
- 参数格式错误时返回400验证错误

#### 步骤4: 查询维护记录
**查询条件**：
- 主键ID匹配 `recordId`
- 软删除标记 `isDeleted = false`

**关联加载**（使用Sequelize include）：
- `equipment`: 关联设备信息（设备ID、编码、名称、类型、状态）
- `maintenanceTask`: 关联维护任务信息（任务ID、编码、标题、类型）
- `executor`: 执行人员信息（用户ID、姓名、邮箱）
- `confirmer`: 确认人员信息（用户ID、姓名、邮箱）
- `creator`: 创建人信息（用户ID、姓名、邮箱）
- `updater`: 更新人信息（用户ID、姓名、邮箱）

#### 步骤5: 记录存在判断
- 检查查询结果是否为空
- 如果记录不存在或已被软删除，返回404错误，错误码 `TPM_RECORD_001`
- 如果记录存在，继续后续处理

#### 步骤6: 数据格式化处理
- **工时字段**：将DECIMAL类型的工时转换为标准的字符串格式（保留两位小数）
- **日期字段**：确保所有日期时间字段使用ISO 8601格式
- **JSONB字段**：确保 `sparePartsUsed` 和 `attachmentUrls` 正确序列化为JSON数组

#### 步骤7: 构建响应数据
- 使用统一的响应格式封装数据
- 设置 `success: true`
- 将维护记录数据放入 `data` 字段
- 设置成功消息 `message: "获取维护记录详情成功"`
- 添加元信息（时间戳、请求ID、API版本）

#### 步骤8: 返回成功响应
- 设置HTTP状态码为200
- 返回JSON格式的响应数据
- 记录操作日志（成功获取维护记录详情）

## 接口文档

### 基本信息

**接口路径**: `GET /v1/mdm/tpm/maintenance-records/:recordId`

**功能描述**: 根据维护记录ID获取完整的维护记录详情，包括关联的设备、任务、人员等信息。用于查看维护记录详细信息、设备健康档案、维护履历追溯等场景。

**认证要求**: JWT Bearer Token，需要有效的用户认证

所有错误的 API 调用都会返回以下统一格式：

```json
{

  "error": {
    "code": "ERROR_CODE",
    "message": "用户友好的错误描述",

    }
  },
  "meta": {
    "timestamp": "2024-01-20T10:30:00.000Z",
    "requestId": "req-1234567890-abcdef",
    "version": "v1"
  }
}
```

**响应字段说明**：

- `success`: 布尔值，表示请求是否成功
- `data`: 成功时包含业务数据，失败时为 null
- `error`: 失败时包含错误信息，成功时为 null
- `message`: 成功时的操作描述
- `error.code`: 标准化的错误码，用于程序化处理
- `error.message`: 用户友好的错误描述，可直接展示给用户
- `error.details`: 可选的错误详细信息
- `meta`: 元数据信息，包含时间戳、请求 ID 和版本号


**请求头**:

```
Authorization: Bearer <access_token>
Content-Type: application/json
```

## 使用示例

### 场景1: 查看维护记录详情

**业务需求**: 设备管理员需要查看某次设备维护的完整记录，包括维护内容、发现的问题、解决方案、使用的备件等详细信息。

**操作步骤**:
1. 从维护记录列表中获取要查看的记录ID
2. 调用查询单个维护记录接口
3. 展示维护记录的完整信息

### 场景2: 设备健康档案查询

**业务需求**: 设备工程师需要追溯某次维护记录，查看当时的维护情况、发现的问题以及采取的措施，用于分析设备故障原因。

**操作步骤**:
1. 从设备维护履历中选择要追溯的维护记录
2. 调用查询接口获取详细信息
3. 分析维护记录，与当前设备状态对比

### 场景3: 维护任务验收确认

**业务需求**: 维护主管需要查看维护任务的执行记录，确认维护工作是否按要求完成，是否需要进一步处理。

**操作步骤**:
1. 从待确认的维护任务中选择需要验收的记录
2. 查询维护记录详情
3. 检查维护内容、使用备件、附件等信息
4. 决定是否确认或要求重新维护

## 常见问题

### Q1: 为什么查询时返回404错误？

**A**: 可能的原因有：
1. **记录ID错误**: 提供的recordId在数据库中不存在
2. **记录已删除**: 维护记录已被软删除（isDeleted=true）
3. **UUID格式错误**: recordId不是有效的UUID格式

**解决方法**:
- 检查recordId是否正确
- 使用列表查询接口确认记录是否存在
- 确保recordId符合UUID格式（包含连字符的36字符字符串）

### Q2: 关联对象（设备、人员等）为什么有时为null？

**A**:
- `maintenanceTask`: 如果维护记录不是从维护任务创建的，此字段为null
- `confirmer`: 如果维护记录尚未被确认，确认人员字段为null
- `problemFound`、`solutionApplied`等可选字段：创建时未填写则为null

这是正常的业务逻辑，前端应做好null值处理。

### Q3: 工时字段为什么是字符串而不是数字？

**A**:
- 后端使用DECIMAL类型存储工时，确保精度
- 序列化为JSON时转换为字符串（如"2.50"）
- 前端使用时可通过`parseFloat()`转换为数字

### Q4: 如何处理大量附件的性能问题？

**A**:
- 接口返回的是附件元信息（URL、文件名、文件类型），不包含文件内容
- 附件文件应存储在对象存储服务（如OSS、S3）
- 前端根据URL按需加载附件，不会一次性加载所有文件
- 建议实现附件预览功能时使用懒加载策略

### Q6: 接口返回401错误怎么办？

**A**:
1. **Token过期**: 重新登录获取新Token
2. **Token格式错误**: 检查Authorization头格式是否为`Bearer <token>`
3. **Token无效**: 使用刷新Token接口获取新的访问Token

### Q7: 如何区分不同类型的维护记录？

**A**: 使用`maintenanceType`字段：
- "日常保养": 日常定期保养
- "定期检查": 定期检查维护
- "大修": 设备大修
- "专项维护": 专项维护任务

### Q8: 备件清单为空数组表示什么？

**A**:
- `sparePartsUsed: []` 表示该次维护未使用任何备件
- 这是正常情况，例如日常检查可能不需要更换备件
- 前端应正确处理空数组，显示"未使用备件"等友好提示

### 数据格式说明

#### UUID格式
- 标准UUID v4格式：`xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx`
- 示例：`aaa11111-e29b-41d4-a716-446655440000`
- 包含连字符的36字符字符串

#### ISO 8601日期时间格式
- 格式：`YYYY-MM-DDTHH:mm:ss.sssZ`
- 示例：`2024-01-20T14:30:00.000Z`
- 使用UTC时区（Z后缀）

#### 工时格式
- 数据库：DECIMAL(10,2)
- JSON响应：字符串格式，保留两位小数
- 示例：`"2.50"`表示2.5小时

### 最佳实践建议

#### 前端开发建议
1. **缓存机制**: 对已查询的维护记录进行本地缓存，减少重复请求
2. **错误处理**: 统一封装API调用，集中处理错误响应
3. **加载状态**: 显示加载指示器，提升用户体验
4. **数据验证**: 前端也应验证recordId格式，提前拦截无效请求
5. **响应式设计**: 根据不同字段的存在性动态调整UI展示

#### 性能优化建议
1. **按需加载**: 在列表页只展示关键信息，详情页才调用此接口
2. **预加载**: 在用户可能点击详情前预加载数据
3. **请求合并**: 如需查询多个记录，考虑使用列表接口而非多次调用此接口
